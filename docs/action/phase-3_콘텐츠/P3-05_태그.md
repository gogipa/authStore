## 1. 목표

이 문서가 끝나면 ⑦ 태그 단계가 최종 태그 10개 이하를 만든다. 시드 키워드·모델명·상품유형·용도어로 커머스API 추천 태그를 받고, 오너가 넣은 경쟁 태그와 합친다. 경쟁 태그는 셀라파인더 엑셀·붙여넣기, 브라우저 응답의 manuTag, 자유 텍스트로 받는다. 그 뒤 정규화 → 규칙 필터 → `restricted-tags` 1차 검증 → 선정 순서를 거친다. 오너는 SCR-07에서 후보표와 뺀 태그·사유를 보고 태그를 더하거나 뺄 수 있고, 이 편집은 다시 실행해도 다시 적용된다. 흐름상 ⑤·⑥과 서로 읽지 않는 ⑦이다. 사전 검증(P4-02)이 최종 태그를 다시 검증하고, 등록(P4-03)이 `code`/`text` 형식으로 보낸다.

## 4. 핵심 규칙

1. ⑦ 시작 조건은 아래와 같다. '선택' 값이 없으면 null 값의 해시로 기록한다. (F-TG-15, US-18 AC5, PRD §5.3 ⑦ 행·필수 시작 조건, ERD `step_run_input.value_hash`)
   - 필수: 시드 키워드(① 선택 키워드·② 검색어·오너 입력), ② 모델명·상품유형, 후보 성별
   - 선택: 활성 경쟁 태그 입력 목록, ④ 리프 경로
2. 추천 태그: 시드 키워드·모델명·상품유형·용도어마다 `GET /v2/tags/recommend-tags?keyword=`를 커머스API 포트로 불러 `{code, text}`를 받는다. 보낸 키워드는 `tag_set.recommend_keywords`에 남긴다. 응답은 메모리에 짧게 캐시하고 DB에 두지 않는다. 캐시 시간과 용도어 출처는 문서에 없음 → 구현 때 Proposed로 정하고 기록. (F-TG-01, US-18 AC1, TG-02, ERD `tag_set`, ERD 부록 A)
3. 경쟁 태그 입력(`POST …/tag-competitor-inputs`)은 세 종류다. 성공하면 201 + `Location`(목록 경로)이다. (F-TG-02~F-TG-05, US-18 AC2, TG-01, CON-09, CON-13, 05-2 `createTagCompetitorInput`)
   - `SELLERFINDER`: xlsx·CSV 파일(multipart) 또는 붙여넣기
   - `BROWSER_RESPONSE`: JSON·HAR 붙여넣기에서 `manuTag`만 뽑는다
   - `FREE_TEXT`: 자유 텍스트
   - 태그·순위·네이버 상품 ID·빈도만 저장한다. 원본·파일 이름·Cookie·Authorization·판매자 연락처는 파싱하면서 버린다. 원본은 로그와 AI 입력에도 넣지 않는다
4. 빈도 열이 있으면 `has_frequency=true`로 빈도순, 없으면 입력 순서(`seq`)로 보여 준다. M0 S5 전에는 파서가 빈도 열을 찾았는지로 정한다. 오류는 아래와 같다. (F-TG-02, 05-2 x-decision §7.4-34·§7.1-6, 05-3)
   - 읽은 태그 0개 → 422 `IMPORT_EMPTY`, 형식 불일치 → 422 `IMPORT_PARSE_FAILED`(`fieldErrors`에 행·열)
   - 지원하지 않는 파일 → 422 `UNSUPPORTED_FILE_TYPE`, 크기 상한 초과 → 413 `PAYLOAD_TOO_LARGE`. 상한 값은 설정 상수이고 문서에 값이 없음 → Proposed
5. 앱은 네이버쇼핑에 요청을 보내지 않는다. 입력란에 '브라우저 확장이나 F12로 응답을 복사하면 네이버쇼핑 접속이 차단(418)될 수 있습니다.'를 보여 준다. (F-TG-05, F-TG-06, CON-03, 시안 Tags.dc.html)
6. 입력 빼기(`DELETE /tag-competitor-inputs/{id}`)는 `removed_at`만 채운다(물리 삭제 금지). 이미 뺐어도 204, 없으면 404 `COMPETITOR_INPUT_NOT_FOUND`. ⑦이 실행 중이면 입력 추가·빼기 모두 409 `STEP_LOCKED_BY_RUNNING_STEP`. 활성 입력이 바뀌면 완료된 ⑦은 '재실행 필요'가 되고 응답의 `rerunRequiredSteps`로 알린다. (05-1 §2.8, ERD `tag_competitor_input`·`ix_tag_competitor_input_active`, ERD §1.3)
7. 정규화: 앞뒤 공백 제거, '#' 제거, 영문 소문자화, 공백 정리를 하고, 정규화 키(`text_key`)로 중복을 없앤다. 추천 태그와 정확히 일치하면 추천의 `text`를 그대로 쓴다. (F-TG-07, US-18 AC3, ERD `tag_candidate.text`·`text_key`)
8. 규칙 필터는 사전으로 하고 AI는 쓰지 않는다. 뺀 태그는 `outcome=FILTERED` + `filter_reason` + `filter_detail`이다. (F-TG-08, US-18 AC3, TG-04, ERD `ck_tag_cand_filter_reason`, 시안 Tags.dc.html)
   - `CATEGORY_TOKEN`: 카테고리 경로 단어(예 리프 '러닝화')
   - `BRAND_NAME`: 브랜드명(예 '나이키운동화')
   - `STORE_NAME`: 판매처·스토어명
   - `PROMOTION`: 가격·혜택·배송·홍보 문구(예 '무료배송')
   - `ATTRIBUTE_MISMATCH`: 성별·용도·시즌이 상품과 맞지 않음(예 남성 성인화의 '키즈운동화')
   - AI 관련성 판정은 기본 꺼짐이다. 켜면 `ai_relevance_enabled=true`로 CON-13 예외를 기록한다
   - 상품 자체 브랜드를 쓴 태그(예 '아식스운동화')는 PRD('자사·타사 브랜드명' 제외)와 시안(최종 태그에 남음)이 다르다 → Proposed
9. ④ 전에 실행하면 카테고리 필터를 빼고 `leaf_category_id=NULL`로 두며, 경고 `CATEGORY_UNDECIDED`와 화면 '카테고리 미확정'을 보인다. ④가 끝나면 ⑦이 '재실행 필요'가 된다(④ 리프 경로가 선택 시작 조건이라서). (F-TG-09, US-30 AC2, PRD §5.3, 05-3 §5.2)
10. 1차 검증: 규칙 필터를 통과한 후보만 `GET /v2/tags/restricted-tags`로 확인한다. `restricted=true`면 `outcome=RESTRICTED`로 빼고 사유를 보여 준다. 규칙에서 빠진 태그는 조회하지 않고 `restricted=NULL`이다. 배열 형식과 1회 최대 개수는 M0 S3에서 정하므로 설정값으로 나눠 부른다. 끝나면 `restricted_checked_at`을 채운다. (F-TG-10, US-18 AC3, PRD §8.6 5, ERD `tag_candidate.restricted`·`ck_tag_cand_restricted`)
11. 선정은 최대 10개다. 선정한 태그는 `outcome=SELECTED` + `final_order 1~10`, 10개를 넘친 태그는 `NOT_SELECTED`다. (F-TG-11, US-18 AC3·AC5, PRD §8.6 6, §16 ③ 태그, ERD `ck_tag_cand_selected`·`ck_tag_cand_order`)
    1. 추천과 정확히 일치하는 경쟁 태그
    2. 나머지 경쟁 태그(빈도가 있으면 빈도순, 없으면 입력 순서)
    3. 추천(사전) 태그
    - 경쟁 태그가 없으면 추천만으로 고르고, 10개를 억지로 채우지 않는다
12. 전송 형식: 추천 태그와 정확히 일치하면 `{code, text}`, 아니면 `{text}`만 보낸다. `code`는 추천에 있을 때만 두고 숫자 문자열이다. (F-TG-12, US-18 AC3, ERD `ck_tag_cand_code`·`ck_tag_cand_code_digits`)
13. 오너 편집(`owner-edits` EDIT, TAGS)은 202다. (F-TG-14, US-18 AC3, 05-1 표 B, ERD `tag_owner_edit`, PRD §16 ③ 태그)
    - `add[]`·`remove[]`를 `tag_owner_edit`에 쌓는다(`edited_at` 유지). 편집한 태그도 정규화 → 규칙 필터 → restricted 검증을 다시 거친 뒤 SSE로 알린다
    - 추가해서 10개를 넘으면 422 `FINAL_TAG_LIMIT_EXCEEDED`, 빈 값·100자 초과 → 422 `VALIDATION_FAILED`
    - `code` 없는 오너 추가 태그는 '사전 미등록' 경고(`dictionaryUnregistered`), 오너가 뺀 태그는 `OWNER_REMOVED`
14. 다시 실행하면 직전 버전의 `tag_owner_edit` 목록을 새 결과에 다시 적용한다. 그 뒤 규칙 필터와 restricted 검증을 다시 한다(오너 수정도 검사를 건너뛰지 않는다). 이전 버전을 다시 고르면 그 버전의 편집 목록이 살아난다. (PRD §5.3 '태그의 추가·삭제', US-33 AC5, ERD `tag_owner_edit` 목적)
15. 최종 태그 10개 이하는 DB가 보장한다(`final_order` 1~10 + UNIQUE). 승인 화면의 `restricted-tags` 재검증과 중복 확인은 이 단계가 아니라 RG-08(P4-02)이 한다. (ERD `tag_candidate` UNIQUE, PRD §5.3 마지막 줄, F-AP-14)

## 6. 테스트

테스트 공통: ESM Jest라 커머스API는 `overrideProvider`로 가짜 서버 클라이언트를 넣는다. e2e는 `autostore_test`, 정리는 `TRUNCATE … RESTART IDENTITY CASCADE`(`tag_competitor_item` 추가만, `tag_competitor_input` 삭제 금지).

**단위**

| 대상 | 확인할 것 |
|---|---|
| `normalize` | `' #Gel Kayano14 '` → `gel kayano14`. `#젤카야노14`와 `젤카야노14`는 한 후보가 된다 |
| `rule-filter` | '러닝화'(리프 러닝화) → `CATEGORY_TOKEN`. '나이키운동화' → `BRAND_NAME`. '무료배송' → `PROMOTION`. '키즈운동화'(남성 성인화) → `ATTRIBUTE_MISMATCH`. 리프가 없으면 `CATEGORY_TOKEN`으로 빼지 않는다 |
| `select-final` | 추천∩경쟁이 먼저, 다음 경쟁(빈도순), 다음 추천. 최대 10개. 경쟁 입력이 없고 추천이 7개면 최종 7개(채우지 않음). `RESTRICTED`는 뽑히지 않는다 |
| `request-format` | 추천과 같은 태그 → `{code, text}`. 오너가 넣은 사전 밖 태그 → `{text}` |
| 파서 | HAR의 Cookie·Authorization·연락처가 결과 객체에 없다(키 목록 검사). JSON `manuTag` → 태그·순위·상품 ID. 빈도 열 있는 xlsx → `hasFrequency=true`. 빈 입력 → `IMPORT_EMPTY`. 깨진 표 → `IMPORT_PARSE_FAILED` |
| 편집 다시 적용 | 이전 편집(add 'x', remove 'y')이 새 결과에 적용된다. 제한 태그를 추가하면 `RESTRICTED`로 빠진다 |

**e2e (커머스API 가짜 서버)**

- `FREE_TEXT` 입력 → 201 + `Location`. `tag_competitor_item`에는 `tag_text`·`source_rank`·`naver_product_id`·`frequency`만 있다. 붙여 넣은 원문이 DB·`call_log`·`user_action_log`·캡처한 앱 로그 어디에도 없다.
- xlsx multipart → 201(`has_frequency=true`). 상한 초과 → 413 `PAYLOAD_TOO_LARGE`. pdf → 422 `UNSUPPORTED_FILE_TYPE`.
- 빼기 → 204, 다시 → 204, 없는 id → 404 `COMPETITOR_INPUT_NOT_FOUND`. 완료된 ⑦은 빼기 뒤 `RERUN_REQUIRED`.
- ⑦ 실행 중 입력 추가 → 409 `STEP_LOCKED_BY_RUNNING_STEP`.
- ④ 전 실행 → 202 + 경고 `CATEGORY_UNDECIDED`, `leafCategoryId=null`. ④ 완료 뒤 ⑦ `RERUN_REQUIRED`.
- 경쟁 입력 없이 실행 → 추천만으로 최종 태그가 생긴다(US-18 AC5). `GET tag-set`의 뺀 태그 목록에 사유가 있다.
- 오너 편집: 11번째 추가 → 422 `FINAL_TAG_LIMIT_EXCEEDED`. 빈 값 → 422 `VALIDATION_FAILED`. 사전 밖 태그 추가 → 202 → SSE → 새 버전에 그 태그, `dictionaryUnregistered=true`. 다시 실행해도 그 태그가 남는다.
- 외부 호출 검사: 가짜 관문에 네이버쇼핑 호스트 요청이 한 건도 없다.

## 8. 주의

- 공통 규칙은 [README §공통 규칙](../README.md#공통-규칙)을 따른다(실행 환경, 외부 호출 금지, 비밀정보, 커밋 안 함).

- 붙여 넣은 원본에는 쿠키·토큰·연락처가 섞여 있을 수 있다. DB뿐 아니라 요청 로그(pino-http 본문), 오류 응답(`IMPORT_PARSE_FAILED`에는 행·열만), AI 입력 어디에도 남기지 않는다. 파일도 디스크에 쓰지 않는다.
- 추천·제한 태그 조회는 실제 스토어 API다. 테스트·개발은 가짜 서버로만 한다. 커머스API 키가 없을 때 ⑦을 409로 막을지(표 A TAGS 행에 `SECRET_NOT_CONFIGURED`가 없음), 실행 실패(`EXTERNAL_API`)로 둘지는 Proposed로 정한다.
- `restricted-tags`는 카테고리를 받지 않는다. 카테고리별 제한은 등록해 봐야 안다(TG-05, M2). 1차 검증을 통과했다고 등록 성공을 약속하는 문구를 화면에 쓰지 않는다.
- `tag_set`·`tag_candidate`·`tag_owner_edit`·`tag_set_competitor_input`은 `trg_output_frozen` 대상이다. TAGS 오너 편집은 202로 새 버전을 만든다. 새 버전의 행을 모두 쓴 뒤 닫는다.
- 빈도 저장은 TG-01 '태그·순위·상품 ID만'과 부딪친다(ERD §7.1-14). ERD대로 저장하되, 오너가 거부하면 빈도 열을 빼고 입력 순서로 대신한다.
- ⑦은 ⑤·⑥ 산출물을 읽지 않는다. ④ 리프 경로만 선택 입력으로 읽는다. 태그 편집 API를 새로 만들지 말고 step-engine의 `owner-edits`(P1-05)에 처리기를 붙인다.
- P4-02가 승인 때 최종 태그를 `restricted-tags`로 다시 검증하고, P4-03이 `{code, text}`로 보낸다. `code`는 추천과 정확히 일치할 때만 넣는다.
