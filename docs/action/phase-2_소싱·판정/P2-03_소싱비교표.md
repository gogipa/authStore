## 1. 목표

② 소싱의 비교표가 완성된다. 오너가 앵커(型番·색상)를 정하면 검색 결과가 일치·확인 필요·불일치로 나뉘고, P2-02의 페이지 조회로 행을 검증해 목표 사이즈 재고와 실질가(송료·쿠폰·포인트)를 계산해 실질가 낮은 순으로 보여 준다.
오너가 검증된 행 하나를 고르면 ②가 완료되고 후보의 itemCode·색상·성별이 정해진다. 이 '소싱 선택'을 ③ 판정(P2-05)·④ 카테고리·⑤·⑥이 step-engine을 거쳐 읽는다.

## 4. 핵심 규칙

1. **앵커 정하기**: `PUT /sourcing-comparisons/{id}/anchor` — `SEARCH_PICK`(`anchorItemCode` 필수) 또는 `CODE_ENTRY`(`anchorModelCode` 필수), `anchorColorCode`·`anchorColorLabel`은 선택(§7-27). 입력 대기 중인 ② 버전에만 쓴다(아니면 409 `STEP_RUN_NOT_WAITING_INPUT`). 202 + `Location: /candidates/{id}/sourcing-comparison` + `SourcingJobAccepted`. 이어서 분류 → (필요하면) 2페이지 → P2-02 페이지 조회 반복이 돌고 SSE `sourcing.row-updated`·`sourcing.page-fetch-finished`로 알린다. 같은 앵커를 다시 보내면 같은 결과. 후보에 확정된 앵커와 다르면 409 `ANCHOR_KEY_MISMATCH`(다른 모델·색상은 새 후보). 필수값 누락 422 `VALIDATION_FAILED`. (F-SO-08, F-CW-03, US-04 AC1, US-35 AC1, 05-2 `fixSourcingAnchor`)
2. **型番 정규화·분류**: NFKC → 대문자 → 공백·하이픈 제거. 앵커와 '모델+색상 코드'가 정확히 같으면 `MATCH`, 시리즈만 같거나 색상 코드가 없으면 `NEEDS_REVIEW`, 나머지는 `NO_MATCH`. `MATCH`가 20개보다 적으면 검색 `page=2`(6시간 캐시)까지 본다. API 행의 型番을 어디서 뽑는지(상품명 패턴 등)와 '시리즈가 같다'의 기준은 문서에 없음 → Proposed. (F-SO-09, US-04 AC1, PRD §8.2 RK-03 2~4)
3. **탐색 모드**: 앵커 전에는 `anchor_input_method`와 행 `anchor_match`가 NULL이고(`exploreMode=true`) 동일 상품 필터 없이 목록만 보인다. 앵커 전에는 최종 선택(G2로 가는 길)을 막는다. 선택 API 오류 목록에 `ANCHOR_NOT_FIXED`가 없다 → 05-2를 먼저 고친 뒤 쓴다. (F-SO-11, PRD §8.2 RK-03 7, ERD 부록 A)
4. **JAN·AI 재확인**: 페이지를 읽은 행은 `articleNumber`(JAN)와 `メーカー型番`으로 앵커와 다시 대조해 `jan_match`·`maker_model_match`에 남긴다(NULL = 확인 안 함). 그래도 불확실한 행은 선택한 AI 엔진(P1-10 실행기 → `AiEngineAdapter.runStructured`)에 두 상품의 이름·속성을 넣어 `{ match, confidence, reason }`을 받아 `ai_match`에 둔다. AI 결과는 참고이고, 최종은 오너 `ownerMatchDecision`(`MATCH`·`NO_MATCH`)이다. SOURCING은 AI를 쓰는 단계라 시작 때 선택 엔진을 쓸 수 없으면 409 `AI_ENGINE_UNAVAILABLE`. 대조 불일치가 `anchor_match`를 바꾸는지, AI를 부를 행의 범위는 문서에 없음 → Proposed. (F-SO-10, F-BS-38, PRD §8.2 RK-03 5~6, 05-1 §2.1 표 A)
5. **성별**: 키워드 cid(50000173 여 / 50000174 남), 라쿠텐 장르 경로(メンズ靴 110983 / レディース靴 100480), 상품명으로 정해 `detected_gender`·`gender_basis`(`KEYWORD_CID`·`GENRE_PATH`·`ITEM_NAME`)에 남긴다. 공용·판단 불가면 ②는 성별 입력 대기(`PUT /candidates/{id}/gender`, P1-04 API → `owner_gender`). 오너가 넣은 성별(`gender_source=OWNER`)은 ② 재실행이 덮어쓰지 않고, 판단이 다르면 `gender_recheck_required=true`. 세 신호가 다를 때의 우선순위는 문서에 없음 → Proposed(기본안: 적힌 순서). (F-SO-18, F-SO-19, F-CW-08, US-30 AC1, PRD §5.3 성별)
6. **사이즈별 재고**: 목표 범위(성별, 기본 남 250~290mm, 여 220~260mm) 안에서 선택 색상·기본 폭(설정, 예 `2E (標準)`) SKU 중 `quantity > 0` AND `hidden = false`인 사이즈가 '재고 있음'이다. 取り寄せ(상품 `back_order_flag`·SKU `back_order`)는 뺀다. JP cm → mm(24.5 → 245), `size_mm`이 NULL(cm 아닌 라벨)이면 '수동 확인'. 결과는 `in_stock_size_count`. 폭 축이 없는 상품의 처리는 문서에 없음 → Proposed. (F-SO-20, US-04 AC4, US-30 AC1, PRD §8.2 RK-05)
7. **재고 부족·제외**: `in_stock_size_count` < 최소 기준(설정 기본 3)이면 `stock_pass=false`('재고 부족'), 미검증 행은 NULL. 앵커 일치나 재고 기준을 통과한 행이 하나도 없으면 후보를 '제외'(`excluded_reason` `ANCHOR_NO_MATCH`·`INSUFFICIENT_STOCK`)로 둔다. 상태 전환은 step-engine(F-CW-05)이 하고, 판단 시점(페이지 조회 반복이 `ENOUGH_CANDIDATES`·`PAGE_CAP`로 끝났을 때 등)은 문서에 없음 → Proposed. (F-SO-21, US-04 AC4, ERD `ck_candidate_excluded_reason`)
8. **대표 SKU·송료**: 대표 SKU = 재고 있는 목표 사이즈 SKU 중 가장 비싼 `taxIncludedPrice`(보수적). 송료 = `postageFlag=0` 또는 `postageIncluded=true`면 0(`FREE`), 그 밖에는 기본 송료(설정 ¥800, `DEFAULT_ESTIMATE`, '송료 추정' 배지)이며 0으로 두지 않는다(DB `ck_scr_shipping_default`). (F-SO-22, F-SO-24, US-05 AC2, PRD §8.2 RK-06)
9. **포인트**: `base = floor((SKU가_대표 − 쿠폰) / 1.1)`. 배율 = 기본 1 + 상품 추가분(`pointRate_includes_base`면 `pointRate − 1`, 기본 true) + 샵·이벤트(행별 오너 입력) + SPU(설정, 기본 0). 기본은 프로그램별 내림 `Σ floor(base × r / 100)`, 설정으로 단순식 `floor((SKU가_대표 − 쿠폰) × Σr / 110)`. 분해값을 `points_base_pt`·`points_item_pt`·`points_shop_event_pt`·`points_spu_pt`·`points_total_pt`에 둔다. 기대값: ¥12,000·10배·쿠폰 0 → base 10,909 → 109 + 981 = **1,090pt**(단순식 1,090). ¥12,099 → base 10,999 → 109 + 989 = **1,098pt**(단순식 1,099). (F-SO-22, F-SO-23, US-04 AC3, PRD §8.2 RK-06)
10. **실질가**: `effective_price_yen` = SKU가_대표 + 송료 − 쿠폰 − 포인트 × `k_rank`(설정 기본 0.5). 검증 행만 계산한다. 판정용 `k_margin`은 0 고정이라 ③ 마진에는 포인트를 넣지 않는다. 0.5엔 처리(내림·반올림)는 문서에 없음 → Proposed(ERD §7.1-7). 적용한 설정값(k_rank, SPU, 내림 방식, 기본 송료, 목표 범위, 최소 사이즈 수, 기본 폭, 取り寄せ 제외, K·M, 아동화 기준 mm)은 `sourcing_comparison.params`에 사본으로 남긴다. (F-SO-22, F-SO-23, US-04 AC3, ERD `sourcing_comparison.params`)
11. **행 수정**: `PATCH /sourcing-comparison-rows/{rowId}`는 바꾼 필드만 받는다(`couponYen` ≥ 0 정수, `shopEventMultiplier` ≥ 0 number, `ownerMatchDecision`). 빈 본문·음수는 422 `VALIDATION_FAILED`. 저장하면 바로 포인트·실질가를 다시 계산해 200 `{ row, rankedRowIds }`(검증 행의 실질가 순). 닫힌 버전의 행은 409 `STEP_RUN_NOT_WAITING_INPUT`. M2 필드(`shippingYen`·쿠폰 %·최소 금액·병용)는 M1 화면이 보내지 않는다. (F-SO-25, F-SO-26, US-05 AC1, 05-2 `updateSourcingComparisonRow`)
12. **미검증 행·재고 확인**: 페이지를 읽지 않은 행은 `is_verified=false`('미검증')이고 실질가 정렬에서 빠지며(맨 뒤) 고를 수 없다. `POST /sourcing-comparison-rows/{rowId}/stock-checks`는 그 페이지만 읽어(`fetch_reason=STOCK_CHECK`, 하루 상한 1건) 행에 `rakuten_item_id`를 잇고 202 `SourcingJobAccepted`(`rowId`), 결과는 SSE `sourcing.row-updated`. 진행 중이면 409 `ALREADY_IN_PROGRESS`(`details.job=STOCK_CHECK`), 상한·쉼은 409 `DAILY_LIMIT_REACHED`·`EXTERNAL_CALL_COOLDOWN`. (F-SO-15, US-04 AC2, 05-2 `requestSourcingRowStockCheck`)
13. **비교표 조회**: `GET /candidates/{id}/sourcing-comparison` — 현재 또는 `?stepRunId=` 버전, 페이징 없음. `sort`는 `effectivePriceYen`(기본 asc, 미검증 뒤)·`searchRank`·`fetchOrder`, 그 밖이나 다른 후보의 `stepRunId`는 422 `INVALID_QUERY_PARAMETER`. `includeNoMatch=false`면 `NO_MATCH` 행을 뺀다. ② 미실행이면 404 `STEP_OUTPUT_NOT_FOUND`. `creditText`='Supported by Rakuten Developers'. 열: 샵명·상품명·앵커 일치(型番·색상·JAN)·검증 여부·목표 사이즈 재고 수·SKU가·송료(추정 여부)·포인트 분해·쿠폰·실질가·리뷰·並行輸入品/アウトレット 표시(상품명에서 계산)·해외 배송 가능·수집 시각·라쿠텐 링크. 네이버 링크는 이 화면에 두지 않는다. 화면에 정렬 기준과 포인트 '근사'를 적는다. 14. **'수동' 행**: `POST /sourcing-comparisons/{id}/rows` `{ rakutenItemId }` → 201 `row_source=MANUAL` 검증 행. 앵커 없음 409 `ANCHOR_NOT_FIXED`, 같은 itemCode 행 409 `ROW_ALREADY_EXISTS`(UNIQUE(sourcing_comparison_id, item_code)), 제외어 422 `RAKUTEN_ITEM_EXCLUDED_WORD`, 스냅샷 없음 404 `RAKUTEN_ITEM_NOT_FOUND`. 그 뒤 재고 판정·실질가·선택은 API 행과 같다. 수동 행의 포인트 배율 출처는 M0 S2 전까지 Proposed(ERD §7.3-3). ## 8. 주의

- 공통 규칙은 [README §공통 규칙](../README.md#공통-규칙)을 따른다(실행 환경, 외부 호출 금지, 비밀정보, 커밋 안 함).

- 부동소수: JS에서 `11000 / 1.1`은 9,999.999…라 base가 1 틀린다. `Math.floor((price − coupon) * 10 / 11)`처럼 정수식으로 계산하고, 배율(`numeric(7,4)`, 예 1.5)은 정수 스케일(×10000)로 다룬다. 쿠폰 ¥1,000 사례를 테스트로 고정한다.
- 시안 샵 B의 '5배 · 590pt · 실질가 ¥12,305'는 PRD 식과 다르다(식대로면 536pt · ¥12,332). 테스트는 PRD 식을 따르고, 시안 숫자 차이를 결과 보고 '오너 검토'에 올린다.
- 후보 앵커는 한 번 확정되면 `trg_candidate_anchor_fixed`가 바꾸지 못하게 막는다. 선택 트랜잭션에서 처음 한 번만 쓰고, 이후 ② 재실행은 이 값을 앵커로 쓴다. `ck_candidate_anchor_fixed`는 색상 코드가 있어야 앵커가 확정되므로 색상 코드를 못 얻는 상품(시안 샵 C)은 고를 수 없다(ERD §7.3-1, M0 S2 뒤 확정).
- `trg_output_frozen`: 쿠폰·배율·오너 판단·재고 확인 결과·수동 행은 ② 버전이 입력 대기일 때만 바뀐다. 완료 뒤 바꾸려면 ② 다시 실행·재조회로 새 버전을 만들고 행을 복사한다(ERD §1.4).
- 재고 확인·앵커 뒤 조회는 P2-02의 직렬 페이지 큐와 하루 상한을 같이 쓴다. 여기서 따로 HTTP를 부르지 않는다.
- '소싱 선택'은 한 곳에만 쓴다. 비교한 버전은 `is_selected` 행, 비교 안 한 버전은 머리 행 `selected_rakuten_item_id`(CHECK `ck_sc_selection_uncompared`). ③(P2-05)·⑤·⑥이 P2-02의 읽기 함수로 이 값을 읽는다. 샵을 바꾸면 G2 지문(P1-06)이 바뀌고 ⑥-2 파생 필드에 '재확인 필요'(`ITEM_CODE_CHANGED`)가 붙는다.
- SOURCING은 AI 단계로 분류돼(05-1 표 A) 선택 AI 엔진을 못 쓰면 ② 시작 자체가 409다. 실행 중 AI 호출이 실패할 때 비교 전체를 실패시킬지 그 행만 참고 없음으로 둘지는 문서에 없음 → Proposed. AI 결과로 `anchor_match`나 선택을 자동으로 바꾸지 않는다(최종 판단은 오너).
