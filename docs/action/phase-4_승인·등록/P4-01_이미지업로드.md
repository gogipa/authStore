## 1. 목표

⑧ 이미지 업로드 단계를 만든다. 단계 실행(`POST …/steps/UPLOAD/runs`)이나 연속 실행으로 ⑧을 돌리면, G3에서 고른 AI 썸네일을 1000×1000 JPEG로 바꿔 커머스API 이미지 업로드(개발·테스트는 가짜 서버)로 차례로 올리고, 받은 `shop-phinf` URL을 원천 파일 해시별로 저장해 다시 쓴다. ⑥-3 HTML의 이미지 자리표시자를 업로드 URL로 바꿔 최종 `detailContent`를 만들고, `GET …/upload-result`와 SCR-08의 ⑧ 영역에서 보여 준다. 흐름에서는 G3·⑥-3 뒤, G4(P4-02) 앞이다. 업로드만으로는 스토어에 노출되지 않는다.

## 4. 핵심 규칙

1. 시작 조건은 두 가지다: ⑤ G3 선택본(현재 버전 `thumbnail_selection` + `thumbnail_selection_image`)과 ⑥-3 HTML(현재 버전 `content_draft_assembly.html`·`html_sha256`). 둘 다 '완료'이고 G3이 유효해야 한다. G3이 없거나 지문이 바뀌었으면 409 `GATE_NOT_PASSED`(`details.gate=G3`), 커머스API 키가 키체인에 없으면 409 `SECRET_NOT_CONFIGURED`로 시작 전에 막는다. (PRD §5.3 ⑧ 행, 05-1 표 A `UPLOAD`, F-AP-01)
2. 임시(`TEMP`) 후보는 ⑧을 실행할 수 없다. M1에는 임시 후보가 생기지 않지만 가드는 지금 둔다(409 `TEMP_CANDIDATE_NOT_ALLOWED`). 등록요청중·결과확인필요·등록됨 후보는 P1-04 잠금(409 `CANDIDATE_LOCKED`)을 그대로 받는다. (PRD §5.2 잠금·'임시 후보는 ⑧·⑨ 불가', F-AP-01, F-CW-07, 05-3)
3. 입력 지문은 G3 선택본 이미지의 `sha256`(sort_order 순)과 ⑥-3 `html_sha256`로만 만든다. 업로드 시각·URL은 넣지 않는다. 두 입력을 `step_run_input`(`source_type=PREV_STEP`, `source_step_run_id`)으로 남겨 P1-05의 '재실행 필요' 전파가 ⑧을 찾게 한다. (PRD §5.3 규칙 1, ERD `uploaded_image.source_sha256`, F-BS-20)
4. 구성: 대표 1장 = G3 대표(sort_order 0), 추가 = G3에서 고른 다른 AI 후보(sort_order 1~9)만이다. `upload_result_image.role`·`sort_order`는 G3 선택과 같게 둔다(`ck_upload_img_rep`: REPRESENTATIVE ⇔ 0). (F-AP-04, PRD §8.4 'M1 업로드 이미지 구성', ERD `upload_result_image`)
5. 참조 전용 거부: 업로드 함수는 `usage_right='REFERENCE_ONLY'` 파일(원본·레퍼런스)이나 그런 파일에서 만든 정규화본을 받으면 외부 호출 전에 예외를 던진다. 끄는 설정은 없다. 이때 ⑧은 `FAILED`(`failureKind=INPUT_VALIDATION`, `errorCode=IMAGE_NOT_ALLOWED`)로 끝나고 업로드 호출은 0건이다. (F-BS-45, US-11 AC2, CON-07, F-BS-04, 05-1 §6)
6. 정규화: 파일 앞 바이트로 실제 포맷을 판별한다(확장자를 믿지 않는다). 1000×1000 정사각 JPEG로 바꿔 `image_asset`(kind=`UPLOAD`, `usage_right=PERMITTED`, `derived_from_image_asset_id`=원천 생성본, `candidate_id`)으로 저장한다. `ck_image_asset_upload`(`image/jpeg`, 1000×1000, 10,485,760바이트 미만)를 지킨다. 정사각이 아닌 원천을 자를지 채울지는 문서에 없음 → 구현 때 Proposed로 정하고 기록. (F-AP-02, PRD §8.4 7, ERD `image_asset` CHECK)
7. 해시 재사용: 원천 파일 `sha256`로 `uploaded_image.source_sha256`을 먼저 찾는다. 있으면 올리지 않고 그 URL을 쓴다(후보·버전이 달라도). 없을 때만 올리고 `uploaded_image`(source_sha256, image_asset_id, url, trace_id, uploaded_at)를 추가한다. (F-AP-05, RG-05, ERD `uploaded_image` UNIQUE)
8. 묶음·순차: 한 호출에 최대 10장, 바이트 합 10,485,760 미만으로 나눈다. 설치본은 스토어 1개라 앱 전체에서 업로드 호출은 한 번에 1건만 보낸다(다른 후보의 ⑧과도 줄을 선다). 호출은 `POST /v1/product-images/upload`, multipart 필드 `imageFiles`다. (F-AP-03, NFR-05, PRD §8.7 등록 호출 순서 4, US-20 AC1)
9. 최종 본문: ⑥-3 `html`의 이미지 자리표시자를 이 버전의 업로드 URL로 모두 바꿔 `upload_result.detail_content`와 `detail_content_sha256`을 만든다. 바꾸지 못한 자리표시자가 하나라도 남으면 ⑧을 실패로 둔다. 자리표시자 형식은 P3-04가 정한 것을 쓴다. (F-AP-06, PRD §8.5 '상세 HTML 조립', ERD `upload_result`)
10. ⑥-3만 바뀐 재실행: 선택본 해시가 그대로면 업로드 호출이 0건이고 `detail_content`만 새로 만든다. 입력이 같아도 '다시 실행'은 새 버전을 만든다. (F-AP-05, F-BS-19, PRD §5.3 '⑥-3만 바뀌어 ⑧을 다시 실행하면…')
11. 재실행 필요: ⑧ 완료 뒤 G3 선택본이나 ⑥-3 HTML이 바뀌면 ⑧만 `RERUN_REQUIRED`가 되고 바뀐 입력 이름이 남는다. 카피·태그는 '완료'로 남는다. 자동으로 다시 올리지 않는다. ⑧에는 '그대로 유지'가 없다. (F-AP-07, US-33 AC3, PRD §5.3 규칙 5·6)
12. 산출물은 추가만 한다. `upload_result`(+`_image`)는 ⑧ StepRun이 열려 있을 때만 쓸 수 있고(`trg_output_frozen`), 산출물 저장·StepRun 종료·뒷단계 표시는 P1-05의 완료 트랜잭션 하나로 한다. (ERD §1.3, C4 §4 '단계 시작·완료')
13. 조회: `GET /candidates/{candidateId}/upload-result`는 현재 버전(`candidate_step.current_step_run_id`), `?stepRunId=`면 그 버전을 준다. `reused` = `uploaded_image.uploaded_at` < 이 실행 시작 시각(계산). 산출물 없음 404 `STEP_OUTPUT_NOT_FOUND`, 후보 없음 404 `CANDIDATE_NOT_FOUND`, 이 후보의 ⑧ 실행이 아닌 `stepRunId` 404 `STEP_RUN_NOT_FOUND`, 틀린 쿼리 422 `INVALID_QUERY_PARAMETER`. 응답에 로컬 파일 경로를 넣지 않는다. (05-1 §2.9·§1.2, 05-2 `getCandidateUploadResult`)
14. 외부 호출 기록: 토큰은 요청 헤더에만 둔다. 업로드 호출마다 P1-01 관문으로 `call_log`(target=`COMMERCE_API`)를 남기고, 응답 헤더 `GNCP-GW-Trace-ID`를 `uploaded_image.trace_id`에 저장한다. 업로드 실패(4xx·5xx·타임아웃)는 HTTP 오류가 아니라 ⑧ `FAILED`(`EXTERNAL_API`) + 한국어 `errorMessage` + SSE로 알린다. (05-1 §1.3, ERD `uploaded_image`, NFR-03)

## 5. 만들 것

**BE** (ESM, 상대 import에 `.js`. 오류는 `ApiException` + `ERROR_CODES`, DB는 `PrismaService`)

- `apps/BE/src/modules/registration/upload/`
  - `upload.step-runner.ts` — `UPLOAD` 러너. P1-05가 정한 `StepRunner` 등록 방식(모듈 초기화 때 step-engine 레지스트리에 `stepCode='UPLOAD'`로 등록)을 따른다. step-engine이 넘긴 입력(⑤·⑥-3 현재 버전)만 읽고 thumbnails·content 모듈을 import하지 않는다. AI를 쓰지 않으므로 `step_run.ai_*`는 비운다.
  - `image-normalizer.ts` — 포맷 판별 + sharp로 1000×1000 JPEG. sharp는 02-ADR-001의 선택이다: `pnpm --filter @autostore/be add -E sharp@<버전>`.
  - `upload-batcher.ts` — 10장·10MB 미만 묶음 나누기(순수 함수).
  - `upload-queue.ts` — 앱 전체 직렬 큐(동시 1건).
  - `image-upload.service.ts` — 해시 재사용 → 참조 전용 거부 → 정규화 → 묶음 업로드 → `uploaded_image` 저장. 참조 전용 검사는 이 함수의 첫 줄이다.
  - `detail-content.ts` — 자리표시자 치환(순수 함수). 자리표시자 형식 상수는 content와 같이 쓰도록 `apps/BE/src/common/` 아래에 둔다(P3-04가 content 안에 뒀으면 옮긴다).
  - `upload-result.controller.ts`·`upload-result.service.ts`·`upload-result.dto.ts` — `getCandidateUploadResult`. DTO는 05-2 `UploadResultOutput`·`UploadResultImageItem` 필드 그대로, Swagger 데코레이터를 단다.

- P1-07·P1-08이 만든 가짜 커머스API 서버가 있으면 `/v1/product-images/upload` 경로를 더하고, 받은 요청 수·multipart 부분 수·바이트 합을 기록해 테스트가 읽게 한다.

**문서 갱신**

- 자리표시자 형식, 정사각이 아닌 원천 처리, 업로드 도중 실패 때 받은 URL 처리를 Proposed로 ERD §3.10(`upload_result` 비고) 또는 05-1 §2.9에 적는다.
- 업로드 응답 모양 가정을 결과 보고 '오너 검토'에 올린다(M0 S3 확인 항목).

**e2e** (`autostore_test`, `seed-upload-ready`)

- `POST /api/v1/candidates/{id}/steps/UPLOAD/runs`(헤더 `X-AutoStore-Client: 1`) → 202, `Location: /step-runs/{id}`. 끝난 뒤 `GET …/upload-result` → 200, `images` 2개(REPRESENTATIVE sortOrder 0, ADDITIONAL 1), `url`은 가짜 shop-phinf 주소, `detailContent`에 자리표시자 없음, `detailContentSha256`은 64자리 hex, 응답에 `filePath` 키 없음.
- G3 통과 기록 없음 → 409 `GATE_NOT_PASSED`, `details.gate=G3`. 가짜 키체인이 비었음 → 409 `SECRET_NOT_CONFIGURED`.
- 입력이 같은 두 번째 실행 → version 2, 가짜 업로드 호출 0, `images[].reused=true`.
- ⑥-3 새 버전만 만듦 → ⑧ `RERUN_REQUIRED`, `staleInputs`에 `NOTICE_HTML`. ⑥-1·⑦은 `COMPLETED` 그대로. 가짜 업로드 호출 0(자동 실행 없음).
- ⑤ 다시 고르기(다른 선택본) → ⑧만 `RERUN_REQUIRED`.
- 가짜 서버 500 → 202로 시작, 실행 기록 `FAILED`·`failureKind=EXTERNAL_API`·한국어 `errorMessage`.
- 선택본에 원본을 억지로 넣은 seed → `FAILED`·`INPUT_VALIDATION`·`errorCode=IMAGE_NOT_ALLOWED`, 업로드 호출 0.
- 산출물 없음 → 404 `STEP_OUTPUT_NOT_FOUND`. `?stepRunId=abc` → 422 `INVALID_QUERY_PARAMETER`. 다른 후보의 실행 id → 404 `STEP_RUN_NOT_FOUND`.

**FE** (Vitest + Testing Library)

- `UploadSection`: 완료면 칩 '완료'와 '버전 v1', 입력 출처 문구가 보인다. `RERUN_REQUIRED`면 '재실행 필요'와 바뀐 입력 이름이 보인다.
- '다시 실행'을 누르면 `POST …/steps/UPLOAD/runs`가 한 번 불린다(가짜 client).
- 이미지 `src`가 모두 `/api/v1/image-assets/…/file`이다(외부 URL 없음).

## 8. 주의

- 공통 규칙은 [README §공통 규칙](../README.md#공통-규칙)을 따른다(실행 환경, 외부 호출 금지, 비밀정보, 커밋 안 함).
- 커머스API 이미지 업로드 실제 호출 금지. 가짜 서버로 검증한다.

- `uploaded_image`·`image_asset`은 추가만 한다(`trg_append_only`). 행을 고치거나 지우는 코드를 쓰지 않는다.
- 업로드 도중 한 묶음이 실패할 때 앞 묶음에서 받은 URL을 남길지는 문서에 없음 → Proposed로 정하고 기록. `uploaded_image`는 산출물이 아니라 해시 캐시라서 묶음마다 바로 커밋해도 산출물 불변 규칙과 부딪히지 않는다. 남기면 다시 실행할 때 이미 올린 파일을 또 올리지 않는다.
- shop-phinf URL의 유효기간과, 상품에 쓰지 않은 업로드 이미지가 지워지는지는 M0 S3 확인 전이다(ERD §7.3-7). 해시 재사용이 이것을 전제로 하므로 결과 보고에 남긴다.
- agy 생성본은 확장자와 실제 포맷이 다를 수 있다(PRD §8.4). MIME은 파일 내용으로만 정한다.
- 재실행 필요 전파는 P1-05 엔진이 한다. ⑧ 러너가 뒷단계 상태를 직접 바꾸거나 ⑤·⑥-3 모듈을 import하지 않는다(03-ADR-003).
- ⑧이 새 버전을 만들면 G4 승인 body의 `expectedUploadResultId`가 달라져 P4-03에서 409 `VERSION_NOT_CURRENT`가 된다. 의도된 동작이다. 새 버전 뒤 P1-04의 자동 전환으로 승인대기 후보가 '작업중'으로 내려갈 수 있다.
- 직렬 큐는 프로세스 메모리다. 앱이 재시작되면 실행중이던 ⑧은 P1-05가 '실패(중단됨)'로 바꾼다. 다시 실행하면 해시 재사용으로 이미 올린 것은 건너뛴다.
- P4-02(이미지 검사·미리보기)와 P4-03(요청 본문)이 `upload_result`·`uploaded_image`를 읽는다. `UploadResultOutput` 필드 이름을 05-2와 다르게 바꾸지 않는다.
