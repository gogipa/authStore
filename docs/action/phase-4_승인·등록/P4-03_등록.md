## 1. 목표

G4 최종 승인과 ⑨ 등록을 만든다. 오너가 SCR-08에서 '승인·등록'을 누르면 서버가 사전 검증을 다시 돌린다. 차단 스위치가 켜져 있으면 요청 JSON과 검증 결과만 저장해 '검증완료'로 두고, 꺼져 있으면 등록 기록을 '등록요청중'으로 먼저 커밋한 뒤 커머스API `POST /v2/products`(개발·테스트는 가짜 서버)를 부른다. 결과에 따라 등록됨·결과확인필요·승인대기(4xx)로 바뀌고, 결과확인필요는 판매자관리코드 조회로 푼다. 같은 상품·색상의 이중 등록을 로컬 DB와 커머스API 양쪽에서 막는다. ①~⑨의 마지막 단계이고, 처음 10건은 전시중지로 올라가 G5(스마트스토어센터)로 이어진다.

## 4. 핵심 규칙

1. 요청 본문: `statusType=SALE`, `deliveryInfo`(`deliveryType=DELIVERY`, 프로필 `deliveryCompany`, 무료 배송비, `claimDeliveryInfo.shippingAddressId`=해외 출고지, `returnAddressId`), `customsTaxType=INCLUDED`, `businessCustomsClearanceSaleYn=false`, `minorPurchasable=true`, `productInfoProvidedNotice.productInfoProvidedNoticeType=SHOES`, `seoInfo.sellerTags` 10개 이하(추천 태그와 같으면 code+text, 아니면 text), 주문당 구매수량 제한(기본 1, 필드 이름은 M0 S3), `sellerCodeInfo.sellerManagementCode`, `naverShoppingRegistration` 기본 켬. `deliveryInfo`를 빼지 않는다. `request_json`에 토큰·시크릿이 없다. (PRD §8.7 '요청 골격', F-AP-25, F-TG-12, US-21 AC2)
2. 판매자관리코드는 `RKT:{itemCode}:{colorCode}`다. itemCode는 API·URL 경로 모두 `샵코드:상품ID`로 정규화한 승인 시점 값, colorCode는 `candidate.anchor_color_code`다. `ck_reg_seller_code`와 같은 식으로 만든다(200자 이하, API 제한은 M0 S3). (F-AP-35, RG-12, ERD `registration.seller_management_code`)
3. 사이즈 옵션: 선택 색상·기본 폭 SKU 가운데 판정에서 판매 가능(M1은 면세 사이즈만)이고 재고 > 0인 사이즈만 조합형(옵션명 '사이즈', mm 표기)으로 만든다. 옵션가는 `price_judgement_size.option_price_krw`다. 사이즈별 재고 = min(라쿠텐 수량, 상한 설정 기본 2), 원상품 `stockQuantity` = 옵션 재고 합이다. 표준형은 카테고리가 지원할 때만(메타 동기화 `STANDARD_OPTIONS`) 승인 화면에서 고르고, 승인 전에는 저장하지 않고 `?optionType`·승인 body로만 넘긴다. (F-AP-39·40·41, RG-06, D-11, 05-2 x-decision §7.5-39)
4. 전시 모드: 이 앱의 실제 등록 건수(상태 `REGISTERING`·`RESULT_CHECK_REQUIRED`·`REGISTERED`이고 `failed_at` 없음. 드라이런·종결 기록 제외)가 설정 N(기본 10)보다 작으면 `SUSPENSION`, 아니면 `ON`이다. 값은 `registration.display_status_type`에 남는다. (F-AP-27, US-20 AC5, ERD §7.1-8)
5. 승인 요청 검사(모두 지나야 기록을 만든다): `Idempotency-Key` 없음 400 `IDEMPOTENCY_KEY_REQUIRED` → 같은 키 기록 있음이면 첫 응답 202 그대로(본문이 다르면 422 `IDEMPOTENCY_KEY_REUSED`) → 후보 없음 404 `CANDIDATE_NOT_FOUND` → 진행 중 기록(등록요청중·결과확인필요, `failed_at` 없음) 409 `REGISTRATION_IN_PROGRESS` → 승인대기 아님 409 `CANDIDATE_STATUS_INVALID` → expected* ≠ 현재 409 `VERSION_NOT_CURRENT` → G2·G3 무효 409 `GATE_NOT_PASSED` → 판정 유효 시간 초과 409 `JUDGEMENT_EXPIRED` → 중복 409 `DUPLICATE_REGISTRATION` → 사전 검증 BLOCK 실패 422 `PRE_VALIDATION_FAILED`(`details.checks[]`). '같은 본문'은 `option_type`·`upload_result_id`·`price_judgement_id` 비교로 판단한다. 409 코드 사이 순서는 표 E에 없음 → 이 순서를 Proposed로 기록. (05-1 표 E·§1.7, 05-3 §5.1)
6. 차단 스위치 켬(드라이런): 한 트랜잭션에서 ⑨ StepRun을 만들어 `COMPLETED`로 닫고, 등록 기록 `VALIDATED`(request_json, validation_result, approved_at. `request_sent_at`·상품 번호 없음 = `ck_reg_validated`), 후보 → `VALIDATED`(`G4_APPROVED_BLOCKED`), `user_action_log`(GATE_PASSED, G4)를 쓴다. `POST /v2/products`를 부르지 않는다. 응답은 202 `status=VALIDATED`. (F-AP-28, US-23 AC1, ERD `registration` '⑨ StepRun과의 대응' ①②)
7. 차단 스위치 끔: 먼저 한 트랜잭션으로 ⑨ StepRun `RUNNING` + 등록 기록 `REGISTERING`(seller code, idempotency_key, approved_at) + 후보 → `REGISTERING`(`G4_APPROVED`) + user_action_log를 커밋하고 202를 준다. 그다음 트랜잭션 밖에서 `request_sent_at`을 적고 `POST /v2/products`를 부른다. ⑧ 산출물의 업로드 URL만 쓰고 이미지를 다시 올리지 않는다. (F-AP-26·29, US-20 AC3·AC4, C4 §4 '⑨ 등록')
8. 결과 반영: 2xx → 기록 `REGISTERED`(origin_product_no·channel_product_no 숫자 문자열, registered_at, response_received_at, http_status), ⑨ `COMPLETED`, 후보 `REGISTERED`(`REGISTER_SUCCEEDED`). 4xx → 기록 상태는 `REGISTERING` 그대로 + `failed_at`·`failure_kind=INVALID_INPUT_4XX`·http_status·error_code·한국어 error_message·invalid_inputs·trace_id, ⑨ `FAILED`(EXTERNAL_API), 후보 `AWAITING_APPROVAL`(`REGISTER_4XX`). 타임아웃·5xx·연결 오류 → 기록 `RESULT_CHECK_REQUIRED`, ⑨ `FAILED`(EXTERNAL_API), 후보 `RESULT_CHECK_REQUIRED`(`REGISTER_UNKNOWN`), 자동 재시도 없음. 전이마다 SSE `registration.status-changed`·`candidate.status-changed`. (F-AP-26·30·33, PRD §5.2 상태도, ERD `registration` 대응 ③, `ck_reg_failure_kind`)
9. 결과 확인(`POST /registrations/{id}/result-checks`, 동기): `RESULT_CHECK_REQUIRED`이고 종결되지 않은 기록만 된다(아니면 409 `REGISTRATION_STATUS_INVALID`). 후보 현재 값이 아니라 `registration.seller_management_code`로 `POST /v1/products/search`(SELLER_CODE)를 부른다. 찾으면 기록 `REGISTERED` + 상품 번호 + 후보 `REGISTERED`(`SELLER_CODE_FOUND`), 없으면 `failed_at`·`NOT_FOUND_ON_CHECK` + 후보 `AWAITING_APPROVAL`(`SELLER_CODE_NOT_FOUND`). `last_result_check_at`은 매번 적는다. 닫힌 ⑨ StepRun과 `candidate_step(REGISTER)`은 바꾸지 않는다. 키 없음 409 `SECRET_NOT_CONFIGURED`, 외부 실패 502 `EXTERNAL_API_ERROR`(`details.target=COMMERCE_API`)·`COMMERCE_AUTH_FAILED`이고 상태는 그대로다. 앱 재시작 복구(F-BS-18)도 이 서비스를 쓴다. (F-AP-31, US-20 AC4, US-29 AC3, 05-2 `checkRegistrationResult`)
10. 중복 교차 확인: 승인 화면을 열 때(사전 검증 `DUPLICATE`)와 승인 직전에 로컬 DB(`uq_registration_live_key`와 같은 조건: 같은 item_code + selected_color, 진행 중·등록됨, `failed_at` 없음)와 커머스API SELLER_CODE 조회를 둘 다 한다. 어느 쪽이든 있으면 중복이다. 끄는 설정은 없다. 부분 UNIQUE 두 개(`uq_registration_live_key`, `uq_registration_live_seller_code`)가 마지막 방어선이고, 위반은 409 `DUPLICATE_REGISTRATION`으로 바꾼다. (F-AP-36, US-22 AC2, F-BS-04, ERD `registration` 인덱스)
11. 기존 상품 보기: 중복이면 '승인·등록' 대신 '기존 상품 보기'를 보이고, 상품 번호·등록 시각을 보여 주며 스마트스토어센터 상품 화면을 새 브라우저 창으로 연다. 주소 형식은 문서에 없음 → 구현 때 Proposed로 정하고 기록. 같은 모델·색상이 다른 `itemCode`로 등록돼 있으면 `warnings[]`에 `SAME_MODEL_REGISTERED`를 넣는다(막지 않음). (F-AP-37·38, 04 §4 #12)
12. 차단 스위치 API: 기본값 켬(`registration_switch.api_blocked=true`, 1행). `PUT`이 같은 값이면 변화 없이 200. 끄면 `VALIDATED` 후보를 모두 `AWAITING_APPROVAL`(`BLOCK_SWITCH_OFF`)로 되돌리고 `user_action_log`(SETTING_CHANGED)를 같은 트랜잭션에 남긴 뒤 `revertedCandidateIds`를 준다. 등록요청중 기록이 있어도 전환을 막지 않는다. SSE `registration-switch.changed`. (F-AP-28, 05-2 `putRegistrationSwitch` x-decision §7.5-40, ERD `registration_switch`)
13. 오류 안내: `invalidInputs`를 한국어로 풀어 `error_message`에 남기고 화면에 보인다. `GNCP-GW-Trace-ID`는 `trace_id`와 로그에 남기고 화면에도 보인다. 모르는 오류 코드는 원문 필드명·메시지를 함께 보인다. 번역 사전은 문서에 없음 → Proposed. (F-AP-32, US-19 AC2, US-20 AC3)
14. 기록 보관·조회: 승인마다 등록 기록 1행과 ⑨ 새 버전이 생긴다(4xx 뒤 다시 승인하면 같은 판매자관리코드로 새 행). 기록은 지우지 않는다(`registration_no_delete`). `GET …/registrations`는 페이징(`page` 0부터, `size` 기본 20·최대 100, `sort` `approvedAt`·`createdAt`, 기본 `approvedAt,desc`, 틀리면 422 `INVALID_QUERY_PARAMETER`), `GET /registrations/{id}`는 `request_json`을 빼고 준다(없으면 404 `REGISTRATION_NOT_FOUND`). (F-AP-33·34, 05-1 §1.4·§2.9)
15. 웹 전용: ⑨로 가는 길은 `POST /candidates/{id}/registrations` 하나뿐이고 로컬 보안 가드(Origin·`X-AutoStore-Client`)를 거친다. 연속 실행·CLI·설정·단계 실행으로 ⑨를 부르는 길을 만들지 않는다. (F-AP-10, 05-1 §1.2 '웹 화면 전용 기록', 05-1 표 E)

## 8. 주의

- 공통 규칙은 [README §공통 규칙](../README.md#공통-규칙)을 따른다(실행 환경, 외부 호출 금지, 비밀정보, 커밋 안 함).
- 등록 API 차단 스위치는 기본으로 켜져 있어야 한다(실제 스토어, 샌드박스 없음). 개발·테스트에서 커머스API 실제 등록 호출 금지.

- 실제 스토어이고 샌드박스가 없다. e2e에서 스위치를 끄기 전에 커머스API 주소가 가짜 서버(127.0.0.1)인지 먼저 단언한다. 개발 환경의 스위치 기본값을 바꾸지 않는다.
- 4xx 종결 기록은 `status=REGISTERING`으로 남는다(`failed_at`으로 종결). '진행 중' 판단에는 반드시 `failed_at IS NULL`을 함께 본다. 빠뜨리면 4xx 뒤 재승인이 `REGISTRATION_IN_PROGRESS`로 막히고 '처음 10건' 셈도 틀린다.
- ⑨ StepRun과 등록 기록 상태가 다를 수 있다(결과확인필요 뒤 등록됨이 돼도 ⑨는 `FAILED` 그대로, ERD §7.1-16). 화면·목록은 등록 기록 상태를 먼저 보인다. 닫힌 step_run을 고치면 `trg_step_run_append_only`가 막는다.
- 401 `GW.AUTHN`·429처럼 입력 오류가 아닌 4xx를 어떻게 닫을지 문서에 없다(PRD는 '401이면 재발급'만 적었다). 등록 POST를 자동으로 다시 보내지 않는 것이 멱등 규칙과 맞다 → 구현 때 Proposed로 정하고 기록. 보내기 직전에 P1-07의 '만료 30분 전 갱신'으로 401을 줄인다.
- 판매자관리코드 길이·문자 제한, SELLER_CODE 조회로 channelProductNo를 얻는지, 구매수량 제한 필드, 해외 출고 `deliveryCompany` 코드는 M0 S3 확인 전이다(ERD §7.3-5·6). fixture 가정을 어댑터 주석과 결과 보고에 남긴다.
- 드라이런 뒤(`VALIDATED`) `GET …/approval`은 409다. 화면은 등록 기록 목록으로 결과를 보이고 '스위치를 끄면 승인대기로 돌아갑니다'를 안내한다. 이 표시는 문서에 없음 → Proposed.
- 시안의 '(3/10)' 개수와 '표준형으로 바꾸기'를 보일지(카테고리 지원 여부)는 `ApprovalPreview`에 필드가 없다. 05-2에 더할지, 화면에서 뺄지 정하고 기록한다.
- 재시작 때 `REGISTERING`이고 `request_sent_at`이 NULL이어도 '결과확인필요'로 두고 조회부터 한다(ERD `registration.request_sent_at`). 이 복구는 P1-05가 부르고, 조회 서비스는 이 문서가 만든다.
