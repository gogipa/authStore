## 1. 목표

후보(작업 단위) 층이 동작한다. 검색어·키워드 경로로 후보를 만들고(라쿠텐 URL 경로는 공통 부분까지), 목록·상세·상태별 수·상태 이력을 보고, 제외·다시 작업·성별 입력을 할 수 있다. 상태 자동 전환(작업중 ↔ 승인대기, 제외), 등록 진행 후보 잠금, 앵커 키 고정, 진행 중 중복 검사가 서버 규칙으로 돈다. SCR-01 대시보드의 M1 부분과 SCR-12 후보 목록이 실제 API로 그려진다. ①~⑨ 흐름에서 ②~⑨ 모든 단계가 올라서는 바닥이고, 단계 실행 엔진(P1-05)과 게이트(P1-06)가 이 위에 붙는다.

## 4. 핵심 규칙

1. **만들기는 한 트랜잭션**: `candidate` 1행 + `candidate_step` 10행(SOURCING~REGISTER, 모두 `NOT_RUN`, `last_version=0`) + `candidate_status_history` 1행(`from_status` NULL, `reason=CREATED`). 응답은 201 + `Location: /api/v1/candidates/{id}` + `CandidateDetail`, 상태는 `WORKING`. `DIRECT_INPUT`(M2, `TEMP`)을 M1에서 받을지는 문서에 없음 → 구현 때 Proposed로 정하고 기록. (05-1 §2.1 `POST /candidates`·표 D, 05-2 `createCandidate`, ERD §3.1 `candidate_step`)
2. **경로별 필수값·검사**: `KEYWORD` = `sourceKeywordId` + `rakutenQuery`. 없는 키워드 404 `KEYWORD_NOT_FOUND`, G1에서 안 고름 409 `KEYWORD_NOT_SELECTED`, 아동화 제외 키워드 409 `KEYWORD_EXCLUDED`. `SEARCH_QUERY` = `rakutenQuery`. `RAKUTEN_URL` = `rakutenItemId` + `selectedColor`, 스냅샷 없음 404 `RAKUTEN_ITEM_NOT_FOUND`. 검색어 규칙 위반 422 `RAKUTEN_QUERY_INVALID`(규칙 함수는 P2-02와 같은 것, 그 전에는 반각 128자만 본다). 빠진 값 422 `VALIDATION_FAILED`. 제외어(`RAKUTEN_ITEM_EXCLUDED_WORD`)는 P2-02 몫. (표 D, 05-3 §5.1, ERD `ck_candidate_keyword_path`·`ck_candidate_url_path`)
3. **진행 중 중복(F-CW-04)**: '진행 중' = `EXCLUDED`·`REGISTERED`가 아닌 후보. 같은 `itemCode + selectedColor`가 있으면 새 행 없이 409 `CANDIDATE_DUPLICATE` + `details.existingCandidateId`(화면은 그 후보를 연다). 앵커 키(型番 또는 앵커 itemCode + 색상 코드)만 같으면 막지 않고 `warnings[ANCHOR_KEY_DUPLICATE]`. 검사 시점은 네 곳: 만들기(RAKUTEN_URL), 임시 후보 연결(M2), ② 소싱 선택 변경(P2-03이 이 서비스를 쓴다), 다시 작업. (PRD §5.2 후보 중복, US-35 AC2, ERD `uq_candidate_active_item_color`)
4. **앵커 키 고정(F-CW-03)**: `anchor_model_code`·`anchor_item_code` 중 하나(`ck_candidate_anchor_one`) + `anchor_color_code`를 한 번 확정하면 `anchor_fixed_at`을 찍는다. 다른 값으로 바꾸려 하면 409 `ANCHOR_KEY_MISMATCH`, 같은 값이면 그대로 둔다. 같은 앵커 키 안의 `item_code` 변경은 허용하고, G2 지문에 들어가 G2를 다시 통과해야 한다(P1-06). DB 트리거 `candidate_anchor_fixed`가 한 번 더 막는다. (PRD §5.2 작업 단위, US-35 AC1, 05-1 §6 F-CW-03)
5. **자동 전환(F-CW-05)**: 필수 9단계(SOURCING·PRICING·CATEGORY·THUMBNAIL·COPY·NOTICE_RAW·NOTICE_HTML·TAGS·UPLOAD)의 `candidate_step.status`가 모두 `COMPLETED`이고 G2·G3이 유효하면 `WORKING` → `AWAITING_APPROVAL`(`READY_FOR_APPROVAL`). `AWAITING_APPROVAL`·`VALIDATED`에서 하나라도 어긋나면 → `WORKING`(단계 때문이면 `STEP_NOT_CURRENT`, 지문 때문이면 `GATE_FINGERPRINT_CHANGED`). 단계 결과가 앵커 일치 없음·재고 부족·판매 후보 아님이면 → `EXCLUDED`(`reason`·`excluded_reason` 같은 코드). REGISTER는 필수에 넣지 않는다. '최신'은 지문 일치만 보고 6시간 경과는 보지 않는다. 재평가는 단계 완료·오너 수정·게이트 통과·전파와 같은 트랜잭션에서 한다. (PRD §5.2 상태도·필수 단계, §5.3 판정 유효 시간, ERD §4.2 reason)
6. **전이 기록**: 전이마다 `candidate.status`·`status_changed_at` 갱신 + 이력 1행(추가만) + 커밋 뒤 SSE `candidate.status-changed`. `EXCLUDED` ⇔ `excluded_reason` 있음(`ck_candidate_excluded_pair`). 승인대기 이상은 `item_code`·`anchor_color_code`·`gender`·`leaf_category_id`가 모두 있어야 한다(`ck_candidate_ready`). 없으면 전환하지 않는다. (ERD §3.1 CHECK, 05-1 §3)
7. **제외(F-CW-06)**: `TEMP`·`WORKING`·`AWAITING_APPROVAL`에서만 → 200 `EXCLUDED`/`OWNER_EXCLUDED`. 이미 `OWNER_EXCLUDED`면 같은 응답, 새 이력 없음. `VALIDATED` 409 `CANDIDATE_STATUS_INVALID`(`details.allowed`), 등록 진행 409 `CANDIDATE_LOCKED`, 실행 중 단계가 있으면 409 `STEP_LOCKED_BY_RUNNING_STEP`. 다른 사유로 이미 제외된 후보의 제외 요청은 문서에 없음 → 구현 때 Proposed로 정하고 기록. (05-2 `excludeCandidate` x-decision §7.2-13)
8. **다시 작업**: `EXCLUDED` → 200 `WORKING`(`REOPENED`, `excluded_reason` NULL). 이미 `WORKING`이면 같은 응답, 그 밖 409 `CANDIDATE_STATUS_INVALID`. 규칙 3의 중복 검사를 거친다. '기준·입력을 바꿨는지'는 검사하지 않는다. (05-2 `reopenCandidate` x-decision §7.2-14)
9. **잠금(F-CW-07)**: `REGISTERING`·`RESULT_CHECK_REQUIRED`·`REGISTERED` 후보는 상태를 바꾸는 step-engine 요청(단계 실행·오너 수정·성별·제외·게이트·연속 실행)이 모두 409 `CANDIDATE_LOCKED`(`details.status`). 상세 `locked`는 이 세 상태면 true. 결과확인 조회는 등록 기록에 저장한 판매자관리코드로 한다(P4-03). (PRD §5.2 잠금, 05-2 `CandidateDetail.locked`)
10. **성별(F-CW-08)**: `PUT …/gender`는 `MALE`·`FEMALE`만 받는다(공용 NULL 복귀 없음) → `gender_source=OWNER`, `gender_recheck_required=false`. 같은 값이면 `changed=false`, 전파 없음. 바뀌면 현재 버전이 있는 PRICING·NOTICE_HTML·TAGS를 `RERUN_REQUIRED`(`stale_inputs`에 `candidate.gender`)로 두고 `affectedSteps`로 준다. ②가 다시 돌아도 `OWNER` 값을 덮어쓰지 않고, 판단이 다르면 `gender_recheck_required=true`(`STEP2` 값은 그냥 바꾼다). 성별을 읽는 단계가 실행 중이면 409 `STEP_LOCKED_BY_RUNNING_STEP`. (PRD §5.3 성별, 05-2 `setCandidateGender` x-decision §7.2-9, ERD `ck_candidate_gender_*`)
11. **목록(F-CW-09)**: `status`를 안 주면 `EXCLUDED`·`REGISTERED`를 뺀다. 필터 `status`(여러 값)·`runnableStep`·`q`(型番·itemCode·검색어 부분 일치, 1~128자). `page` 0부터, `size` 기본 20·최대 100, `sort`는 `statusChangedAt`·`createdAt`·`id`(기본 `statusChangedAt,desc`). 그 밖 422 `INVALID_QUERY_PARAMETER`. 응답 `{ content, page: { number, size, totalElements, totalPages } }`, 줄마다 `steps` 10개와 `resumeStepCode`. `status-counts`는 `{ items: [{ status, count }] }`. (05-1 §1.4, 05-2 `listCandidates`)
12. **이어 하기(F-CW-10)**: `resumeStepCode` = 흐름 순서(②→③→④→⑤→⑥-1→⑥-2→⑥-3→⑦→⑧→⑨)에서 첫 `WAITING_INPUT`·`NOT_RUN`·`FAILED`·`RERUN_REQUIRED` 단계(`RUNNING`은 건너뜀), 없으면 null. `resume-target`은 진행 중 후보를 `statusChangedAt desc`로 보고 첫 후보의 첫 단계 또는 대기 게이트(③ 뒤 G2, ⑧ 앞 G3, 끝 G4)를 준다. 없으면 204. 이어 하기는 화면만 열고 아무것도 다시 만들지 않는다. (US-29 AC1·AC2, 05-2 `getCandidateResumeTarget` x-decision §7.2-11)
13. **입력 고르기(F-CW-22)**: `runnableStep=X`는 X를 지금 실행할 수 있는 후보만 준다. 잠김·제외가 아니고, X의 필수 앞 단계가 모두 `COMPLETED`(PRD §5.3 시작 조건 표)이고, X와 이어진 단계가 실행 중이 아니어야 한다. 판단 함수는 단계 레일의 '실행' 버튼 계산과 같은 것을 쓴다(P1-05가 완성). (05-1 §2.1, FE 05-1 route맵 §3-4)
14. **재실행 필요 모아 보기(F-DB-01)**: `GET /candidate-steps` 기본 `status` = `RERUN_REQUIRED`·`FAILED`·`WAITING_INPUT`, 필터 `stepCode`, `sort`는 `staleSince`·`updatedAt`(기본 `updatedAt,desc`). 줄마다 `staleInputs`·`failureKind`·`errorMessage`·`waitingSince`. 필드별 '재확인 필요'는 합치지 않는다. (05-2 `listAttentionCandidateSteps` x-decision §7.2-18)
15. **표시명**: `displayName`의 원본 컬럼이 없다(05-1 §7.2-10). 문서에 없음 → 구현 때 Proposed로 정하고 기록(예: 현재 ② 버전 상품명, 그 전에는 null).

## 8. 주의

- 공통 규칙은 [README §공통 규칙](../README.md#공통-규칙)을 따른다(실행 환경, 외부 호출 금지, 비밀정보, 커밋 안 함).

- `ck_candidate_ready`: 승인대기 이상은 itemCode·색상 코드·성별·리프 카테고리가 모두 있어야 한다. 전환 함수가 이 값을 먼저 보지 않으면 CHECK 위반으로 500이 난다. '색상 코드를 늘 얻는다'는 가정은 M0 S2 뒤 확정한다(ERD §7.3-1).
- 부분 UNIQUE `uq_candidate_active_item_color`가 동시 요청도 막는다. 앱 검사를 지나 DB에서 걸리면(Postgres 23505) `CANDIDATE_DUPLICATE`로 바꾸고 기존 후보 id를 찾아 준다. 500으로 새지 않게 한다.
- `candidate`·`candidate_step`은 삭제 금지, `candidate_status_history`는 추가만이다. 테스트 정리는 `TRUNCATE`로만 된다.
- 게이트 유효성과 '지금 실행 가능'은 P1-05·P1-06이 완성한다. 포트로 두고 `true`로 박지 않는다. 박으면 승인대기 전환이 거짓으로 일어난다.
- SSE는 트랜잭션 커밋 뒤에 보낸다. 롤백된 전이를 화면이 보지 않게 한다.
- 목록의 `resumeStepCode`, `resume-target`, FE `CandidateIndexRedirect`는 같은 흐름 순서 함수를 쓴다. 따로 만들면 '이어 하기'가 서로 다른 화면을 연다. `CandidateDetail`에는 `resumeStepCode`가 없으니 FE는 레일·목록 값으로 계산한다.
- 잠긴 후보의 결과확인 조회(P4-03)는 등록 기록의 판매자관리코드를 쓴다. 후보 현재값으로 다시 만들지 않으므로, 잠긴 후보의 값 변경을 여기서 빠짐없이 막아야 한다.
- 성별을 바꿨을 때 ④(CATEGORY)도 재실행 필요인지 문서끼리 다르다(PRD §5.3은 ④ 시작 조건에 성별을 넣고, 05-2는 PRICING·NOTICE_HTML·TAGS만). 05-2대로 만들고 결과 보고 '오너 검토'에 올린다.
