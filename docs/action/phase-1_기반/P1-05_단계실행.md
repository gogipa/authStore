# P1-05. 단계 실행 엔진: 실행·버전·입력 지문·재실행 필요 전파

## 1. 목표

후보의 단계 하나를 실행·다시 실행하면 새 버전이 쌓이고, 입력 지문으로 '재실행 필요'가 그 값을 읽는 뒷단계에만 붙는 공통 엔진이 동작한다. 시작 조건 검사, 실행 중 잠금, 입력 대기·실패, 앱 재시작 정리, 오너 수정(값 편집의 틀·그대로 유지·이전 버전 다시 고르기), 버전 이력과 바뀐 입력 비교가 API로 된다. SCR-12 단계 표와 단계 레일이 상태·마지막 실행·입력 출처·버전·재실행 사유를 보여 준다. ①~⑨ 흐름의 ②~⑧ 단계 문서(P2~P4)는 여기서 정한 `StepRunner` 규약으로 실행기를 꽂기만 한다.

## 4. 핵심 규칙

1. **단일 진입점(F-BS-15)**: 단계 실행·연속 실행(P1-06)·일괄(M2)·CLI(M3)는 모두 `StepExecutionService.start(candidateId, stepCode, { mode, ownerInputs, stepChainId })` 하나를 부른다. 게이트·안전 검사는 호출자가 아니라 실행기(단계 모듈) 안에 둔다. M1의 `execution_mode`는 `STEP`·`CHAIN`·`OWNER_EDIT`. REGISTER와 모르는 코드는 422 `INVALID_STEP_CODE`. (F-BS-15, 05-1 표 A, 03-2 C4 §3)
2. **시작 조건(F-BS-16)**: 필수 앞 단계는 `candidate_step.status=COMPLETED`인 현재 버전만 읽는다. `NOT_RUN`·`RUNNING`·`WAITING_INPUT`·`FAILED`·`RERUN_REQUIRED`면 409 `STEP_START_CONDITION_UNMET`, `fieldErrors[].field` = 빠진 입력 키(예 `owner.domesticPrice`, `candidate.gender`). '선택' 입력은 없으면 빼고 실행하고 null 값의 해시를 남긴다. 조건만 맞으면 흐름 순서와 관계없이 실행한다. 로드된 설정 스냅샷이 없으면 503 `SETTINGS_INVALID`. (PRD §5.3 필수 시작 조건, US-33 AC1, 05-3 §5.1, ERD `step_run.settings_snapshot_id` NOT NULL)
3. **시작 트랜잭션**: `candidate_step.last_version`을 `UPDATE … RETURNING`으로 +1 → `step_run`(`version`, `RUNNING`, `settings_snapshot_id`, `input_fingerprint_start`) + `step_run_input` 행 + `candidate_step`(`current_step_run_id`=새 행, `status=RUNNING`, `stale_inputs='{}'`, `stale_since` NULL)을 한 트랜잭션으로 쓴다. 응답 202 + `Location: /api/v1/step-runs/{id}` + `StepRunAccepted`(`version`, `executionMode=STEP`, `status=RUNNING`, `warnings`). 다음 단계를 자동으로 시작하지 않는다. (ERD `candidate_step`, C4 §4, 05-1 §1.3)
4. **끝 트랜잭션(F-BS-17)**: 실행기 결과(산출물) + `step_run` 종료(`status`·`ended_at`·`input_fingerprint_end`) + `candidate_step.status` + 뒷단계 전파 + 후보 상태 재평가(P1-04)를 한 트랜잭션으로 쓴다. 외부·AI 호출은 트랜잭션 밖에서 한다. 결과는 `COMPLETED` / `WAITING_INPUT`(`waiting_since`, `pendingInputs`) / `FAILED`(`failure_kind` = `EXTERNAL_API`·`AI`·`INPUT_VALIDATION`, `error_code`, 한국어 `error_message`, 비밀정보 금지). 실행 중 실패는 HTTP 오류가 아니라 실행 기록과 SSE `step-run.status-changed`로 알린다. (C4 §4, 05-1 §1.3, ERD `ck_step_run_failure_pair`·`ck_step_run_waiting`)
5. **입력 지문(F-BS-20)**: `value_hash` = 값의 SHA-256(정규화 JSON. 이미지는 파일 해시, 설명은 NFKC + 공백 정리 텍스트). 지문 = 시작 조건(`is_start_condition=true`) `{ inputKey: valueHash }`를 키 정렬 JSON으로 만든 SHA-256 hex 64자. 설정은 그 단계가 읽는 키만 넣고, 수집 시각과 실행 중 오너 입력(`ownerInputs`)은 뺀다. 끝날 때 다시 계산해 다르면 결과는 저장하고 `step_run`·`candidate_step`을 `RERUN_REQUIRED`로 둔다(`rerun_reason_inputs` 비지 않음). (PRD §5.3 판정 규칙 1·2, ERD `ck_step_run_fp`·`ck_step_run_rerun_reason`)
6. **전파(F-BS-21)**: 새 버전 완료·오너 수정·이전 버전 다시 고르기·설정 변경(`settings.reloaded`의 `changedKeys`)이 생기면 그 값을 **직접** 읽는 단계만 지문을 다시 계산한다. 다르면 `status=RERUN_REQUIRED`, `stale_inputs`=바뀐 `input_key`, `stale_since=now`. 읽는 값이 같으면 그대로 둔다. 자동으로 다시 실행하지 않는다. 현재 버전이 없는(`NOT_RUN`) 단계는 표시하지 않는다(`ck_candidate_step_pointer`). 입력 대기 중이던 실행은 `step_run`도 `RERUN_REQUIRED`로 닫는다. 예: ⑤ 새 선택 → ⑧만, ③ 재판정에서 판매 사이즈가 같음 → ⑥-3 완료 유지. (PRD §5.3 규칙 3~5, US-33 AC3, ERD `step_run_input`)
7. **완료 뒤 오너 입력**: ③ 국내 기준가(`domestic_price` 새 행)와 ⑤ 레퍼런스 선택(`thumbnail_reference_input` 새 행)은 최신 값 해시를 현재 버전의 같은 `input_key` `value_hash`와 비교해 다르면 그 단계를 `RERUN_REQUIRED`로 둔다. URL 후보 ③ 쿠폰(`owner.coupon`)은 시작 조건이라 지문 재계산으로 잡는다. 다시 실행할 때(재조회 포함) 직전 버전의 실행 중 오너 입력을 기본값으로 넘긴다. (PRD §5.3 실행 중 오너 입력, ERD §1.4·§7.2-19)
8. **버전(F-BS-19·F-CW-21)**: '다시 실행'은 입력이 같아도 새 버전이다. 결과 캐시는 쓰지 않고 외부 조회 캐시는 그대로 쓴다. 이전 버전 행은 지우지 않는다. `UNIQUE(candidate_id, step_code, version)`. 이력 `GET …/runs`는 `page`·`size`, `sort=version`(기본 `version,desc`), 줄마다 `isCurrent`. (US-29 AC2, 05-1 §1.4·§1.7, ERD `trg_step_run_append_only`)
9. **잠금(F-CW-18)**: 단계 X가 `RUNNING`이면 X를 직·간접으로 읽는 단계의 실행과, X가 직·간접으로 읽는 앞 단계의 실행·수정을 409 `STEP_LOCKED_BY_RUNNING_STEP`으로 막는다. 같은 단계의 열린 실행은 409 `STEP_ALREADY_RUNNING`(`uq_step_run_one_open` 위반도 같은 코드). `WAITING_INPUT`은 잠그지 않는다. 입력 대기 중인 단계에 새 실행 요청이 오면 어떻게 답할지는 문서에 없음 → Proposed로 정하고 기록(ERD §7.1-15 기본안: 새 실행을 열지 않음). 레일 `actions.*.disabledReason.code`는 실행 API의 409 코드와 같은 함수로 계산한다. (PRD §5.3 동시 실행과 잠금, US-33 AC4, 05-2 `listCandidateSteps`)
10. **오너 수정(표 B)**: 새 `step_run`(`OWNER_EDIT`, `owner_action`, `base_step_run_id`, `COMPLETED`) + 산출물 복사(실행기 몫) + 포인터 + 전파를 한 트랜잭션으로 쓰고 201. `baseStepRunId`가 현재 버전이 아니면 409 `VERSION_NOT_CURRENT`. `KEEP_AS_IS`는 COPY만(그 밖 422 `KEEP_AS_IS_NOT_ALLOWED`), 그 단계가 `RERUN_REQUIRED`일 때만(409 `STEP_NOT_RERUN_REQUIRED`)이고 새 지문과 `user_action_log`(`OWNER_CONFIRMED`)를 남긴다. `RESTORE_VERSION`은 REGISTER 뺀 전 단계. 완료 버전이 아니면 409 `STEP_NOT_COMPLETED`, 이미 현재면 409 `STEP_RUN_ALREADY_CURRENT`, 다른 앵커의 ② 버전이면 409 `ANCHOR_KEY_MISMATCH`, 응답에 `propagatedSteps`. `stale-diff`는 `RERUN_REQUIRED`가 아니면 409 `STEP_NOT_RERUN_REQUIRED`, `keepAsIsAllowed`는 COPY일 때만 true. EDIT의 필드별 규칙은 P3(content·tags)가 채운다. (05-1 표 B, US-35 AC3·AC6, ERD `ck_step_run_keep_copy_only`·`ck_step_run_owner_base`)
11. **직접 고친 값 보존(F-CW-01)**: 엔진은 실행기에 직전 완료 버전 id와 그 버전의 오너 입력 필드를 넘긴다. 실행기는 오너 입력 필드를 덮어쓰지 않고, 새 결과가 다르면 나란히 고르게 한다. 태그 추가·삭제는 새 결과에 다시 적용한 뒤 규칙 필터와 `restricted-tags` 검증을 다시 거친다(P3-05). (PRD §5.3 다시 실행과 오너 수정, US-33 AC5)
12. **재시작 정리(F-BS-18)**: 앱이 요청을 받기 전에 `RUNNING` `step_run` → `FAILED` + `failure_kind=INTERRUPTED` + `ended_at`, `candidate_step`도 `FAILED`로 바꾼다. `WAITING_INPUT`은 그대로 둔다. REGISTER였으면 등록 기록이 `REGISTERING`이면 후보를 `RESULT_CHECK_REQUIRED`(`APP_RESTART`)로, 기록 저장 전이거나 차단 스위치가 켜져 있었으면 `AWAITING_APPROVAL`(`RESTART_REVERTED`)로 둔다. 이 판단은 REGISTER 실행기 훅(P4-03)이 한다. (PRD §5.2, US-29 AC3, ERD §4.2 reason)
13. **시간·입력 출처(F-BS-22·F-BS-23)**: `started_at`·`ended_at`·`waiting_since`·`wait_seconds_total`(입력 대기 누적 초)을 남긴다. 자동 처리 시간 = (`ended_at` − `started_at`) − `wait_seconds_total`. 읽은 입력마다 `step_run_input` 1행(`source_type` = `PREV_STEP`·`OWNER_INPUT`·`SETTINGS`, `PREV_STEP`이면 `source_step_run_id` 필수). M1은 단계를 직렬로 처리한다. (ERD `step_run`·`ck_step_run_input_prev`, NFR-01)
14. **⑥ 묶음(F-CW-13)**: `stepCode=COPY` + `throughStepCode=NOTICE_HTML`이면 COPY → NOTICE_RAW → NOTICE_HTML을 차례로 실행한다(각각 새 `step_run`, `STEP`). 응답은 첫 실행만 곧바로 만들고 나머지는 SSE로 알린다. 중간 단계가 실패·입력 대기면 멈출지는 문서에 없음 → Proposed로 정하고 기록. (05-2 `startCandidateStepRun` x-decision §7.2-8)
15. **표시(F-CW-11·12·17·20)**: 레일은 10칸(페이징 없음)에 상태·현재 버전·입력 출처·`staleInputs`·버튼 켜짐과 이유를 준다. G2가 유효하지 않을 때 THUMBNAIL·COPY·NOTICE_RAW 실행은 막지 않고 `warnings[PRE_G2_AI_COST]`. 페이지 데이터 오래됨 = 현재 ② 버전 수집 시각 + 판정 유효 시간(설정, 기본 6시간) < 지금이고 '재실행 필요'로 바꾸지 않는다. `creationPath=RAKUTEN_URL`이면 '수동'·'비교 안 함' 배지를 보이고 어떤 단계든 바로 실행할 수 있다. (05-1 §5.2, US-35 AC5, US-06 AC3, PRD §5.3 판정 유효 시간)

## 5. 만들 것

**BE — 실행기 규약** `modules/step-engine/contracts/step-runner.ts`. 단계 모듈이 step-engine에서 가져오는 것은 이 파일과 `StepEngineApi`뿐이다.

```ts
export interface StepRunner {
  readonly stepCode: StepCode;
  readonly usesAi: boolean;                                   // PRE_G2_AI_COST·AI 엔진 고정(P1-10)
  readInputs(ctx: StepInputContext): Promise<StepInput[]>;   // { inputKey, sourceType, sourceStepRunId?, isStartCondition, required, value }
  run(ctx: StepRunContext): Promise<StepOutcome>;            // 트랜잭션 밖. 외부·AI 호출은 여기서만
  persist(tx: Tx, stepRunId: number, outcome: StepOutcome): Promise<void>;          // 끝 트랜잭션 안
  copyOutput(tx: Tx, fromStepRunId: number, toStepRunId: number, edit?: unknown): Promise<void>; // 오너 수정·다시 고르기
  onInterrupted?(tx: Tx, run: StepRunRow): Promise<CandidateStatusEffect | null>; // 재시작 정리(⑨, P4-03)
}
export type StepOutcome =
  | { kind: 'COMPLETED'; output: unknown; candidateEffects?: CandidateEffects }
  | { kind: 'WAITING_INPUT'; waitingReasonCode: string; pendingInputs: string[] }
  | { kind: 'FAILED'; failureKind: 'EXTERNAL_API' | 'AI' | 'INPUT_VALIDATION'; errorCode: string; errorMessage: string };
export const StepRunnerFor = (code: StepCode) => SetMetadata(STEP_RUNNER_META, code);
```

- **등록 방법**: 단계 모듈은 실행기 클래스에 `@StepRunnerFor('PRICING')`을 달고 자기 모듈 `providers`에 넣는다. `StepRunnerRegistry`가 `onModuleInit`에서 `DiscoveryService`(`@nestjs/core`)로 모은다. 한 단계에 실행기가 둘이면 앱 시작을 멈춘다. step-engine은 단계 모듈을 import하지 않는다(순환 없음). 실행기가 없는 단계의 실행 요청 응답은 Proposed로 정한다(예: 422 `INVALID_STEP_CODE`).
- `candidateEffects`: ② 앵커 확정·소싱 선택·성별 판단, ④ 리프 카테고리, 제외 사유(`ANCHOR_NO_MATCH` 등). 엔진이 끝 트랜잭션 안에서 P1-04 서비스(중복·앵커·성별·상태 재평가)로 적용한다. 단계 모듈은 `candidate`를 직접 쓰지 않는다.
- `StepEngineApi`(export): 입력 대기 실행 이어 가기·끝내기(`resumeWaiting`), 완료 뒤 오너 입력 변경 알림(`ownerInputChanged(candidateId, inputKey)`), 현재 완료 버전 읽기(`currentCompletedRun(candidateId, stepCode)`).

## 6. 테스트

**단위**

- 지문: 키 순서가 달라도 같다. 소문자 hex 64자. 'ＡＢＣ  x'와 'ABC x'가 같은 해시(NFKC·공백). 수집 시각·`ownerInputs`를 바꿔도 지문은 그대로. 선택 입력 없음 = null 값 해시.
- 시작 조건: ③의 앞 ②가 `NOT_RUN`·`RUNNING`·`WAITING_INPUT`·`FAILED`·`RERUN_REQUIRED`면 막고 `fieldErrors`에 입력 키. ⑦은 ④(선택)가 미실행이어도 통과. ⑤는 ③ 없이 통과(흐름 순서 무관).
- 잠금: ② `RUNNING` → ③·⑥-3 실행 막힘(후손). ③ `RUNNING` → ② 다시 실행·수정 막힘(조상). ⑥-1 `RUNNING` → ⑤ 실행 허용. ⑤ `WAITING_INPUT` → 아무것도 잠그지 않음.
- 전파(US-33 AC3): ⑤ 새 선택 완료 → ⑧만 `RERUN_REQUIRED`, ⑥-1·⑦은 `COMPLETED`. ③ 국내가만 바뀌고 판매 사이즈 같음 → ⑥-3 `COMPLETED`. 같은 값으로 ② 다시 실행 → 아무 단계도 안 바뀜. `NOT_RUN` 단계는 표시 안 됨. 입력 대기 중인 ⑤의 시작 조건 변경 → `step_run`·`candidate_step` 모두 `RERUN_REQUIRED`.
- 끝 지문 불일치: 실행 중에 입력 값을 바꾸면 결과는 저장되고 `RERUN_REQUIRED` + `rerun_reason_inputs`.
- 완료 뒤 `owner.domesticPrice` 새 값 → ③ `RERUN_REQUIRED`. 다시 실행 때 실행기가 받은 기본값이 직전 국내 기준가.

## 8. 주의

- 공통 규칙은 [README §공통 규칙](../README.md#공통-규칙)을 따른다(실행 환경, 외부 호출 금지, 비밀정보, 커밋 안 함).
- 단계 모듈(②~⑨)은 아직 없다. 실행기 인터페이스(StepRunner 등록)와 테스트용 가짜 단계로 엔진을 검증한다.

- 현재 버전 포인터는 **시작** 트랜잭션에서 옮긴다(ERD §7.2-17, C4 §4). 끝날 때 옮기면 실패한 실행 뒤에 뒷단계가 옛 산출물을 '완료'로 읽는다.
- DB 트랜잭션 안에서 `runner.run()`(외부·AI 호출)을 부르지 않는다. Prisma 대화형 트랜잭션은 기본 5초에 끊긴다. 실행 → 결과 → 짧은 끝 트랜잭션 순서다.
- `step_run`은 닫히면 못 고친다(`trg_step_run_append_only`). 종료 상태는 한 번에 쓰고, 완료 뒤의 '재실행 필요'는 `candidate_step`에만 적는다. `ai_engine`·`ai_model`·`ai_cli_version`은 INSERT 때만 쓸 수 있으니 P1-10 훅 자리를 시작 INSERT 앞에 둔다.
- `step_run_input`과 산출물은 실행이 열려 있는 동안만 고칠 수 있다(`trg_output_frozen`). 입력 행은 시작 트랜잭션에서 쓴다.
- `uq_step_run_one_open`은 입력 대기도 '열린 실행'으로 센다. 대기 중인 단계에 새 실행 행을 넣으면 DB가 막는다(ERD §7.1-15).
- 전파는 버전 번호가 아니라 값 해시로 비교한다. 수집 시각을 지문에 넣으면 재조회 한 번에 모든 뒷단계가 '재실행 필요'가 된다.
- 재시작 정리는 HTTP를 받기 전에 끝낸다. e2e는 앱을 띄울 때마다 정리가 도니 테스트 데이터는 앱을 띄운 뒤 넣는다.
- Jest가 ESM이라 `jest.mock`을 못 쓴다. 가짜 실행기는 테스트 모듈로 등록하고, 비동기 완료는 `sleep` 대신 `whenIdle()`로 기다린다.
- ⑨의 등록 기록 판단은 P4-03 몫이다. 여기서는 `registration`을 읽거나 쓰지 않고 훅만 부른다.
