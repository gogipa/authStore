## 1. 목표

이 작업이 끝나면 커머스API 메타데이터 8종(리프 카테고리, 카테고리 상세, 표준옵션, 속성, 원산지 코드, 주소록, `SHOES` 고시, 반품 택배사)을 하루 한 번 자동으로, 또는 SCR-11 '지금 동기화'로 받아 DB 캐시에 둔다. 대상별 실행 기록과 마지막 성공 시각이 '메타데이터 동기화' 패널에 보인다. ①~⑨ 흐름 밖의 기반이며, 카테고리·원산지 ID를 코드에 박지 않게 하는 유일한 출처다. 프로필(P1-09)이 주소록·반품 택배사를, ④ 카테고리(P2-06)가 리프·예외 유형을, ⑥-3(P3-04)이 원산지 코드·`SHOES` 고시를, ⑧⑨(P4-02·P4-03)가 표준옵션·속성을 여기서 읽는다.

## 4. 핵심 규칙

대상표(규칙 1의 근거: PRD §8.7 등록 호출 순서 2, R04 C1~C5, ERD §3.12 `ck_cmsr_target`·`ck_cmd_kind`)

| 대상(`target`) | 커머스API (GET) | 저장 |
|---|---|---|
| `CATEGORY` | `/v1/categories?last=true` | `commerce_category` |
| `CATEGORY_DETAIL` | `/v1/categories/{id}` | `commerce_meta_document`(kind `CATEGORY_DETAIL`, scope = categoryId) + `commerce_category.exceptional_categories`·`detail_synced_at` |
| `STANDARD_OPTIONS` | `/v1/options/standard-options?categoryId=` | `commerce_meta_document`(scope = categoryId) |
| `PRODUCT_ATTRIBUTES` | `/v1/product-attributes/attributes?categoryId=`(+ `attribute-values`) | `commerce_meta_document`(scope = categoryId) |
| `ORIGIN_AREA` | `/v1/product-origin-areas/*`(하위 계층 포함) | `commerce_origin_area` |
| `ADDRESSBOOK` | `/v1/seller/addressbooks-for-page`(모든 페이지) | `commerce_addressbook`(`is_overseas` ← `overseasAddress`) |
| `PROVIDED_NOTICE` | `/v1/products-for-provided-notice/SHOES` | `commerce_meta_document`(scope `SHOES`) |
| `RETURN_DELIVERY_COMPANY` | `/v2/product-delivery-info/return-delivery-companies` | `commerce_return_delivery_company` |

1. 위 8개 대상을 하루 한 번 받아 캐시한다. `CATEGORY_DETAIL`·`STANDARD_OPTIONS`·`PRODUCT_ATTRIBUTES`를 어느 리프에 대해 받을지는 문서에 없음(ERD §7.3-9, M0 S3) → Proposed: 성별 신발 경로의 리프만. (F-BS-48, US-21 AC1, RG-03)
2. 카테고리·원산지 ID를 코드·설정에 박지 않는다. 쓰는 곳은 모두 이 캐시에서 읽는다. (F-BS-48, RG-03)
3. 캐시 쓰기: 자연키(`category_id`·`origin_area_code`·`address_book_no`·`code`)로 upsert해 `id`를 유지한다. 이번 응답에 없는 행은 지우지 않고 `removed_at=now()`, 다시 나타나면 `removed_at=null`. 문서형은 `(kind, scope_key)` 1행을 덮어쓰고 `payload_sha256`(정규화 JSON의 SHA-256, 소문자 hex 64자)을 갱신한다. (ERD §1.3·§3.12, `ck_cmd_sha`, `ck_addressbook_no`)
4. 실행 기록: 대상마다 실행 한 번에 `commerce_meta_sync_run` 1행. 시작 때 `RUNNING`(`finished_at` NULL), 끝나면 `SUCCEEDED`+`item_count` 또는 `FAILED`+`error_message`(필수, 비밀 없음). 행은 지우지 않는다. (ERD `commerce_meta_sync_run`, `ck_cmsr_finished`·`ck_cmsr_error`, `trg_forbid_delete`)
5. 트랜잭션: 외부 응답을 다 받은 뒤, 한 대상의 캐시 쓰기 + `removed_at` 표시 + run `SUCCEEDED`를 한 트랜잭션으로 한다. 외부 호출은 트랜잭션 밖이다. 실패하면 이전 캐시가 그대로 남는다. (03-2 §4 원칙 — 메타 동기화 행은 없음 → Proposed)
6. `POST /commerce-meta-sync-runs`: 본문은 선택이고 `targets[]`는 1개 이상·중복 없음·위 8개 값이다. 없으면 8개 전부. 성공은 202 + `Location: /api/v1/commerce-meta-sync-runs/latest` + `{ items: [RUNNING run…] }`. 빈 배열·중복·알 수 없는 대상은 422 `VALIDATION_FAILED`. 요청 대상 중 `RUNNING`이 있으면 409 `ALREADY_IN_PROGRESS`(`details.job=META_SYNC`). 커머스 키가 없으면 409 `SECRET_NOT_CONFIGURED`, 키체인 오류는 503 `KEYCHAIN_UNAVAILABLE`. (05-1 §1.3·§2.13, 05-2 createCommerceMetaSyncRuns, 05-3)
7. 대상 하나가 끝날 때마다 SSE `commerce-meta-sync.completed` `{ runId, target, status, finishedAt, itemCount, errorMessage }`를 보낸다(수동·자동 모두). (05-1 §3)
8. `GET /commerce-meta-sync-runs/latest`: 대상 8개를 05-2 enum 순서로 `{ target, latestRun, lastSucceededAt }`. 돈 적 없으면 `latestRun=null`. `lastSucceededAt`은 마지막 `SUCCEEDED` 행의 `finished_at`(계산). 페이징 없음. 화면은 이 값으로 마지막 동기화 시각과 성공·실패를 보여 준다. (05-2 getLatestCommerceMetaSyncRuns, F-SY-03)
9. 하루 1회 자동 실행은 수동과 같은 서비스를 쓰고, 대상별 마지막 성공 시각으로 실행 여부를 정한다. '하루'의 기준(24시간 vs KST 날짜)과 실행 시점(앱 시작·주기)은 문서에 없음 → Proposed. 커머스 키가 없으면 자동 실행은 조용히 건너뛴다(Proposed). (F-BS-48, ERD `commerce_meta_sync_run` 목적)
10. 앱을 켤 때 `RUNNING`으로 남은 행은 `FAILED`로 바꾸고 `finished_at`과 중단 사유 `error_message`를 채운다. (ERD `commerce_meta_sync_run`, 03-2 §4 앱 재시작)
11. `GET /commerce-categories`: `gender`(`MALE`·`FEMALE`) 필수, 없거나 다른 값이면 422 `INVALID_QUERY_PARAMETER`. `whole_category_name`이 `패션잡화>남성신발>`·`패션잡화>여성신발>`로 시작하는 리프만 준다. `removed_at` 행, 예외 유형 `CHILD_CERTIFICATION`·아동 카테고리, CON-08 제외 품목 카테고리는 뺀다(CON-08 목록의 출처는 문서에 없음 → Proposed). 캐시가 비면 409 `COMMERCE_META_NOT_SYNCED`(`details.target=CATEGORY`). `sort`는 `wholeCategoryName`만(기본 asc). `q`는 M2라 만들지 않는다. (05-1 §1.4·§2.13, 05-2 listCommerceCategories, F-CA-04·F-CA-07, PRD §8.7)
12. `GET /commerce-origin-areas`: `q`(이름·코드 부분 일치), `parentCode`, `sort`는 `name`·`originAreaCode`(기본 `name,asc`), `removed_at` 행 제외. 캐시가 비면 409 `COMMERCE_META_NOT_SYNCED`(`details.target=ORIGIN_AREA`). (05-2 listCommerceOriginAreas)
13. `GET /commerce-addressbooks`: `overseas=true`면 `is_overseas`만, `includeRemoved` 기본 false, `sort=name`. 응답에 `raw`를 넣지 않는다. `GET /commerce-return-delivery-companies`: `includeRemoved` 기본 false, `sort=name`. 둘 다 빈 캐시는 빈 페이지 200이다. (05-2 listCommerceAddressbooks·listCommerceReturnDeliveryCompanies)
14. 목록 공통: `page`(0부터), `size`(기본 20, 최대 100), 응답 `{ content[], page: { number, size, totalElements, totalPages } }`. 허용 밖 필터·정렬 값과 `size>100`은 422 `INVALID_QUERY_PARAMETER`. (05-1 §1.4, 05-3 §1)
15. 커머스API 호출은 모두 P1-07 `CommerceApiClient`(토큰·401 재발급)와 P1-01 외부 호출 관문을 지나 호출마다 `call_log` 1행(`target=COMMERCE_API`)을 남긴다. 호출은 하나씩 차례로 하고 `GNCP-GW-RateLimit-*` 헤더와 429 `GW.RATE_LIMIT`에 맞춰 늦춘다. (NFR-05, R04 A11, ERD `call_log`)

## 6. 테스트

**단위** (Jest ESM, 가짜 transport·시계는 DI로)

- mapper 대상별: fixture → 행 수와 필드(`isOverseas` ← `overseasAddress`, `addressBookNo` 숫자 문자열, `exceptionalCategories` 배열, `parentCode`).
- upsert: `categories-last` 적용 → `categories-last-v2` 적용 → 빠진 행 `removed_at` 채움·`id` 그대로·새 행 추가. 다시 `categories-last` → `removed_at=null`.
- 문서: 같은 payload 두 번 → 행 1개, sha 같음. 다른 payload → 덮어씀, sha 바뀜, 소문자 hex 64자.
- 실패 격리: `ADDRESSBOOK`에서 500 → 그 run만 `FAILED`·`error_message` 있음, 이전 주소록 행 그대로, 나머지 대상은 `SUCCEEDED`.
- 복구: `RUNNING` 행 → 부트스트랩 뒤 `FAILED`, `finished_at` 채움.
- 자동 실행 판단(가짜 시계): 마지막 성공이 기준 안이면 건너뜀, 넘으면 실행, 커머스 키가 없으면 건너뜀.
- 카테고리 필터: `MALE` → 남성 리프 3개(아동·`removed_at`·신발 밖 제외), `FEMALE` → 3개.

**e2e** (`autostore_test`, 정리는 `TRUNCATE … RESTART IDENTITY CASCADE` — `purchase_agency_profile`이 FK로 묶여 있고 `commerce_meta_sync_run`은 삭제 금지)

- 빈 DB `GET /commerce-meta-sync-runs/latest` → 200, `items` 8개, 모두 `latestRun=null`·`lastSucceededAt=null`.
- 키 없이 `POST /commerce-meta-sync-runs` → 409 `SECRET_NOT_CONFIGURED`. `X-AutoStore-Client` 없이 → 403.
- 키를 넣고(메모리 저장소) 빈 본문 `POST` → 202, `Location` 헤더, `items` 8개 모두 `RUNNING`. latest를 폴링해 완료를 기다린 뒤 8개 `SUCCEEDED`, `itemCount`가 fixture 개수와 같다. SSE 발행 기록 8건.
- 막히는 가짜 transport로 진행 중에 `POST { targets: ["ADDRESSBOOK"] }` → 409 `ALREADY_IN_PROGRESS`, `details.job=META_SYNC`.
- `{ targets: [] }`·`{ targets: ["FOO"] }`·`{ targets: ["CATEGORY","CATEGORY"] }` → 422 `VALIDATION_FAILED`.
- `GET /commerce-categories`(gender 없음) → 422 `INVALID_QUERY_PARAMETER`. 동기화 전 `?gender=MALE` → 409 `COMMERCE_META_NOT_SYNCED`, `details.target=CATEGORY`. 동기화 뒤 → 3건, `wholeCategoryName` 오름차순, `page.totalElements=3`. `sort=name,asc` → 422. `size=101` → 422.
- `GET /commerce-origin-areas?q=` 부분 일치. 비었을 때 409 `details.target=ORIGIN_AREA`.
- `GET /commerce-addressbooks?overseas=true` → 해외 2건만, 응답 객체에 `raw` 키 없음. `includeRemoved=true`면 빠진 행도 나온다.
- `call_log`: 가짜 호출 수만큼 `target=COMMERCE_API` 행, `url_masked`에 비밀 없음.

**FE** (Vitest)

- `MetaSyncPanel`: latest 응답(성공·실패·`RUNNING` 섞음)을 주면 줄 상태·시각·캡션이 보드 문구대로 나온다. '지금 동기화' → `POST /commerce-meta-sync-runs` 1회. `RUNNING`이면 버튼 꺼짐과 이유 글. 409 `SECRET_NOT_CONFIGURED`면 안내와 키 입력 링크. SSE 이벤트를 받으면 latest를 다시 부른다.

## 8. 주의

- 공통 규칙은 [README §공통 규칙](../README.md#공통-규칙)을 따른다(실행 환경, 외부 호출 금지, 비밀정보, 커밋 안 함).

- 메타 응답 구조(주소록 유형 enum, 원산지 계층, 표준옵션·속성 범위)는 M0 S3 전 추정이다(ERD §7.3-9). 변환 함수를 대상별로 떼고 `raw`·문서 원문을 남겨, S3 뒤 변환만 고치게 한다. 외부 enum에는 CHECK를 걸지 않는다.
- `commerce_addressbook`·`commerce_return_delivery_company`는 `purchase_agency_profile`이 FK(ON DELETE RESTRICT)로 가리킨다. 사라진 행을 지우거나 캐시를 비우고 다시 넣으면 동기화가 깨지거나 `id`가 바뀌어 프로필이 끊긴다. 항상 upsert + `removed_at`만 쓴다.
- 카테고리 상세·옵션·속성을 리프 전체(수천 개)에 부르면 호출이 폭증하고 429가 난다. 커머스API Rate limit 수치는 비공개다. 성별 신발 리프만 하나씩 차례로 부른다.
- 202 뒤 백그라운드 작업이 e2e 정리(`TRUNCATE`)와 겹치지 않게 완료를 기다리는 도우미를 둔다. 자동 스케줄러는 테스트에서 DI로 끈다. 켜 두면 테스트 중에 몰래 가짜 서버를 부른다.
- 주소록 조회는 커머스API 앱의 '판매자정보' API 그룹 권한이 있어야 한다(R04 A3). 403이면 `error_message`에 권한 안내를 넣는다. 해외 주소록은 API로 만들 수 없으니(P-03) 스마트스토어센터로 안내만 한다.
- 이 캐시는 P1-09·P2-06·P3-04·P4-02·P4-03이 읽는다. 읽기는 `CommerceMetaCacheService`로만 열고 함수 이름을 바꾸지 않는다.
- `system.module.ts` 주석은 메타 동기화를 system 소유로 적었지만 ERD·05-2·이 문서는 integrations다. integrations에 두고 주석을 고친다.
- 실제 커머스API 호출 금지(앱 등록·S3 전). 실제 첫 동기화는 오너가 키를 넣은 뒤 SCR-11에서 직접 누른다.
