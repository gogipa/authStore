## 1. 목표

밖으로 나가는 모든 HTTP 호출이 관문 하나(`ExternalHttpGateway`)를 거친다. 관문은 허용 목록, 정직한 UA, 대상별 간격, 하루 상한, 24시간 쉼, `call_log` 기록을 지킨다. 이와 함께 진행 알림 SSE(`GET /events`), 이미지 파일 저장·조회(`image_asset`), 감사 기록(`user_action_log`) 서비스가 동작한다.
①~⑨ 어느 단계에도 속하지 않는 바닥 공사다. ① 데이터랩, ② 라쿠텐 API·페이지, ⑧⑨ 커머스API가 모두 이 관문으로 밖을 부른다. ⑤ 썸네일, ⑥ 콘텐츠, ⑧ 업로드는 이미지 서비스에 파일을 두고, 모든 실행 문서가 SSE 발행과 감사 기록을 여기서 만든 서비스로 한다.

## 4. 핵심 규칙

1. 서버는 `127.0.0.1`에만 붙고 로그인 없이 쓴다. 바인딩 주소를 바꾸는 환경변수·설정은 두지 않는다. 지금의 `BIND_HOST`와 `localSecurityMiddleware`를 그대로 둔다. 스토어를 바꿔 쓰는 기능도 없다 (F-BS-01, GEN-01, 03-2 §5).
2. 설정 JSON·이미지·로그는 `APP_DATA_DIR` 아래에만 쓴다. 코드 폴더(`apps/`)에는 쓰지 않는다. `image_asset.file_path`는 데이터 폴더 기준 **상대 경로**다. 응답·SSE·로그에는 절대 경로를 내보내지 않는다. 운영(설치본)의 기본 데이터 폴더가 저장소 밖 어디인지는 문서에 없음 → 구현 때 Proposed로 정하고 기록 (F-BS-02, US-36 AC3, 05-1 §1.2, ERD §3.6).
3. 코드와 기본 템플릿에는 개인 값을 넣지 않는다. 개인 값은 키·계정, 상호·연락처, 배대지·창고 주소, 요금표, 고지의 배송기간·반품비, `importer`, 파일 경로다. 그 자리에는 PRD §8.5 템플릿처럼 `{상호}` 모양의 자리표시자만 둔다. 비용 파라미터 같은 일반 기본값은 넣어도 된다 (F-BS-03, US-37 AC3, GEN-01).
4. 안전장치 5개(G4 최종 승인, 아동화 차단, 실존 인물 차단, 중복 등록 방지, 원본 업로드 거부)를 끄는 환경변수·설정 키·요청 파라미터를 만들지 않는다. 검사는 단계 모듈·승인 검사 안에 둔다. 단계·연속·일괄·CLI 어느 경로로도 건너뛸 수 없어야 한다 (F-BS-04, US-36 AC4, 03-2 §3).
5. 외부 HTTP는 `ExternalHttpGateway` 하나로만 나간다. 허용 호스트는 대상(`CallLogTarget` 13종)마다 한 표에 둔다. 표에 없는 호스트는 요청도 `call_log` 행도 만들지 않고 거부한다. 문서에 있는 호스트는 아래와 같다.
   - `COMMERCE_API`: `api.commerce.naver.com`
   - `RAKUTEN_API`: `openapi.rakuten.co.jp` (구 도메인 `app.rakuten.co.jp`는 금지)
   - `RAKUTEN_PAGE`: `item.rakuten.co.jp`
   - `DATALAB`: `datalab.naver.com`
   - 환율 두 곳은 P2-04에서 더한다. `NOTICE_MONITOR`·`UPDATE_CHECK`는 M2라 비워 둔다.
   - 거부할 때 쓰는 오류 코드는 문서에 없음 → 구현 때 Proposed로 정하고 기록

   (F-BS-06, GEN-01, US-36 AC5, PRD §8.2·§8.7, ERD `ck_call_log_target`).
6. 모든 외부 요청에 앱 고유 UA를 붙인다. `Mozilla/…` 같은 브라우저 UA는 쓰지 않는다. 호출하는 쪽이 `User-Agent`·`Origin`·`Cookie` 헤더를 넣으면 거부한다. 프록시·IP 교체는 쓰지 않는다. `Referer`는 `DATALAB`에서만, PRD §8.1 값(`https://datalab.naver.com/shoppingInsight/sCategory.naver`)으로 허용한다. UA 문자열 형식은 문서에 없음 → 구현 때 Proposed로 정하고 기록 (F-BS-08, CON-04, PRD §8.1·§10).
7. 대상마다 요청을 한 번에 하나씩 차례로 보낸다. 최소 간격은 아래와 같다. 간격을 앞 요청의 시작부터 잴지 끝부터 잴지는 문서에 없음 → 구현 때 Proposed로 정하고 기록(끝부터 재는 쪽이 더 보수적이다).
   - 비공식 수집: `DATALAB` 2초, `RAKUTEN_PAGE` 3초
   - 공식 API: `RAKUTEN_API` 1.5초

   (F-BS-09, CON-05, NFR-05, PRD §8.2).
8. 하루 상한은 `call_log`의 (`kst_date`, `target`) 행 수로 센다. 카운터 표는 따로 두지 않는다.
   - 행을 요청 **직전에** 넣는다. 그래서 실패·중단된 요청도 센다.
   - 오늘 수가 상한 이상이면 요청을 보내지 않고 409 `DAILY_LIMIT_REACHED`로 막는다. `details.target`과 `Retry-After`(다음 KST 0시까지 남은 초)를 붙인다.
   - `RAKUTEN_PAGE` 상한은 설정값(기본 110)이고 KST 0시에 새로 센다.
   - 데이터랩 하루 상한 값은 문서에 없음 → 구현 때 Proposed로 정하고 기록

   (F-BS-09, RK-04, PRD §8.8, ERD §3.12, 05-3 §5.1).
9. 비공식 수집이 403·418·429를 받으면 그 수집을 바로 멈춘다. 남은 요청은 보내지 않는다. 그 대상은 해당 응답 행의 `called_at` + 24시간까지 요청하지 않는다.
   - 쉼 여부는 최근 24시간 안에 403·418·429 `call_log` 행이 있는지로만 판단한다.
   - 쉼 중인 요청은 409 `EXTERNAL_CALL_COOLDOWN`으로 막는다. `details.target`·`details.blockedUntil`·`Retry-After`를 붙인다.
   - 공식 API(`RAKUTEN_API` 429·503)에는 24시간 쉼을 걸지 않는다. 백오프만 한다(P2-02).

   (F-BS-10, CON-05, ERD 결정 ⑦, 05-3 §5.1).
10. 호출 1번에 `call_log` 1행을 남긴다.
    - 보내기 직전에 넣는 열: `called_at`, `kst_date`(Asia/Seoul, CHECK `ck_call_log_kst`), `target`, `http_method`, `host`, `url_masked`
    - 응답 뒤 한 번만 채우는 열: `http_status`, `succeeded`, `error_code`, `error_message`, `item_count`, `duration_ms`, `trace_id`
    - `url_masked`는 `accessKey`·`applicationId`·`client_secret`·`authkey`·`serviceKey` 값을 `***`로 가린다(CHECK `ck_call_log_no_secret`).
    - 응답 전에 앱이 꺼지면 `succeeded`는 NULL로 남는다. 행은 지우지 않는다(`trg_forbid_delete`).

    (F-BS-11, NFR-02·03, ERD §3.12).
11. `GET /call-usage`는 `{ items[] }`를 페이징 없이 준다. 항목은 대상별 `{ target, kstDate, count, dailyLimit, remaining, limitReached, blockedUntil, httpStatus, countsByFetchReason, budgetBuckets }`다.
    - 상한이 없는 대상은 `dailyLimit`·`remaining`이 null이다.
    - `countsByFetchReason`은 `RAKUTEN_PAGE`에만 채운다(SOURCING·URL_ENTRY·STOCK_CHECK·REFETCH·SYNC). `budgetBuckets`는 M1에서 null이다.
    - 목록에 넣을 대상의 범위는 문서에 없음 → 구현 때 Proposed로 정하고 기록
    - 조회 수가 늘 때, 상한에 닿을 때, 24시간 쉼이 시작될 때, KST 0시에 새로 셀 때 SSE `call-usage.changed`를 보낸다. 필드는 위와 같다.

    (05-2 `getCallUsage`·`CallUsageByTarget`, 05-1 §2.13·§3).
12. `GET /events`의 응답 형식은 아래와 같다.
    - `text/event-stream`, `Cache-Control: no-cache`
    - 프레임마다 `id`(단조 증가), `event`(05-1 §3 이름), `data`(한 줄 JSON, camelCase)
    - 이벤트는 바뀐 사실만 알린다. 비밀정보와 로컬 경로는 넣지 않는다.
    - `candidateId`를 주면 그 후보의 이벤트와, 후보에 딸리지 않은 전역 이벤트만 보낸다.
    - `Last-Event-ID`는 받기만 한다. 놓친 이벤트를 다시 보내지 않고 버퍼도 두지 않는다.
    - GET이라 Host 검사만 받는다.

    (05-1 §2.15·§3, 05-2 `streamProgressEvents` x-decision §7.1-3).
13. 이미지 API 두 개는 아래처럼 답한다.
    - `GET /image-assets/{id}`: `ImageAssetMeta`를 준다. `file_path` 대신 `fileUrl`=`/api/v1/image-assets/{id}/file`이다. 행이 없으면 404 `IMAGE_ASSET_NOT_FOUND`.
    - `GET …/file` 헤더: `Content-Type`=`mime_type`, `ETag`=따옴표로 감싼 sha256 64자, `Cache-Control: private, immutable`
    - `If-None-Match`가 같으면 304를 준다.
    - 행은 있는데 파일이 없으면 404 `IMAGE_FILE_MISSING`.

    (05-1 §2.15, 05-2 `getImageAsset`·`getImageAssetFile`, 05-3 §5.1).
14. 이미지는 내용 주소로 저장한다.
    - 같은 sha256 파일은 디스크에 한 번만 둔다.
    - `mime_type`은 확장자가 아니라 파일 내용으로 판별한다. `width`·`height`·`byte_size`도 채운다.
    - `image_asset`은 추가만 한다(`trg_append_only`).
    - ORIGINAL은 (`source_item_code`, `sha256`) 부분 UNIQUE(`uq_image_asset_original`)다. 같은 원본을 다시 넣으면 기존 행을 돌려준다.
    - CHECK를 앱에서도 먼저 검사한다: 원본·레퍼런스는 `REFERENCE_ONLY`, 생성·업로드는 `PERMITTED`. ORIGINAL만 `candidate_id`가 NULL이다. UPLOAD는 1000×1000 JPEG이고 10MB(10,485,760바이트) 미만이다.

    (ERD §3.6, F-BS-45, CON-07).
15. `user_action_log`는 추가만 한다.
    - `kst_date`는 `occurred_at`의 Asia/Seoul 날짜다.
    - `event_type`은 CHECK `ck_ual_event`의 11종 중 하나다. `GATE_ENTERED`·`GATE_PASSED`에는 `gate`가 꼭 있어야 한다.
    - `detail`에는 비밀값과 경쟁 태그 원문을 넣지 않는다.
    - 부르는 쪽의 Prisma 트랜잭션 안에서도 쓸 수 있어야 한다. 게이트 통과와 기록이 한 트랜잭션이어야 하기 때문이다.

    (ERD §3.13, NFR-03, 03-2 §4).

외부 호출 관문(가짜 fetch, 가짜 시계):
- 허용 목록 밖(`https://example.com`)과 `https://app.rakuten.co.jp/...`는 거부한다. fetch 0회, `call_log` 0행.
- 가짜 fetch가 받은 `User-Agent`가 앱 UA이고 `Mozilla/`로 시작하지 않는다. 호출자가 `Origin`·`Cookie`·`User-Agent`를 넣으면 거부한다. `Referer`는 DATALAB만 통과한다.
- `RAKUTEN_PAGE` 요청 3개를 동시에 넣어도 겹치지 않는다. 시작 간격 ≥ 3000ms. DATALAB은 ≥ 2000ms, RAKUTEN_API는 ≥ 1500ms.
- 오늘(KST) `RAKUTEN_PAGE` 행 110개를 넣은 뒤 요청하면 409 `DAILY_LIMIT_REACHED`, fetch 0회, `Retry-After`는 다음 KST 0시까지 초. 같은 110행이 어제 날짜면 통과한다.
- fetch가 예외를 던져도 `call_log` 행이 남는다(`succeeded=false`). 이 행도 상한 수에 든다.
- 429 → 예외가 나고 곧바로 다음 요청은 409 `EXTERNAL_CALL_COOLDOWN`. `details.blockedUntil`은 그 행의 `called_at`+24h다. 시계를 24h+1s 옮기면 통과한다. 403·418도 같다. `RAKUTEN_API` 429는 쉼을 만들지 않는다.
- 결과 열(`http_status`, `duration_ms ≥ 0`)이 채워지고, `call-usage.changed`가 발행된다(`ProgressEventsService`를 구독해 확인).

`GET /api/v1/call-usage`:
- 빈 DB면 RAKUTEN_PAGE 항목이 `{count:0, dailyLimit:110, remaining:110, limitReached:false, blockedUntil:null, httpStatus:null, budgetBuckets:null}`이다.
- 오늘 행 38개 → `count 38·remaining 72`. 110개 → `limitReached true·remaining 0`.
- 1시간 전 429 행 → `blockedUntil`이 지금+23h, `httpStatus 429`.

이미지:
- 없는 id → 404 `IMAGE_ASSET_NOT_FOUND` 봉투.
- 같은 바이트를 두 번 `saveImage(ORIGINAL)` → 행 1개, 파일 1개.
- 메타 200: 키가 `ImageAssetMeta` required 19개와 같고, `filePath`가 없다.
- `/file` 200: `Content-Type: image/jpeg`, `ETag: "<sha256>"`, `Cache-Control: private, immutable`. 같은 `If-None-Match` → 304, 본문 없음.
- 파일을 지운 뒤 → 404 `IMAGE_FILE_MISSING`.
- `.jpg` 이름의 PNG → `mimeType` `image/png`.

`GET /api/v1/events`: supertest는 스트림이 끝나지 않으므로 `node:http`로 붙어 첫 청크를 읽고 끊는다.
- 헤더: `text/event-stream`, `cache-control: no-cache`.
- `publish` 뒤 `id:`·`event:`·`data:`(한 줄 JSON) 프레임이 온다.
- `?candidateId=12` 구독자는 후보 13 이벤트를 받지 않고 전역 이벤트는 받는다.
- `?candidateId=abc` → 422 `INVALID_QUERY_PARAMETER`. Host가 틀리면 403 `HOST_NOT_ALLOWED`.

## 8. 주의

- 공통 규칙은 [README §공통 규칙](../README.md#공통-규칙)을 따른다(실행 환경, 외부 호출 금지, 비밀정보, 커밋 안 함).

- 이후 실행 문서 20여 개가 이 문서의 공개 시그니처를 그대로 쓴다: `ExternalHttpGateway.request`, `ProgressEventsService.publish`, `ImageAssetsService.saveImage`, `UserActionLogService.record`. 정한 모양을 결과 보고에 적고, 나중에 바꾸지 않는다.
- 쉼과 상한 판단의 원본은 `call_log` 하나다. 메모리로 따로 세지 않는다. 앱을 다시 켜도 판단이 같아야 한다. 직렬 큐와 간격 대기만 프로세스 메모리에 둔다(수집기가 하나라 경합이 없다, ERD §3.12). 결과 열은 한 번만 채운다.
- `RAKUTEN_PAGE` 하루 상한 110의 원본은 P1-03 설정 파일이다. 지금은 `DAILY_LIMIT_PROVIDER`의 기본값으로 두고, 숫자 110을 코드 여러 곳에 적지 않는다.
- 관문은 응답 본문을 문자열로 바꾸지 않고 `Buffer`로 넘긴다. 라쿠텐 상품 페이지는 EUC-JP라서, P2-02가 iconv-lite로 디코딩한다.
- 라쿠텐 상품 이미지를 내려받을 호스트와 그 호출의 `CallLogTarget`이 문서에 없다. `RAKUTEN_PAGE`로 세면 이미지가 하루 110 예산을 먹는다. 여기서는 허용 표에 넣지 않는다. P3-01 전에 정한다.
- `countsByFetchReason`은 `rakuten_item.fetch_reason`으로 센다(`call_log`에는 조회 이유 열이 없다). 파싱에 실패해 `rakuten_item`이 안 생긴 호출은 빠진다. 그래서 합이 `count`보다 작을 수 있다. 이 차이를 결과 보고에 적는다.
- AI CLI는 HTTP가 아니라 하위 프로세스라서 관문을 거치지 않는다. 대신 `cli-isolation` 검사기가 격리를 지킨다. 실제 CLI를 부르는 테스트는 만들지 않는다.
- SSE는 개발 때 Vite 프록시(5173 → 3100)를 거친다. `pnpm dev`로 이벤트가 끊기지 않고 오는지 한 번 확인한다. SSE 연결도 로컬 보안(Host 검사)을 먼저 지난다.
