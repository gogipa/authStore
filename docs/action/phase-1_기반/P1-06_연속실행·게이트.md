## 1. 목표

'여기부터 연속 실행'과 '재실행 필요 단계 모두 실행'이 서버 규칙대로 돌고 멈춘다. G2 전에는 ③에서 멈추고, G2 뒤에는 막힌 단계의 결과를 읽는 단계만 멈추며, G3·G4에서 멈춘다. 멈춘 이유와 건너뛴 단계를 화면에서 본다. G2·G3 통과를 게이트 지문과 함께 기록하고, 지문이 바뀌면 다시 통과해야 하며 후보가 승인대기에서 작업중으로 내려온다. ①~⑨ 흐름에서 게이트 G2·G3의 기록과 ②→⑧ 자동 진행을 맡고, G2 판정 세부(P2-05)와 G3 썸네일 선택(P3-02)은 이 틀에 꽂힌다.

## 4. 핵심 규칙

1. **순서와 묶음**: SOURCING → PRICING → [G2] → CATEGORY → THUMBNAIL → COPY → NOTICE_RAW → NOTICE_HTML → TAGS → [G3] → UPLOAD → [G4]. body는 `{ kind: FROM_HERE, startStepCode }`(FROM_HERE는 `startStepCode` 필수, REGISTER 불가) 또는 `{ kind: RERUN_STALE }`. `step_chain` 1행을 만들고, 묶음 안 실행은 `execution_mode=CHAIN` + `step_chain_id`다. 응답 202 + `Location: /api/v1/continuous-runs/{stepChainId}` + `ContinuousRunAccepted`. (PRD §5.3 연속 실행 세부, 05-2 `startCandidateContinuousRun`, ERD `step_chain`·`ck_step_run_chain`)
2. **건너뛰기(F-CW-14)**: 고른 단계는 상태와 관계없이 실행한다. 그 뒤 단계는 `COMPLETED`이고 최신(지문 일치)이면 건너뛰고 `skipped_step_codes`에 남긴다. `GET /continuous-runs/{id}`는 `stepRuns`와 `skippedStepCodes`를 준다. (US-33 AC2, US-29 AC2, ERD v0.3 `skipped_step_codes`, 05-2 `getContinuousRun` x-decision §7.2-16)
3. **6시간 규칙**: 판정에 쓴 라쿠텐 페이지 수집 시각이 6시간(설정)을 넘었으면 ③이 완료여도 건너뛰지 않고 ② 재조회 → ③ 재판정부터 한다. 이 시간 조건은 건너뛰기와 RG-08에만 쓰고 후보 상태의 '최신'에는 쓰지 않는다. (F-CW-14, PRD §5.3 판정 유효 시간)
4. **G2 전(F-CW-15)**: G2가 유효하지 않으면 `startStepCode`는 SOURCING·PRICING만 된다. 그 밖은 409 `CONTINUOUS_RUN_BEFORE_G2`. ③이 국내 기준가나 G2 확인을 기다리면 `stop_reason=AWAIT_G2`, `stop_step_code=PRICING`로 멈춘다. 레일의 '여기부터 연속 실행'은 ②·③에서만 켜고, ④ 이후는 같은 코드로 끈다. (US-33 AC2, 05-3 §5.1)
5. **G2 뒤(F-CW-15)**: 입력 대기·실패 단계의 결과를 직·간접으로 읽는 단계만 건너뛰고 나머지는 계속 실행한다. 예: ⑤가 레퍼런스를 기다려도 ⑥-1·⑥-2·⑦은 돈다. UPLOAD 앞에서 G3이 유효하지 않으면 `AWAIT_G3`, 이미 통과했고 지문이 그대로면 넘어간다. 끝까지 가면 `AWAIT_G4`. 더 실행할 단계가 없으면 `NO_RUNNABLE_STEP`. 막혀서 끝날 때의 `stop_step_code`는 문서에 없음 → Proposed로 정하고 기록. (PRD §5.3 G2 뒤, ERD §4.2 `stop_reason`)
6. **재실행 필요 모두(F-CW-16)**: `RERUN_REQUIRED` 단계를 흐름 순서로 실행하고, 그 사이 새로 `RERUN_REQUIRED`가 된 단계까지 표시가 없어질 때까지 이어 간다. 오너 입력과 게이트에서 멈춘다. 대상이 없으면 409 `NO_RERUN_REQUIRED_STEPS`. 끝없는 반복을 막는 한도는 문서에 없음 → Proposed로 정하고 기록(예: 한 묶음에서 단계당 1번). (PRD §5.3 규칙 5)
7. **열린 묶음 하나**: 후보에 `ended_at` NULL인 묶음이 있으면 409 `CONTINUOUS_RUN_ALREADY_OPEN`. 그 밖 409 `STEP_ALREADY_RUNNING`·`CANDIDATE_LOCKED`·`CANDIDATE_EXCLUDED`·`AI_ENGINE_UNAVAILABLE`(P1-10 훅), 422 `INVALID_STEP_CODE`·`VALIDATION_FAILED`. 취소 API는 없다. 멈추거나 끝나면 `ended_at`·`stop_reason`·`stop_step_code`를 한 번에 쓰고 SSE `continuous-run.stopped`. 앱 재시작 때 열린 묶음은 `APP_RESTART`로 닫는다. (05-2 x-decision §7.2-17, ERD `ck_step_chain_end`, F-BS-18)
8. **게이트 지문(F-CW-02)**: G2 = `{ itemCode, selectedColor, saleCandidate, saleSizes(정렬), 사이즈별 salePrice·optionPrice }`, G3 = `{ 레퍼런스 파일 해시(정렬), 선택본 파일 해시, 앵커 키(型番 또는 앵커 itemCode + 색상 코드) }`. 키 정렬 JSON의 SHA-256 hex 64자. 구성값은 `fingerprint_basis`(jsonb)에 둔다. ③을 다시 돌려도 지문이 같으면(예: 환율로 P_min만 바뀜) G2는 유효하다. (PRD §5.1 게이트 지문, US-35 AC1, ERD `gate_pass`·`ck_gate_pass_fp`)
9. **유효성과 무효화**: 게이트별 최신 `gate_pass`(`candidate_id, gate, passed_at DESC`)의 지문이 지금 값으로 다시 계산한 지문과 같으면 유효하다. `changedBasisKeys` = basis 차이 키. ③·⑤ 완료, ② 소싱 선택 변경, 오너 수정으로 무효가 되면 같은 트랜잭션에서 후보를 재평가하고(`AWAITING_APPROVAL`·`VALIDATED` → `WORKING`, `GATE_FINGERPRINT_CHANGED`) 커밋 뒤 SSE `gate.invalidated { previousGatePassId, changedBasisKeys }`. (PRD §5.2 상태도, 05-1 §3, US-33 AC6)
10. **통과 요청(표 C)**: `POST …/gates/{G2|G3}/pass`만 된다. 그 밖(G1·G4 포함) 422 `INVALID_GATE_CODE`. `basisStepRunId`가 ③(G2)·⑤(G3)의 현재 버전이 아니면 409 `VERSION_NOT_CURRENT`, 그 단계가 `COMPLETED`가 아니면 409 `STEP_NOT_COMPLETED`. G2는 판매 후보 아님 409 `NOT_SALE_CANDIDATE`, 비교 안 한 URL 후보에 '비교 없이 확정'이 없으면 409 `NO_COMPARISON_NOT_CONFIRMED`(검사 본문은 P2-05). G3 검사(`CHECKLIST_INCOMPLETE` 등)는 P3-02. 공통 409 `CANDIDATE_LOCKED`·`CANDIDATE_EXCLUDED`·`STEP_LOCKED_BY_RUNNING_STEP`. (05-1 표 C, 05-3 §5.1)
11. **통과 트랜잭션**: `gate_pass`(추가만) + 후보 상태 재평가·이력(`gate_pass_id`) + `user_action_log`(`GATE_PASSED`, `gate`)를 한 트랜잭션으로 쓴다. 201 + `Location: /api/v1/candidates/{id}/gates` + `GatePassResult`(`candidateStatus`, `statusChanged`). 지문이 최신 통과와 같으면 새 행 없이 200 + 기존 기록. 커밋 뒤 SSE `gate.passed`. (C4 §4, 05-2 `passCandidateGate` x-decision §7.2-12)
12. **웹 화면 전용**: 게이트 통과는 로컬 보안 가드를 통과한 웹 요청으로만 기록한다. CLI(M3)가 부를 수 있는 내부 경로로 열지 않는다. G4는 `gate_pass`가 아니라 `registration.approved_at`(P4-03)이다. (PRD §5.1 단계 실행과 게이트, 05-1 §1.2, ERD `ck_gate_pass_gate`)
13. **게이트 목록**: `GET …/gates`는 `items` 4개(G1~G4, 페이징 없음). G1 = `keyword.selected_at`, G2·G3 = 최신 통과·`fingerprintValid`·`changedBasisKeys`·`blockedReasons`(`code`는 통과 API의 409·422 코드와 같음)·`warnings`, G4 = `registration.approved_at`. 키워드 경로가 아닌 후보의 G1 표시는 문서에 없음 → Proposed로 정하고 기록(G1은 키워드 경로만 거친다). (05-2 `listCandidateGates`, PRD §5.1)
14. **게이트가 필요한 곳**: UPLOAD는 G3 유효가 시작 조건이다. 아니면 409 `GATE_NOT_PASSED`(`details.gate=G3`). 승인대기에 들어가려면 G2·G3이 모두 유효해야 한다. 판정(G2) 전 AI 단계는 막지 않고 경고만 한다(P1-05). (05-1 표 A UPLOAD, PRD §5.1)

## 5. 만들 것

**BE** — `modules/step-engine/`

- 게이트 규약 `contracts/gate-basis.ts`. 등록 방법은 `StepRunner`와 같다(`DiscoveryService`). P2-05(pricing)가 G2, P3-02(thumbnails)가 G3을 등록한다.

```ts
export interface GateBasisProvider {
  readonly gate: 'G2' | 'G3';
  basis(tx: Tx, candidateId: number, basisStepRunId: number): Promise<Record<string, unknown>>;           // 지문 구성값
  blockers(tx: Tx, candidateId: number, basisStepRunId: number, body: unknown): Promise<CandidateBlockReason[]>; // NOT_SALE_CANDIDATE 등
  onPass?(tx: Tx, candidateId: number, gatePassId: number, body: unknown): Promise<void>;                 // G3: thumbnail_selection·⑤ 완료(P3-02)
}
export const GateBasisFor = (gate: 'G2' | 'G3') => SetMetadata(GATE_BASIS_META, gate);
```

## 6. 테스트

**단위**

- G2 지문: 사이즈 순서만 다름 → 같음. P_min만 바뀜(판매가·판매 사이즈 그대로) → 같음(PRD §5.1 예). 250mm 판매가 +100원 → 다름, `changedBasisKeys`에 그 키. itemCode 변경 → 다름.
- G3 지문: 레퍼런스 해시·선택본 해시·앵커 색상 중 하나만 바꿔도 다름.
- `chain-planner`:
  - G2 무효 + FROM_HERE SOURCING: ② 실행 → ③ 실행 → ③ 입력 대기 → `AWAIT_G2`/`PRICING`.
  - G2 무효 + CATEGORY 시작 → `CONTINUOUS_RUN_BEFORE_G2`.
  - G2 유효·⑤ 입력 대기: ⑥-1·⑥-2·⑥-3·⑦ 실행, ⑧은 실행 안 함 → `NO_RUNNABLE_STEP`.
  - ⑤ 완료·G3 무효 → ⑧ 앞 `AWAIT_G3`. G3 유효·지문 그대로 → ⑧ 실행 → `AWAIT_G4`.
  - 완료·최신 단계는 `skip`. ③ 판정 페이지가 7시간 전 → ③을 건너뛰지 않고 ② 재조회 → ③.
  - RERUN_STALE: ③이 다시 돌아 ⑥-3이 새로 재실행 필요 → ⑥-3까지 실행. 대상 없음 → `NO_RERUN_REQUIRED_STEPS`. 같은 단계가 계속 재실행 필요가 되어도 한도에서 멈춘다.

**e2e**(`test/step-engine/continuous-gates.e2e-spec.ts`, 가짜 실행기·가짜 게이트 공급자)

- `POST …/continuous-runs { kind: FROM_HERE, startStepCode: SOURCING }` → 202, `Location: /api/v1/continuous-runs/{id}`. 끝난 뒤 `GET` → `stepRuns`(모두 `executionMode=CHAIN`), `skippedStepCodes`, `stopReason=AWAIT_G2`. SSE `continuous-run.stopped`.
- FROM_HERE인데 `startStepCode` 없음 → 422 `VALIDATION_FAILED`. `startStepCode=REGISTER` → 422 `INVALID_STEP_CODE`. 열린 묶음이 있을 때 두 번째 → 409 `CONTINUOUS_RUN_ALREADY_OPEN`. 재실행 필요 없음 → 409 `NO_RERUN_REQUIRED_STEPS`. `GET /continuous-runs/999999` → 404 `CONTINUOUS_RUN_NOT_FOUND`.
- 게이트: `…/gates/G4/pass` → 422 `INVALID_GATE_CODE`. 옛 ③ 버전 → 409 `VERSION_NOT_CURRENT`. 가짜 G2가 판매 후보 아님 → 409 `NOT_SALE_CANDIDATE`. 비교 안 한 URL 후보·체크 없음 → 409 `NO_COMPARISON_NOT_CONFIRMED`. 통과 → 201, `Location: /api/v1/candidates/{id}/gates`, `gate_pass` 1행·`user_action_log` `GATE_PASSED` 1행. 같은 요청 다시 → 200 같은 `gatePassId`, 행 수 그대로.

- G3 없이 UPLOAD 실행 → 409 `GATE_NOT_PASSED`(`details.gate=G3`).

## 8. 주의

- 공통 규칙은 [README §공통 규칙](../README.md#공통-규칙)을 따른다(실행 환경, 외부 호출 금지, 비밀정보, 커밋 안 함).

- 후보당 열린 묶음 하나는 DB가 막지 않는다(`ix_step_chain_open`은 UNIQUE가 아니다, ERD §7.2-12). 묶음을 만들 때 후보 행을 `SELECT … FOR UPDATE`로 잠그고 열린 묶음을 확인한다.
- 묶음 안 실행은 `execution_mode=CHAIN`과 `step_chain_id`가 짝이다(`ck_step_run_chain`). 복합 FK `(step_chain_id, candidate_id)`라 다른 후보의 묶음을 가리키면 FK 오류가 난다.
- `gate_pass`는 추가만이다. 같은 지문 재통과에 새 행을 넣지 않는다. 근거 버전은 G2 → PRICING, G3 → THUMBNAIL만 된다(`ck_gate_pass_basis`, 복합 FK).
- 6시간 규칙을 후보 상태의 '최신'에 넣지 않는다. 넣으면 승인대기 후보가 6시간마다 작업중으로 떨어진다(PRD §5.3).
- 6시간 재조회는 라쿠텐 페이지 하루 상한(110)을 쓴다. 테스트는 가짜 실행기로만 한다. 상한·24시간 쉼으로 ②가 실패하면 ②를 읽는 단계만 멈추는지 본다.
- 묶음 진행은 프로세스 안 이벤트로 이어 간다. HTTP 요청이나 SSE 연결에 기대지 않는다. 앱이 꺼지면 묶음은 `APP_RESTART`로 끝나고 다시 이어 가지 않는다.
- G3 통과 세부(`thumbnail_selection` 저장, ⑤ 완료 또는 OWNER_EDIT 새 버전)는 P3-02가 `onPass`로 같은 트랜잭션에 넣는다. 여기서 썸네일 표를 직접 쓰지 않는다.
- 연속 실행에 AI 단계가 있으면 시작 때 선택 엔진을 확인한다(P1-10 훅, `AI_ENGINE_UNAVAILABLE`). 묶음 안 각 단계는 그 단계가 시작할 때의 엔진을 고정한다.
