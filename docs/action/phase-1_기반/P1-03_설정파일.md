## 1. 목표

앱을 켤 때 설정 JSON 파일(비밀 아님)을 두 가지로 검사한다. 하나는 JSON Schema, 다른 하나는 안전 기준 하한이다. 통과한 내용은 `settings_snapshot`에 내용 해시별로 한 번 저장하고, 이것을 '현재 설정'으로 쓴다.
`GET /settings`는 현재 값과 검사 결과를 보여 준다. `POST /settings-snapshots`는 파일을 고친 뒤 앱을 다시 켜지 않고 다시 읽는다. SCR-10에서는 탭 틀, '설정 파일 검사', '적용 중인 기본값'이 보인다.
①~⑨ 흐름 밖의 기반이다. 이 스냅샷을 읽는 곳은 아래와 같다.
- ② 소싱 기본값
- ③ 판정의 비용 기본값·과세 사이즈 판매 설정
- AI 엔진 선택(`ai` 섹션)
- 모든 StepRun(어떤 설정으로 실행했는지 참조한다)

## 4. 핵심 규칙

1. 설정 원본은 `APP_DATA_DIR` 안의 JSON이다.
   - 파일이 하나인지 여럿인지는 문서에 없음(ERD §7.4-1) → 구현 때 Proposed로 정하고 기록(권장: 파일 하나).
   - 첫 실행에 파일이 없을 때 기본 템플릿을 복사해 만들지도 문서에 없음 → 구현 때 Proposed로 정하고 기록.
   - `file_manifest`에는 파일별 이름·SHA-256·크기만 담는다. 경로는 담지 않는다.

   (F-ST-01, ERD §3.11, 05-2 `SettingsSnapshot.fileManifest`).
2. 시작할 때 Ajv로 스키마를 검사한다. 오류는 모두 모은다(`allErrors`). 각 오류는 `{ field: JSON 경로, message }`다.
   - 검사에 실패해도 앱은 뜬다. 오류를 화면에 보여 줘야 하기 때문이다.
   - 전에 통과한 스냅샷이 있으면 그것을 현재 설정으로 쓰고, `GET /settings`는 `valid=false`와 `errors[]`를 준다.
   - 통과한 스냅샷이 하나도 없으면 503 `SETTINGS_INVALID`를 준다. `fieldErrors`에 검사 오류를 담는다.

   (F-ST-01, US-09 AC1, 05-2 `getSettings`·`SettingsView`, 05-3 §5.1).
3. 스키마는 비밀 키(API 키·시크릿·토큰)를 받지 않는다. 모든 객체에 `additionalProperties: false`를 걸어 모르는 키도 오류로 한다(Proposed). 설정은 비밀이 아니므로 `GET /settings`는 `content` 전체를 준다. 설정 파일의 절대 경로는 응답·로그에 넣지 않는다 (NFR-02, 05-1 §1.2·§2.12).
4. 스냅샷은 아래처럼 만든다.
   - 통과한 내용을 정규화(키 정렬 JSON)해서 SHA-256을 `content_sha256`(UNIQUE)에 넣는다.
   - 같은 해시가 이미 있으면 새 행 없이 `last_loaded_at`만 바꾼다.
   - 새 해시면 새 행을 만든다(`first_loaded_at = last_loaded_at = now`). `schema_version`과 `app_version`(`package.json`의 `version`)도 채운다.
   - 현재 스냅샷은 `last_loaded_at`이 가장 큰 행이다. 행은 지우지 않는다(`trg_forbid_delete`).
   - DB CHECK: `ck_settings_snapshot_sha`(64자 hex), `ck_settings_snapshot_time`(last ≥ first).

   (ERD §3.11).
5. `POST /settings-snapshots`는 시작 검사와 같은 코드를 쓴다. `X-AutoStore-Client`가 필요하다. 결과는 아래와 같다.

   | 경우 | 응답 |
   |---|---|
   | 새 내용 | 201, `Location: /api/v1/settings`, `created=true` |
   | 같은 내용 | 200, `created=false` |
   | 스키마 위반 | 422 `SETTINGS_SCHEMA_INVALID`, `fieldErrors[].field`에 JSON 경로 |
   | 안전 기준 완화 | 422 `SAFETY_SETTING_RELAXATION_REJECTED` |

   - 성공 본문은 `SettingsReloadResult { snapshot, created, changedKeys[], rerunRequiredStepCount }`다.
   - 실패하면 현재 스냅샷은 그대로 둔다.
   - 성공하면 SSE `settings.reloaded { settingsSnapshotId, changedKeys, valid, errors, rerunRequiredStepCount }`를 보낸다. 실패할 때도 보낼지는 문서에 없음 → 구현 때 Proposed로 정하고 기록.

   (05-2 `createSettingsSnapshot` x-decision §7.5-42, 05-1 §1.7·§3).
6. `changedKeys[]`는 직전 현재 스냅샷과 달라진 설정 키다(점 경로, 예: `costs.targetMarginRate`). `rerunRequiredStepCount`는 재실행 필요 전파(F-BS-21, P1-05)가 붙기 전까지 0이다. `ai` 섹션만 바뀐 경우는 나중에도 전파 대상이 아니다 (05-2 `SettingsReloadResult`, ERD §3.11, D-16 R9).
7. 안전 기준 하한은 시작 때와 다시 읽을 때 모두 검사한다. 어기면 422 `SAFETY_SETTING_RELAXATION_REJECTED`다. 어떤 항목을 어겼는지 `details`에 담고, 그 내용은 스냅샷에 들어가지 않는다.
   - 내장 목록 3종은 더하기만 된다. 내장 항목이 하나라도 빠지면 거부한다. 3종: 실존 인물 차단어, 아동 키워드와 `NGKeyword`의 아동 단어, 구매대행 고지 필수 블록.
   - 아동화 의심 사이즈 기준이 235mm 미만이면 거부한다(235mm는 통과).
   - 판정 유효 시간이 6시간을 넘으면 거부한다(6시간은 통과).
   - 고지 필수 블록은 앱에 내장한 해시와 비교한다.

   (F-BS-05, F-BS-39, GEN-01, US-36 AC4, 05-3 §5.1).
8. 내장 아동 단어의 최소 목록은 문서에 나온 단어다.
   - KW-01: 키즈·주니어·아동·キッズ·ジュニア·ベビー
   - NGKeyword의 아동 단어: キッズ·ジュニア·ベビー
   - 실존 인물 차단어 기본 목록은 문서에 없음 → 구현 때 Proposed로 정하고 기록
   - 고지 필수 블록의 블록 ID와, 해시할 문장 범위(PRD §8.5 템플릿 초안 중 어디까지)도 문서에 없음 → 구현 때 Proposed로 정하고 기록

   (KW-01, PRD §8.2·§8.4·§8.5, CT-04).
9. 비용 기본값은 PRD §8.3 '기본 파라미터' 표의 값이다(5장 표): 카드 가산 2.5%, 판매수수료 3.0%(광고 유입 1.0%, 배송비에도 부과가 기본 true), Npay 3.63%, 기타비용 3,000원, 목표 마진 10%, 최소 이익 5,000원, 판정 여유 1%, 반올림 100원. 키 이름과 비율 표기(2.5인지 0.025인지)는 문서에 없음 → 구현 때 Proposed로 정하고 기록 (F-ST-03, PRD §8.3).
10. 비용 관련 선택 설정 두 가지:
    - 과세 사이즈 판매: 기본 꺼짐(`false`, 면세만 판매). M1에는 설정 편집 화면이 없어서(F-ST-12는 M2) 파일로만 켠다.
    - 셀러라이프 배대지 쿠폰 차감: 기본 꺼짐. 쿠폰당 약 2,000원, 월 사용 한도 안에서만 뺀다. 월 한도의 기본값은 문서에 없음 → 구현 때 Proposed로 정하고 기록.

    (F-ST-02, F-ST-05, US-08 AC2, PRD §8.3 계산 순서 3), D-03).
11. 소싱 기본값은 아래와 같다.
    - 장르 `558885`, `minPrice` 3000(PRD에 '예'로 적힌 값)
    - NGKeyword `中古 インソール 靴紐 シューレース 箱のみ キッズ ジュニア ベビー`
    - 페이지 조회 개수: 재고 통과 후보 3개가 되거나 10페이지에 닿으면 멈춘다
    - 목표 사이즈 남 250~290mm, 여 220~260mm. 최소 사이즈 수 3
    - 기본 폭 `2E (標準)`, 取り寄せ 제외 `true`, 기본 송료 ¥800
    - 하루 조회 상한 110, 아동화 의심 기준 235mm, 판정 유효 시간 6시간

    (F-BS-39, PRD §8.2·§8.8, RK-04·RK-05, RG-08).
12. `ai` 섹션의 기본값은 `engine: CLAUDE`, CLAUDE의 텍스트·비전 모델은 `sonnet`·`sonnet`이다. AGY 기본 모델은 M0 S7에서 정하고, CODEX는 `null`이다. 이 섹션을 파일에 쓰는 일은 `PUT /settings/ai-engine`(P1-11)만 한다. 이 문서는 읽기와 스키마만 만든다 (D-16, 05-1 §2.12, 05-2 `AiEngineModelPair`, F-ST-30).
13. 기본 템플릿에는 개인 값 대신 자리표시자만 둔다. 개인 값은 상호·A/S 연락처, 배대지·창고 주소, 요금표, 고지의 배송기간·반품비, `importer`, 파일 경로다. 동료 설치본에 오너 값이 섞이면 안 된다 (F-BS-03, US-37 AC3, GEN-01).
14. 다른 모듈은 설정 파일을 직접 읽지 않는다. `SettingsService`의 타입 있는 `current()`와 `currentSnapshotId()`만 쓴다. StepRun은 이 스냅샷 id로 '어떤 설정으로 했는지'를 남긴다(P1-05) (ERD §3.11, 03-ADR-003).

## 8. 주의

- 공통 규칙은 [README §공통 규칙](../README.md#공통-규칙)을 따른다(실행 환경, 외부 호출 금지, 비밀정보, 커밋 안 함).

- 05-1 §7.5-51이 아직 열려 있다. 오너가 파일에서 `ai` 섹션을 직접 고치고 다시 읽으면, AI 엔진 저장 조건(10분 안에 연결 테스트 통과, R8)을 건너뛴다. 받아들일지, 아니면 다시 읽기에서 `ai` 변경을 422로 막을지는 문서에 없음 → 구현 때 Proposed로 정하고 기록. P1-11이 이 결정에 기댄다.
- 비율 표기(2.5인지 0.025인지)와 키 이름은 P2-05 가격 엔진이 그대로 읽는다. P2-05가 PRD §8.3 기대값(P_min 153,100원, 순이익 15,365원)을 고정하므로 여기서 한 번 정하면 바꾸지 않는다. JSON 숫자 정밀도 문제(05-1 §7.1-4)도 함께 기록한다.
- 문서끼리 다르다. F-BS-03·US-37 AC3는 고지의 배송기간을 개인 값(자리표시자)으로 본다. ERD §3.11 `content` 설명은 '배송기간 최소·최대 기본 10~20영업일'을 둔다. 어느 쪽을 따를지 결과 보고의 '오너 검토'에 올린다.
- `settings_snapshot`은 삭제 금지 트리거가 있다. 기존 `test/app.e2e-spec.ts`도 이 표를 TRUNCATE한다. 새 e2e도 같은 방식으로 정리하고, 저장소의 `.data/settings`를 건드리지 않는다.
- `AiCliChecksService.readSelectedEngine()`은 지금 스냅샷을 직접 읽는다. 이 문서에서는 고치지 않는다. P1-11이 `SettingsService`로 바꾼다. 그 전까지 스냅샷 `content.ai.engine` 경로를 바꾸지 않는다.
- 재실행 필요 전파는 P1-05 몫이다. 여기서 `candidate_step`을 고치거나 `rerunRequiredStepCount`를 지어내지 않는다. 포트를 통해서만 0을 돌려준다.
- 대시보드(SCR-01)의 '설정 파일 검사 · 앱을 켤 때 오류 없음' 줄도 `useSettingsQuery`를 쓴다. 이 줄은 P1-04가 붙인다. 쿼리 키와 훅 이름을 결과 보고에 적는다.
