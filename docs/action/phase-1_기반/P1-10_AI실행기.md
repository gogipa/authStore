## 1. 목표

이 작업이 끝나면 단계 모듈은 설정에서 고른 AI 엔진(`claude`·`agy`·`codex`) 하나를 `AiExecutor` 한 곳으로 부른다. 호출은 격리 규약(빈 작업 폴더·환경변수 화이트리스트·셸 없는 인자 배열·stdin 닫기·`--model` 명시)을 지키고, 앱은 스키마로 다시 검증한 JSON만 받는다.
step-engine은 AI 단계를 시작할 때 엔진·모델·CLI 버전을 `step_run.ai_*`에 고정하고, 선택 엔진을 쓸 수 없으면 409 `AI_ENGINE_UNAVAILABLE`로 막는다. 앱을 켜면 선택 엔진 계약 테스트가 돌아 `ai_cli_check`에 남는다.
①~⑨의 한 단계가 아니다. AI를 쓰는 단계들이 함께 쓰는 기반이다: ② 동일 상품 판정 보조, ⑤ 썸네일 검사, ⑥-1 카피, ⑥-2 추출·색상 표기, ⑥-3 상품명(AI를 쓸 때). P1-11(AI 엔진 페이지)·P3-02·P3-03이 이 작업에 기댄다.

## 4. 핵심 규칙

1. **부르는 대상**: 실행 파일 이름은 `claude`·`agy`·`codex` 3개만 허용한다. 사용자 본인 계정으로 로그인한 공식 CLI다. 서드파티 래퍼(`agy-image` 등)·Gemini CLI·그 밖의 이름은 실행기가 spawn 전에 거부한다. 로그인 정보·OAuth 토큰 파일은 읽지 않는다. (PRD §8.9 R14, F-BS-26, CON-11·CON-12, US-28 AC1)
2. **격리 실행**: 호출마다 새 빈 작업 폴더를 cwd로 쓴다. 이 폴더에는 `.claude/`·`.mcp.json`이 없다. `spawn(bin, args, { shell: false })`로 인자 배열을 넘기고, stdin은 닫는다(`stdio[0] = 'ignore'`). `--model`은 항상 넣는다. 모델 값이 비어 있으면 spawn하지 않고 오류로 끝낸다. (PRD §8.9 필수 실행 규약, F-BS-27, US-28 AC1)
3. **환경변수 화이트리스트**: 허용 목록에 있는 변수만 자식 프로세스에 넘긴다. `ANTHROPIC_API_KEY`·`OPENAI_API_KEY`는 부모에 있어도 절대 넘기지 않는다(구독 대신 API 과금). `claude`에는 `DISABLE_AUTOUPDATER=1`을 더한다. 허용 목록의 내용은 문서에 없음 → 구현 때 Proposed로 정하고 기록. (PRD §8.9 R14·버전, F-BS-27, F-BS-29)
4. **전역 설정 차단**: `claude`는 `--safe-mode`로 사용자 전역 훅·CLAUDE.md·MCP·플러그인을 읽지 않게 한다. M0 S6 결과에 따라 `--setting-sources`·`--strict-mcp-config` 조합으로 바뀔 수 있으니 격리 플래그는 상수 한 곳에 둔다. `agy`의 사용자 MCP 끄기와 `codex`의 `~/.codex`(AGENTS.md·MCP) 격리는 M0 S6·S7 결과를 받을 때까지 설계대로 두고, 녹화한 출력으로만 검증한다. (F-BS-28, US-36 AC5)
5. **CLI를 바꾸지 않음**: 앱은 CLI를 설치·업데이트하지 않고, 버전을 바꾸거나 전역 설정 파일(`~/.claude`·`~/.codex` 등)을 쓰지 않는다. 자동 업데이트는 규칙 3의 환경변수로만 끈다. (F-BS-29, CON-11)
6. **호출 템플릿**: 아래 표 그대로 인자를 만든다. 텍스트 호출은 도구를 모두 끈다(`--tools ""`). 비전 호출에는 `--tools ""`를 넣지 않는다. `agy`의 `--print-timeout`에는 단위를 붙인다: 텍스트 `120s`, 비전 `180s`. 0이나 빈 값은 무제한이라 금지다. (PRD §8.9 호출 템플릿·AI-03, F-BS-30, F-BS-73)

   | 엔진·종류 | 인자 배열(순서대로, 격리 플래그는 규칙 4) |
   |---|---|
   | claude 텍스트 | `-p <prompt> --model <alias> --output-format json --json-schema <schema JSON> --tools "" --no-session-persistence` |
   | claude 비전 | `-p <prompt> --model <alias> --output-format json --json-schema <schema JSON> --tools Read --allowedTools Read --add-dir <이미지 전용 폴더> --no-session-persistence` |
   | agy 텍스트·비전 | `-p <prompt> --model <id> --output-format json --json-schema <schema JSON> --print-timeout <120s·180s>` (비전은 `--add-dir <이미지 전용 폴더>`) |
   | codex 텍스트 | `exec <prompt> --model <id> --output-schema <스키마 파일> --sandbox read-only --skip-git-repo-check --ephemeral --output-last-message <결과 파일>` |
   | codex 비전 | codex 텍스트 + 프롬프트 인자 뒤에 `--image <path>`(이미지마다 반복) |

7. **스키마 규칙**: 모든 텍스트·비전 호출에 JSON Schema를 붙인다(`claude`·`agy`는 `--json-schema` 문자열, `codex`는 `--output-schema` 파일). draft-07 공통 부분집합만 쓴다. 모든 object는 `additionalProperties: false`이고 모든 필드가 `required`다. 선택 값은 `["string","null"]`처럼 null 허용 타입으로 쓴다. `format` 키워드는 쓰지 않는다. 규칙을 어긴 스키마는 호출 전에 거부한다. (PRD §8.9 스키마 규칙, F-BS-31, AI-02, US-28 AC1)
8. **결과 재검증**: `claude`·`agy`는 결과 JSON의 `structured_output` 필드만, `codex`는 `--output-last-message` 파일의 JSON만 읽고 Ajv로 다시 검증한다. stdout의 나머지와 `codex --json` 이벤트는 진행 표시에만 쓴다. 아래는 모두 실패다: exit code ≠ 0, stderr에 `AGY_ERROR`, `status`가 `SUCCESS`인데 `structured_output`이 비었음, 부분 출력 경고, 스키마 불일치. (PRD §8.9 agy·codex, F-BS-32, F-BS-73, US-28 AC1)
9. **비전 확인**: 비전 호출은 Read 도구와 이미지 전용 폴더만 연다. 이 폴더에는 이번 호출의 이미지만 둔다. 스키마에 `images_seen`을 넣고, 넘긴 이미지를 실제로 읽었다고 답하지 않으면 실패로 처리한다. `codex`는 `--image`로 넘긴다. `images_seen`의 형식(개수 또는 파일 이름 목록)은 문서에 없음 → 구현 때 Proposed로 정하고 기록. (PRD §8.9 claude 비전, F-BS-30)
10. **엔진 고정·기록**: AI 단계가 시작할 때 선택 엔진과 모델을 고정한다. `step_run`을 INSERT할 때 `ai_engine`·`ai_model`·`ai_cli_version`을 함께 쓴다. 이 세 열은 트리거 `trg_step_run_append_only` 때문에 열린 행이어도 나중에 못 바꾼다. AI를 쓰지 않는 단계는 셋 다 NULL이다(`ck_step_run_ai_model`: 엔진과 모델은 함께 있거나 함께 없음, `ck_step_run_ai_cli_version`: 버전만 있을 수 없음). `ai_model`은 그 단계 주 작업의 모델이다. `ai_cli_version`은 시작 때 `--version`으로 감지하고, 실패하면 NULL이다. 실행 도중 설정이 바뀌어도 그 실행은 고정한 엔진으로 끝낸다. 화면의 'AI 생성' 표시는 'AI 생성 · Claude Code'처럼 엔진 이름을 붙인다. (PRD §8.9 R9·R11, F-BS-75, ERD §3.1 step_run, US-38 AC4)
11. **시작 전 거절**: AI 단계 시작(단계 실행 `startCandidateStepRun`, 연속 실행 묶음에 AI 단계가 있을 때)에서 선택 엔진의 최신 `ai_cli_check` 행을 본다. 사유별로 409 `AI_ENGINE_UNAVAILABLE`, `details: { engineCode, reason, settingsPath: "/settings/ai-engine" }`로 거절하고 `step_run`을 만들지 않는다. 사유: `installed=false` → `NOT_INSTALLED`, `auth_status=NOT_LOGGED_IN` → `NOT_LOGGED_IN`, `smoke_status=FAILED` → `CONTRACT_FAILED`. 지원 밖 버전은 문서끼리 다르다: 05-3은 거절 사유 `VERSION_UNSUPPORTED`, PRD §8.9·F-SY-13은 경고만 한다. 구현 전에 한쪽으로 정해 Proposed로 기록한다. 점검 행이 아예 없는 경우도 문서에 없음 → Proposed. (PRD §8.9 R10, F-BS-76, 05-1 §2.1, 05-3 `AI_ENGINE_UNAVAILABLE`, US-38 AC3)
12. **실행 중 실패**: 실행 중 선택 엔진을 쓸 수 없게 되면 그 실행을 끝낸다: `status=FAILED`, `failure_kind=AI`, `error_code=AI_ENGINE_UNAVAILABLE`. 사유는 실행 파일 없음(ENOENT), 로그인 풀림 같은 것이다. 다른 엔진으로 넘어가지 않는다. 대체 어댑터 호출은 0회다. (PRD §8.9 R10, F-BS-76, ERD step_run.error_code, US-38 AC3)
13. **계약 테스트**: 앱을 켜면 세 엔진을 감지한다(`--version`·실행 파일 경로·로그인 상태, 호출 비용 없음). 그다음 선택 엔진만 그 텍스트 모델로 'OK' 한 단어를 스키마로 받는 호출을 1회 한다. 엔진마다 `ai_cli_check` 1행(`trigger=STARTUP`)을 쓰고 SSE `ai-cli-check.completed`를 보낸다. 선택하지 않은 엔진과 미설치 엔진은 `smoke_status=SKIPPED`이고 `model`·`latency_ms`는 NULL이다(`ck_ai_cli_check_not_installed`·`ck_ai_cli_check_skipped`). 선택 엔진이 `agy`이고 사용자 MCP를 끌 수 없으면 MCP가 올라오는지 검사해 경고한다. 검사 방법은 M0 결과에 따른다. (PRD §8.9 R7·버전, F-BS-67, ERD §3.14 ai_cli_check)
14. **AI 입력 보호**: 프롬프트에 비밀정보(client_secret·토큰·API 키)와 개인정보를 넣지 않는다. 실행기가 spawn 전에 검사하고, 걸리면 호출하지 않는다. 네이버 출처 데이터(데이터랩 키워드·manuTag)는 M1에서 AI 입력으로 받지 않는다. 키워드 1개의 검색어 변환(KW-06)은 M2다. 예외(태그 관련성 AI 판정 등)를 켜면 그 사실을 기록한다. 검사 패턴과 기록 위치는 문서에 없음 → 구현 때 Proposed로 정하고 기록. (F-BS-13, F-BS-14, CON-09·CON-13, NFR-02)
15. **호출 기록**: 연결 테스트와 구조화 실행 1회마다 `call_log` 1행을 남긴다. `target`은 `AI_CLAUDE_CLI`·`AI_AGY_CLI`·`AI_CODEX_CLI` 중 하나다. 보내기 직전에 INSERT하고, 끝나면 `succeeded`·`duration_ms`·`error_code`를 채운다. 단계 실행 안이면 `step_run_id`·`candidate_id`도 채운다. 프롬프트와 출력 본문은 남기지 않는다. (ERD §3.12 call_log 목적·`ck_call_log_target`, NFR-02)

## 8. 주의

- 공통 규칙은 [README §공통 규칙](../README.md#공통-규칙)을 따른다(실행 환경, 외부 호출 금지, 비밀정보, 커밋 안 함).
- CLI를 실제로 부르는 테스트는 기본으로 돌지 않게 한다(가짜 실행 파일·녹화한 출력으로 검증). codex는 미설치라 M0 S7 전까지 fixture로만 검증한다.

- **작업 폴더를 저장소 안에 두지 않는다.** `APP_DATA_DIR` 기본값은 저장소 루트의 `.data`이고, 저장소 루트에는 `.claude/`가 있다. CLI는 부모 폴더의 설정·CLAUDE.md를 읽을 수 있다. 작업 폴더는 `os.tmpdir()` 아래에 만들고, 테스트로 `REPO_ROOT` 밖인지 확인한다.
- **`ai_*`는 INSERT 때 쓴다.** 'INSERT 뒤 UPDATE'로 짜면 열린 행이어도 트리거가 막는다. 사용 가능 판정과 `--version` 감지는 시작 트랜잭션 전에 끝낸다. spawn 같은 오래 걸리는 일을 DB 트랜잭션 안에서 하지 않는다.
- **M2를 미리 만들지 않는다.** 단계적 종료(SIGINT → SIGTERM), 재시도, 동시 실행 2개, 영속 큐, 입력 해시 캐시는 M2다(F-BS-59~64). 다만 시간 제한이 없으면 자식이 멈춰 버리므로 넘으면 자식을 끝내고 실패로 둔다. 이 동작은 Proposed로 적는다. 캐시를 만들 때는 캐시 키에 엔진·모델을 넣는다(R9).
- **녹화본이 아직 없다.** `claude`의 `structured_output` 봉투, `agy`의 `status`·부분 출력 경고, `codex` 결과 파일 모양은 M0 S6·S7 전에는 PRD 템플릿으로 만든 합성본이다. 파서를 한 곳(`adapters/*`)에 모아 두면 녹화본이 오면 그것만 고친다. `codex`는 미설치라 실제 확인은 S7 뒤다.
- **앱 시작 점검이 테스트에서 진짜 CLI를 부르면 안 된다.** e2e는 `AppModule`을 띄우므로 `OnApplicationBootstrap` 점검이 돈다. `AI_ENGINE_ADAPTERS`를 가짜로 바꾸거나 시작 점검을 끄는 DI 스위치를 둔다. 켜진 채로 두면 개발 PC에서 구독 쿼터를 쓴다.
- **다른 실행 문서가 이 결과에 기댄다.** P1-01의 F-BS-07 테스트는 여기서 export한 인자 빌더로 격리 옵션을 확인한다. P3-02 이미지 생성 공급자는 `IsolatedCliRunner`를 다시 쓴다. P3-03은 `AiExecutor`·`PinnedAiContext`를 쓴다. 이름을 바꾸면 P1-11·P3-02·P3-03 문서도 고친다.
- **최신 점검 행만 보고 판정하는 규칙의 틈**: [다시 감지]처럼 감지만 한 행(`SKIPPED`)이 최신이면, 그보다 앞의 `FAILED`는 보지 않게 된다. 문서 규칙(ERD §3.14 '최신 행') 그대로 두되, 결과 보고의 '오너 검토'에 올린다.
- **사용자 PC를 바꾸지 않는다.** `claude update`, `npm i -g`, `~/.claude/settings.json`·`~/.codex` 쓰기는 코드에도 테스트에도 넣지 않는다(F-BS-29).
