## 1. 목표

이 작업이 끝나면 SCR-11 '키 입력'에서 커머스API·라쿠텐·환율 키 6개를 넣을 수 있고, 값은 macOS 키체인에만 저장돼 화면·로그·DB 어디에도 나오지 않는다. 커머스API 토큰을 규격대로(bcrypt 서명, form 본문, `type=SELF`) 받아 메모리에 캐시하고, 만료 30분 전과 401 `GW.AUTHN` 때 다시 받는다. 재발급도 실패하면 '인증 상태' 패널이 원인 네 가지(휴면·시크릿 변경·이용정지·IP)로 안내하고 시크릿 다시 넣기로 잇는다. ①~⑨ 흐름 밖의 기반이다. 메타 동기화(P1-08)·⑧ 업로드(P4-01)·⑨ 등록(P4-03)이 이 토큰·클라이언트를 쓰고, ② 라쿠텐(P2-02)·환율(P2-04)이 같은 비밀정보 저장소를 쓴다.

## 4. 핵심 규칙

1. 비밀정보는 macOS 키체인에만 저장한다. `.env`·설정 JSON·DB·로그·SSE·AI 프롬프트·API 응답에 값이 나오면 안 된다. 저장소는 `SecretStore` 포트 뒤에 두어 OS별 구현으로 바꿔 끼운다(M1 구현은 키체인 하나). (NFR-02, F-BS-24, US-27 AC1, US-36 AC3)
2. 허용 키는 6개다: `COMMERCE_CLIENT_ID`·`COMMERCE_CLIENT_SECRET`·`RAKUTEN_APPLICATION_ID`·`RAKUTEN_ACCESS_KEY`·`KOREAEXIM_API_KEY`·`CUSTOMS_SERVICE_KEY`. 목록 밖 키는 404 `SECRET_KEY_UNKNOWN`. (05-2 `SecretKey` · x-decision §7.5-44, 05-3 §5.1)
3. `PUT /secrets/{secretKey}`: 본문 `{ value }`(1~4096자). 성공은 204, 본문 없음. 빈 값·4097자 이상은 422 `VALIDATION_FAILED`이고 `fieldErrors`에 `rejectedValue`를 넣지 않는다. 같은 값 덮어쓰기는 멱등이다. 요청 본문은 pino·`call_log`·`user_action_log`에 남기지 않는다(남긴다면 키 이름만). (05-2 saveSecret, 05-1 §1.2)
4. `GET /secrets`: 허용 키 6개 전부를 `{ secretKey, configured, updatedAt }`로 준다. 값·가림값은 주지 않는다. `updatedAt`은 키체인 항목 수정 시각을 얻으면 넣고, 못 얻으면 `null`. 키체인을 못 열면 GET·PUT 모두 503 `KEYCHAIN_UNAVAILABLE`. (05-2 listSecrets · x-decision, 05-3)
5. 가림: 화면은 저장한 값을 다시 보여 주지 않는다(입력칸 `type=password`, 저장 뒤 비움). 로그는 들어오는 요청의 `authorization`·`x-*-secret` 헤더와 밖으로 나가는 요청의 `Authorization: Bearer`, 토큰 폼 본문을 가린다. `call_log.url_masked`는 `ck_call_log_no_secret`를 통과해야 한다. 오류 `message`·`details`에 비밀값이 없다. (F-BS-25, NFR-02, ERD `call_log`, 05-1 §1.5)
6. 토큰 요청 규격: `POST {base}/v1/oauth2/token`, `Content-Type: application/x-www-form-urlencoded`. 폼 필드는 정확히 `client_id`, `timestamp`(13자리 ms), `grant_type=client_credentials`, `client_secret_sign`, `type=SELF` 다섯 개다. `account_id`는 넣지 않고 JSON 본문을 쓰지 않는다. 어기면 내 스토어 앱 호출이 시간당 1회로 제한되므로 단위 테스트로 고정한다. 기본 base는 `https://api.commerce.naver.com/external`. (F-BS-46, PRD §8.7 RG-01, R04 A4·A13)
7. 서명: `client_secret_sign = Base64(bcrypt(client_id + "_" + timestamp, salt = client_secret))`. `client_secret` 자체가 bcrypt salt다. `timestamp`는 서명하는 순간의 현재 시각이고 5분만 유효하니 재사용하지 않는다. (F-BS-46, PRD §8.7, R04 A5·A6)
8. 토큰 캐시: 유효 3시간(`expires_in` 10800초). 쓰기 전에 남은 시간이 30분 미만이면 새로 받는다(예: 14:00 발급 → 16:30부터 재발급, 만료 17:00). 커머스API가 401 `GW.AUTHN`을 주면 토큰을 다시 받아 원래 요청을 다시 보낸다(재시도 횟수는 문서에 없음 → Proposed 1회). 토큰은 BE 메모리에만 두고 DB·파일·로그에 쓰지 않는다. (F-BS-47, PRD §8.7, R04 A7, 05-2 `CommerceAuthStatus.tokenValid`)
9. `COMMERCE_CLIENT_ID`·`COMMERCE_CLIENT_SECRET`를 PUT하면 토큰 캐시를 바로 비운다(`tokenValid=false`). (05-2 saveSecret)
10. `POST /auth-checks`: 캐시와 상관없이 토큰 발급을 한 번 동기로 부르고 200 `CommerceAuthStatus`를 준다. 커머스 키가 하나라도 없으면 409 `SECRET_NOT_CONFIGURED`, 키체인 오류는 503 `KEYCHAIN_UNAVAILABLE`, 발급 거절은 502 `COMMERCE_AUTH_FAILED`(`details.causeCategory`), 응답 없음·연결 오류는 502 `EXTERNAL_API_ERROR`(`details.target`·`reason`·`traceId`). 5xx를 어느 쪽으로 볼지는 문서에 없음 → Proposed. (05-1 §2.14, 05-2 createAuthCheck, 05-3)
11. 원인 분류 `causeCategory`: `DORMANT_AUTH`·`SECRET_CHANGED`·`STORE_SUSPENDED`·`IP_NOT_ALLOWED`·`UNKNOWN`. 403 `GW.IP_NOT_ALLOWED`는 `IP_NOT_ALLOWED`다. 나머지 세 원인을 가르는 커머스API 오류 코드는 문서에 없음 → 구현 때 Proposed 매핑표를 만들고 기록한다. 모르면 `UNKNOWN`. 분류 근거는 `call_log.error_code`다. (F-SY-02, US-27 AC2, R04 A8, 05-2 getAuthStatus)
12. 재발급까지 실패하면(401 뒤 재발급 실패, `POST /auth-checks` 실패 모두) SSE `auth.failed` `{ target: "COMMERCE_API", errorCode, causeCategory, occurredAt }`를 보낸다. (05-1 §3, 05-2 createAuthCheck)
13. 토큰 호출은 모두 P1-01 외부 호출 관문을 지나 `call_log` 1행(`target=COMMERCE_API`, `http_status`, `error_code`, `trace_id`=`GNCP-GW-Trace-ID`)을 남긴다. `GET /auth-status`는 토큰 값 없이 이 기록과 메모리 캐시로 `secretsConfigured`·`tokenValid`·`tokenExpiresAt`·`lastCheckedAt`·`lastSucceeded`·`lastHttpStatus`·`lastErrorCode`·`causeCategory`(성공이거나 기록이 없으면 `null`)·`lastTraceId`를 채운다. (05-2 `CommerceAuthStatus`, ERD `call_log`)
14. 화면: '키 입력' 패널은 키마다 '키체인에 저장됨' 칩과 '다시 넣기'를 보여 준다. '인증 상태' 패널은 토큰 상태·발급 시각·재발급 시각('14:00 발급 · 16:30에 새로 받음')과 원인 네 가지 안내를 보여 주고, '시크릿 변경'의 'client_secret 다시 넣기'는 키 입력 행으로 이어진다. 다른 화면의 커머스API 인증 실패 안내도 `/system` 키 입력으로 잇는다. (F-SY-01, F-SY-02, US-27 AC1·AC2, System.dc.html)

## 8. 주의

- 공통 규칙은 [README §공통 규칙](../README.md#공통-규칙)을 따른다(실행 환경, 외부 호출 금지, 비밀정보, 커밋 안 함).
- 커머스API 실제 호출 금지. 서명(bcrypt)·토큰 캐시는 고정 벡터와 가짜 서버로 검증한다.

- 커머스API `llms.txt`의 curl 예시(JSON Content-Type 등)는 틀렸다. 요청·응답 표만 믿는다(PRD §8.7). 폼 인코딩·`account_id` 규격 테스트는 시간당 1회 제재를 막는 장치이니 지우거나 느슨하게 하지 않는다.
- `bcryptjs`로 `hashSync(password, salt)` 형태를 쓴다. `client_secret`이 salt다. rounds 숫자를 넘겨 새 salt를 만들면 서명이 틀린다.
- `@napi-rs/keyring`은 네이티브 모듈이다. ESM import와 darwin-arm64 바이너리 설치를 확인한다. 처음 쓸 때 macOS가 키체인 접근을 물을 수 있다. 자동 테스트는 실제 키체인을 건드리지 않는다(DI로 메모리 저장소).
- 실제 커머스API 호출 금지. 앱 등록(PRD §0 5번)·S3 전이라 가짜 transport로만 검증한다. 실제 연결 확인은 오너가 키를 넣고 SCR-11에서 직접 한 번 한다. fixture의 토큰·salt는 가짜임이 드러나게 만들어 secretlint에 걸리지 않게 한다.
- 토큰 보관 위치가 문서끼리 다르다: 05-1 §1.2는 '토큰도 키체인에만', 05-2 `CommerceAuthStatus`는 '메모리 캐시'. 메모리로 만들고 Proposed로 기록한다. BE를 다시 켜면 첫 호출 때 새로 받는다.
- `SecretStore`·`CommerceApiClient`·`CommerceTokenService`는 P1-08·P2-02·P2-04·P4-01·P4-03이 그대로 쓴다. 이름·시그니처를 바꾸면 그 문서가 깨진다. 토큰 값을 꺼내는 함수는 export하지 않는다.
- SCR-11은 P1-08(메타 동기화)·P1-11(AI 도구 상태·첫 실행 점검)과 같이 쓴다. 페이지 틀과 열만 만들고 패널은 부품으로 나눠, 뒤 작업이 패널만 끼우게 한다.
- F-SY-01의 '터미널 명령' 입력을 만들 경우 값을 명령 인자로 받지 않는다(셸 기록에 남는다). 가려진 표준 입력으로 받는다 — 문서에 없음 → Proposed.
