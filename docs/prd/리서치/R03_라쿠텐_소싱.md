## 1. 요약

1. 라쿠텐 상품 검색은 **Rakuten Web Service "Ichiba Item Search API" `20260701` 버전**을 써야 한다. 엔드포인트는 `https://openapi.rakuten.co.jp/ichibams/api/IchibaItem/Search/20260701`이고 `applicationId`와 `accessKey`가 **둘 다** 필수다. 2026-02 신규 플랫폼 이전 후 Referer/Origin 검사(웹앱형) 또는 IP 허용 목록(백엔드형)이 추가됐다. 구 도메인 `app.rakuten.co.jp`는 2026-05-14에 완전히 중단됐다. 요청 한도는 약 1초당 1회이고, 실무 권장 간격은 1.5초 이상이다. ⚠️정정됨(검증 결과 참조)
2. `sort=+itemPrice&hits=20&availability=1`로 "가격 낮은순 20개·재고 있음"은 한 번에 받을 수 있다. 다만 API가 주는 것은 **상품 단위 재고(0/1)와 포인트 배율(`pointRate`)뿐**이다. **쿠폰, 사이즈별 재고, 실제 송료 금액, JAN**은 API에 없다.
3. 사이즈별 재고·SKU 가격·JAN·원산지·소재·굽높이는 **상품 페이지 HTML에 들어 있는 JSON `<script id="item-page-app-data">`**에 구조화돼 있다([직접검증]). 경로는 `newApi.itemInfoSku.sku[]`, `purchaseInfo.variantMappedInventories[].quantity`, `sku[].articleNumber`, `sku[].attributes[]`다. 쿠폰은 페이지 로드 뒤 JS가 내부 API(`api.coupon.rakuten.co.jp`)로 따로 불러온다. 게다가 로그인 획득형·타깃형(개인별) 쿠폰이 있어서 **자동으로 정확히 구하기 어렵다**.
4. **규약 리스크가 크다.** Rakuten Web Service 규약 제10조가 금지하는 행위 중에 (4) 어필리에이트 외 수익화, (7) 상품정보(이미지·설명 포함)의 목적 외 사용·복제·개변, (10) "특정인만 접근 가능한 환경에서의 사용"이 있다. 1인 로컬 소싱·재판매 도구는 이 조항들과 정면으로 부딪힐 소지가 있다. 검색결과 페이지(`search.rakuten.co.jp`)는 robots.txt가 정렬 파라미터 `s=`를 Disallow하고, Akamai 봇 차단도 관찰됐다.
5. 해외 직배송은 사실상 기대하기 어렵다. Rakuten Global Market은 2020-06-01에 종료됐고, 국제배송 여부는 샵마다 다르다. **배대지(전송 서비스)가 전제**가 된다. 라쿠텐은 "타 몰 판매자가 타 몰 주문자 정보로 라쿠텐에서 구매·배송시키는 행위"를 **なりすまし(사칭)로 금지**하고, 자동 주문도 금지한다. 따라서 **구매는 오너 본인 명의로, 수동으로** 해야 한다.

**"실질가 = 가격 + 送料 − 포인트 − 쿠폰" 계산 시 주의점**

1. 포인트는 **세금 제외·쿠폰 적용 후 금액** 기준이다. 세금 포함 가격에 배율을 곱하면 과대계상된다. 식은 `floor((税込価格 − 쿠폰)/1.1 × 배율%)`이고, 단수 처리는 [미확인]이다. ⚠️정정됨(검증 결과 참조)
2. 포인트는 현금이 아니다. 기간 한정이고, 다음 달 15일쯤 지급되며, 라쿠텐 안에서만 쓸 수 있다. 재판매 원가에서 얼마로 볼지 **환산계수 k(0~1)**를 오너가 정해야 한다.
3. SPU 배율은 **오너 계정 상태**에 달려 있어 상품마다 다르지 않다. 설정값(상수)으로 입력받는다.
4. 쿠폰은 로그인·획득·선착순·타깃·최소 금액 조건이 있어 "보이는 쿠폰 = 내가 쓸 수 있는 쿠폰"이 아니다. 자동 반영은 오차 위험이 크다.
5. 송료는 배송지(배대지가 있는 도도부현)에 따라 다르다. 39ショップ는 税込 3,980엔 이상이면 무료지만, 오키나와·이도·일부 지역은 9,800엔 이상이어야 한다([S30]). API는 `postageFlag`만 주고, 페이지 JSON의 `sku[].shipping`에는 `postageIncluded`, `singleItemShipping`, `postageSegment` 같은 값이 있다[직접검증]. 실제 금액은 내부 `shippingCalculation` API로 계산된다[번들].

`https://item.rakuten.co.jp/newbalance-store/ml574evg/`(EUC-JP 인코딩)의 `<script type="application/json" id="item-page-app-data">`를 파싱해 확인했다.

- 라쿠텐 SKU 프로젝트(2023-04~)로 SKU별 가격·재고·속성 입력이 가능해졌고, 브랜드명 등 **商品属性 입력이 필수**가 됐다([S31]). 이것이 JSON에 구조화된 속성이 있는 배경이다.

### 2.5 "가격 낮은순 20개"의 함정

1. SKU 상품은 SKU마다 가격이 다를 수 있다([S31]). `sort=+itemPrice`의 기준가가 **품절 사이즈의 할인가**일 수 있다. API `itemPriceMin3`(Purchasable)를 병행해 보고, 최종 판정은 목표 사이즈 SKU 가격으로 해야 한다.
2. 키워드만으로 가격 오름차순을 하면 **신발끈·인솔·키즈·중고·박스만** 같은 저가 비대상이 상위를 채운다. `genreId`, `minPrice`, `NGKeyword`로 막아야 한다.
3. `hits` 최대치는 30이다. 20개 비교는 1회 호출(`hits=20`)로 끝나지만, 동일 모델 필터 뒤에 20개를 채우려면 30개를 받아 거르거나 2페이지까지 봐야 한다.

### 누락 주제 (PRD 반영 필요)

1. **API와 사이트 결과가 다를 수 있다**: 오너가 말한 "최저가 낮은순"은 사이트 기준일 가능성이 크다. 사이트에는 `安い順(価格＋送料)`(`s=11`)이 있지만 API는 `+itemPrice`(송료 제외)만 있다. 그래서 API 상위 20개와 오너가 브라우저에서 보는 상위 20개가 다를 수 있다. 어느 쪽을 기준으로 할지 정하고, UI에 명시해야 한다.
2. **샵 전체 포인트 배율과 몰 이벤트 배율이 빠져 있다**: API `pointRate`는 상품별 배율만 준다. ショップ別ポイント倍付け, お買い物マラソン·楽天スーパーSALE 買いまわり, 5と0のつく日 같은 이벤트 배율은 API로 얻을 수 없다. 실질가 계산에서 이들을 "수동 입력/설정값"으로 받을지 정해야 한다.
3. **기간한정 포인트 만료(付与月の翌月末)**: 재판매 원가에 넣을 환산계수 k의 근거로 써야 하고, 포인트를 쓸 계획(재구매 주기)과 연결해야 한다.
4. **타임세일 가격의 유효기간**: API 응답의 `startTime`/`endTime`(タイムセール)을 쓰지 않았다. 세일가를 기준으로 판매가를 정하면, 세일이 끝난 뒤 역마진이 날 위험이 있다.
5. **429·503 처리**: 게이트웨이 429 본문 형식이 문서와 다르다. 전체 사용자 한도 초과(503)도 있다. 상태 코드로 판정하고 `Retry-After`나 메시지의 초 수를 따르는 백오프가 필요하다.
6. **`variantMappedInventories`와 `sku[]` 개수 불일치**: 고아 재고 행이 있다. variantId로 조인하고, `stockCondition`(sold-out/almost-out)은 조건부 키로 다뤄야 한다.
7. **`purchaseType=0`(通常購入) 고정과 `carrier=0` 지정**: 定期購入·頒布会 상품이 섞이지 않게 하고, `itemCaption`이 PC용으로 오게 해야 한다.
8. **앱 만료·재등록 운영 절차**: 1년 유효는 공식 발표가 없다. 대시보드의 만료일을 오너가 입력해 알림을 받는 방식이 안전하다.
9. **구 도메인 잔존 응답**: `app.rakuten.co.jp`가 400으로 응답하므로, 오래된 예제 코드를 가져다 쓰면 "연결은 되는데 키가 틀렸다"는 오진을 할 수 있다. 신규 도메인을 강제해야 한다.
