- 작성일: 2026-09-24
- 대상 요구(원천자료 01): "네이버 데이터랩에서 기간 최근 1개월로 설정하여 패젼잡화 -> 신발쪽만 수집"
- 조사 방법: 공식 문서·공지·약관 1차 출처 확인 + 데이터랩 웹 UI의 프런트엔드 번들 분석 + **조회성 요청 직접 검증**(2026-09-24 07:48~08:10 KST, 로그인 없음, 요청 간격 1.5~2.5초, 총 약 38회: `getCategory.naver` 22회, `getCategoryKeywordRank.naver` 16회)

## 1. 요약

1. 인기검색어 **순위(TOP 500)**는 공식 Open API로는 받을 수 없다. 공식 쇼핑인사이트 API 8종은 모두 **클릭량 상대비율(ratio)**만 반환한다. 순위는 웹 UI 내부 엔드포인트 `POST datalab.naver.com/shoppingInsight/getCategoryKeywordRank.naver`로만 얻을 수 있다. 이 엔드포인트는 2026-09-24 현재 동작하며, 한 번 호출에 20개, cid 하나당 최대 500개를 준다. Referer 헤더가 없으면 404를 반환한다.
2. 패션잡화(50000001) 아래에는 단일 "신발" 노드가 **없다**. 수집 대상은 **여성신발(50000173)·남성신발(50000174)**(+선택 사항으로 신발용품 50000175)이며, 콤마로 여러 cid를 묶어 보내도 합산되지 않는다(첫 cid 결과만 나오는 것으로 관찰). ⚠️정정됨(검증 결과 참조) 그래서 cid마다 따로 호출한 뒤 결과를 합쳐야 한다.
3. **네이버 쇼핑 검색 API(`/v1/search/shop.json`)는 2026-07-31에 종료**되었다. 기존 키로도 호출할 수 없고, NAVER API HUB를 포함해 대체 API도 없다. "키워드 → 국내 최저가" 단계는 네이버 공식 API로 자동화할 수 없다.
4. 쇼핑인사이트 API는 NCP **NAVER API HUB**로 옮겨졌다(개발자센터 신규 신청은 2026-07-31 차단, 기존 키는 2027-06-30까지). HUB 한도는 월 50,000건, 50 RPS이며 현재 한시 무료다. 검색 API 약관(2026-09-07 개정)은 **데이터를 AI에 입력하는 행위와 저장·캐싱을 금지**한다.
5. 웹 UI 내부 엔드포인트를 자동으로 호출하는 방식은 robots.txt(`Disallow: /`)와 네이버 이용약관의 "사전 허락 없는 자동화 수단" 조항에 걸릴 소지가 있다. 오너가 저빈도 자동 호출, 반자동, 수동 붙여넣기 중 하나를 골라야 한다(질문 Q1).

### 2.4 공식 Open API "데이터랩 쇼핑인사이트" — 반환값과 한도

| 엔드포인트 (개발자센터, POST, JSON 바디) | 용도 | 출처 |
|---|---|---|
| `https://openapi.naver.com/v1/datalab/shopping/categories` | 분야별 클릭 추이. `category`는 {name, param[]} 쌍 **최대 3개** | [S1] |
| `/v1/datalab/shopping/category/device` · `/gender` · `/age` | 분야 안의 기기·성별·연령별 추이 (`category` 단일 문자열) | [S1] |
| `/v1/datalab/shopping/category/keywords` | 분야 안의 키워드별 추이. `keyword`는 {name, param[]} **최대 5쌍**, `param`은 **1개만** | [S1] |
| `/v1/datalab/shopping/category/keyword/device` · `/gender` · `/age` | 키워드 하나의 기기·성별·연령별 추이 | [S1] |

- 공통 파라미터: `startDate`(yyyy-mm-dd, **2017-08-01부터**), `endDate`, `timeUnit`(date/week/month), `device`(pc/mo), `gender`(m/f), `ages`(["10".."60"]) [S1]
- **응답**: `startDate, endDate, timeUnit, results[].title, results[].category|keyword, results[].data[].period, results[].data[].ratio`(+`group`). `ratio`는 "구간별 결과에서 가장 큰 값을 100으로 설정한 상댓값"이다. 즉 **절대 클릭 수도, 인기검색어 순위도 제공하지 않는다**. 순위를 주는 엔드포인트는 목록에 없다 [S1].
- 한도: 개발자센터는 "하루 호출 한도 1,000회" [S1]. HUB는 **Data Lab API마다 월 최대 50,000건, API 키당 최대 50 RPS, 초과하면 429** [S7][S10].
- HUB 엔드포인트 예: `POST https://naverapihub.apigw.ntruss.com/shopping/v1/category/keywords`, 헤더 `X-NCP-APIGW-API-KEY-ID`, `X-NCP-APIGW-API-KEY` [S8][S9]. 파라미터와 제약(최대 5쌍, param 1개, 2017-08-01~)은 개발자센터와 같다 [S9]. 다른 경로(`/shopping/v1/categories` 등)도 같은 규칙일 것으로 보이나 [미확인].
- 오류: 400/401/403/404/405, **429(일일 한도 초과, 검색 API는 초당 한도 초과)**, 500. 본문은 `{errorMessage, errorCode}` [S3].
- 활용 가치: 키워드를 **발굴**하는 데는 쓸 수 없다. 이미 확보한 후보 키워드끼리 **상대 추세(상승·하락)를 비교해 보강**하는 용도로 쓸 수 있다. 5개를 넘는 키워드를 비교하려면 각 호출에 **기준(anchor) 키워드를 하나씩 넣어 정규화**해야 한다(설계 제안이며 공식 문서에 적힌 방법은 아님).

### 누락 주제 (PRD 반영 검토 필요)

1. **네이버 "검색결과 수집에 대한 정책"**: robots.txt로 보호되는 DB를 무시하고 계속 수집하면 법적 조치를 하겠다고 명시돼 있다. 리스크 표(robots·약관 리스크)와 Q1의 판단 근거에 추가해야 한다.
2. **약관의 역설계·소스코드 추출 금지 조항**: 프런트 번들을 분석해 내부 엔드포인트를 알아내는 개발 방식 자체가 이 조항에 걸릴 수 있다.
3. **NAVER API HUB(NCP) 자체 약관과 데이터 이용 조건**: 저장·캐싱·AI 입력 제한이 있는지 확인하지 못했다. 부칙 ④에 따르면 HUB에는 별도 약관이 적용된다.
4. **HUB 오류 응답 형식**: 개발자센터와 다르다. Gateway 오류는 `{error:{errorCode,message,details}}`, Shopping Insight 오류는 `{errMsg, errId, body}`다. 한도 관리 단위(월 단위 vs "하루 허용량 초과")를 두고 문서끼리 표현이 다르다. R01-NFR-02와 R01-C-04에 반영해야 한다.
5. **복수 cid의 서버 동작**: 순서와 관계없이 가장 작은 cid의 결과만 오는 것으로 관찰됐다. 오류 없이 결과가 빠지므로, 단일 cid 입력을 강제하는 검증이 필요하다.
6. **timeUnit에 따른 "1개월" 기간 차이**: week/month를 고르면 기간이 달라진다. R01-FR-02는 `timeUnit=date` 고정을 명시하거나 week/month 선택을 금지해야 한다.
7. **절대 수요량 지표 부재**: 순위와 ratio만으로는 검색량 규모를 알 수 없다. 네이버 검색광고 API(키워드 도구의 월간 검색수)처럼 공식 절대량 지표를 쓸 수 있는지 조사하지 않았다(미검증).
8. **국내 법령상 수집 리스크**: 부정경쟁방지법의 데이터 부정사용 조항, 저작권법의 데이터베이스제작자 권리, 정보통신망법 등을 법률 검토 항목으로 두어야 한다(이번 검증 범위 밖, 미검증).
