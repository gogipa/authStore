## 한눈에 보기

- **모든 경로는 `/api/v1`로 시작한다.** 로그인은 없다(로컬 1인, GEN-01). 대신 상태를 바꾸는 요청은 `X-AutoStore-Client: 1` 헤더와 앱 자신의 `Origin`이 있어야 받는다.
- **후보 한 건이 중심이다.** 단계 실행은 `POST /candidates/{candidateId}/steps/{stepCode}/runs` 하나로 ②~⑧을 모두 돌린다. 202와 실행 기록 id를 돌려주고, 진행은 SSE(`GET /events`)로 알린다.
- **게이트.** G2·G3은 `POST /candidates/{candidateId}/gates/{gateCode}/pass`, 최종 승인(G4)은 등록 기록을 만드는 `POST /candidates/{candidateId}/registrations`(Idempotency-Key 필수)다.
- **막힌 이유는 도메인 오류 코드로 준다.** 409·422와 코드(§5)를 돌려주고, 단계 레일의 '꺼진 이유'도 같은 코드를 쓴다.
- **비밀정보는 어떤 응답에도 없다.** 키 입력 API는 값을 받기만 하고 204를 돌려준다.
- **AI 엔진은 사용자가 고른다(D-16).** 텍스트·비전 작업은 설정의 선택 엔진(Claude Code `CLAUDE` · Antigravity CLI `AGY` · Codex `CODEX`) 하나로 돈다. 엔진·모델은 `GET·PUT /settings/ai-engine`, 설치·로그인·연결 테스트는 `/ai-cli-checks`다. 10분 안에 연결 테스트를 통과해야 저장되고(409 `AI_ENGINE_NOT_VERIFIED`), 선택 엔진을 쓸 수 없으면 AI 단계 시작을 409 `AI_ENGINE_UNAVAILABLE`로 막는다(다른 엔진으로 넘어가지 않는다). 실행 기록마다 `aiEngine`·`aiModel`·`aiCliVersion`이 남는다.
- **정해지지 않은 것은 지어내지 않았다.** §7에 ⚠️로 남겼다.

### 1.2 로컬 보안 (03-2 §5)

| 검사 | 대상 | 막으면 |
|---|---|---|
| `Host`가 `127.0.0.1:포트`·`localhost:포트` | 모든 요청(SSE 포함) | 403 `HOST_NOT_ALLOWED` |
| `Origin`이 앱 자신 | POST·PUT·PATCH·DELETE | 403 `ORIGIN_NOT_ALLOWED` |
| `X-AutoStore-Client: 1` | POST·PUT·PATCH·DELETE | 403 `CLIENT_HEADER_REQUIRED` |
| CORS | 열지 않는다 | — |

- **인증·권한 열이 없다.** 설치 사용자 1명이 이 PC에서만 쓴다(GEN-01). 위 세 검사가 인증을 대신한다.
- **비밀정보**: API 키·토큰·쿠키는 macOS 키체인에만 둔다. 어떤 응답·오류 `message`·SSE 데이터에도 넣지 않는다. `PUT /secrets/{secretKey}`는 204만 돌려주고, 요청 본문은 로그·`call_log`·`user_action_log`에 남기지 않는다(키 이름만).
  - P1-07(Proposed, 2026-09-30 — 오너 검토): 커머스API **토큰은 키체인이 아니라 BE 메모리에만** 둔다(05-2 `CommerceAuthStatus` '메모리 캐시'를 따름). DB·파일·로그에는 쓰지 않고, BE를 다시 켜면 첫 호출 때 새로 받는다. 키 입력은 `user_action_log`(`SETTING_CHANGED`, `detail = { secretKey }`)에 키 이름만 남긴다. 로그·오류 응답·SSE·`call_log`에서는 키체인에서 읽거나 쓴 값과 받은 토큰을 값으로도 지운다(`***`, 06-2 §9-32).
- **로컬 경로를 내보내지 않는다**: `image_asset.file_path`, `install_info.data_dir_path`는 응답에서 뺀다. 이미지는 `GET /image-assets/{imageAssetId}/file`로 받는다. 예외: `ai_cli_check.bin_path`(AI CLI 실행 파일 위치)는 AI 엔진 페이지가 보여 줘야 해서 `GET /ai-cli-checks/latest`의 `binPath`로 준다(D-16 R5). CLI 로그인 정보·토큰 파일은 읽지도 주지도 않는다(CON-11).
- **웹 화면 전용 기록**(F-CW-28, F-AP-10, F-SO-06, F-TH-05, F-PJ-02, F-CA-08): 아래 요청은 오너가 웹 화면에서 누른 것만 기록한다. M1은 위 가드로 웹 요청만 받는다. M3 CLI(F-CW-27)가 생기면 구분 방법이 필요하다(⚠️ §7.1).

| 기록 | 엔드포인트 |
|---|---|
| G2·G3 통과, '같은 상품·색상' 확인 | `POST /candidates/{candidateId}/gates/{gateCode}/pass` |
| G4 최종 승인·등록 | `POST /candidates/{candidateId}/registrations` |

### 1.3 오래 걸리는 작업: 202 + SSE

- 오래 걸리는 작업은 **202 Accepted**와 `Location`(진행 조회 경로), 본문에 실행 기록 id를 돌려준다. 진행·완료는 SSE(`GET /events`, `text/event-stream`)로 알리고, 같은 내용을 조회 API로 다시 읽을 수 있다.
- SSE 이벤트는 '무엇이 바뀌었는지'만 알린다. FE는 이벤트를 받으면 조회 API로 다시 읽는다(재연결 때 놓친 이벤트 대비). 재전송 버퍼 여부는 ⚠️ §7.1.
- 비동기 작업 도중의 외부 실패는 HTTP 오류가 아니다. 실행 기록(`step_run.status=FAILED`, `failureKind=EXTERNAL_API`, `errorCode`, 한국어 `errorMessage`)과 SSE로 알린다. 시작 전에 알 수 있는 것(하루 상한, 24시간 쉼, 키 없음, 선택 AI 엔진을 쓸 수 없음)만 409로 막는다. 실행 중 AI 엔진 실패는 `errorCode=AI_ENGINE_UNAVAILABLE`로 남는다(D-16 R10).

### 1.5 오류 응답

```json
{
  "code": "STEP_START_CONDITION_UNMET",
  "message": "시작에 필요한 값이 없습니다: 국내 기준가.",
  "status": 409,
  "timestamp": "2026-09-27T14:02:11+09:00",
  "path": "/api/v1/candidates/12/steps/PRICING/runs",
  "fieldErrors": [{ "field": "owner.domesticPrice", "reason": "MISSING" }],
  "details": { "stepCode": "PRICING" }
}
```

- `code`: 대문자 스네이크 도메인 코드(§5). `message`: 한국어, 셀러가 아는 말. 비밀정보를 넣지 않는다.
- `fieldErrors[]`: `{ field, reason, rejectedValue? }`. 값 검증(422)과 빠진 입력(409 `STEP_START_CONDITION_UNMET`)에 쓴다.
- `details`(선택, **규약 확장 제안 ⚠️ §7.1**): 코드별 추가 정보. 예: `blockedUntil`·`target`(24시간 쉼), `existingCandidateId`(중복 후보), `missingFields[]`(프로필 빈칸), `checks[]`(사전 검증), `stepCode`·`gate`·`job`.
- 24시간 쉼·하루 상한(409)에는 `Retry-After` 헤더도 붙인다.
- **409와 422 가르기**: 요청 값은 맞지만 지금 상태에서 할 수 없으면 409(상태가 바뀌면 같은 요청이 통과한다). 요청 값 자체가 규칙에 맞지 않으면 422(값을 고쳐야 한다). 본문 체크 항목이 빠진 것(`CHECKLIST_INCOMPLETE`)은 422, 앞서 해야 할 확인 동작을 안 한 것(`ADULT_CONFIRMATION_REQUIRED`)은 409다.
- **경고(막지 않음)**: 성공 응답에 `warnings[{ code, message }]`로 준다(§5.2). 예: G2 전 AI 비용 경고(F-CW-17).

### 1.6 상태 코드 매핑

| 코드 | 쓰는 때 | 예 |
|---|---|---|
| 200 | 조회, 동기 처리·상태 전이 결과, 같은 내용 재요청을 기존 기록으로 돌려줄 때 | 모든 GET, PUT, `POST …/exclude`, 같은 파일 다시 올리기 |

| 202 | 오래 걸리는 작업을 받았을 때(`Location` = 진행 조회) | 단계 실행, 연속 실행, 키워드 버튼 수집, G4 승인 |
| 204 | 삭제, 돌려줄 값이 없는 성공 | DELETE, `PUT /secrets/{secretKey}`, 이어 할 곳 없음 |
| 400 | 요청을 읽을 수 없음, 필수 헤더 없음 | `MALFORMED_REQUEST`, `IDEMPOTENCY_KEY_REQUIRED` |
| 403 | 로컬 보안 가드 | `HOST_NOT_ALLOWED`, `ORIGIN_NOT_ALLOWED`, `CLIENT_HEADER_REQUIRED` |
| 404 | 대상 없음(경로·본문의 id) | `CANDIDATE_NOT_FOUND`, `STEP_OUTPUT_NOT_FOUND` |
| 409 | 충돌·상태 위반·막힌 이유 | `STEP_START_CONDITION_UNMET`, `GATE_NOT_PASSED`, `DAILY_LIMIT_REACHED`, `EXTERNAL_CALL_COOLDOWN` |
| 413 ⚠️ | 파일·본문이 너무 큼 | `PAYLOAD_TOO_LARGE` |

## 2. 엔드포인트 표

- 모듈은 C4 §3의 모듈 하나로 정했다. 한 모듈의 표 안에서는 M1을 먼저 적었다. M1 엔드포인트가 M2 필드를 함께 받으면 기능 ID에 '(M2)'를 붙였다.
- 열: **비동기** = 동기 / 202 / 스트림. **멱등성**은 §1.7 규칙. **기능 ID**는 [04 기능 리스트](../../prd/04_기능리스트.md). **근거**는 ERD 테이블·인덱스·규칙과 설계 이유 한 줄.
- 요청·응답 필드 전체는 05-2 OpenAPI에서 ERD 컬럼으로 파생한다. 여기에는 판단에 필요한 것만 적었다.

**표 E. G4 최종 승인·등록** — `POST /candidates/{candidateId}/registrations`

- 헤더: `Idempotency-Key`(UUID, 필수), `X-AutoStore-Client: 1`. body: `{ optionType: COMBINATION·STANDARD, expectedUploadResultId, expectedPriceJudgementId }`(expected*는 화면이 본 버전 확인용, 저장하지 않는다).
- 흐름: 승인 직전 사전 검증을 다시 돌린다 → 차단 스위치 켬이면 등록 기록 VALIDATED(드라이런)로 끝 / 끔이면 REGISTERING을 먼저 커밋 → 커머스API 등록(트랜잭션 밖) → REGISTERED·RESULT_CHECK_REQUIRED·4xx 종결(`failed_at`·`failure_kind`). 승인 행위는 `user_action_log`(GATE_PASSED, G4).
- 응답: 202 `Location: /registrations/{id}` `{ registrationId, stepRunId, candidateId, status: VALIDATED·REGISTERING, sellerManagementCode, displayStatusType, approvedAt }`. 같은 키 재요청은 첫 응답.
- 오류: 404 `CANDIDATE_NOT_FOUND`, 409 `CANDIDATE_STATUS_INVALID`(승인대기 아님), `GATE_NOT_PASSED`(G2·G3 무효), `DUPLICATE_REGISTRATION`, `REGISTRATION_IN_PROGRESS`, `VERSION_NOT_CURRENT`, `JUDGEMENT_EXPIRED`(M1은 막음, M2는 자동 재조회 F-AP-52), (M2) `TEMP_CANDIDATE_NOT_ALLOWED`, 422 `PRE_VALIDATION_FAILED`(`details.checks[]`), `IDEMPOTENCY_KEY_REUSED`, 400 `IDEMPOTENCY_KEY_REQUIRED`.
- 연속 실행·CLI·설정으로 이 승인을 대신할 수 없다(F-AP-10). 이 경로 말고 ⑨를 돌리는 길은 없다.

**P1-09 구매대행 프로필 구현 결정(Proposed, 2026-09-30 — 오너 검토)**

- **반품 택배사 id 오류**: 동기화 목록(`commerce_return_delivery_company`)에 없거나 `removed_at`이 있으면 404 `RETURN_DELIVERY_COMPANY_NOT_FOUND`('반품 택배사를 찾을 수 없습니다. 동기화한 목록에서 다시 골라 주세요.'). 주소록(404 `ADDRESSBOOK_NOT_FOUND`)과 같게 404로 두었다(§5.1·05-3에 더함).
- **검사 순서**: 본문 형식(422 `VALIDATION_FAILED`) → 칸 순서대로 해외 출고지(404·422 `ADDRESS_NOT_OVERSEAS`) → 반품·교환지(404) → 발송 택배사(현재 설정 스냅샷 목록 밖 422 `DELIVERY_COMPANY_NOT_ALLOWED`, 스냅샷이 없으면 503 `SETTINGS_INVALID`) → 반품 택배사(404). 도메인 오류도 `fieldErrors[0].field`에 그 칸을 담는다. null 칸은 검사하지 않는다(빈칸이 있어도 저장).
- **`missingFields` 전체 목록**: nullable 칸 10개 — `overseasShippingCommerceAddressbookId`, `returnCommerceAddressbookId`, `dispatchDeliveryCompanyCode`, `commerceReturnDeliveryCompanyId`, `returnFeeKrw`, `exchangeFeeKrw`, `businessName`, `afterServicePhone`, `afterServiceGuide`, `importer`(이 순서). ⑥-3 시작 검사(409 `PROFILE_INCOMPLETE`, P3-04)는 이 가운데 상호·A/S 연락처·A/S 안내·수입자만 본다(`NOTICE_HTML_REQUIRED_PROFILE_FIELDS`). G4 사전 검증(P4-02)은 `missingFields` 전체를 쓸 수 있다.
- **빈 문자열**: 저장할 때 글 칸(상호·A/S 연락처·A/S 안내·수입자·발송 택배사 코드)의 앞뒤 공백을 지우고, 비면 null로 저장한다. 그래서 빈 문자열은 빈칸으로 `missingFields`에 들어간다. `noticeFixedTexts`의 빈 문구는 키째 뺀다.
- **같은 값**: 정리한 값이 현재 행(없으면 빈 기본값)과 같으면 아무것도 쓰지 않는다(행·`updated_at`·전파·감사 기록 없음, 200 + `rerunRequiredStepCount=0`). 빈 기본값을 그대로 보내면 행도 만들지 않는다.
- **트랜잭션**: upsert(`singleton_key=1`) + 재실행 필요 전파 + `user_action_log`(`SETTING_CHANGED`, detail `{ setting: 'PURCHASE_AGENCY_PROFILE', changedKeys: [...] }` — 값 없음)를 한 트랜잭션으로 한다. 전파 SSE(`candidate-step.changed`)는 커밋 뒤에 보낸다. 저장은 프로세스 안에서 한 번에 하나씩 돈다.
- **전파 입력 이름**: 단계가 프로필을 읽으면 `step_run_input`에 `profile.<필드>`(예 `profile.importer`, `source_type=SETTINGS`, 시작 조건)를 남긴다(`profileStepInputs(stepCode, values)`, settings/purchase-agency-profile/profile-input-keys.ts). 저장은 값이 바뀐 키만 이 이름으로 넘기고, step-engine(`PropagationService.onProfileChanged`)이 현재 버전에 그 이름이 있는 단계만 재실행 필요로 둔다(잠긴 후보 건너뜀, 승인대기·검증완료 후보는 작업중으로 — 설정 변경 전파와 같은 규칙). ⑥-3은 상호·반품비·교환비·주문당 수량·A/S·수입자·고시 문구를, ⑨는 주소록·택배사·반품비·교환비·A/S·수입자·주문당 수량을 읽는다. **⑧ UPLOAD는 프로필을 직접 읽지 않는다**(P4-01 시작 조건은 ⑤ G3 선택본·⑥-3 HTML) — 프로필이 바뀌면 ⑥-3이 재실행 필요가 되고, ⑥-3을 다시 돌려 HTML이 바뀌면 ⑧이 재실행 필요가 된다(위 표 '⑥-3·⑧·⑨'의 ⑧).
- **발송 택배사 목록 설정 키**: `delivery.dispatchCompanies[{ code, name, source }]`(06-4 §2.2). 기본 템플릿은 빈 목록(출처가 있는 코드가 아직 없다, M0 S3). 코드는 영문·숫자·`_`·`-`·`.` 40자까지, 목록 안에서 겹치면 설정 검사 오류.
- **고시 고정 문구 키**: `noticeFixedTexts`의 키는 커머스API `SHOES` 고시 필드 이름이다. 설정 화면 '품질보증기준' 칸 = `warrantyPolicy`, '나머지 항목' 칸 = `returnCostReason`·`noRefundReason`·`qualityAssuranceStandard`·`compensationProcedure`·`troubleShootingContents`에 같은 문구. 비어 있는 키는 ⑥-3 기본 문구(F-CT-22)를 쓴다. 20개·키 영문 64자·문구 1000자까지.
- **⑨ 요청 조각**: `buildProfileFragment(profile, { shipping, return }, returnCompany)`가 `deliveryInfo`(DELIVERY·NORMAL·무료배송·`claimDeliveryInfo`의 **네이버 주소록 번호**(`address_book_no`, 숫자)·반품비·교환비·개인통관 false)·`customsTaxType=INCLUDED`·`minorPurchasable=true`·`afterServiceInfo`를 만든다. 필드 이름이 확인되지 않은 주문당 구매수량 제한·반품 택배사는 요청 본문에 넣지 않고 `unconfirmedFields`로 따로 준다(M0 S3 뒤 P4-03이 자리를 정한다).

**P1-11 AI 엔진 설정 구현 결정(Proposed, 2026-09-30 — 오너 검토)** — `GET·PUT /settings/ai-engine`

- **검사 순서(PUT)**: 본문 형식 422 `VALIDATION_FAILED`(정의 밖 필드·빠진 키) → 로드된 설정 없음 503 `SETTINGS_INVALID` → 모델 422 `AI_MODEL_INVALID` → 같은 값이면 200 + 현재 설정(새 스냅샷·SSE·파일 쓰기 없음) → 10분 조건 409 `AI_ENGINE_NOT_VERIFIED` → 파일 쓰기 → 스냅샷. 모델 검사를 10분 조건보다 먼저 한다(고칠 수 있는 오류를 먼저 알린다).
- **모델 검사**: CLAUDE `sonnet`·`opus`·`haiku`, AGY는 `modelOptions`와 같은 목록, CODEX는 공백 없는 1~100자. 선택 엔진의 텍스트·비전 모델이 null이면 422(두 칸 모두 `--model`에 쓴다), 다른 엔진의 null은 받는다. **현재 설정과 같은 값은 목록 검사를 건너뛴다** — `agy models` 목록이 바뀌거나 설정 파일에 목록 밖 값이 있어도 다른 엔진 저장이 막히지 않게. `fieldErrors`는 어긴 칸 모두, `message`는 첫 칸 문구.
- **AGY 모델 목록**: `agy models`(호출 비용 없는 감지 호출, P1-10 러너의 probe 모드) 결과를 앱 메모리에 둔다. AGY가 설치돼 있으면 감지할 때마다(앱 시작·[다시 감지]) 다시 받고, 한 번도 받지 않았으면 처음 필요할 때 한 번 받는다. 받지 못했으면(미설치·실패·빈 목록) 전에 받은 목록, 그것도 없으면 기본 모델 2개(`gemini-3.8-flash-medium`·`gemini-3.8-flash-high`)를 목록으로 쓴다. 화면 목록과 저장·연결 테스트 검사가 같은 목록을 쓴다. 출력 모양은 녹화본이 없어(M0 S7) 한 줄에 하나·JSON 배열을 넓게 받는다(fixture `test/fixtures/ai-engine/agy/models.txt`).
- **10분 계산**: `ai_cli_check.checked_at`을 찍는 것과 같은 앱 시계(주입 `CLOCK`)로 `checked_at ≥ 지금 − 10분`(정확히 10분 전은 통과). `engine_code`·`model`(= 선택 엔진 텍스트 모델)·`smoke_status=PASSED`가 모두 맞아야 한다. 비전 모델은 조건에 들지 않는다.
- **파일 쓰기**: 설정 파일을 다시 읽어 JSON의 `ai` 키만 바꾸고 나머지 키·순서는 그대로 둔 채 원자적으로 쓴다(같은 폴더 임시 파일 → fsync → rename, 실패하면 임시 파일을 지우고 원래 파일은 그대로). 다시 읽지 않은 사용자 수정은 파일에 남고, 새 스냅샷 내용은 '현재 설정 + 새 ai'다(다른 수정은 다음 다시 읽기·시작 때 반영). 파일이 없으면 현재 설정 전체를, 파일이 JSON이 아니면 쓰지 않고 422 `SETTINGS_SCHEMA_INVALID`(고치는 중인 파일을 덮지 않는다).
- **스냅샷·감사·SSE**: 스냅샷 저장과 같은 트랜잭션에 `user_action_log`(`SETTING_CHANGED`, detail `{ setting: 'AI_ENGINE', changedKeys }`, 값 없음 — P1-09 프로필과 같은 모양)를 남긴다. SSE `settings.reloaded`의 `rerunRequiredStepCount`는 늘 0(ai 키는 전파에 넘기지 않는다). `valid`·`errors`는 방금 저장한 스냅샷의 검사 결과라 늘 `true`·`[]`다 — 앞선 다시 읽기가 실패한(파일의 다른 칸 오류) 상태에서 저장해도 그 오류는 싣지 않고, 파일 검사 결과는 GET /settings의 `valid`·`errors`에 그대로 남는다. 저장은 설정 다시 읽기와 같은 줄에서 한 번에 하나씩 돈다.
- **'새 스냅샷'과 중복 제거**: 스냅샷은 P1-03 내용 해시 중복 제거를 따른다. 예전에 쓴 적 있는 ai 설정으로 돌아가(예: AGY로 바꿨다가 기본 CLAUDE로) 같은 내용의 스냅샷이 이미 있으면 새 행을 만들지 않고 그 행의 `last_loaded_at`만 갱신해 현재 스냅샷으로 쓴다(응답 `settingsSnapshotId`는 그 행, `updatedAt`은 갱신 시각). 설정은 바뀐 것이므로 파일 쓰기·감사 기록·SSE는 새 행일 때와 같다.
- **'실험적'**: `AiEngineOption.experimental`(05-2에 더함). M0 S7 측정값이 없어 앱 상수(`settings/ai-engine/ai-engine-options.ts`)이고, S7 전에는 설치·로그인도 확인하지 못한 CODEX만 true.
- **모듈 의존**: settings는 system의 `AiCliCheckQueryService`(`ai_cli_check` 읽기 창구)만 부른다. SystemModule이 선택 엔진을 읽으려고 SettingsModule을 import하므로, 읽기 창구를 DB만 쓰는 작은 `AiCliCheckQueryModule`로 떼어 SettingsModule·SystemModule이 함께 import한다(`forwardRef` 없음, 03-2 §3).

**P1-08 메타데이터 동기화 구현 결정(Proposed, 2026-09-30 — 오너 검토)**

- **자동 실행 기준('하루')**: 한국 날짜. 대상마다 **오늘(KST) 끝난 SUCCEEDED가 없으면** 돌린다(`lastSucceededAt`으로 판단). 24시간 기준으로 하면 매일 조금씩 늦어지고, 다른 '오늘' 값(하루 조회 상한, KST 0시)과 기준이 달라진다.
- **자동 실행 시점**: 라이브러리 없이 앱 시작 10초 뒤 한 번 + 매시간(`setTimeout`·`setInterval`, 둘 다 unref) 확인한다. 지금 RUNNING인 대상은 건너뛰고, 마지막 실행이 FAILED면 **시작 6시간 뒤에** 다시 해 본다(계속 실패하는 대상을 매시간 부르지 않게). 수동 '지금 동기화'는 언제든 된다. 커머스 키가 없으면 조용히 건너뛰고, 키체인을 열 수 없으면 경고 로그만 남긴다. 끄기: 환경변수 `COMMERCE_META_AUTO_SYNC=off`(06-4), 테스트는 DI(`COMMERCE_META_SCHEDULE`)로 끈다.
- **실행 순서·대상별 독립 실패**: 대상은 05-2 enum 순서로 하나씩 돈다(CATEGORY 먼저, 커머스API 호출이 겹치지 않는다). 대상 하나가 실패해도 나머지는 계속한다. 다만 키 없음(SECRET_NOT_CONFIGURED)·키체인(KEYCHAIN_UNAVAILABLE)·인증 실패(COMMERCE_AUTH_FAILED)는 대상마다 되풀이해도 같으므로 남은 대상을 부르지 않고 같은 사유로 FAILED로 닫는다.
- **트랜잭션 경계**: 대상 하나의 외부 호출을 모두 끝낸 뒤(트랜잭션 밖) 캐시 upsert + `removed_at` 표시 + run SUCCEEDED를 한 트랜잭션으로 한다. 실패하면 run만 FAILED(`error_message`)로 따로 쓰고 이전 캐시는 그대로다(03-2 §4에 행을 더했다).
- **POST 검사 순서**: 본문 422 → 진행 중 409 `ALREADY_IN_PROGRESS`(`details.job=META_SYNC`, `details.targets` = 요청 대상 중 RUNNING) → 키 409 `SECRET_NOT_CONFIGURED`·503 → 대상별 RUNNING 행(한 트랜잭션, `pg_advisory_xact_lock`으로 동시 요청 직렬화) → 202.
- **카테고리 단위 대상의 범위**: CATEGORY_DETAIL·STANDARD_OPTIONS·PRODUCT_ATTRIBUTES는 캐시의 성별 신발 리프(`패션잡화>남성신발>`·`패션잡화>여성신발>`, `removed_at` 없음, 아동·제외 품목 포함)만 부른다(ERD §7.3-9). 캐시에 그런 리프가 없으면 부르지 않고 FAILED('카테고리 목록을 먼저 받아 주세요').
- **빈 응답**: CATEGORY·ORIGIN_AREA·RETURN_DELIVERY_COMPANY 목록이 비면 FAILED(모든 행을 '사라짐'으로 만들지 않게). 주소록은 0건이 정상일 수 있어 그대로 받는다.
- **호출 속도(NFR-05, R04 A11)**: 응답의 `GNCP-GW-RateLimit-Remaining`이 0 이하면 다음 호출 전에 `1000 / Replenish-Rate` ms(없으면 1초) 쉰다. 429면 `Retry-After`(없으면 1·2·4초) 뒤 같은 요청을 다시 보낸다(최대 3번, 넘으면 그 대상 FAILED).
- **`GET /commerce-categories`가 빼는 것(CON-08 목록 출처 없음)**: 예외 유형 CHILD_CERTIFICATION, 이름·전체 경로에 아동 말(아동·키즈·주니어·유아·베이비), CON-08 제외 품목 말(바퀴·롤러·힐리스·실버·효도). `GET /commerce-addressbooks`의 `overseas=false`는 국내 주소록만.
- **재시작**: 앱을 켤 때 RUNNING 행을 FAILED(`finished_at` = 켠 시각, '앱이 다시 시작되어 동기화가 중단되었습니다.')로 닫는다. 자동 실행은 이 정리가 끝난 뒤에 돈다.

**P1-11 AI CLI 점검 구현 결정(Proposed, 2026-09-30 — 오너 검토)** — `POST /ai-cli-checks`·`GET /ai-cli-checks`·SCR-11

- **검사 순서(POST)**: 본문 형식 422 `VALIDATION_FAILED`(trigger `STARTUP`, 빈·중복 `engineCodes`, 정의 밖 필드) → `smokeTest=true`인데 `engineCodes` 없음 422 `VALIDATION_FAILED`(fieldErrors `engineCodes`) → 연결 테스트 모델 422 `AI_MODEL_INVALID`(fieldErrors `models.{엔진}`) → 잠금 409 `ALREADY_IN_PROGRESS`(`details.job=AI_CLI_CHECK`, `{작업}` = 'AI 엔진 점검') → 202. 검사에서 막히면 잠금을 잡지 않는다.
- **연결 테스트 모델**: `models[엔진]`, 없으면 설정의 그 엔진 텍스트 모델. 둘 다 비면 422(`{모델}` 자리 '(비어 있음)'). 목록 검사는 저장과 같고, 설정에 이미 있는 값(텍스트·비전)은 건너뛴다. `smokeTest=false`면 `models`는 쓰지 않는다. `engineCodes`는 준 순서대로 점검한다(없으면 CLAUDE·AGY·CODEX).
- **잠금**: 메모리 하나(`AiCliCheckLock`). 앱 시작 점검(STARTUP)과 설정 다시 읽기 뒤 점검도 같은 잠금을 쓴다(그동안 POST는 409). 점검이 오류로 끝나도 `finally`에서 푼다. 앱을 다시 켜면 없다.
- **이력 API**: `GET /ai-cli-checks`(위 표). 화면은 한 번에 100행(`size` 최대)을 읽어 표에 처음 10행을 보이고 [전체 이력]으로 100행까지 편다. 카드·시스템 상태의 '마지막 연결 테스트'도 이 목록에서 찾는다(감지만 한 SKIPPED 행이 최신이면 그 뒤에 가려진 테스트 결과를 보이려고).
- **화면이 부르는 때(R7)**: AI 엔진 페이지를 열 때·[다시 감지]·시스템 상태 [다시 점검]은 감지만(`smokeTest: false`, MANUAL). 카드의 [연결 테스트]는 그 엔진만(MANUAL). [저장]은 10분 안 통과 기록이 없을 때만 그 엔진을 BEFORE_SAVE로 테스트한 뒤 SSE로 새 행을 받아 PASSED면 [저장]을 누른 때의 값으로 PUT한다. 그동안 카드(라디오·모델·[연결 테스트])와 저장 바는 잠긴다. 결과가 180초(BE 연결 테스트 제한 120초 + 감지 여유) 안에 오지 않으면 기다림을 멈추고 '연결 테스트 결과를 받지 못했습니다. 최근 점검 이력을 확인한 뒤 다시 저장해 주세요.'를 보인다(점검은 BE에서 끝까지 돌고 결과는 이력에 남는다). 최종 판정은 BE 409다. 첫 실행 점검의 [AI 엔진] 링크(`/settings/ai-engine?from=first-run`)로 연 화면은 감지·연결 테스트의 계기가 FIRST_RUN이다. 모델을 바꾸거나 추천을 만들 때 스스로 연결 테스트를 보내지 않는다.
- **첫 실행 'AI 엔진 고르기'(F-SY-23)**: 확정 여부·시각을 둘 M1 저장 위치가 없어(`install_info`는 M2) 있는 기록으로 판단한다 — 선택 엔진의 마지막 연결 테스트가 통과면 '완료'이고 캡션 '{엔진} ({모델})로 확정 · {HH:MM}'은 그 테스트의 모델·시각이다. 아니면 '할 일'과 추천(설치됐고 마지막 연결 테스트가 PASSED인 엔진 가운데 CLAUDE → CODEX → AGY 순서의 첫 번째). 기본값 CLAUDE를 그대로 쓰면 저장할 것이 없어(같은 값) 저장 없이도 통과 기록으로 '완료'가 된다. 첫 실행인지 기록할 곳이 없어 패널은 늘 보인다.
- **이미지 생성 CLI 줄(F-SY-13)**: M1에 조회 API가 없고 `ai_cli_check` CHECK도 CLAUDE·AGY·CODEX만 받아 SCR-11 'AI 도구 상태'의 '이미지 생성 도구' 묶음은 그리지 않는다. P3-02(이미지 생성 경로)가 점검 자리를 정할 때 붙인다.
- **설정 다시 읽기 뒤 점검(§7.5-51 P1-03 처리의 훅)**: SSE `settings.reloaded`(통과한 새 스냅샷)의 `changedKeys`에 선택 엔진(`ai.engine`)이나 그 텍스트 모델이 있고 그 엔진·모델로 10분 안 통과가 없으면, 앱 시작 점검처럼 선택 엔진 하나만 계약 테스트를 1회 돌린다(trigger `STARTUP` — 앱이 스스로 하는 선택 엔진 점검, CHECK를 바꾸지 않으려고). PUT 저장은 늘 10분 안 통과가 있어 부르지 않는다. 잠금이 잡혀 있으면 건너뛴다. 스위치는 앱 시작 점검과 같은 환경변수(`AI_ENGINE_STARTUP_CHECK`), 테스트는 DI(`AI_ENGINE_RELOAD_CHECK`)로 따로 끈다. 작업 지시 §8 '자동 점검은 앱 시작 때 선택 엔진 1개뿐'과 부딪히고 이력에 '앱 시작'으로 보이는 점은 오너 검토에 올렸다(§7.5-51 오너 검토 ①·②).

## 4. Richardson 성숙도 점검

**평가: Level 2(목표 달성).** 리소스 URI(Level 1)와 HTTP 메서드·상태 코드 의미(Level 2)를 지킨다. HATEOAS(Level 3)는 1인 로컬 앱에 과설계라 두지 않는다. 대신 201·202에 `Location`을 붙인다.

| 점검 | 결과 |
|---|---|
| 리소스는 명사 | 합치며 동사형 경로 4개(`keep-as-is`·`restore`·`paste`·`reload`)를 명사 리소스로 바꿨다(아래 표). 남은 동사는 근거 있는 도메인 액션 8개뿐 |
| GET은 상태를 바꾸지 않는다 | 모두 지킨다. `GET /candidates/{candidateId}/catalog-match-suggestions`(M2)만 외부 조회를 하지만 상태를 바꾸지 않고 `call_log`만 남긴다 |
| PUT은 전체 교체·목표 상태, PATCH는 부분 수정 | PATCH는 두 곳(비교표 행, 등록 상품). 체크·선택·스위치는 멱등하게 PUT |
| DELETE | 물리 삭제는 없다. 선택 취소·체크 해제·`removed_at`·`revoked_at` 표시다(ERD §1.3). 브랜드 사전만 ⚠️ §7.5 |
| 상태 코드 | 생성 201, 비동기 수락 202, 값 없는 성공 204, 충돌·상태 위반 409, 검증 실패 422, 없음 404(§1.6) |
| 멱등성 키 | G4 승인·일괄 승인·문제 태그 재시도(M2)에 `Idempotency-Key`(§1.7) |

## 5. 오류 코드 초안

- 화면 문구는 `message`의 기본값이다. `{…}`는 `details`로 채운다. 셀러가 아는 말로 쓰고, 내부 용어(지문·StepRun)는 쓰지 않았다.
- 05-3 규약과 BE 전역 예외 핸들러가 이 표를 같이 쓴다.

## 7. ⚠️ 확인 필요

모르는 것은 지어내지 않고 여기에 남겼다. 오너 결정이 필요한 것과 합칠 때 해석한 것을 함께 적었다.

### 7.1 규약·공통

1. ⚠️ 확인 필요: 오류 응답에 `details` 객체(코드별 추가 정보: `blockedUntil`, `existingCandidateId`, `missingFields`, `checks[]`)를 더하는 규약 확장, 그리고 상태 코드 400·413·502·503을 쓰는 것. 주어진 규약에는 없다.
2. ⚠️ 확인 필요: 웹 전용 기록(게이트·확인 체크·원산지 입력·G4)을 M1은 Origin + `X-AutoStore-Client` 가드로만 보장한다. M3 CLI(F-CW-27)가 같은 BE HTTP API를 부르면 구분이 약하다. CLI 전용 경로·토큰을 둘지, CLI가 BE를 거치지 않고 모듈을 직접 부를지.
3. ⚠️ 확인 필요: SSE 재연결 때 `Last-Event-ID`로 놓친 이벤트를 다시 보낼지(이벤트 버퍼), FE가 조회 API로 다시 읽는 것만으로 충분한지.

- **입력 대기 중인 단계에 새 실행 요청(ERD §7.1-15)**: 새 실행을 열지 않는다. `POST …/runs`는 409 `STEP_ALREADY_RUNNING`(`details.status = WAITING_INPUT`, 문구 '이 단계가 입력을 기다리고 있습니다. 입력을 마치면 이어서 실행됩니다.'). 05-3의 조건이 '같은 후보·단계에 열린 실행'(실행중·입력 대기)이라 새 코드를 만들지 않았다. 오너 수정(EDIT·KEEP_AS_IS·RESTORE_VERSION)도 열린 실행이 있으면 같은 409다. 입력 대기에서 이어 가거나 끝내는 것은 단계 모듈이 `StepEngineApi.resumeWaiting`으로 한다(기다리지 않는 실행이면 409 `STEP_RUN_NOT_WAITING_INPUT`). 다른 실행으로 대체하려면 `failure_kind`에 SUPERSEDED를 더해야 해서(PRD 전이 라벨 추가) 하지 않았다.
- **실행기가 없는 단계**: 422 `INVALID_STEP_CODE`(`details.reason = NO_RUNNER`, 문구 '이 단계는 아직 준비 중이라 실행할 수 없습니다.'). ⑨ REGISTER는 `details.reason = NOT_RUNNABLE`('최종 승인(G4)에서만 등록합니다.'), 편집 단계가 아닌 EDIT은 `NOT_EDITABLE`. 레일 `actions.run.disabledReason`도 같은 함수로 같은 코드·문구다. 단계 모듈(P2~P4)이 실행기를 등록하기 전까지 모든 단계가 이렇게 꺼진다.
- **⑥ 묶음 중간 멈춤(§7.2-8)**: 첫 실행(⑥-1)만 202로 곧바로 만들고, 앞 실행이 끝나면 다음 단계를 차례로 시작한다(각각 새 `step_run`, `execution_mode = STEP`). 다음 단계가 시작 조건·잠금에 걸리면 그 단계를 건너뛰고 묶음 안의 다음 단계를 시도한다. 그래서 ⑥-1이 실패·입력 대기면 ⑥-2(⑥-1을 읽지 않는다)는 돌고, ⑥-3(⑥-1을 읽는다)은 시작하지 않고 묶음이 끝난다. 연속 실행(PRD §5.3 '실패·입력 대기는 그 결과를 읽는 단계만 막는다')과 같은 규칙이다.
- **이전 버전 다시 고르기의 지문(RESTORE_VERSION)**: 새 버전은 바탕 버전의 `step_run_input`(값 해시·출처)과 `input_fingerprint_start`를 그대로 가져가고, 지금 입력으로 다시 계산한 지문을 `input_fingerprint_end`에 쓴다. 둘이 다르면 새 버전을 곧바로 `RERUN_REQUIRED`(`rerun_reason_inputs` = 바뀐 입력)로 두고 뒷단계로 전파하지 않는다. 같으면 `COMPLETED`이고 뒷단계로 전파한다. EDIT도 같은 규칙이다. KEEP_AS_IS는 지금 입력으로 새 지문을 남기고 늘 `COMPLETED`(+ `user_action_log` OWNER_CONFIRMED). 오너 수정 버전의 `ai_engine`·`ai_model`·`ai_cli_version`은 바탕 버전 값을 이어 쓴다(산출물을 만든 엔진 표시, F-BS-75).
- **`propagatedSteps`(05-2 StepOwnerEditResult)**: RESTORE_VERSION이 뒷단계로 전파해 재실행 필요가 된 단계(= `staleDownstreamSteps`). 다른 단계를 함께 되돌리지 않는다. 다른 동작은 빈 배열.
- **설정 변경 전파 대상**: `settings.reloaded`의 `changedKeys`(ai 섹션 제외)와 현재 버전의 SETTINGS 시작 조건 입력(`settings.<경로>`)을 앞부분 일치로 맞춰(섹션 전체를 읽는 입력도, 한 키만 읽는 입력도) 그 단계만 재실행 필요로 둔다. 대상 상태는 완료·재실행 필요·입력 대기(입력 대기는 `step_run`도 RERUN_REQUIRED로 닫는다). 등록 진행 잠금 후보(등록요청중·결과확인필요·등록됨)는 건너뛰고, 제외 후보는 다시 작업할 때를 위해 표시한다. 승인대기·검증완료 후보는 작업중(STEP_NOT_CURRENT)으로 돌아간다. 전파 SSE는 설정 트랜잭션 커밋 뒤(`settings.reloaded` 뒤) 보낸다 — 설정 포트 `SettingsRerunPropagator`에 선택 인자 `afterCommit`을 더했다.
- **재실행 필요 전파 대상 단계**: 값이 바뀐 단계의 산출물을 **직접** 읽는 단계(STEP_GRAPH의 필수·선택 앞 단계)만 실행기 `readInputs`로 지문을 다시 계산한다. ⑨ REGISTER는 빼고(등록 기록이 원본), 현재 버전이 없는(미실행)·실행 중·실패 단계는 바꾸지 않는다(성별 전파 P1-04와 같음). 끝 지문이 달라 RERUN_REQUIRED로 끝난 실행은 뒷단계로 전파하지 않는다(뒷단계는 완료가 아닌 앞 단계를 읽지 않는다).
- **⑥-3 ← ④(ERD §7.2-10)**: 상품명(⑥-3 산출물)이 ④를 읽으므로 ⑥-3의 **선택** 입력(`category.leafPath`)으로 둔다. ④ 없이도 ⑥-3을 실행하고, ④가 바뀌면 ⑥-3이 재실행 필요가 된다. 실행 중 잠금도 이 관계를 따른다(④ 실행 중이면 ⑥-3을 시작하지 않는다).
- **없는 선택 입력의 행**: 앞 단계가 완료가 아닌 선택 입력(⑦·⑥-3 ← ④)은 `ck_step_run_input_prev` 때문에 `step_run_input` 행을 남기지 않고, 지문에는 null 값 해시로 넣는다. 전파·비교는 행이 없는 키를 null 값 해시로 본다. 오너·설정 선택 입력(URL 후보 쿠폰 등)은 null 값 해시 행을 남긴다.
- **실행 중 오너 입력 행**: 시작 때 읽은 값으로 행을 남기고, 완료로 끝날 때 그때 값으로 맞춘다(입력 대기 중에 넣은 국내 기준가 등). 완료 뒤 오너 입력 변경(`StepEngineApi.ownerInputChanged`, 규칙 7)은 이 해시와 비교한다. 입력 대기 중인 단계는 시작 조건 키(URL 후보 쿠폰)만 재실행 필요로 닫고, 실행 중 오너 입력 키(국내 기준가)는 정상 입력이라 그대로 둔다.
- **중단 안내 문구(F-BS-18)**: 재시작 정리로 닫은 실행은 `error_code = APP_RESTART`, `error_message = '앱이 꺼져 실행이 중단되었습니다. 다시 실행해 주세요.'`(화면은 '실패(중단됨)'). 실행기 예외(규약 밖 오류)는 `failure_kind = INPUT_VALIDATION`, `error_code = INTERNAL_ERROR`, 문구 '실행 중 앱 오류가 났습니다. 다시 실행해 보고, 계속되면 앱 로그를 확인해 주세요.'로 남기고 예외 글은 로그에만 쓴다(비밀정보·경로가 새지 않게). 후보 효과(앵커·소싱 선택 등)가 409·422로 막히면 그 실행을 `INPUT_VALIDATION` + 그 오류 코드·문구로 닫는다.
- **실행 방식·순서**: 시작 트랜잭션에서 후보 상태를 다시 계산한다(승인대기 후보의 단계를 다시 실행하면 작업중 STEP_NOT_CURRENT). 비동기 실행은 프로세스 안 대기열(M1 동시 1개, P1-10이 상한을 붙인다). 경고 PRE_G2_AI_COST 문구는 ⑤ '판정(G2) 전에 썸네일을 만들면 …', ⑥-1 '카피를 만들면', ⑥-2 '원산지·소재를 뽑으면'. CATEGORY_UNDECIDED 문구 '④ 카테고리 전이라 카테고리 필터 없이 태그를 뽑습니다.' 레일 `continuousRun`은 G2 전 ②·③ 밖이면 `CONTINUOUS_RUN_BEFORE_G2`(연속 실행 API는 P1-06).
- **입력 키 이름**: `candidate.*`(후보 필드) · `<단계>.*`(앞 단계 산출물: sourcing·pricing·category·thumbnail·copy·noticeRaw·noticeHtml·tags·upload) · `owner.*`(오너 입력) · `settings.<설정 경로>`. 표는 BE `step-engine/domain/input-keys.ts`·`step-graph.ts`(`STEP_INPUT_SPECS`), 화면 이름은 FE `features/step-engine/model/inputLabels.ts`. 단계 모듈(P2~P4)의 실행기가 이 키로 입력을 낸다.

**P1-06 구현 결정(Proposed, 2026-09-30 — 오너 검토)** — 연속 실행·게이트(G1~G4) 통과 기록

- **§7.2-16 건너뛴 단계**: ERD v0.3 `step_chain.skipped_step_codes`로 기록하고 `GET /continuous-runs/{id}`의 `skippedStepCodes`로 준다(위 §2.1 표를 고쳤다). FROM_HERE에서 고른 단계 뒤의 '완료·최신(COMPLETED)' 단계만 적는다. RERUN_STALE은 재실행 필요 단계만 돌리므로 적지 않는다.
- **RERUN_STALE 반복 한도(PRD §5.3 규칙 5)**: 한 묶음에서 단계마다 **1번**만 실행한다(`CHAIN_RUN_LIMIT = 1`). 흐름 순서로 돌면 앞 단계가 먼저 돌아 보통 한 번으로 표시가 없어진다. 끝 지문이 달라 다시 재실행 필요가 되거나, 입력 대기에서 이어 간 앞 단계가 뒤늦게 바꾼 단계는 다시 돌리지 않고 NO_RUNNABLE_STEP으로 멈춘다(그 단계가 `stop_step_code`). FROM_HERE도 같은 한도다(6시간 규칙의 ② 재조회 → ③은 서로 다른 단계라 걸리지 않는다).
- **멈출 때 `stop_step_code`(ERD §4.2)**: AWAIT_G2 = PRICING(② 입력 대기로 ③을 못 돌리면 SOURCING — G2 흐름에 앵커·성별·후보 고르기가 들어간다), AWAIT_G3 = THUMBNAIL(G3을 고르는 ⑤), AWAIT_G4 = REGISTER(최종 승인 뒤 ⑨), NO_RUNNABLE_STEP = 흐름 순서로 첫 '완료가 아닌' 필수 단계(막힌 곳), APP_RESTART = 그 묶음의 마지막 실행 단계(없으면 null). ② 또는 ③이 실패해 G2 앞에서 멈추면 NO_RUNNABLE_STEP(실패한 단계).
- **G2·G3 자리에서의 순서**: G2 자리(③ 뒤)는 ③이 묶음 안에 있을 때 본다(④ 이후에서 시작하면 시작 때 G2 유효를 확인했다). G3 자리(⑧ 앞)는 ⑤가 완료인데 G3이 무효면 ⑧의 다른 시작 조건(⑥-3)보다 먼저 AWAIT_G3으로 멈춘다. ⑤가 입력 대기·실패면 ⑧이 시작 조건에서 막혀 NO_RUNNABLE_STEP이다. 필수 단계가 모두 완료인 채 끝나면 남은 게이트 순서(G2 → G3 → G4)로 AWAIT_*.
- **6시간 규칙의 범위**: ③ 실행기의 `judgementPageCollectedAt`(P2-05)이 준 시각 + 설정 `safety.judgementValidityHours` < 지금이면 '판정 페이지 오래됨'. FROM_HERE에서 ③을 건너뛸 차례이거나 고른 단계가 ③일 때, RERUN_STALE에서 ③이 재실행 필요일 때, 이 묶음에서 ②를 아직 안 돌렸으면 ② 재조회(실행기 `refetch`, P2-02 — 없으면 `run`)부터 한다. 고른 단계가 ②면 ②가 새로 받으므로 재조회를 따로 하지 않는다. 후보 상태의 '최신'에는 쓰지 않는다.
- **시작 거절(202는 늘 실행 하나)**: 첫 행동이 멈춤이면 묶음을 만들지 않고 409를 준다 — FROM_HERE는 고른 단계를 지금 실행할 수 없으면 단계 실행 API와 같은 코드(STEP_START_CONDITION_UNMET·STEP_LOCKED_BY_RUNNING_STEP·GATE_NOT_PASSED·STEP_ALREADY_RUNNING, 설정 없음 503 SETTINGS_INVALID — 05-2에 503을 더했다), RERUN_STALE은 첫 재실행 필요 단계의 막힌 이유, G2 전에 ②·③ 밖의 재실행 필요만 남았으면 CONTINUOUS_RUN_BEFORE_G2. 검사 순서: 잠금·제외 → 열린 묶음 → G2 전·재실행 필요 없음 → 고른 단계 → AI 엔진(P1-10 훅). RERUN_STALE의 `startStepCode`는 쓰지 않는다. 이어 가다가 단계를 시작하지 못하면(경합·실행기 없음 등) 묶음을 NO_RUNNABLE_STEP(그 단계)으로 닫는다.
- **레일 `continuousRun`**: 연속 실행 API와 같은 순서 — 후보(잠금·제외·단계 코드) → 열린 묶음(CONTINUOUS_RUN_ALREADY_OPEN) → G2 전 ②·③ 밖(CONTINUOUS_RUN_BEFORE_G2) → 고른 단계를 지금 실행할 수 있는가.
- **이어 가기 방식**: 묶음 안 실행이 끝날 때마다(`StepExecutionService.onChainRunSettled`, 프로세스 안) 새 트랜잭션에서 후보 행을 잠그고 지금 상태로 순수 함수 `nextChainAction`을 부른다. 입력 대기에서 이어 간 묶음 실행이 돌고 있으면 기다린다. 묶음이 닫힌 뒤 끝난 실행(입력 대기 뒤 완료 등)은 묶음을 다시 열지 않는다.

**P1-10 구현 결정(Proposed, 2026-09-30 — 오너 검토)** — AI 실행기와 엔진 어댑터(claude·agy·codex)

- **거절 판정 자리**: AI 단계 시작(`startCandidateStepRun`)·연속 실행 시작은 선택 엔진 사용 가능 판정과 `--version` 감지를 **시작 트랜잭션 전에** 끝내고(spawn을 트랜잭션에 넣지 않는다), 쓸 수 없음(409)은 트랜잭션 안의 잠금·시작 조건 검사 **뒤에** 던진다 — 다른 막힌 이유(`CANDIDATE_LOCKED`·`CANDIDATE_EXCLUDED`·`STEP_START_CONDITION_UNMET`·`CONTINUOUS_RUN_ALREADY_OPEN` 등)가 먼저 나온다. 거절이면 `step_run`·`step_chain`을 만들지 않는다.
- **`details.reason` 추가 2개**: `NOT_CHECKED`(선택 엔진의 `ai_cli_check` 행이 아예 없음 — 앱 시작 점검을 껐거나 아직 한 번도 점검하지 않음), `MODEL_NOT_SET`(단계 주 작업 — 텍스트·비전 — 의 모델이 설정 `ai.models[엔진]`에 없음, 예: 기본 템플릿의 CODEX). 앱 시작 점검이 도는 중이면 판정은 그 점검이 끝날 때까지 기다린다.
- **지원 밖 버전**: 05-3은 거절 사유 `VERSION_UNSUPPORTED`, PRD §8.9·F-SY-13은 경고만 — **경고만** 한다(PRD 쪽). P-13 범위가 없어 M1은 `version_supported`가 늘 NULL이다. 범위가 정해지면 `ai-engine.constants.ts`의 `AI_SUPPORTED_VERSION_RANGE`에 넣고 앱 로그에 경고를 남긴다.
- **최신 행 규칙의 틈(오너 검토)**: ERD §3.14 '최신 행' 그대로 판정한다. 감지만 한 행(`SKIPPED`)이 최신이면 앞의 `FAILED`를 보지 않는다(쓸 수 있다고 본다).
- **실행 중 AI 오류의 `errorCode`**: `AI_ENGINE_UNAVAILABLE`(실행 파일 없음·로그인 풀림·모델 없음, `failureKind=AI`), `AI_OUTPUT_INVALID`(스키마 불일치·추가 필드·JSON 아님·SUCCESS인데 빈 결과·부분 출력), `AI_IMAGES_NOT_SEEN`(비전 `images_seen` 없음·불일치), `AGY_ERROR`(agy stderr), `AI_CLI_FAILED`(exit ≠ 0), `AI_TIMEOUT`(텍스트 120s·비전 180s + 5s 여유를 넘겨 자식을 끝냄) — 모두 `failureKind=AI`. 입력에 비밀·개인정보·네이버 출처 데이터가 있으면 부르지 않고 `failureKind=INPUT_VALIDATION`·`AI_INPUT_BLOCKED`. 다른 엔진으로 다시 부르지 않는다.
- **이어 가기**: 입력 대기에서 이어 가는 실행은 `step_run.ai_*`와 그 실행의 설정 스냅샷 모델로 다시 부른다(현재 설정을 읽지 않는다, R9). 연속 실행이 이어 가다가 AI 단계 차례에 선택 엔진을 쓸 수 없으면 묶음을 `NO_RUNNABLE_STEP`으로 닫는다(P1-06 규칙과 같다).
- **'AI 엔진 설정으로' 링크(F-BS-76)**: 화면은 시작 409의 `code`나 실행 기록 `errorCode`가 `AI_ENGINE_UNAVAILABLE`이면 오류 문구 옆에 `/settings/ai-engine` 링크를 붙인다(SCR-12 단계 표 실패 줄·실행 오류 띠·연속 실행 버튼·`StepStatusBar`). 실행 기록에 엔진이 있으면 'AI 생성 · Claude Code' 칩(F-BS-75, R11).

    - **P1-11 처리(Proposed, 2026-09-30 — 오너 검토)**: P1-03 처리의 훅을 붙였다(§2.14 'P1-11 AI CLI 점검 구현 결정'의 '설정 다시 읽기 뒤 점검'). 직접 고쳐 다시 읽으면 선택 엔진 하나만 계약 테스트를 1회 돌리고(trigger STARTUP) 그 결과가 R10 판정의 최신 행이 된다. 10분 규칙 자체를 다시 읽기에 걸지는 않았다 — 막을지 받을지는 여전히 오너 결정이다.
      - **오너 검토 ①(자동 점검 범위)**: 이 훅은 P1-11 작업 지시 §8 '자동 점검은 앱 시작 때 선택 엔진 1개뿐'(R7 구독 쿼터 보호)과 부딪힌다 — 다시 읽기로 선택 엔진·텍스트 모델이 바뀌면 앱이 스스로 연결 테스트 1회(구독 쿼터 사용)를 한다. 끄는 길은 둘이다: 환경변수 `AI_ENGINE_STARTUP_CHECK=off`(앱 시작 점검까지 함께 꺼짐), 또는 훅을 빼고 R10(AI 단계 시작 때 최신 점검으로 거절)만 안전망으로 둔다.
      - **오너 검토 ②(계기 표시)**: 이 점검은 `ck_ai_cli_check_trigger`를 바꾸지 않으려고 trigger `STARTUP`으로 기록해 SCR-13 이력 표와 SCR-11에 '앱 시작'으로 보인다. 따로 보이게 하려면 ERD §3.14 CHECK에 계기 값(예: `SETTINGS_RELOAD`)을 더하는 스키마 변경(04 원본 → 마이그레이션 → 05-2 `AiCliCheckTrigger`)이 필요하다.
    - **P1-03 처리(Proposed, 2026-09-30 — 오너 검토)**: **받아들인다.** 다시 읽기에서만 막으면 앱을 다시 켜는 것으로 똑같이 건너뛸 수 있어(시작 검사는 파일이 원본이라 막을 수 없다) 막는 효과가 없다. 안전망은 R10(AI 단계 시작 때 선택 엔진의 최신 점검이 미설치·실패면 거절)이다. `ai` 키는 `changedKeys`에 들어가지만 재실행 필요 전파에는 넘기지 않는다(R9). P1-11은 `changedKeys`에 `ai.*`가 있으면 앱 시작 때처럼 선택 엔진 계약 테스트(`ai_cli_check` 기록, trigger 코드는 P1-11이 정한다)를 돌리는 훅을 붙인다(SSE `settings.reloaded` 또는 `SettingsService.reload()` 결과로 안다).
