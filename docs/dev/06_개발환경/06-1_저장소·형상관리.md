## 1. 저장소 구조

```
autoStore/
├─ apps/
│  ├─ BE/   @autostore/be  NestJS 12 · Prisma 7.10 (API /api/v1, 배포본에서는 화면 정적 파일도 내보냄)
│  └─ FE/   @autostore/fe  React 19 · Vite 8 · React Router 8
├─ docs/    prd · design · dev
├─ .husky/  pre-commit · commit-msg
├─ package.json · pnpm-workspace.yaml · pnpm-lock.yaml
├─ tsconfig.base.json · .prettierrc.json · commitlint.config.mjs · .lintstagedrc.mjs · .secretlintrc.json
└─ .nvmrc · .npmrc · .editorconfig · .gitignore
```

- pnpm workspace 모노레포다. 두 앱은 서로 import하지 않는다. FE와 BE가 공유하는 것은 API 명세(05-2 openapi.yaml)뿐이고, FE는 여기서 타입을 만든다.

## 2. 실행 환경

| 항목 | 값 | 이유 |
|---|---|---|
| Node | **24.21.0** (`.nvmrc`, `engines >=24.15.0`) | Nest CLI와 테스트 도구의 하위 의존성이 Node 24.15 이상을 요구한다(`@angular-devkit/core`, `jsdom` 30). 오너 PC의 24.11.1로는 설치가 막혔다 |
| pnpm | 9.15.0 (`packageManager`, corepack) | 02-ADR-001 |
| PostgreSQL | 14.20 (Homebrew, 이 PC) | D-14. DB `autostore_dev`(개발)·`autostore_test`(테스트) |

- 오너 PC에는 nvm으로 Node 24.21.0을 **추가로** 설치했다. nvm 기본값은 24.11.1로 고정해 두었다. 기존 기본값이 `lts/*`여서 새 버전을 설치하면 기본값이 바뀌는데, 그러면 24.11.1에 설치된 전역 도구(pnpm, gemini, firebase 등)가 새 터미널에서 사라지기 때문이다.
- 이 저장소에서 작업할 때는 먼저 `nvm use`를 실행한다(`.nvmrc`를 읽는다). pnpm은 `corepack enable pnpm`으로 24.21.0에 붙여 두었다.

## 3. 버전 고정

- 모든 의존성을 정확한 버전으로 고정한다(`.npmrc`의 `save-exact=true`). Node 버전이 맞지 않으면 설치를 멈춘다(`engine-strict=true`).
- 설치 통계 전송(`@scarf/scarf`)은 루트 `package.json`의 `scarfSettings.enabled=false`로 끈다(외부 호출 최소화, GEN-01).

| 패키지 | 고른 버전 | 최신과 다른 이유 |
|---|---|---|
| TypeScript | 5.9.3 | 7.0(Go 기반 새 컴파일러)은 `ts-jest`(<7)와 `typescript-eslint`(<6.1)가 아직 지원하지 않는다 |
| ESLint | 9.39.5 | `eslint-plugin-jsx-a11y` 6.10이 ESLint 10을 지원하지 않는다 |
| Prisma | 7.10.0 | npm의 `latest` 태그가 8.0 RC를 가리킨다. 02-ADR-001대로 안정판 7.10을 쓴다 |
| jsdom | 29.1.1 | 30은 Node 24.15 이상이 필요하다. Node를 24.21로 올렸으니 13 테스트 단계에서 30으로 올려도 된다 |
| `@nestjs/schematics` | 넣지 않음 | 코드 생성기(`nest g`)라 빌드·실행에 필요 없다. Node 24.15 이상이 필요해 처음 설치에서 뺐다. 필요하면 다시 넣는다 |

## 4. 브랜치 전략 (Proposed)

**트렁크 기반**으로 한다.

- `main` 하나를 늘 빌드·테스트가 통과하는 상태로 둔다.
- 작업은 짧게 사는 브랜치에서 한다: `feat/<모듈>-<요약>`, `fix/<모듈>-<요약>`, `docs/<요약>`. 모듈 이름은 BE 모듈(03-ADR-003)과 같게 쓴다(예: `feat/step-engine-run-start`, `feat/fe-ai-engine-page`).
- 브랜치는 하루~이틀 안에 `main`에 합친다.

Git Flow를 고르지 않은 이유는 셋이다.
- 개발자가 한 명(오너 + AI 에이전트)이다.
- 정해진 출시 주기가 없다.
- `develop`·`release` 브랜치를 따로 두어도 얻는 것이 없다.

**원격 저장소는 아직 없다.** GitHub에 올리게 되면 16 CI·CD 단계에서 `main` 보호 규칙을 건다. 규칙은 PR 필수, CI(lint·typecheck·test·build) 통과 후 병합, 강제 push 금지다.

## 5. 커밋 규약 (Proposed)

[Conventional Commits](https://www.conventionalcommits.org/)를 따르고 `commitlint`가 검사한다.

- 형식: `<타입>(<범위>): <요약>`. 요약은 한국어로 써도 된다.
- 타입: `feat` 기능, `fix` 버그 수정, `docs` 문서, `refactor` 동작 변화 없는 구조 변경, `test` 테스트, `chore` 설정·빌드·의존성, `perf` 성능, `ci` CI.
- 범위: `be`, `fe`, `db`, `api`, `docs`, `design`, `deps` 또는 BE 모듈 이름.

예시:

```
feat(step-engine): 단계 실행 시작 API와 StepRun 생성
fix(fe): AI 엔진 페이지 저장 버튼 비활성 조건 수정
docs(prd): D-16 AI 엔진 선택 반영
chore(deps): prisma 7.10.1로 올림
test(be): 로컬 보안 가드 e2e 추가
```

## 6. 커밋 전 검사 (husky)

| 훅 | 실행 | 막는 것 |
|---|---|---|
| `pre-commit` | `lint-staged` → 스테이징한 모든 파일에 `secretlint`, 코드 파일에 `prettier --write` | 토큰·키·비밀번호가 들어간 파일 |
| `commit-msg` | `commitlint` | 규약에 안 맞는 커밋 메시지 |

- `pnpm install`의 `prepare` 스크립트가 훅을 설치한다(`core.hooksPath=.husky/_`).
- 비밀정보 검사기는 `secretlint`(npm 패키지)다. 스킬이 권하는 gitleaks는 따로 설치해야 하는 프로그램이라, 동료 셀러 설치본에서도 pnpm만으로 돌아가게 하려고 바꿨다.

**검증 결과 (2026-09-27)**
- `secretlint`: 저장소 안에 GitHub 토큰 형식 문자열이 든 파일을 두자 `[GITHUB_TOKEN]` 오류와 exit 1로 막았다. 값은 가려서 출력했다.
- `commitlint`: `"그냥 고침"`은 exit 1로 거부했고 `"chore: 저장소 뼈대"`는 통과했다.
- 실제 커밋으로는 확인하지 않았다. 오너가 첫 커밋을 허락하면 그때 훅이 도는지 본다.

## 7. 커밋하지 않는 것 (`.gitignore`)

- `node_modules/`, 빌드 산출물(`dist/`, `coverage/`), Prisma 생성 코드(`apps/BE/src/generated/`)
- `.env`, `.env.*` (`.env.example`만 커밋한다)
- 앱 로컬 데이터 `.data/`(설정 JSON, 이미지, 로그)
- OS·편집기 파일

비밀정보(커머스API client_secret, 토큰, API 키)는 파일이 아니라 OS 키체인에만 둔다(NFR-02). 그래서 `.env`에도 비밀정보가 없다.
