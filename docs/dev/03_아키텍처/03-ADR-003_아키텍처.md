## 맥락

설치본 하나를 사용자 1명이 이 PC에서만 쓴다(GEN-01). 단계(②~⑨)를 따로·이어서·여러 후보에 실행하고(GEN-02·06), 앱을 껐다 켜도 이어서 한다(GEN-03). 외부 연동은 실제 스토어라 샌드박스가 없고, fixture로 테스트해야 한다(NFR-06).

## 결정

1. **배포 단위**: 모듈러 모놀리식. NestJS 프로세스 하나가 API(`/api/v1`)와 화면 정적 파일을 함께 내보낸다.
2. **내부 구조**: 레이어드. 외부 연동(커머스API, 라쿠텐, 데이터랩, 환율, AI 엔진 CLI, 이미지 생성)만 포트·어댑터로 두어 fixture로 바꿔 끼운다. AI 엔진은 `AiEngineAdapter` 포트 하나에 어댑터 3개(`ClaudeCodeAdapter`·`AgyAdapter`·`CodexAdapter`)다(D-16).
3. **모듈 경계**: 단계 단위(keywords, sourcing, pricing, category, thumbnails, content, tags, registration) + 핵심(step-engine) + 관리(products, settings, system) + 기반(integrations, common). DB 테이블도 이 경계로 소유한다(04에서 이어받음).
4. **작업 실행**: StepRun 테이블이 상태 원본이다. BE 안의 실행기가 동시 실행 상한(선택 AI 엔진 2, 이미지 1 — AI-05, D-16 R13)을 지키며 처리하고, 진행은 SSE로 알린다.
5. **트랜잭션**: 단계 완료·게이트 통과는 한 트랜잭션. ⑨ 등록은 '등록요청중' 선커밋 → 외부 호출 → 결과 갱신(03-2 §4).
6. **로컬 보안**: 127.0.0.1 바인딩, Host·Origin 검사, 사용자 정의 헤더 요구, CORS 닫음(03-2 §5).
7. **AI 엔진 선택(D-16)**: 사용자가 설정 페이지에서 엔진(claude·agy·codex) 하나와 모델을 고른다. 원본은 설정 JSON `ai` 섹션이고 settings 모듈이 쓴다. 감지·연결 테스트 기록(`ai_cli_check`)은 system 모듈이 소유한다. 실행기는 단계 시작 때 선택 엔진을 StepRun에 고정하고, 쓸 수 없으면 멈춘다(M1은 자동 대체 없음, 작업별 엔진·자동 대체는 M2).

## 검토한 대안

- 단순 모놀리식: 모듈 수(단계 8 + 관리 3 + 외부 연동 6)가 커서 경계 없이는 엉킨다.
- MSA: 로컬 1인 도구에 프로세스 여러 개는 설치·운영 부담만 늘린다(GEN-09).
- 헥사고날 전면: 외부 연동 외에는 이점보다 코드량이 크다.
- 외부 큐(Redis + BullMQ): 설치 부담(02-ADR-001 §3).

## 영향

- 좋은 점: 설치·실행이 프로세스 하나(+ PostgreSQL). 단계 모듈을 하나씩 만들고 fixture로 검증할 수 있다.
- 감수하는 것: 모듈 경계는 규칙(단계 모듈끼리 직접 호출 금지)으로 지켜야 한다. 긴 AI 작업이 BE 프로세스 안에서 돌아 BE를 재시작하면 실행 중 단계가 '실패(중단됨)'가 된다(PRD가 허용한 동작).

## 재검토 트리거

- 동시 실행을 크게 늘려 BE 한 프로세스가 버거워지면 → 실행기를 별도 프로세스로 뗀다.
- 단계 실행 CLI(GEN-08, M3)를 만들 때 → 같은 모듈을 CLI 진입점에서 부르는지 확인한다.
