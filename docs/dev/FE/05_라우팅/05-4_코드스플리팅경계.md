## 1. 기본 규칙

- **화면(page) 하나 = 청크 하나.** route `lazy`로 나눈다(05-3 §2). App Router처럼 저절로 나뉘지 않으므로 직접 적는다.
- **나누지 않는 것(첫 청크)**: `AppLayout`·`AppNav`, `CandidateLayout`·`StepRail`, `NotFoundPage`, `shared/ui`, `shared/api`, `tokens.css`·`global.css`. 모든 화면이 쓰거나 아주 작다.
- 적용 시점: **[P1-02](../../../action/phase-1_기반/P1-02_FE공통부품.md)(2026-09-30)에 적용했다.** 06-3 §9(번들이 커지면)와 이 문서(화면 구현 때)가 달랐는데, 실행 문서가 지금 적용하라고 정했다. `app/routes.tsx`의 `page(load, pick)`가 route `lazy`(`{ Component }`)를 만든다. 첫 진입 때는 경로 없는 layout route의 `hydrateFallbackElement`(빈 fragment)로 앱 틀 + 빈 본문을 그린다.
- 빌드 결과(2026-09-30): 화면 13개가 각자 청크(각 0.2~0.4 kB, 아직 자리표시자), 첫 청크 `index-*.js` 372 kB(gzip 118 kB), CSS 10 kB. 검사: `routes.test.tsx`가 화면 route는 `lazy`, 틀·`*`는 eager임을 확인한다.
- D-29(2026-10-03): 화면 청크는 `/guide`(SCR-14)를 더해 14개다(`routes.test.tsx`가 `guide`도 lazy인지 본다). 그날 빌드(`vite build`)에서 `GuidePage-*.js` 2.69 kB(gzip 0.94 kB), 첫 청크 `index-*.js` 308 kB(gzip 96.9 kB). 안내 글(`features/guide/content.ts`)은 **첫 청크**에 든다 — 첫 청크의 `CandidateLayout`(eager)이 단계 화면 '?' 도움말에 `ScreenHelp`를 쓰기 때문이다. 글 한 파일이고 무거운 모듈이 아니라 지금은 따로 나누지 않았다.
- 로컬 앱이라 네트워크 비용이 거의 없다. 분할의 목적은 **첫 화면을 빨리 그리는 것**과 **화면별 번들 크기를 보이게 하는 것**이다.

## 4. 과분할 경고

- 작은 부품(칩·버튼·표)을 lazy로 나누지 않는다. 요청만 늘고 깜빡임이 생긴다.
- 단계 화면끼리 오갈 때 틀(`CandidateLayout`)이 다시 받아지면 안 된다 → 틀은 eager.
- 한 화면 안 탭(설정 탭 등)은 나누지 않는다. 탭 전환이 느려진다.
- 13단계에서 `vite build` 결과의 청크 크기를 보고, 50KB(gzip)를 넘는 화면만 안쪽 분할을 검토한다(기준값은 Proposed).
