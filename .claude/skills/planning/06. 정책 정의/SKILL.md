# 정책 정의 (Policy Definition)

04 원페이저 + 05 비즈니스모델을 받아 **정책 정의서 1부**(정책 매트릭스 + 운영정책 + 약관 초안)를
만든다. **적대적 레드팀**으로 엣지케이스를 펼치고, 사람 개입 게이트는
**정책 영역 인벤토리 확정 1곳 + 매트릭스 ⚠️미정 결정 1곳, 총 2곳**이다.

**AI의 역할**: **질문 생성·구조화까지. 결정은 사람, 약관은 법무 검토.** AI가 그럴듯하게 확정한 정책은 검토 없이 통과되기 쉽다.

**핵심 원칙**:
- 정책의 빈틈은 단일이 아니라 **조합**(탈퇴×환불, 쿠폰×부분취소)에서 나온다 — 빈 셀 = 미정 정책.
- **AI 산출물 ≠ 법률 자문.** 약관은 반드시 법무 검토. 청약철회·위약금·개인정보 보유기간은 **법정 기준**이라 임의로 정할 수 없다(`[법정기준 placeholder]`로 비워 둔다).
- **법조항 환각 주의.** AI는 조문을 확정하지 않는다. 조문 인용 시 `[조문 미확인—사람 검증]` 태그를 붙이고, 확인 주체는 **사람**이다(한국 기준 law.go.kr; 타 관할은 해당 정부 법령 DB).
- **타사 약관은 참고용·복사 금지**(저작권 + 그 회사 BM에 맞춘 조항은 독). 구조·항목만 벤치마크.
- 레드팀 결과를 **전부 정책화하지 마라** — 상/중만, '하'는 운영자 재량.

> **관할(jurisdiction) 가정 = 한국**(전자상거래법·청약철회·law.go.kr).

## 파이프라인

### Stage 0 — 입력 확인
04(필수)·05(필수)·03(선택)을 읽는다. 04·05 없으면 위치 묻고 중단. 05 없으면 환불·정산 정책 ⚠️미정 강제.
05의 요금제·paywall을 환불·정산 정책의 전제로 삼는다. **관할 = 한국**으로 둔다(위 변경 지점).

### Stage 1 — 정책 영역 인벤토리
04·05를 근거로 정책 영역을 2층으로 나열한다:
- **공통 코어**(모든 서비스): 회원/계정(가입·휴면·탈퇴/데이터삭제) · 결제(환불·부분환불·쿠폰) · 개인정보 · 분쟁 · 어뷰징.
- **BM 의존 영역**(해당 BM일 때만): 예약(취소·변경·노쇼) · 정산(호스트) · 콘텐츠(리뷰·신고) 등. BM 특성상 추가 영역은 이유와 함께 제안.

- → `06-1_정책영역인벤토리.md`

### 🚦 게이트1 — 정책 영역 인벤토리 확정 (사람 개입, 필수)
AskUserQuestion으로 "이 영역 목록 + BM 추가 영역이 맞는가, 빠진 영역은?" → 사용자 확정.
**확정된 인벤토리로만 Stage 2 레드팀을 돌린다**(인벤토리 누락은 이후 전체를 헛돌게 함).

### Stage 2 — 레드팀 엣지케이스 발굴
AI에게 **3개 역할을 명시 부여**: (A) 환불·정책 허점을 노리는 악성 유저, (B) 10년차 CS 팀장, (C) 플랫폼 분쟁을 다뤄본 법무 담당자.
<!-- 변경 포인트: 3역할을 사업에 맞게. 예) B2B면 악성유저→계약위반 고객사·권한오남용 관리자, 사내 법무 없으면 외부 자문·규제기관 관점. 역할 '수'보다 '관점 축'이 본질. -->
- **각 역할별로 정책이 답하지 못하는 질문을 최소 10개씩** 생성한다(동기·악용 시나리오·조합 포함, 인라인 예시 1~2개). 예: 호스트가 일방 취소하면? 탈퇴 유저의 환불 계좌는? 쿠폰이 이미 만료됐다면?
- 먼저 많이 뽑은 뒤 → **중복·자명한 질문 제거** → 질문마다 **[발생 가능성 상/중/하]** + **[방치 시 리스크]** 태그.
- → `06-2_레드팀_엣지케이스.md`

### Stage 3 — 정책 매트릭스
레드팀 질문을 조건 조합 표로 구조화한다. 열: `케이스ID | 상황 | 조건(시점/주체/결제수단) | 처리 방안(옵션 A vs B + 트레이드오프) | 예외 | 담당(시스템/운영자) | 미정⚠️`.
- 판단이 갈리는 케이스는 **1안 확정 말고 옵션 A/B 병기** + 각 트레이드오프 한 줄. **AI가 임의로 확정하지 마라.**
- 결정이 필요한 항목은 **미정 열에 ⚠️**.
- **곱집합 자체점검**: 인벤토리·조건 열에서 핵심 축(예: 취소 주체 × 시점 × 결제수단)을 도출해 곱집합 커버리지를 점검하고, **미커버 조합은 ⚠️미정 행으로 강제 생성**한다. *미정이 0개면 AI가 임의확정한 것이므로 의심하고 재점검.*
- **상/중만 정책화**하고, '하'는 표 하단 "운영자 재량 / 사례 축적 대기" 목록으로 이관(삭제 아님).
- → `06-3_정책매트릭스.md`

### 🚦 게이트2 — 매트릭스 ⚠️미정 결정 (사람 개입, 필수)
AskUserQuestion으로 ⚠️미정 항목별 **옵션 A/B(또는 값)**를 제시 → 사용자가 확정한다(미정이 많으면 우선순위·묶음으로). **확정 전에는 Stage 5(약관 초안)로 넘어가지 않는다.** 위약금 비율 같은 비즈니스 판단은 AI가 정하지 않는다.

### Stage 4 — 타사 약관 벤치마크
> ⚠️ **약관 페이지는 대부분 SPA·로그인·PDF 뷰어라 WebFetch 단독으론 거의 안 잡힌다.** 그래서:

1. **WebSearch 우선**: `"<타사> 환불정책"`, `"<타사> 이용약관 청약철회"`, `"<타사> 취소 수수료"` 등으로 약관 요약·기사·도움말을 찾아 추출한다(출처 명시).
2. **WebFetch 보조**: 공식 약관 URL을 알면 WebFetch로 보강(리다이렉트 응답이면 반환 URL로 1회 재호출).
3. **둘 다 실패 시**: 사용자에게 **약관 텍스트를 복사해 붙여넣어 달라고 요청**한다(셀을 "확인 불가"로 비우는 건 포기지 폴백이 아니다).

같은 관할·같은 BM 서비스 2~3곳을 비교 축(환불 시점 구간·위약금 비율·귀책 보상·분쟁 중재·노쇼)으로 마크다운 표 정리. **복사 금지 — 구조·항목만.** 마지막에 "차별화/추격할 지점" 3개. **전부 확인 불가(0곳)면 사용자에게 보고하고 벤치마크 없이 진행할지 확인.**
- → `06-4_약관벤치마크.md`

### Stage 5 — 운영정책 + 약관 초안
확정된 매트릭스(⚠️ 항목 = 사용자 결정값 반영)를 근거로:
1. **운영정책**: CS가 보고 바로 처리할 수준. **케이스 ID를 인용**해 매트릭스와 추적 가능하게(→ 15.QA 테스트케이스·CS 매뉴얼의 원천).
2. **약관 초안**: 맨 위에 **"본 약관은 법무 검토 전 초안임"** 경고. 청약철회 조항 충돌 등은 `[법무 확인 필요]` 태그.
   - **법조항을 본문에 확정해 적지 마라.** 조문 인용이 필요하면 `[조문 미확인—사람 검증]` 태그만, 청약철회 기간·위약금 상한·개인정보 보유기간은 `[법정기준 placeholder]`로 비워 둔다(임의값 금지).

## 주의
- **AI 산출물은 법률 자문이 아니다.** 약관은 전자상거래법·약관규제법·개인정보보호법 적용 — 법무/외부 전문가 검토 필수.
- **법조항 환각** — 조문 번호·내용은 존재하지 않거나 개정 전일 수 있다. AI가 확정하지 말고 사람이 law.go.kr에서 확인.
- **타사 약관 복사 금지** — 구조·항목만 벤치마크, 문구는 우리 매트릭스에서 도출.
- **레드팀 결과 전부 정책화 금지** — 상/중만. 하까지 만들면 운영정책이 비대해진다.
- **⚠️미정을 그대로 다음 단계로 넘기지 마라** — 12단계 기능명세에서 그대로 구멍이 된다.
- **deep-research는 기본 미사용** — 명료화 질문으로 무인 흐름을 멈추고, 좁은 조문 확인엔 과투자. 여러 법령 충돌/해외 비교가 꼭 필요할 때만 사용자에게 물은 뒤 별도 호출.
