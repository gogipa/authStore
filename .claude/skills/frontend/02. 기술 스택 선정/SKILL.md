# 기술 스택 선정 (Tech Stack Selection)

01단계 산출물(화면 목록·컴포넌트 인벤토리·화면↔API 의존맵)을 입력으로, "이 프론트엔드를
무엇으로 지을 것인가"를 결정한다. 산출물 = 제약 요구표 → 후보 비교 매트릭스 → ADR(Architecture
Decision Record). 코드는 한 줄도 쓰지 않지만 시리즈 전체에서 **되돌리기 가장 비싼 결정**을 내리는
구간이다. **AI는 조사·정리·초안(후보 회수·최신 사실 확인·비교표 작성), 스택 결정은 사람**(팀 일정·
운영 현실·채용 시장을 아는 사람의 책임). 비교는 AI, 결정은 사람.

## 핵심 원칙

- **조사와 결정을 분리한다.** deep-research·Context7에는 "후보를 빠짐없이, 최신 사실로, 출처와
  함께 모으기"까지만 시킨다. "우리 제약에서 무엇을 고를지"는 사람이 한다. 이 경계를 흐리면 AI
  비교표가 곧 결정이 된다 — **AI 비교표는 결정이 아니라 초안**.
- **제약을 먼저 글로 박는다 ("제약 먼저, 후보 나중").** SEO·성능·팀 역량 3축을 Step 1에서
  명시하면 이후 모든 비교가 그 제약을 기준으로 추적 가능해진다. 제약이 없으면 비교는 취향 싸움이다.
- **셀은 점수가 아니라 근거 한 줄로 채운다.** 가중치 합산 점수표는 "왜 그 점수인지"가 사라진다.
  근거 문장을 강제하면 결정 회의가 "점수 흥정"에서 "근거 검증"으로 바뀐다.
- **상위 산출물 계승, 재발명 금지 — 단 확정 상태일 때만.** 01의 화면 목록·화면↔API 의존맵을
  제약 추출의 입력으로 계승. **BE 05 OpenAPI에 실제로 정의된 스키마명을 그대로 인용**(재작명 금지).
  FE는 이 API 계약의 소비자이지 재정의자가 아니다. 도메인마다 스키마가 다르므로 **그 주제의
  `05-2_openapi.yaml`을 직접 파싱해 실재 용어만 계승**하고, 존재하지 않는 개념을 끼워넣지 않는다
  (예: 포밋(돌봄)=`SitterProfile`·`Booking`·`Review`·`Chat`; 펫사료구독=`SubscriptionPlan`·
  `Subscription`·`Payment`·status enum 5값 — 도메인에 없는 엔티티는 인용하지 않음).
  01에 잔존한 `⚠️`/`[확인 필요]`는 제약표에 보존.
- **Context7로 최신 사실을 못 박는다.** React 19·Next 15·TanStack Query v5는 최근 메이저가
  올라 블로그·AI 학습 데이터가 옛 버전 기준인 경우가 많다. 1순위 후보는 반드시 공식 문서로
  breaking change를 확인하고, 리서치와 어긋나는 지점은 표시한다(버전 환각 경계).
- **유행과 적합을 혼동하지 않는다.** deep-research는 화제성 높은 신생 도구를 후보로 올리기 쉽다.
  생태계 성숙도·운영 사례·러닝커브를 반드시 평가 축에 넣고, "새것"이 "맞는 것"인지 따로 검증.
- **단계별 파일로 끊는다.** 제약표(02-1) → 비교 매트릭스(02-2) → ADR(02-ADR). 한 방 생성 금지
  (제약 없이 결론부터 뽑으면 ADR이 사후 합리화가 된다).
- **디자인 토큰 "정의"는 이 단계가 아니다.** 스타일링 도구(Tailwind)를 **고르는 것까지**가 FE의
  일. 토큰 값 자체는 디자인 시리즈가 정의한 것을 04단계에서 코드화한다. 여기서 색·간격 값을 새로
  만들지 않는다(디자인 시리즈 중복 금지).

## 파이프라인

### Stage 0 — 입력 확인·도구 probe·degrade
- `<루트>/01_핸드오프분석/`를 읽는다. **없으면 중단**(위치 질의).
- BE 05 OpenAPI 로드 시도(있으면 도메인 용어·API 계약 계승, 없으면 ⚠️ "API 계약 미대조" + 01 용어 계승).
- **도구 probe**: deep-research(스킬 가용 확인) / Context7(ToolSearch 존재) / superpowers:brainstorming(스킬 가용).
  없으면 degrade(아래 "도구 정확성").

### Stage 1 — 제약 명시화 → 02-1
- 01 산출물(화면 목록·컴포넌트 인벤토리·화면↔API 의존맵)을 읽어 **SEO·성능·팀역량 3축**으로 제약 정리:
  - **SEO**: 검색 노출이 필요한 공개·검색 유입 화면 vs 인증 영역 구분(포밋 예: 시터 검색/상세 = 공개 / 예약·결제·채팅·마이 = 인증).
  - **성능**: 모바일웹 우선 등 환경. 화면별 Core Web Vitals 민감도(LCP 중요 화면 vs INP 중요 화면).
  - **팀 역량**: React 경험치, App Router 경험, 운영·인프라 인력(서버리스 선호 여부).
- 각 제약이 **"어떤 기술 결정에 영향을 주는지"를 한 줄씩 매핑**. 판단 갈리는 곳은 `[확인 필요]` 태그.
- (선택) superpowers:brainstorming으로 빠진 평가 축(국제화·오프라인·접근성 의무)을 발산 점검.
- → `02-1_제약요구표.md`

### Stage 2 — 후보 조사 (deep-research) → 02-2 초안
- 02-1 제약을 전제로 **축마다 후보를 같은 깊이로** 조사(한 번에 다 시키지 말고 축별로 끊는다).
  각 후보: 강점 / 약점 / 포밋 제약 적합도 / 실사용 사례 / **출처**.
  - 프레임워크/렌더링: Next.js 15(App Router) vs Remix vs Vite SPA
  - 서버 상태: TanStack Query v5 vs SWR vs RTK Query
  - 전역 클라 상태: Zustand vs Redux Toolkit vs Jotai
  - 스타일링: Tailwind CSS vs CSS Modules vs styled-components(런타임 비용)
  - 폼/검증: React Hook Form + Zod vs Formik + Yup
- deep-research 부재 시 degrade: 내장 지식으로 비교하되 **출처 없는 칸에 ⚠️** + "외부 리서치로 보강 필요".
- → `02-2_후보비교매트릭스.md`(리서치 섹션)

### Stage 3 — 최신 사실 확인 (Context7) → 02-2에 "최신 사실" 컬럼 추가
- 1순위 후보(Next 15 / TanStack Query v5 / Zustand / Tailwind / RHF+Zod)를 **공식 문서로 검증**:
  - Next.js 15: App Router 캐싱 기본값 변경, React 19 RSC/Server Actions 상호작용
  - TanStack Query v5: v4→v5 breaking change(useQuery 객체 시그니처 등)
  - Zustand: React 19 호환성, persist 미들웨어 최신 API
  - Tailwind: 현재 메이저 버전·설정 방식(CSS-first 여부)
- Context7 2-step(resolve-library-id → query-docs ≤3, 모호 시 생략·⚠️). 확인 결과를 비교표에 **"최신 사실"
  컬럼**으로 덧붙이고, **리서치와 공식 문서가 어긋나는 지점은 따로 표시**(버전 환각 차단).
- Context7 부재 시 degrade: 내장 지식 + **"버전 확인 필요 ⚠️"** 표기(임의로 확정하지 않음).

### Stage 4 — 비교 매트릭스 완성 → 02-2
- 02-1(제약)·02-2(리서치)·Stage 3(최신 확인)를 합쳐 축별 가중 비교표 완성:
  - 행: 각 축의 후보 / 열: SEO 적합 · 성능 · 팀 러닝커브 · 생태계 성숙도 · BE 계약 연동 용이성 · 최신 사실
  - **각 셀은 점수가 아니라 "근거 한 줄"**(점수만 있으면 판단 추적 불가).
  - 마지막에 **"권고안"과 "기각안별 기각 사유"를 분리** 제시.
  - **결정란은 비워둔다** — 최종 결정은 사람(게이트).

### 🚦 게이트 — 스택 결정 (🔴 사람 확정·승인, 필수)
AskUserQuestion으로 02-2(축별 비교 매트릭스 + 권고안 + 기각 사유)를 제시 → **사용자가 축별로 결정/승인**.
- 핵심 결정 항목(사람이 쥐는 비즈니스 판단):
  - **프레임워크/렌더링** — SPA vs SSR/SSG 혼용(공개 검색 화면 SEO·LCP vs 인증 영역 CSR).
  - **서버 상태 vs 전역 클라 상태** — TanStack Query가 흡수하는 범위, 남는 클라 상태에 Zustand면 충분한지.
  - **스타일링·폼** — 토큰 코드화 적합성, BE 검증 규칙과 Zod 한 소스로 묶기.
  - **`[확인 필요]` 항목 처리** — 팀 일정·채용 시장·운영 인력 현실 반영.
- **AI는 추천만, 결정은 사람.** 비교표를 그대로 결정으로 박제하지 않는다.
- **02-2를 사람이 확정하기 전에는 Stage 5(ADR)로 넘어가지 않는다**(한 방 생성 방지 — ADR이 사후 합리화가 되지 않도록).
- 포밋 예시 귀결(참고용, 강제 아님): 공개 검색·시터 상세 SEO/LCP → **Next.js 15** SSR/SSG(SPA 탈락),
  인증 영역 CSR 혼용 / 서버 데이터 → **TanStack Query v5** 캐싱·무효화 → 남는 클라 상태 최소 → **Zustand**
  (Redux 탈락 — 보일러플레이트 대비 이득 없음) / **Tailwind CSS**(런타임 비용 0, 토큰 코드화 용이) /
  **React Hook Form + Zod**(BE 검증과 한 소스).

### Stage 5 — ADR 작성 + 검증 체크리스트
- 확정된 결정을 **축별 ADR**로 박제(ADR-001 프레임워크 ~ ADR-005 폼/검증). 각 ADR 구조:
  - 제목 / 상태(Accepted) / 날짜 / 컨텍스트(어떤 제약 때문에 결정이 필요했나)
  - 결정(무엇을 골랐나) / 근거(02-1·02-2 인용) / 기각안과 기각 사유
  - 결과(이후 단계 영향: 03 렌더링 전략 · 04 토큰 코드화 · 10 API 연동)
  - 재검토 트리거(어떤 상황이 오면 이 결정을 다시 본다)
- **BE 도메인 용어는 그 주제 `05-2_openapi.yaml`의 실재 스키마명을 재작명 없이 그대로 인용**(도메인에 없는 엔티티는 끼워넣지 않음 — 포밋이면 `SitterProfile`/`Booking`, 펫사료구독이면 `SubscriptionPlan`/`Subscription`/`Payment`).
- `_검증체크리스트.md` 생성(`<주제>`/`<날짜>` 치환, 아래 본문).
- 마지막으로 산출물 폴더 경로와 "확정 ADR은 03 아키텍처·04 토큰 코드화의 전제 — 비교는 AI, 결정은 사람" 고지를 보고한다.

## 도구 정확성 (probe·degrade)
- **deep-research 스킬**(probe) = 후보 트레이드오프·실사용 사례·생태계 성숙도를 출처와 함께 다출처
  조사. 부재 시 degrade: 내장 지식 비교 + 출처 없는 칸 ⚠️ + "외부 리서치 보강 필요".
- **Context7 MCP**(probe = ToolSearch 존재) = 1순위 후보의 최신 버전·API·breaking change 공식 문서
  확인(2-step: resolve-library-id → query-docs ≤3). 부재 **또는 호출 실패(quota 초과·auth 만료 등
  도구는 등재됐으나 실제 응답을 못 받는 경우 포함)** 시 degrade: 내장 지식 + **"버전 확인 필요 ⚠️"**
  (임의 확정 금지). 각 후속 단계(03/04/09/10/11) 착수 전 공식 문서 1회 확인을 ADR 재검토 트리거로 남긴다.
- **superpowers:brainstorming 스킬**(선택) = 제약 정의 전 평가 축 누락(국제화·오프라인·접근성 의무)
  발산 점검. 부재 시 생략.
- **중단**은 필수 입력(01 핸드오프) 부재 시에만. 그 외는 degrade.

## _검증체크리스트 본문 (Stage 5 생성)
```markdown
# 검증 체크리스트 — <주제> 기술 스택 선정 (작성일: <날짜>)

> AI는 조사·정리·초안까지. 스택 결정은 사람의 판단이다. 비교는 AI, 결정은 사람.

- [ ] 02-2 비교 매트릭스를 사람이 확정한 뒤 ADR로 넘어갔는가 (한 방 생성 금지)
- [ ] 02-1 제약(SEO·성능·팀역량)을 먼저 박고 거기서 후보를 걸렀는가 (스택 먼저·제약 나중 금지)
- [ ] 비교 매트릭스 셀이 점수가 아니라 "근거 한 줄"로 채워졌는가
- [ ] 1순위 후보를 Context7 공식 문서로 대조했는가 (버전 환각 — 리서치↔문서 어긋남 표시)
- [ ] deep-research 후보에 출처가 달렸는가 (출처 없는 비교 칸 ⚠️ 확인)
- [ ] 유행≠적합 — 생태계 성숙도·운영 사례·러닝커브가 평가 축에 있는가
- [ ] ADR마다 기각안과 기각 사유, 재검토 트리거가 있는가 (슬랙으로 끝내지 않고 ADR로 박제)
- [ ] BE 도메인 용어 재작명 0건 (그 주제 `05-2_openapi.yaml`의 실재 스키마명만 계승 — 도메인에 없는 엔티티 인용 0건)
- [ ] 디자인 토큰 "값"을 새로 만들지 않았는가 (스타일링 도구 선택까지가 FE 몫, 토큰 정의는 디자인)
- [ ] 최종 스택 결정은 사람이 내렸는가 (AI 비교표를 그대로 결정으로 박제하지 않았는가)
```

## 주의
- **AI 비교표는 결정이 아니라 초안.** AI는 팀 일정·채용 시장·사내 정치·운영 인력 현실을 모른다.
  "기술적으로 최선"과 "우리가 6개월 안에 안정적으로 운영할 수 있는 것"은 다르다. 비교는 AI, 결정은 사람.
- **유행과 적합을 혼동하지 않는다** — 신생 도구는 생태계 성숙도·운영 사례·러닝커브를 별도 검증.
- **버전 환각 경계** — AI가 옛 버전 API(TanStack Query v4 시그니처 등)를 v5인 양 설명할 수 있다.
  1순위 후보는 반드시 Context7로 대조, 어긋나는 지점 표시.
- **BE 계약·도메인 용어를 임의로 바꾸지 않는다** — FE는 BE 05 OpenAPI 계약의 소비자이지 재정의자가 아니다.
- **디자인 토큰 정의는 이 단계가 아니다** — 스타일링 도구 선택까지가 FE, 토큰 값은 04에서 코드화.
- **흔한 실수 — 스택 먼저, 제약 나중**: 결론을 정해놓고 제약을 끼워 맞추면 ADR이 사후 합리화가 된다.
  반드시 Stage 1(제약)을 먼저 박고 거기서 후보를 거른다.
- **흔한 실수 — ADR을 안 쓰고 슬랙으로 끝냄**: 결정이 채팅에 흩어지면 6개월 뒤 같은 논쟁을 반복한다.
  결정은 반드시 ADR로 박제한다(기각안·재검토 트리거 포함).
