# fe-tech-stack-selection — 기술 스택 선정 자동화 스킬

01단계 핸드오프 분석(화면 목록·컴포넌트 인벤토리·화면↔API 의존맵)을 넣으면, 제약(SEO·성능·팀역량)을
박고 → deep-research로 후보를 조사하고 → Context7로 최신 사실을 확인하고 → 근거 비교 매트릭스를 만든 뒤
→ **사람이 결정**한 스택을 ADR로 박제하는 Claude Code 스킬입니다. 코드는 한 줄도 쓰지 않지만 시리즈에서
가장 되돌리기 비싼 결정을 다룹니다.

> FE 프로세스 2단계 "기술 스택 선정"을 자동화합니다.
> 역할 분담: AI는 조사·정리·초안(후보 회수·최신 사실 확인·비교표). **스택 결정은 사람**(비교는 AI, 결정은 사람).

## 무엇을 만들어 주나

`frontend-output/<주제>/02_기술스택/`에 생성:

| 파일 | 내용 |
|---|---|
| `02-1_제약요구표.md` | SEO·성능·팀역량 3축 제약 + 각 제약→기술 결정 매핑, `[확인 필요]` 태그 |
| `02-2_후보비교매트릭스.md` | 축별 후보 비교(강점·약점·적합도·사례·출처) + Context7 "최신 사실" 컬럼 + 셀=근거 한 줄, 권고안/기각 사유 분리, 결정란은 비움 |
| `02-ADR-NNN_<축>.md` | 축별 ADR(컨텍스트·결정·근거·기각안·결과·재검토 트리거) |
| `_검증체크리스트.md` | 사람이 확인할 항목 |

## 준비물 (입력)

1. **(필수) 01 핸드오프 분석** — `frontend-output/<주제>/01_핸드오프분석/`의 화면 목록·컴포넌트
   인벤토리·화면↔API 의존맵. 제약 추출의 원천. 없으면 스킬이 위치를 묻고 중단합니다.
2. **(권장) BE 05 OpenAPI** — `backend-output/<주제>/05_API/05-2_openapi.yaml`. 도메인 용어·API
   계약을 비교 전제로 둘 때. 없으면 "API 계약 미대조 ⚠️"로 표기하고 01에서 용어를 계승합니다.

## 사용법

01 핸드오프 분석 산출물을 준비한 뒤:

```
01 핸드오프 분석 읽고 포밋 프론트 기술 스택 선정해줘
```

1. 제약 명시화(02-1) → deep-research 후보 조사(02-2) → Context7 최신 사실 확인 자동
2. 비교 매트릭스 완성(셀=근거 한 줄, 결정란 비움)
3. **🔴 스택 결정 게이트** → 당신이 축별로 결정/승인 (유일한 사람 확정 지점)
4. 확정 결정만 ADR로 박제 + 검증 체크리스트

발동 키워드: `프론트 기술 스택 선정`, `프레임워크 선정`, `상태관리 선택`, `스타일링 선택`, `ADR`,
`비교 매트릭스`, `frontend stack`, `framework selection`

## 주의

- **AI 비교표는 결정이 아니라 초안.** 팀 일정·채용 시장·운영 인력 현실은 사람만 안다. 비교는 AI, 결정은 사람.
- **유행≠적합.** 화제성 높은 신생 도구는 생태계 성숙도·운영 사례·러닝커브를 별도 검증하세요.
- **버전 환각 경계.** 1순위 후보는 Context7 공식 문서로 대조(옛 버전 API를 최신인 양 설명 가능).
- **BE 계약·도메인 용어를 임의로 바꾸지 않습니다** — FE는 계약의 소비자이지 재정의자가 아닙니다.
- **디자인 토큰 정의는 이 단계가 아닙니다** — 스타일링 도구 선택까지가 FE, 토큰 값은 04에서 코드화.
- **제약 먼저, 스택 나중** — 결론부터 정하면 ADR이 사후 합리화가 됩니다. ADR은 슬랙이 아니라 파일로 박제.
