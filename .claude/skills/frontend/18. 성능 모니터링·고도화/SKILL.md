# 성능 모니터링·고도화 (Performance Monitoring & Tuning)

17단계가 켜둔 관측 파이프라인(Sentry·web-vitals RUM·GA4)이 쌓은 며칠치 데이터를 입력으로,
"지금 포밋 프론트엔드가 실사용자에게 얼마나 빠른가"를 **숫자로 읽고, 어디가 느려지는지 추세로 보고,
무엇을 고칠지 우선순위로 정리하는** 운영·고도화를 자동화한다. 산출물 = RUM 지표 해석 → 회귀 추세 →
개선 백로그(→01 회귀) + Lighthouse CI 회귀 게이트. **AI는 분산 데이터 회수·정리·계산(추세·p75)과
백로그 초안, "이 수치가 비즈니스적으로 아픈가·이번 스프린트에 넣을 가치가 있나"라는 판단은 사람.**

## 핵심 원칙
- **상위 산출물 계승, 재발명 금지 — 단 확정 상태일 때만.**
  - **17 RUM·Sentry·GA4 = 데이터 출처**: 화면(라우트)·이벤트 택소노미·알림 임계는 17에서 정의된 것 계승. 새 화면 ID·이벤트명을 지어내지 말고, RUM export에 17과 다른 라벨이 보이면 ⚠️ 표기 후 사람 대조.
  - **13 성능 = 랩(lab) 기준선**: 13의 출시 전 Core Web Vitals 측정값·번들 분석·코드 스플리팅 경계를 "랩 vs 필드 괴리" 비교의 기준으로 계승. 13이 부재하면 필드(RUM)만으로 분석하고 "랩 비교 미수행 ⚠️" 표기.
  - 17/13에 잔존한 `⚠️`/`[확인 필요]`(미합의 임계 등)는 보존(임의 확정 금지).
- **랩과 필드를 분리해 읽는다**: Lighthouse(랩) 점수가 좋아도 RUM(필드) p75가 나쁠 수 있다. **현장 분포를 1급 진실로** 본다(13 랩 점수를 믿고 끝내지 않음).
- **숫자는 스크립트가 낸다**: p75·이동평균·증감률을 LLM이 추정하면 그럴듯하게 틀린다. **계산은 반드시 python3**로 — 회수·정리는 AI가, 산술은 코드가, 해석은 사람이.
- **평균이 아닌 p75**: 성능은 분포다. 평균은 빠른 사용자가 느린 사용자를 가린다(CWV 기준이 p75인 이유). **표본 수(n)도 함께** 뽑고 n<100 화면은 "해석 보류".
- **상관을 인과로 단정하지 않는다**: 회귀 추적은 변곡점-배포 **매칭 후보 + 대안 가설(트래픽·외부SDK·노이즈)**까지만 AI에게. 인과 확정은 사람이.
- **단계별 파일로 끊는다**: 현황(18-1)→추세(18-2)→백로그(18-3)→CI/입력변환. 한 방 생성 금지(중간 판단 검토 불가).
- **개선 효과는 다음 사이클 RUM으로만 검증**: "고쳤다"가 아니라 "다음 측정으로 확인"으로 닫는다. budget은 회귀 *방지선*이지 최적화 *목표*가 아니다.

## 파이프라인

### Stage 0 — 입력 확인·도구 probe·degrade
- `<루트>/리서치/rum/`의 RUM export CSV를 읽는다. **없으면 중단**(위치 질의 — 며칠치 데이터 필요). **중단 시, 17-2 web-vitals RUM이 정의한 분해축(`metric_route`·`metric_rating`·`connection_type`·`save_data`·`device_band`·`release`·일자)을 그대로 export 형식으로 안내**한다(사용자가 Vercel Analytics·GA4 Web Vitals에서 무엇을 어떤 컬럼으로 내보내면 되는지 알도록). 17/13 산출물 로드 시도(부재면 권장 degrade + ⚠️).
- **도구 probe**: Context7(ToolSearch 존재) / python3·gh·pnpm·npx(bash 시도). 없으면 degrade(아래 "도구 정확성·degrade").
- 화면 라벨이 17 정의와 일치하는지 1차 점검(불일치 시 ⚠️).

### Stage 1 — RUM 지표 화면별 집계·해석 → 18-1
- 화면(라우트)별 LCP/INP/CLS를 **모두 p75 기준**으로 집계(평균 금지). **계산은 python3 스크립트로 실제 산출**, 표본 수(n) 병기.
- CWV good/needs-improvement/poor 임계로 🟢🟡🔴 라벨(임계값은 **Context7로 web.dev 최신 기준 확인** 후 적용 — 갱신됨, 예: INP good 200ms). 부재 시 내장 기준 + "임계 버전 확인 필요 ⚠️".
- GA4 기준 기기군(모바일 저사양/고사양/데스크톱)별 분포 분해.
- **랩(13 Lighthouse)과 필드(RUM)가 크게 어긋난 화면**을 따로 표시(13 부재면 "랩 비교 미수행 ⚠️").
- **n<100 화면은 "표본 부족 — 해석 보류"** 표시(출렁이는 p75로 우선순위 정하면 헛다리).

### Stage 2 — 회귀 추세 + 배포 상관 추정 → 18-2
- 지표 시계열 + 배포·머지 타임라인(gh) 대조. 화면별 **7일 이동평균·전주 대비 증감률**(python3 계산).
- 추세에서 **변곡점(급격 악화)** 검출 → 직전 배포/PR을 인접 후보로 매칭.
- **"상관은 인과가 아니다" 명시** — 트래픽 구성 변화(저사양 기기 유입↑)·외부 SDK(지도·결제)·측정 노이즈를 **대안 가설**로 함께 적는다.
- 회귀 의심 목록 표: `의심 배포/PR | 대안 가설 | 확인 방법`. **인과 확정은 사람** — AI는 후보 좁히기까지만.

### Stage 3 — 병목을 React/Next 개선안으로 번역 (vercel-react-best-practices)
- 회귀 의심 화면 코드를 **`/vercel-react-best-practices`**로 점검(13에서 1차 최적화에 쓴 스킬을, 여기선 "현장 데이터가 가리키는 병목을 어떤 React 패턴으로 풀지").
- LCP 악화: 데이터 페칭 워터폴 / `'use client'` 경계 과확장으로 서버 렌더 손실 / next/image 미적용 / 폰트 로딩.
- INP 악화: 불필요한 리렌더 / 무거운 동기 작업 / 디바운스 누락(LCP는 로딩, INP는 상호작용 — **원인이 다르므로 지표별로 따로**).
- 각 후보에 `[근거(어느 코드/패턴)] [예상 효과(어느 지표)] [난이도]`. **코드를 바로 고치지 말고 개선안만** — 적용 여부는 백로그·게이트에서 판단. (점검 결과는 18-3 백로그의 근거로 반영.)
- `/vercel-react-best-practices` 스킬이 없으면 **일반 React/Next 점검으로 degrade**(워터폴·리렌더·`'use client'` 경계·next/image 관점 수기 점검) + ⚠️.

### Stage 4 — RICE 개선 백로그 초안 → 18-3
- 18-1·18-2·Stage 3 점검 + 17 Sentry 느린 트랜잭션 종합. 각 항목: 가설 / 대상 화면·컴포넌트 / **목표 지표와 목표값** / 근거(산출물) / 예상 효과 / 난이도.
- **RICE(Reach·Impact·Confidence·Effort) 초안** 점수 + 각 점수 근거 1줄(**점수는 초안 — 실제 우선순위는 다음 게이트에서 사람이 조정**).
- 성능 외 기술부채(번들 비대·미사용 의존성)는 **별도 섹션**.

### 🚦 게이트 — 개선 우선순위 확정 (사람 개입, 필수)
AskUserQuestion으로 18-1/18-2/Stage 3 점검과 **Stage 4가 만든 18-3 백로그 초안**을 제시 → 사용자가 우선순위·채택 확정.
- 핵심 결정 항목(사람이 쥐는 판단):
  - **무엇을 먼저** — 한정된 시간에 LCP를 깎을지 INP를 잡을지, 어느 화면부터.
  - **이 수치가 비즈니스적으로 아픈가** — RUM p75가 나빠도 트래픽·전환 영향이 작으면 후순위일 수 있다.
  - **회귀 인과 확정** — 18-2 후보 중 실제 범인 판정(코드·배포 확인) vs 대안 가설 채택.
  - **표본 부족 항목 처리** — n<100 화면은 데이터 더 모을지 보류.
- **18-3 백로그(초안)를 사람이 확정하기 전에는 Stage 5(CI 게이트·01 입력 변환)로 넘어가지 않는다**(한 방 생성 방지 — 중간 판단 검토). 채택·우선순위 확정은 사람이 한다.

### Stage 5 — Lighthouse CI 회귀 게이트 + 01 회귀(루프 마감) → 18-5·18-4
- **18-5 lighthouserc.js**: 주요 화면(17 RUM 분해 대상·13 위험 화면 = 본 서비스 라우트)에 performance budget. **🔴 LCP·CLS·번들 크기는 lab에서 직접 assert / INP는 lab(Lighthouse)에서 측정 불가한 field 전용 지표 → TBT(Total Blocking Time)로 대리**(핵심 원칙 "랩과 필드 분리"의 직접 귀결 — lab 도구에 field 지표 budget을 직접 걸지 말 것). **16단계 GitHub Actions에 PR 잡으로 추가** 안내, budget 초과 시 실패 + PR 코멘트 룰. `@lhci/cli` 설정은 Context7로 최신 확인(부재 시 내장 + ⚠️). 상단 "초안 — 로컬 실행·검증 필요" 고지. **budget은 회귀 방지선이지 최적화 목표 아님** 명시(lab budget을 field p75(저사양)와 같게 잡으면 PR마다 깨져 무력화 — 현 lab 수준+여유로 회귀를 잡고 개선 후 조인다).

## 도구 정확성·degrade (probe·degrade)
- **Context7 MCP**(probe) = CWV 임계값(갱신됨)·`web-vitals` API·`next/image`·`@lhci/cli` 설정 최신 조회. 없으면 **내장 지식 + "임계/설정 버전 확인 필요 ⚠️"**.
- **python3**(bash probe) = p75·이동평균·증감률 산출의 본체. **없으면 중단 위험 경고** — 산술을 LLM이 추정하면 틀린다. 표본·계산식을 사람이 검증하도록 명시(눈대중 금지).
- **gh CLI**(bash probe) = 배포·머지 타임라인 조회(회귀 상관). 없으면 배포 타임라인 수기 입력 안내(없이는 18-2 변곡점-배포 매칭 생략·⚠️).
- **pnpm / npx / @lhci/cli**(bash probe) = Lighthouse CI. 없으면 **lighthouserc.js·워크플로우는 생성하되 "로컬에서 직접 실행·검증 필요"** 안내(설정 산출은 degrade 안 됨).
- **중단**은 필수 입력(RUM export) 부재 시에만, 그 외는 degrade: 17 부재→화면 라벨 CSV 추출+⚠️ / 13 부재→랩 비교 미수행+⚠️ / Sentry 트랜잭션 부재→백로그 근거 축소 / gh 부재→배포 매칭 생략.

- **한계**: 핵심 원칙(p75·상관≠인과·python3 강제·budget은 방지선·다음 사이클 RUM 검증)을 운영 중 반복 위반하기 쉽다. AI는 회수·정리·계산까지이고, "이 수치가 아픈가"의 판단·인과 확정은 사람이다.
