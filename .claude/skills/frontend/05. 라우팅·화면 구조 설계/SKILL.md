# 라우팅·화면 구조 설계 (Routing & Screen Structure)

01 화면 목록과 03 렌더링 전략, BE 05 OpenAPI를 받아 **화면을 실제 URL 구조와 `app/` 파일 트리로 옮기는** 작업을 자동화한다. Next.js 15 App Router에서 라우트는 곧 파일 시스템이다. 산출물 = 화면→라우트 매핑표(route map) → route group·layout 경계 → `app/` 트리 골격 → 코드 스플리팅 경계. **AI는 방대한 화면을 빠짐없이 라우트로 매핑하고 특수 파일을 갖춘 트리를 찍어내는 회수 작업, 어디에 레이아웃 경계를 그을지·결제에서 탭을 숨길지 같은 구조·UX 판단은 사람.**

## 핵심 원칙

- **상위 산출물 계승, 재발명 금지 — 단 확정 상태일 때만.**
  - **03 렌더링 전략 → 세그먼트 옵션으로 "번역"만**: 어떤 화면이 SSR/SSG/ISR/CSR인지는 03에서 이미 정했다. 이 단계는 그 결정을 `dynamic`/`revalidate`/`generateStaticParams`로 옮길 뿐 — 설계 중 전략을 바꾸고 싶으면 03으로 돌아가 합의한다(여기서 슬쩍 바꾸지 않는다). 03과 어긋나는 행은 `[확인 필요]` + 사유.
  - **BE 05 OpenAPI 계약 계승, 임의 재작명 금지**: 경로·리소스명은 BE 05 OpenAPI에서 온다. `/sitters/{id}`를 `/caregiver/{id}`로 바꾸면 10(API 연동)에서 매핑 비용·혼선이 생긴다. route map에 `operationId`를 함께 적는다. 다르게 가고 싶으면 BE와 합의.
  - 01/03에 잔존한 `⚠️`/`[확인 필요]`는 route map에 보존(임의 확정 금지).
- **route map을 SSOT로 둔다**: 파일 트리가 곧 라우팅이라 표와 코드가 따로 놀면 사고가 난다. 화면→경로→세그먼트→렌더링→인증→API를 한 표에 묶으면 08(화면 구현)·10(API 연동)·12(가드)가 모두 이 표를 참조한다.
- **경계 판단은 사람이 한다**: route group을 어디서 가를지, 결제 화면에서 하단탭을 숨길지는 UX·정보구조 판단이다. AI에게는 "갈리는 속성을 비교해 후보를 근거와 함께 제시"까지만 시키고 단정 금지 — 옵션 2개를 받아 사람이 고른다.
- **단계별 파일로 끊는다**: route map(05-1) → 경계(05-2) → 트리(05-3) → 스플리팅(05-4). 한 방 스캐폴딩 금지 — route map 검토 없이 트리를 찍으면 잘못된 경계가 파일 구조로 굳어 되돌리기 비싸진다.
- **App Router 규칙은 버전마다 바뀐다**: 서버/클라 경계·`template` vs `layout`·`loading`/`error` 동작·`generateStaticParams`/`dynamic` 옵션은 Next 버전에 따라 다르다. **기억이 아니라 Context7로 Next 15 기준 문서를 확인**하며 진행한다(특히 `error.tsx`는 클라이언트 컴포넌트여야 하는 함정).

## 파이프라인

### Stage 0 — 입력 확인·도구 probe·degrade
- `<루트>/01_핸드오프분석/`(화면 목록)과 `<루트>/03_아키텍처/03-1_렌더링전략맵.md`를 읽는다. **둘 중 하나라도 없으면 중단**(위치 질의).
- BE 05 `openapi.yaml` 로드 시도(있으면 계약 계승 모드 — 경로·operationId 1:1, 없으면 화면 목록만으로 도출 + ⚠️ "API 미대조").
- **도구 probe**: Context7(ToolSearch 존재 — 이 단계 핵심) / Figma read(`get_metadata`, ToolSearch 존재). 없으면 degrade(아래 "도구 정확성").

### Stage 1 — 화면→라우트 매핑표(route map) → 05-1
- 화면 1개당 1행. 컬럼: `화면명 | URL 경로 | App Router 세그먼트(파일 경로) | 렌더링(03 계승) | 인증 | 연동 API(operationId)`.
  - **인증 열 = 도메인의 actor에서 도출**(예시 `public/보호자/시터`는 포밋 다중 actor 기준). 01에서 도메인 actor를 확인해 그 도메인 값으로 적는다(단일 actor면 `public/member` 등). actor를 발명하지 말 것.
  - **operationId**: openapi.yaml에 `operationId` 필드가 있으면 그대로 계승. **path만 있고 operationId 필드가 없으면** path 기반 추정 식별자(camelCase 관례) + ⚠️ 표기 후 10 착수 전 BE 대조(operationId 부여 요청). openapi.yaml 자체 부재면 공란(degrade).
- **경로·리소스명은 BE 05 OpenAPI 그대로 계승, 임의 재작명 금지**(예: 시터 상세 `GET /sitters/{id}` → `/sitters/[id]`). 동적 데이터(시터 ID·예약 ID)는 `[id]` 동적 세그먼트로 표기.
- **03 렌더링 전략을 그대로 계승**. 어긋나는 행에는 `[확인 필요]` + 사유.
- **미매핑/고아 섹션 분리**: 01 화면 목록에 있는데 라우트가 안 잡히는 화면, 반대로 라우트만 있고 대응 화면이 없는 경우를 따로 뽑는다(억지 매핑 금지).
- → `05-1_route맵.md`.

### Stage 2 — route group·layout 경계 설계 → 05-2
- **Next.js 15 App Router route group·중첩 layout 규칙을 Context7로 확인하며** 진행.
- 인증 여부·헤더/하단탭 유무·가드가 갈리는 묶음을 `(group)`으로 제안하고, 각 그룹에 어떤 화면이 들어가는지 + 왜 묶었는지 한 줄 근거(예: `(auth)` 로그인/회원가입 — 미니멀 레이아웃 / `(app)` 본체 — 하단탭 공유).
- 각 그룹·세그먼트 layout.tsx가 무엇을 공유하는지(헤더/탭바/Provider) 명시. 루트↔그룹↔세그먼트 layout 중첩을 트리로 표현.
- **경계 애매 화면(예: 결제는 본체 탭을 숨겨야 하나?)은 단정 금지 — 옵션 2개를 장단점과 함께 제시.** 결정은 사람.
- → `05-2_layout구조.md`(트리 + 표).

### 🚦 게이트 — 라우트 구조 확정 (사람 개입, 필수)
AskUserQuestion으로 05-1(route map) + 05-2(경계 후보·옵션)를 제시 → 사용자가 OK/수정.
- 핵심 결정 항목(사람이 쥐는 구조·UX 판단):
  - **route group 경계** — 어디서 레이아웃·가드를 가를지(인증 전/후, 보호자/시터).
  - **경계 애매 화면 처리** — 결제에서 하단탭 숨김 여부 등 옵션 2개 중 택1.
  - **미매핑/고아 항목 처리** — 라우트 없는 화면 추가 / 화면 없는 라우트 제거.
  - **`[확인 필요]`(03 렌더링 불일치) 처리** — 03으로 환원해 합의할지, 사유 두고 진행할지.
- **05-1·05-2를 사람이 확정하기 전에는 Stage 3(트리 스캐폴딩)로 넘어가지 않는다**("한 방 스캐폴딩" 방지 — 잘못된 경계가 파일 구조로 굳으면 되돌리기 비싸다).

### Stage 3 — `app/` 파일 트리 스캐폴딩 → 05-3
- **특수 파일의 정확한 역할은 Context7로 Next 15 기준 확인**하며 진행.
- 확정된 05-1·05-2를 종합해 `src/app/` 트리 골격 생성:
  - 각 라우트에 `page.tsx` + `loading.tsx`/`error.tsx`, 404가 필요한 동적 라우트에는 `not-found.tsx`.
  - 각 `page.tsx` 상단 주석: 화면명 / 렌더링 전략 / 인증 / 연동 operationId.
  - **서버 컴포넌트가 기본**. 클라이언트 상호작용이 필요한 화면(필터/채팅/결제)은 `'use client'` 경계를 잎 컴포넌트에 두도록 주석으로 표시 — **page.tsx 전체를 client로 만들지 않는다**(RSC 이점 상실).
  - 동적 세그먼트 `[id]`에는 `generateStaticParams` 적용 후보 여부를 주석으로(시터 상세는 ISR 후보, 예약 상세는 항상 동적 — 03 전략 따름).
  - **구현 코드는 채우지 말고 골격(파일·export 시그니처·TODO 주석)만.** 트리를 `05-3_app트리.md`에도 적는다(06에서 프로젝트가 서면 옮길 수 있게).
- **route group은 URL에 안 나타남을 확인**: `(auth)`·`(app)`는 레이아웃만 가르고 경로엔 미포함. 그룹명을 실제 URL에 끼운 트리(예: `/(app)/sitters`를 URL로 오해)는 잘못.

### Stage 4 — 코드 스플리팅 경계 표시 → 05-4
- **next/dynamic 사용 기준을 Context7로 확인**하며 진행.
- 초기 진입에 불필요하고 무거운 모듈(지도 SDK·채팅 소켓·결제 위젯·리치 에디터)을 쓰는 세그먼트를 식별, `next/dynamic` 분할 후보로 표시.
- **App Router에서 라우트 단위 분할은 자동임을 전제**로, "라우트 내부에서 더 쪼갤 지점"만 제안(**과분할 경고** — 작은 컴포넌트까지 lazy하면 손해).
- 각 후보에 `ssr: false` 필요 여부(브라우저 전용 API 의존) 표기.
- 표: `세그먼트 | 무거운 모듈 | 분할 방식 | ssr 옵션 | 근거`. → `05-4_코드스플리팅경계.md`(13단계 성능 최적화 입력).

### Stage 5 — 라우트 교차 검증 + 검증 체크리스트
- AI에게 **route map ↔ 화면 목록·렌더링 전략·API 계약 교차 검증**: ① 01 화면 목록의 모든 화면이 05-1에 라우트를 가졌는가(미매핑) ② 라우트만 있고 화면 없는 것(고아) ③ 03 렌더링 전략과 05-3 세그먼트 옵션 일치 ④ openapi.yaml에 없는 경로를 만들지 않았는가 — **불일치 목록만** 뽑는다.
- **미매핑·고아·렌더링 불일치 항목만 모아 사람이 직접 결정**(상태 화면의 실제 UI는 08에서 채움).
- `_검증체크리스트.md` 생성(`<주제>`/`<날짜>` 치환, 아래 본문).
- 마지막으로 산출물 폴더 경로와 "route map이 SSOT — 06에서 프로젝트가 서면 그대로 옮기고 08(화면 구현)의 작업 단위" 고지를 보고한다.

## 도구 정확성 (probe·degrade)
- **Context7 MCP**(probe — 이 단계 핵심) = Next 15 App Router 규칙(route group·중첩 layout·특수 파일·`generateStaticParams`/`dynamic`·next/dynamic) 최신 조회. 프롬프트에 `use context7` 또는 `/vercel/next.js`를 붙여 해당 버전 문서 근거로 진행. 없으면 **내장 지식 + "Next 15 규칙 확인 필요 ⚠️"** 표기(특히 `error.tsx`=클라 컴포넌트, route group=URL 미포함 함정 명시).
- **Figma MCP read**(probe) = `get_metadata`로 프레임 목록을 받아 "그려진 화면이 모두 라우트를 가졌는가"만 교차 점검. 시안 제작·토큰 추출은 디자인 시리즈 몫(여기선 read만, 화면 누락 확인 용도). 없으면 01 화면 목록만으로 점검.
- **중단**은 필수 입력(01 화면 목록·03 렌더링 전략) 부재 시에만. 그 외는 degrade.

## _검증체크리스트 본문 (Stage 5 생성)
```markdown
# 검증 체크리스트 — <주제> 라우팅·화면 구조 설계 (작성일: <날짜>)

> AI는 매핑·트리 골격까지. route group 경계·UX 흐름 결정은 사람의 판단이다.

- [ ] 05-1·05-2를 사람이 확정한 뒤 트리(05-3)로 넘어갔는가 (한 방 스캐폴딩 금지)
- [ ] 01 화면 목록의 모든 화면이 05-1에 라우트를 가졌는가 (미매핑 0건) / 고아 라우트 0건
- [ ] 경로·operationId가 BE 05 OpenAPI 1:1 계승 (재작명 0건 — 다르면 BE 합의 기록)
- [ ] 03 렌더링 전략과 05-3 세그먼트 옵션(dynamic/revalidate/generateStaticParams) 일치 (불일치는 [확인 필요] 후 03 환원)
- [ ] route group `(group)`이 실제 URL에 끼지 않았는가 (트리 생성 후 의도한 URL 확인)
- [ ] page.tsx 전체를 'use client'로 만들지 않았는가 (상호작용은 잎 컴포넌트 경계)
- [ ] 동적 [id] 라우트에 not-found.tsx·loading.tsx 존재 (page.tsx만 찍지 않았는가)
- [ ] error.tsx가 클라이언트 컴포넌트인가 (Next 15 규칙 — Context7 확인)
- [ ] 05-4 코드 스플리팅 후보가 과분할 아닌가 (라우트 내부 무거운 모듈만 / 13단계 입력)
- [ ] 미매핑·고아·렌더링 불일치 항목을 사람이 직접 결정했는가
```

## degrade vs 중단 vs 게이트 블로킹
- **중단**: 01 화면 목록 또는 03 렌더링 전략 부재(원천).
- **degrade**: BE 05 openapi.yaml 부재 → 화면 목록만으로 도출 + ⚠️ "API 계약 미대조"(operationId 열 공란·10에서 채움) / Context7 부재 → 내장 지식 + "Next 15 규칙 확인 필요 ⚠️" / Figma read 부재 → 01 화면 목록만으로 누락 점검 / 01-3 상태화면 커버리지 부재 → 특수 파일은 트리 규칙(동적 라우트 not-found/loading)으로만 배치 + ⚠️.
- **게이트 블로킹**: 게이트(라우트 구조 확정) 미통과 시 Stage 3(트리 스캐폴딩) 차단.

## 주의
- **App Router 규칙은 버전마다 바뀐다** — 기억이 아니라 Context7로 Next 15 기준 확인. `error.tsx`는 클라이언트 컴포넌트여야 하는 등 함정이 있다.
- **route group은 URL에 안 나타난다** — `(auth)`·`(app)`는 레이아웃만 가른다. 그룹명을 경로에 끼운 트리는 잘못 — 트리 생성 후 실제 URL이 의도대로 나오는지 확인.
- **전체 페이지를 `'use client'`로 만들지 않는다** — 상호작용이 필요해도 page 최상단에 붙이면 RSC 이점이 사라진다. 잎 컴포넌트에만 경계를 두고, AI가 page.tsx 전체를 client로 만들었다면 되돌린다.
- **동적 라우트의 not-found·loading 누락** — `[id]` 화면은 404·로딩을 반드시 다룬다. AI가 `page.tsx`만 찍고 빠뜨리는 경우가 잦으니 트리에서 확인(상태 화면 실제 UI는 08에서).
- **흔한 실수 — API 경로 재작명**: BE 경로를 바꾸면 10단계 매핑 비용 발생. OpenAPI 경로를 그대로 따오고, 다르면 BE와 합의.
- **흔한 실수 — 한 방 스캐폴딩**: 게이트(05-1·05-2 확정) 없이 트리를 찍으면 잘못된 경계가 파일 구조로 굳는다.
