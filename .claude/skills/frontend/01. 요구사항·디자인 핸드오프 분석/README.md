# fe-handoff-analysis — 요구사항·디자인 핸드오프 분석 자동화 스킬

디자인 핸드오프(시안·에셋·스펙)와 BE의 OpenAPI 계약을 넣으면, 프론트엔드 관점으로 다시 읽어
화면 목록·컴포넌트 인벤토리·상태화면 커버리지·화면↔API 의존맵·모호점 질문 리스트를 만드는
Claude Code 스킬입니다. 사람은 **화면·컴포넌트 범위 확정 1번**만 개입합니다.

> FE 프로세스 01단계 "요구사항·디자인 핸드오프 분석"을 자동화합니다.
> 역할 분담: AI는 시안·계약에서 빠짐없이 추출(회수율), **무엇을 공통화할지·누구에게 질문할지 판단은 사람**.

## 무엇을 만들어 주나

`frontend-output/<주제>/01_핸드오프분석/`에 생성:

| 파일 | 내용 |
|---|---|
| `01-1_화면목록·컴포넌트인벤토리.md` | 화면 목록(화면ID·플로우·표시 형태·미배치) + 컴포넌트 인벤토리(배리언트·범용/도메인·Code Connect·구현 우선순위) |
| `01-2_화면API의존맵.md` | 화면↔엔드포인트 매핑 + 근거 + API 갭/미사용 플래그 + Booking 상태 전이 표 |
| `01-3_상태화면커버리지.md` | 화면 × 상태(정상/빈/로딩/에러/권한없음) 매트릭스 + 디자인에 요청할 상태 화면 |
| `01-4_질문리스트.md` | [디자인/BE/기획/FE내부]로 분류한 모호점 + 근거 + 막히는 작업 + 담당자 |
| `_검증체크리스트.md` | 사람이 확인할 항목 |

## 준비물 (입력)

1. **디자인 13 핸드오프** — 시안(Figma 파일/프레임), 에셋, 스펙(간격·컬러·타이포), 디자인 토큰.
   Figma MCP로 읽거나, MCP가 없으면 디자이너가 준 스크린샷·스펙 .md를 작업 폴더에 둡니다.
2. **BE 05 openapi.yaml** — 화면↔API 의존맵의 계약 원본(BE 산출물 `05_API/`에서). 작업 폴더에 둡니다.
3. 둘 중 **하나라도 있으면** 진행(나머지는 "입력 부재"로 표기), **둘 다 없으면** 위치를 묻고 중단.

> 시안 제작·디자인 토큰 정의는 디자인 시리즈 몫입니다. 이 스킬은 시안을 **분석**할 뿐, 만들거나 토큰을 새로 정의하지 않습니다(토큰 코드화는 04단계).

## 사용법

디자인 핸드오프와 `openapi.yaml`을 작업 폴더에 둔 뒤:

```
디자인 핸드오프랑 openapi.yaml 읽고 FE 착수 분석해줘
```

1. 화면 목록 추출 → 컴포넌트 인벤토리 자동 생성
2. **화면·컴포넌트 범위 확정** → 당신이 OK (유일한 개입)
3. 화면↔API 의존맵 → 상태화면 커버리지 → 질문 리스트 자동

발동 키워드: `디자인 핸드오프 분석`, `화면 목록`, `컴포넌트 인벤토리`, `화면 API 의존맵`, `FE 착수 분석`, `handoff analysis`, `component inventory`

## 주의

- **AI는 화면↔API 의존관계를 그럴듯하게 지어냅니다.** 근거 표기를 강제하고, 핵심 화면은 OpenAPI 원문과 직접 대조하세요.
- **시안에 없다고 "없다"고 단정하지 마세요.** 못 찾은 상태 화면은 다른 파일에 있을 수 있습니다 — "디자인에 질문"으로.
- **토큰·컴포넌트를 새로 만들지 마세요.** 시안에 있는 것만 기록 — 토큰 정의는 디자인, 코드화는 04.
- **도메인 용어를 한글화·재작명하지 마세요.** SitterProfile·Booking 등은 BE 계약 그대로.
- **한 방 프롬프트 금지.** 단계별 산출물을 파일로 남기고 게이트에서 확인합니다.
- **질문 리스트는 코딩 전 합의 자료입니다.** 이게 이 단계의 진짜 목적 — 검토·합의 시간은 줄지 않습니다.
