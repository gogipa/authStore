# 요구사항·디자인 핸드오프 분석 (Handoff Analysis)

프론트엔드가 코드를 한 줄 쓰기 전에 **무엇을 만들지** 확정하는 단계. 입력은 둘 — 디자인 시리즈의
핸드오프(시안·에셋·스펙·토큰)와 BE 시리즈의 OpenAPI 계약. 이 둘을 FE 관점으로 다시 읽어
화면 목록·컴포넌트 인벤토리·상태화면 커버리지·화면↔API 의존맵·질문 리스트를 산출한다.
**AI는 회수율(시안·계약에서 화면·컴포넌트·의존관계를 빠짐없이 출처와 함께 추출), 무엇을 공통화할지·
무엇을 누구에게 질문할지 판단은 사람.**

## 핵심 원칙

- **상위 산출물 계승, 재발명 금지 — 단 확정 상태일 때만.**
  - **BE 05 도메인 용어를 OpenAPI 스키마명 그대로 1:1 계승**: 도메인 용어·엔티티·상태 enum은 **해당 서비스의 BE 05 `openapi.yaml`(`components/schemas`)에서 실측한 이름을 그대로** 쓴다. **임의 재작명·한글화 금지**(예: 영문 스키마명→한글 별칭 금지). 화면 라벨(사용자에게 보이는 한글)과 코드/스키마 식별자(영문 도메인 용어)를 **분리해** 기록한다.
    - 관통 예시(포밋·돌봄): `Member`·`Pet`·`SitterProfile`·`Booking`(REQUESTED→ACCEPTED→IN_PROGRESS→COMPLETED|CANCELED)·`Payment`·`Review`·`Chat`·`Notification`. **이는 포밋 도메인의 예시일 뿐** — 다른 서비스면 그 BE 05 스키마(예: 펫사료구독 = `Subscription`(status: active/alt_offered/cancelling/cancelled/paused)·`SubscriptionPlan`·`Pet`·`Payment`)가 정본이다. **예시 용어를 도메인과 무관하게 강제하지 말 것**(없는 엔티티·상태머신을 지어내지 말 것).
  - **디자인 토큰을 새로 만들지 않는다**: 인벤토리에는 시안에 **있는** 토큰/컴포넌트 매핑만 기록. 토큰 정의·시안 제작은 디자인 몫이고 토큰 코드화는 04에서 한다(여기서 발명 금지 — 디자인 시리즈 중복 경계).
  - **Code Connect 매핑이 이미 있으면 그대로 계승**: `get_code_connect_map`에 코드 컴포넌트명이 잡히면 인벤토리에 표기만(본격 매핑은 04).
- **추출과 판단을 분리한다**: AI에게는 "빠짐없이 건져서 출처와 함께 표로"라는 회수 작업만 시킨다. 공통화 여부·질문 대상·우선순위는 사람.
- **의존관계는 추론이지 사실이 아니다**: "이 화면이 이 엔드포인트를 호출할 것"은 AI의 추정. **근거(어느 시안·어느 OpenAPI path) 표기를 강제**하고, API 갭·미사용 표시는 사람이 OpenAPI 원문과 대조한다.
- **시안에 없는 것을 "없다"고 단정하지 않는다**: 못 찾은 상태 화면은 다른 페이지·파일에 있을 수 있다. 누락은 **"디자인에 질문"**으로 남기고 단정 금지.
- **상태 화면을 1급으로 점검한다**: 시안은 happy path만 그려지기 쉽다. 빈/로딩/에러/권한은 구현 분량의 절반 가까이인데 핸드오프에서 빠지기 일쑤 — 화면×상태 매트릭스로 강제 점검.
- **단계별 파일로 끊는다**: 화면 목록·인벤토리(01-1) → 의존맵(01-2) → 커버리지(01-3) → 질문(01-4). 한 방 프롬프트 금지(중간 오류가 뒤로 전파).

## 파이프라인

### Stage 0 — 입력 확인·도구 probe·degrade
- 디자인 13 핸드오프와 BE 05 `openapi.yaml`을 찾아 읽는다. **둘 다 없으면 중단**(위치 질의).
- **도구 probe**: Figma MCP(ToolSearch에 `get_metadata`/`get_design_context`/`get_screenshot`/`get_code_connect_map` 존재로 판별) / Context7(존재) / python3(bash로 `yaml` 파싱 가능 여부). 부재 시 degrade(아래 "도구 정확성").
- OpenAPI는 python3 `yaml.safe_load`로 파싱해 path·schema 목록을 먼저 확보(의존맵 근거).

### Stage 1 — 화면 목록 추출 → 01-1 (상)
- Figma `get_metadata`로 프레임 계층을 가볍게 받아 화면 목록의 뼈대를 만든다(토큰 절약 1차 스캔).
- 규칙: 화면마다 **화면ID(SCR-xx) · 화면명 · 플로우 · 표시 형태**. 모달/바텀시트/토스트 같은 비-라우트 오버레이는 "표시 형태"로 구분. 같은 화면의 상태 변형(빈/로딩/에러)은 같은 화면ID로 묶음. 어느 플로우에도 안 붙는 프레임은 **"미배치"** 섹션으로 분리(억지 배치 금지).
- 표: `화면ID | 화면명 | 플로우 | 표시 형태 | 비고`.

### Stage 2 — 컴포넌트 인벤토리 추출 → 01-1 (하)
- 핵심 화면 몇 개를 `get_design_context`로 상세히 읽어 반복 UI를 카탈로그화.
- 컴포넌트 후보마다: 이름(가칭) · 등장 화면 · 배리언트(크기/상태/종류) · **디자인 시스템 컴포넌트 매핑 여부**. `get_code_connect_map`에 이미 매핑된 코드 컴포넌트명이 있으면 함께 표기.
- **범용(Button/Input/Card/Badge)과 도메인 전용을 구분**(도메인 전용 예시 — 포밋: SitterCard/BookingStatusChip, 펫사료구독: PlanCard/SubscriptionStatusChip). 아직 코드 없으니 "구현 예정"으로 두되 04·07 구현 우선순위(등장 빈도순)를 제안.
- **시안 토큰을 새로 정의하지 말고 있는 것만 기록**(디자인 중복 경계).

### 🚦 게이트 — 화면·컴포넌트 범위 확정 (사람 개입, 필수)
AskUserQuestion으로 01-1(화면 목록 + 컴포넌트 인벤토리)을 제시 → 사용자가 OK/수정.
- 핵심 결정 항목(사람이 쥐는 판단):
  - **화면 범위** — 이번 사이클에 만들 화면, "미배치" 프레임 처리(포함/제외/디자인 확인).
  - **컴포넌트 공통화 경계** — 이 반복 요소를 정말 공통 컴포넌트로 뽑을지(과추출 경계).
  - **도메인/범용 구분** — 04·07로 넘길 우선순위.
- **01-1을 사람이 확정하기 전에는 Stage 3로 넘어가지 않는다**(한 방 생성 방지 — 잘못 추출된 화면이 의존맵·커버리지로 전파되는 것을 차단).

### Stage 3 — 화면↔API 의존맵 → 01-2
- BE `openapi.yaml`(Stage 0 파싱본)과 확정된 화면 목록을 함께 읽어 각 화면이 호출할 엔드포인트(method+path)를 매핑.
- **도메인 용어는 OpenAPI 스키마명 그대로**(해당 서비스 BE 05 `components/schemas` 실측 이름), 재작명 금지. 예시 용어(Member/Pet/SitterProfile/Booking 등)는 포밋 도메인 — 다른 서비스엔 없을 수 있으니 강제하지 말 것.
- **갭 표시**: 화면이 필요로 하는 데이터인데 응답 스키마에 필드 없음 → **"API 갭(미정의)"**. OpenAPI엔 있는데 어느 화면도 안 씀 → **"미사용(확인 필요)"**. **05-1 엔드포인트표 등 다른 BE 산출물엔 있으나 `openapi.yaml`에 path 없음 → "path 미정의(BE 산출물 내부 불일치)"** — `openapi.yaml`을 계약 SSOT로 삼되 차이를 BE 질문으로 회수. 각 매핑에 **근거(출처 시안/path)** 강제.
- **핵심 엔티티 상태 전이**(BE 05 스키마 enum 실측 — 포밋 예시 Booking REQUESTED→…→COMPLETED|CANCELED / 펫사료구독 예시 Subscription active→…→cancelled|paused)를 화면이 어떻게 표시/전이시키는지 별도 표. 도메인에 상태머신이 둘 이상이면(예: Subscription status + Payment status) 각각.
- 갭·미사용·상태 매핑은 추론이므로, 사람이 핵심 화면 몇 개를 OpenAPI 원문과 직접 대조하도록 안내.

### Stage 4 — 상태화면 커버리지 매트릭스 → 01-3
- 화면 목록의 각 화면에 대해 **정상 / 빈(empty) / 로딩(스켈레톤) / 에러 / 권한없음** 열로 O/X 점검.
- `get_screenshot`으로 해당 상태 프레임이 시안에 실제로 있는지 사람이 눈으로 확인(텍스트로 안 잡히는 시각 맥락).
- **데이터를 부르는 화면(목록·상세·검색)인데 빈/에러 상태가 없으면 "시안 누락" 강조**. 로그인 필요 화면(예약·결제·마이)인데 권한없음 분기가 없으면 표시.
- 누락 칸을 모아 끝에 **"디자인에 요청할 상태 화면"** 목록으로 분리. **단정 금지** — "디자인에 질문"으로(다른 파일에 있을 수 있음).

### Stage 5 — 모호점 질문 리스트 통합 + 검증 체크리스트 → 01-4, _검증체크리스트
- 01-1~01-3의 "확인 필요"·"누락"·"갭" 태그를 모아 한 장으로 통합.
- **분류**: [디자인에 질문] / [BE에 질문] / [기획에 질문] / [FE 내부 결정]. 각 질문에 **근거(출처 산출물·항목)**와 **막히는 작업**(안 정해지면 무엇을 못 만드나)을 표기. **답을 지어내지 말 것 — 모르면 질문으로 남긴다.**
- `_검증체크리스트.md` 생성(`<주제>`/`<날짜>` 치환):

```markdown
# 검증 체크리스트 — <주제> 요구사항·디자인 핸드오프 분석 (작성일: <날짜>)

> AI는 추출·구조화(회수율)까지. 공통화·질문 대상·범위 확정은 사람의 판단이다.

- [ ] 화면 목록: "미배치" 프레임을 게이트에서 처리(포함/제외/디자인 확인)했는가
- [ ] 컴포넌트 인벤토리: 시안에 없는 토큰/컴포넌트를 새로 지어내지 않았는가 (있는 것만 기록 — 디자인 중복 경계)
- [ ] 의존맵: 각 엔드포인트 매핑에 근거(시안/path) 표기 / 핵심 화면 몇 개는 OpenAPI 원문과 직접 대조(AI가 지어낸 의존관계 차단)
- [ ] 의존맵: 도메인 용어가 해당 서비스 OpenAPI 스키마명과 1:1 (재작명 0건). 포밋 예시 용어(Booking/SitterProfile 등)를 도메인에 없는데 끌어다 쓰지 않았는가(상태머신은 실측 enum 기준)
- [ ] 의존맵: "API 갭(미정의)"·"미사용(확인 필요)"이 BE에 질문으로 넘어갔는가
- [ ] 커버리지: 데이터 화면의 빈/에러, 인증 화면의 권한없음 누락을 "디자인에 질문"으로(단정해서 그려달라 하기 전 확인)
- [ ] 질문 리스트: 모든 항목에 근거·막히는 작업·담당자 표기 / 답을 지어낸 항목 없음
- [ ] 질문 리스트는 코딩 시작 전 디자인·BE·기획과 합의(이 단계의 진짜 목적)
```

- 마지막으로 산출물 폴더 경로와 "질문 리스트는 코딩 전 합의 자료 — 이 단계 산출물은 02·03·04·05·10의 입력" 고지를 보고한다.

## 도구 정확성 (probe·degrade)
- **Figma MCP**(probe) = 시안을 코드 관점으로 읽는 핵심. `get_metadata`(화면 목록 1차 스캔) / `get_design_context`(인벤토리·스펙) / `get_screenshot`(상태 화면 시각 확인) / `get_code_connect_map`(기존 매핑 계승). **read만 사용 — `use_figma`/`create_new_file` 등 write 도구 호출 금지**(시안 제작·토큰 정의는 디자인 몫). 부재 시 degrade: 디자이너가 준 스크린샷·스펙 .md를 수기 입력으로 받아 화면 목록·인벤토리를 만들고 "Figma 미연동 — 프레임 구조 추정 ⚠️" 표기.
- **Context7 MCP**(probe) = 보조. 이 단계는 코드를 거의 안 쓰지만, OpenAPI를 FE 타입으로 어떻게 계승할지 가늠할 때 `openapi-typescript` 최신 사용법 조회 정도(실제 타입 생성은 10). 부재 시 내장 지식 + "버전 확인 필요 ⚠️".
- **python3**(bash probe) = `yaml.safe_load`로 openapi.yaml의 `paths`·`components/schemas` 목록을 추출해 의존맵(01-2)의 근거로 쓴다(엔드포인트를 손으로 옮기다 생기는 오기 방지). pyyaml 미설치면 `pip install pyyaml`(대개 즉시 가용) 안내, 그래도 안 되면 사람이 YAML을 텍스트로 읽도록 degrade. 파싱 실패 시 YAML 형식 오류를 알리고 의존맵은 ⚠️ 표기 후 수기 진행.
  - ⚠️ **경로 주의**: 한글·공백 포함 경로(볼트 폴더)에서 일부 CLI가 깨질 수 있으니, 필요 시 yaml을 scratchpad로 복사해 파싱한다.
- **중단**은 필수 입력(시안·OpenAPI 둘 다) 부재 시에만. 하나만 부재면 가능한 산출물만 만들고 나머지는 "입력 부재"로 명시.

## 주의
- **AI는 의존관계를 그럴듯하게 지어낸다.** "이 화면이 이 엔드포인트를 호출"은 추론. 근거 표기 강제 + 핵심 화면은 OpenAPI 원문 직접 대조. 특히 API 갭·미사용은 AI가 잘못 연결했을 수 있다.
- **시안에 없는 것을 "없다"고 단정하지 않는다.** 못 찾은 상태 화면은 다른 페이지·파일에 있을 수 있다 — "디자인에 질문"으로 남기고 단정해서 새로 그려달라 하기 전에 확인.
- **디자인 시리즈와 중복하지 않는다.** 이 단계는 시안을 **분석**하는 것이지 시안 제작·토큰 정의가 아니다(그건 디자인 몫). 인벤토리에 토큰을 새로 만들지 말고 있는 것만 기록 — 토큰 코드화는 04.
- **도메인 용어를 임의로 바꾸지 않는다.** SitterProfile→"시터정보", Booking→"예약건" 식 재작명은 BE 계약과 어긋난다. 화면 라벨(한글)과 코드/스키마 식별자(영문)를 구분해 기록.
- **흔한 실수 — 한 방 프롬프트**: 화면 목록부터 질문 리스트까지 한 번에 시키면 중간 오류(잘못 추출된 화면, 틀린 의존관계)가 뒤로 전파된다. Stage를 끊어 게이트에서 사람이 확인하고 넘어간다.
- **흔한 실수 — 정상 화면만 보고 끝내기**: 시안이 happy path만 그려져 있을 때 그대로 화면 목록을 확정하면 빈/에러/권한 상태가 통째로 누락된 채 다음 단계로 간다. 상태 커버리지 매트릭스(Stage 4)를 반드시 거친다.
