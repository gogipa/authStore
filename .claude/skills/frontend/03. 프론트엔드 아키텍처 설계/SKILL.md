# 프론트엔드 아키텍처 설계 (Frontend Architecture Design)

스택을 정한 뒤 "이 화면들을 어떤 구조 위에 올릴 것인가"를 코드 한 줄 쓰기 전에 결정한다. 산출물 =
① 페이지별 렌더링 전략 매핑(CSR/SSR/SSG/ISR) ② feature-based 폴더 구조·모듈 경계 ③ 데이터 흐름 규약
+ 결정을 굳히는 ADR. **AI는 후보 회수·문서화·lint 변환·다이어그램 초안, 렌더링 전략·모듈 경계 같은
트레이드오프 판단은 사람**(위임하면 우리 제약을 모르는 그럴듯한 구조가 나온다).

## 핵심 원칙

- **상위 산출물 계승, 재발명 금지 — 단 확정 상태일 때만.**
  - **01 화면 목록·화면↔API 의존맵 → 렌더링 전략 입력**: 화면명·상태(빈/로딩/에러)·의존 API를 그대로
    계승. 01에 없는 화면을 지어내지 말고, 누락 의심은 "확인 필요"로.
  - **02 스택 ADR → 전제**: Next.js 15 App Router / TanStack Query v5 / Zustand / Tailwind 귀결을 전제로만
    쓰고 재논의하지 않는다. 02에 잔존한 `⚠️`/`[확인 필요]`는 보존(임의 확정 금지).
  - **BE 05 OpenAPI 계약·도메인 용어 계승**: feature 이름·도메인 타입은 **그 서비스의 BE 정본 스키마명을
    실제로 읽고** 그대로 계승(임의 재작명·발명 금지). ⚠️ 도메인 목록은 서비스마다 다르다 — 아래 "포밋 예시"의
    `Member·Pet·SitterProfile·Booking·Payment·Review·Chat·Notification`은 **포밋(돌봄) 전용 예시일 뿐**,
    고정 리스트가 아니다. 그 서비스 BE 05 OpenAPI에 없는 도메인(예: 단일 actor 커머스엔 SitterProfile·
    Booking·Chat이 없음)을 끌어다 쓰지 말 것.
- **결정과 기록을 분리한다**: AI에게는 "후보를 빠짐없이 표로 / 결정을 ADR로 / 경계를 lint로" 같은
  회수·기록·코드화만 맡긴다. 렌더링 전략·모듈 경계는 **사람이 확정**(게이트).
- **`'use client'` 경계는 화면이 아니라 트리로 본다**: "이 페이지는 CSR"이 아니라 "어느 서브트리부터
  클라이언트인가". 인터랙티브한 필터·폼만 클라이언트로 내려 경계를 잘게 잡는다(번들 축소).
- **화면이 아니라 도메인(feature)으로 묶는다**: page 단위로 나누면 "시터 정보"가 여러 폴더에 흩어진다.
  feature(sitter/booking…) 단위 + BE 도메인 이름 1:1 계승으로 변경을 한 폴더에 가둔다.
- **경계는 글이 아니라 lint로 박는다 — 단 적용은 06**: 03에서는 ESLint 경계 규칙을 **초안**으로만 남기고
  의존 방향(app→features→shared/entities)을 못 박는다. 실제 머지·검증은 06 개발 환경 구축에서.
- **여기서 구현하지 않는다(경계)**: 디자인 토큰·Tailwind config는 04, 라우트 맵·route groups는 05, 상태 훅·스토어 구현은 09·10. 03은 **규약 선언**까지.

## 파이프라인

> 사람 검토 지점을 끼워 **끊어 간다**. 한 방 프롬프트(렌더링 매핑~폴더 생성 일괄)는 잘못된 렌더링 가정 위에 폴더가 생성돼 오류가 뒤로 전파된다.

### Stage 0 — 입력 확인·도구 probe·degrade
- `<루트>/01_핸드오프분석/`을 읽는다(화면 목록·화면↔API 의존맵·상태화면). 없으면 **중단**(위치 질의).
- `02_기술스택/`ADR·BE `05-2_openapi.yaml` 로드 시도(있으면 계승, 없으면 정본 가정 + ⚠️).
- **도구 probe**: Context7(ToolSearch 존재) / deep-research(스킬 존재). 없으면 degrade(아래 "도구 정확성").

### Stage 1 — 화면별 렌더링 전략 1차 매핑 → 03-1
- 01의 화면 전수에 대해 **결정이 아니라 후보**를 근거와 함께 표로 매핑.
- 판단 기준(이 기준으로만, 임의 추가 금지):
  - SEO 필요 / 공개 접근 가능 → SSR 또는 SSG/ISR 후보
  - 로그인 후에만 보이는 개인화 화면 → CSR(클라이언트 페칭) 후보
  - 거의 안 바뀌는 정적 콘텐츠(약관 등) → SSG 후보
  - 자주 바뀌지만 매 요청 최신일 필요 없는 목록 → ISR(revalidate) 후보
  - 실시간성이 핵심(채팅) → CSR + 별도 실시간 채널
- 표 컬럼: `화면 | 공개여부 | 데이터 신선도 | SEO 필요 | 전략 후보 | 근거 한 줄 | 확인 필요`.
- 판단이 갈리는 화면은 단정하지 말고 **"확인 필요"**에 무엇이 모호한지 기재.
- 최신 App Router 캐싱·`dynamic` 동작은 **use context7로 확인**, `getServerSideProps`(Pages Router) 등 구버전 API는 쓰지 않는다.
- **포밋(돌봄 도메인) 귀결 예시**(사람이 검토·확정 / 다른 서비스엔 그대로 적용 금지): 시터 검색/상세=SSR(SEO·LCP, 필터는 클라이언트 서브트리), 홈=ISR, 약관류=SSG, 마이/예약/결제/알림=CSR, 채팅=CSR+실시간 채널. ⚠️ 채팅·실시간·시터 검색 같은 화면이 **없는 도메인**(예: 단일 actor 구독 커머스)에선 해당 항목을 빼고, 그 서비스의 공개/인증 화면 분할로 다시 판단한다.

### 🚦 게이트 — 렌더링 전략·아키텍처 확정 (사람 개입, 필수)
AskUserQuestion으로 03-1(렌더링 전략 후보 표 + "확인 필요" 항목)을 제시 → 사용자가 OK/수정.
- 핵심 결정 항목(사람이 쥐는 트레이드오프 판단):
  - **화면별 렌더링 전략** — 포밋의 SEO 목표·트래픽·인증 경계 맥락은 AI가 모른다(일반론 "보통 SSR" 금지).
  - **`'use client'` 경계 위치** — 페이지 전체가 아니라 어느 서브트리부터 클라이언트인가.
  - **feature 스코프** — 그 서비스 BE 도메인에서 도출한 feature 중 MVP(01·기획 03 Must)에 드는 것부터. 나머지는 규칙만 두고 비워둠(과설계·죽은 폴더 경계).
  - **"확인 필요" 항목 처리**.
- **03-1을 사람이 확정하기 전에는 Stage 2(ADR)·Stage 3(폴더)로 넘어가지 않는다**(한 방 생성 방지).

### Stage 2 — 렌더링 전략 확정 + ADR 기록 → 03-ADR-003
- 사람이 확정한 결정·기각안을 ADR 포맷으로 굳힌다: 제목 / 상태(Accepted) / 맥락 / 결정 / 근거 / 기각안 / 영향(폴더·캐싱 규약에 미치는 영향).
- 기각안은 사람이 준 것만 기록(예: "전부 CSR(SPA)"=검색 SEO 손해로 기각 / "전부 SSR"=개인화·실시간까지 서버 렌더하면 캐시·인증 복잡도만 증가로 기각). AI가 기각 사유를 발명하지 않는다.
- ADR 번호는 **02 ADR 시리즈의 마지막 번호 +1**로 이어붙임(02가 001~005면 `006`). 02 산출물을 실제로 확인해 결정 — 고정값 아님.

### Stage 3 — feature-based 폴더 구조 합의·스캐폴딩 → 03-2
- **도메인(feature) 단위**로 묶고 BE 도메인 이름 1:1 계승. ⚠️ features 목록은 **그 서비스 BE 05 OpenAPI에서 실제로 도출** — 예: 포밋(돌봄)이면 `auth, pet, sitter, booking, payment, review, chat, notification`, 단일 actor 구독 커머스면 `auth, pet, plan, subscription, payment`처럼 도메인마다 다르다. 없는 도메인(sitter·booking·chat 등)을 예시에서 그대로 베껴오지 말 것. MVP(01·기획 03 Must) 스코프만 우선 생성.
- 레이어 규칙:
  - `app/` : Next App Router 라우트·layout·page (얇게, feature 조립만)
  - `features/*` : 도메인별 api·hooks·components·model(타입/스키마)·store
  - `shared/` : 도메인 무관 재사용 — ui(공통 컴포넌트 자리만, 토큰 코드화는 04), lib(fetcher·utils), config
  - `entities/` : 여러 feature 공유 도메인 타입(Member, Money 등)
- 각 feature는 `index.ts`(배럴)로 public API만 노출, 내부 파일 직접 import 금지.
- **먼저 (1) 트리 다이어그램 (2) "무엇을 어디 둘지" 1줄 설명표를 보여주고, 사람이 OK한 뒤에만** 빈 폴더·index.ts placeholder를 실제 생성. `'use client'` 경계 위치도 이 문서에 함께 기록.
- ⚠️ `shared/ui`는 **자리만** 잡는다 — 색·간격·컴포넌트 계층(디자인 토큰)은 04의 몫. 03에서 Tailwind config를 건드리지 않는다.

### Stage 4 — 모듈 경계 ESLint 규칙 초안 → 03-2에 추가
- 경계를 구두 약속이 아니라 CI에서 깨지는 규칙으로 변환(**초안만** — 적용은 06):
  - `features/A`가 `features/B`의 내부 파일 직접 import 금지(feature 간 통신은 각자 `index.ts` public API로만).
  - `shared/`·`entities/`는 `features/`·`app/`을 import 금지(의존 방향: `app→features→shared/entities`).
  - `eslint no-restricted-imports` 또는 import 경계 패턴으로 표현, 각 규칙 위에 "왜 막는지" 주석 한 줄.
- 의존 방향 mermaid 다이어그램 동봉. **use context7로 현재 ESLint flat config 문법 확인** 후 맞춘다.
- ⚠️ 이 규칙을 바로 머지하면 환경(06) 미비로 충돌 — **문서 초안으로만 남기고** 실제 적용·검증은 06으로 넘긴다.

### Stage 5 — 데이터 흐름 규약 + 검증 체크리스트 → 03-2 / _검증체크리스트
- 03-2에 데이터 흐름 규약 섹션 추가(**경로·규약만**, 구현은 09·10 참조 링크):
  - SSR/RSC 화면: 서버 컴포넌트에서 직접 fetch → props로 클라이언트 컴포넌트 전달, 목록은 서버에서 TanStack Query prefetch + `HydrationBoundary`로 클라이언트 전달.
  - CSR 화면: 클라이언트에서 TanStack Query 훅 페칭(queryKey 규약 `[feature, 동작, params]`).
  - **서버 상태(원격 데이터)=TanStack Query 전담 / 전역 클라이언트 상태(UI·세션)=Zustand 전담** → "이건 서버 상태인가 클라 상태인가" 판단 기준 표. 상세 구현은 `[[09. 상태 관리]]` 참조 링크만(중복 서술 금지).
  - 인증 토큰을 어디서 읽고 RSC fetch / 클라 fetch에 각각 어떻게 실리는지 **경로만** 표시(상세는 09·12).
- mermaid 시퀀스/플로우로 흐름 초안.

## 도구 정확성 (probe·degrade)
- **Context7 MCP**(probe) = Next.js 15·React 19 RSC·서버 액션·캐싱(`fetch` 캐시·`revalidate`·`dynamic`·`generateStaticParams`)·ESLint flat config 최신 표기 조회. **이 단계의 핵심** — 14→15 사이 동작·기본값이 바뀐 영역이라 학습 지식/블로그로 판단하면 구버전 패턴이 섞인다. 부재 시 **내장 지식 + "버전 확인 필요 ⚠️"** 표기.
- **deep-research 스킬**(probe) = "검색 결과 페이지 SSR + SEO·캐시 전략" 같은 설계 트레이드오프에 외부 근거가 필요할 때 교차 검증 리포트(`/deep-research`). 라이브러리 API는 Context7, 설계 트레이드오프 조사는 deep-research로 역할 분담. 부재 시 생략 + 사람 판단 명시.
- **Figma MCP는 이 단계에서 거의 안 쓴다** — 시안→코드는 04·07의 몫. 03 입력은 01 화면 목록·상태·의존맵.
- **중단**은 필수 입력(01) 부재 시에만. 그 외는 degrade.

## 주의
- **렌더링 전략을 AI에게 결정시키지 않는다** — AI는 "보통 SSR" 일반론을 그럴듯하게 내놓지만 포밋의 SEO 목표·트래픽·인증 경계를 모른다. AI 출력은 후보 표, 확정은 사람.
- **`'use client'`를 페이지 전체로 덮지 않는지 검수** — 인터랙티브한 필터·폼만 클라이언트로 내려야 번들이 작다. "이 페이지는 CSR"이 아니라 "어느 서브트리부터 클라이언트"가 정확한 질문.
- **폴더 구조는 과설계하기 쉽다** — feature 8개를 처음부터 다 만들지 말 것. MVP Must feature부터, 나머지는 규칙만 두고 비워둔다(죽은 빈 폴더·배럴 경계).
- **모듈 경계 lint는 초안일 뿐 적용은 06** — 지금 머지하면 환경 미비로 충돌. 규칙은 문서로 남기고 적용·검증은 개발 환경 구축에서.
- **상태 분리·API 연동을 여기서 구현하지 않는다** — 03은 "서버 상태=Query, 클라 상태=Zustand" 규약 선언까지. 훅·스토어 구현을 시작하면 09·10과 중복되고 결정이 흩어진다.
- **흔한 실수 — 디자인 토큰을 여기서 손대기**: 색·간격·컴포넌트 계층은 04의 몫. 03은 `shared/ui` 폴더 자리만 잡고 토큰 코드화는 04로 넘긴다.
- **흔한 실수 — 한 방 프롬프트**: 렌더링 매핑~폴더 생성을 한 번에 시키면 잘못된 렌더링 가정 위에 폴더가 생성돼 오류가 뒤로 전파된다. Stage 1(매핑)→게이트→Stage 2(확정)→Stage 3(구조)로 사람 검토 지점을 끼워 끊는다.
