# 상태 관리 (State Management)

08에서 조립한 화면들이 **어떤 데이터를 어디에 두고 누가 그 데이터의 주인인지**를 결정한다.
산출물 = 상태 인벤토리 → 서버/클라 분류 → 위치 결정(local/global/URL) → Zustand store 골격.
스택은 02에서 TanStack Query v5·Zustand로 확정됐다(라이브러리를 고르는 단계가 아니다).
**AI는 상태 조각 회수·분류 초안·store 보일러플레이트, 무엇을 전역에 올릴지의 경계 판단은 사람.**

## 핵심 원칙

- **상위 산출물 계승, 재발명 금지 — 단 확정 상태일 때만.** 상태 인벤토리는 08 화면 구현 코드와
  01 화면↔API 의존맵에서 **추출**한다. 코드·의존맵에 근거 없는 상태를 지어내지 말 것. 근거가
  없으면 **"확인 필요"** 태그 + 어느 화면에서 필요해 보이는지만 적는다.
- **도메인 용어는 BE 정본 계승**: 01 화면↔API 의존맵이 인용한 **BE 05 OpenAPI 스키마명·enum을 그대로**
  쓴다(상태명·필드명·상태머신 enum 1:1, 임의 재작명 금지). 도메인 상태머신(예: 주문/예약/구독의 status
  enum)은 **서버 데이터**이므로 클라 전역 상태로 올리지 않는다(서버 상태로 분류). 어떤 스키마명이 정본인지는
  01-2 의존맵·BE 계약에서 확인 — SKILL 본문에 특정 도메인 스키마를 박지 않는다(주제마다 다름).
- **규칙을 분류보다 먼저 준다.** 서버/클라 분류 규칙(서버가 진실인가)과 위치 규칙(여러 라우트가
  공유하는가)을 프롬프트에 박아두고 AI는 그 규칙으로만 판단·근거를 단다. 사람은 규칙에만 합의한다.
- **서버 상태를 Zustand에 넣지 않는다.** 가장 비싼 안티패턴. 서버 데이터는 TanStack Query가
  캐싱·무효화·재요청의 단일 출처. store로 복사하면 화면 간 동기화 버그가 생긴다 → 분류에서 경고로 잡는다.
- **전역의 기본값은 local이다.** global(Zustand)은 "여러 라우트가 진짜 공유하는가?"에 예일 때만.
  검색 필터·정렬·페이지네이션은 전역이 아니라 **URL(searchParams)**가 정답.
- **이 단계가 만드는 것은 클라이언트 전역 store뿐**이다. TanStack Query 훅·queryClient 설정·낙관적
  업데이트는 다음 10 API 연동에서 BE 05 OpenAPI 계약을 타입으로 계승해 구현한다(여기선 분류만,
  `QueryClientProvider`를 앱 루트에 두는 준비까지).
- **단계별 파일로 끊는다**: 인벤토리(09-1) → 분류(09-1 표) → 위치(09-1 표) → store(09-2/09-3).
  한 방 프롬프트 금지 — 추출부터 store까지 한 번에 시키면 분류 오류·전역 과적이 그대로 코드에 박힌다.

## 파이프라인

### Stage 0 — 입력 확인·도구 probe·degrade
- `<루트>/08_화면구현/` 화면 코드를 읽는다. **없으면 위치 질의 후 중단**.
- `01_핸드오프분석/01-2_화면API의존맵.md` 로드 시도(있으면 "출처=서버" 판별 근거, 없으면 코드 호출로 추정 + ⚠️).
- **도구 probe**: Context7(ToolSearch 존재로 판별) / pnpm·npx(bash 시도). 없으면 degrade(아래 "도구 정확성").

### Stage 1 — 상태 인벤토리 추출 → 09-1
- 08 화면 코드 + 01 의존맵을 읽고 포밋이 다루는 상태 조각을 **전수 목록화**.
- 각 상태: 이름 / 사용 화면 / 데이터 출처(API 응답·사용자 입력·UI 토글) / 변경 주체 / 비고.
- BE API(시터 검색·예약 목록·프로필 등)에서 오는 데이터는 **"출처=서버"**로 표시.
- **추측 금지** — 코드·의존맵에 근거 없는 상태는 **"확인 필요"** 태그 + 어느 화면에서 필요해 보이는지만.
- 표: `상태명 | 사용 화면 | 출처 | 변경 주체 | 비고` → 09-1에 기록.

### Stage 2 — 서버 상태 vs 클라이언트 상태 분류 → 09-1에 추가
- **분류 규칙(이 기준으로만 판단)을 먼저 명시**:
  - **서버 상태**: 서버가 진실의 원천이고 다른 사용자·세션과 공유되며 내가 갱신해도 서버 응답이
    최종값(예: 예약 목록·시터 프로필·리뷰) → **TanStack Query 관리, Zustand에 복사 금지**.
  - **클라이언트 상태**: 이 브라우저 세션에서만 의미 있고 서버에 없는 데이터(예: 필터 패널 열림·
    토스트 큐·입력 중인 검색값·다크모드) → useState 또는 Zustand.
- 각 항목 분류 근거 1문장. **"서버 응답을 클라 상태로 복사"하려는 항목은 경고로 표시**.
- 경계가 흐린 항목(장바구니 등)은 **"경계 사례"**로 따로 모아 양쪽 트레이드오프를 적는다.

### 🚦 게이트 — 상태 위치(서버/클라 경계 + global 승격) 확정 (사람 개입, 필수)
AskUserQuestion으로 다음을 제시 → 사용자가 OK/수정. 확정 전 Stage 4(query 키·store 생성)로 넘어가지 않는다.
- **경계 사례 귀속**(Stage 2 산출 — 서버로 볼지 클라로 볼지: 도메인 맥락 필요).
- **global 승격 후보**(Stage 2의 클라 분류에서 도출 — "정말 여러 라우트가 공유하나?"를 사람이 재검증).
- **위치 결정 규칙 합의**(아래 Stage 3 규칙을 그대로 쓸지/수정할지).
- AI는 의심스러우면 전역으로 올리는 경향이 있다 — 이 게이트가 전역 과적을 막는 지점이다.

### Stage 3 — 클라이언트 상태의 위치 결정(local/global/URL) → 09-1에 추가
클라이언트 상태로 분류된 것만 위치를 정한다. **기본값은 local**.
- **local (useState)**: 한 컴포넌트와 직계 자식만 쓰는 상태(모달 열림·인풋 포커스·아코디언 펼침).
- **global (Zustand)**: 라우트가 다른 여러 화면이 진짜 공유하는 상태에만 한정(토스트/스낵바 큐·
  로그인 사용자 요약·전역 모달·테마). global로 올리려면 "여러 라우트가 공유하는가?"에 예라고 답할 수 있어야 한다.
- **URL (searchParams)**: 새로고침·공유·뒤로가기로 보존돼야 하는 상태(검색 필터·정렬·페이지네이션·탭).
  검색 필터처럼 공유 URL이 의미 있는 것은 Zustand가 아니라 URL에 둔다(Next App Router `useSearchParams`).
- 각 항목 최종 위치 + 근거 1문장을 표로 → 09-1.

### Stage 4a — query key 설계 → 09-2
- 서버 상태로 분류된 항목에 대해 **query key 네이밍 규약·계층**만 설계(예: `['bookings', { status }]`,
  `['sitters', { region, date }]`, `['sitter', sitterId]`)와 무효화 키 메모.
- **훅·queryClient·낙관적 업데이트 구현은 만들지 않는다 — 10 API 연동 위임**을 파일 상단에 명시
  (BE 05 OpenAPI 계약을 타입으로 계승해 10에서 구현). 여기선 `QueryClientProvider` 앱 루트 배치 준비까지.

### Stage 4b — Zustand store 골격 생성 → 09-3
global로 **확정된** 항목만으로 store 초안. Context7로 TanStack Query v5·Zustand 최신 API 확인 후 작성.
- TypeScript strict. 모든 상태·액션에 타입 명시.
- **slice 패턴**: ui slice(토스트 큐·전역 모달) / session slice(로그인 사용자 요약)로 분리. `src/stores/` 하위 slice별 파일.
- **셀렉터 구독 예시만**(예: `useStore(s => s.toasts)`). store 전체 구독(`const s = useStore()`) 예시는 만들지 않는다.
- **서버 상태(예약·프로필)는 절대 store에 넣지 않는다** — TanStack Query 몫.
- 각 slice가 왜 전역이어야 하는지 근거 주석 1줄씩 + 사용 예시 주석.
- ⚠️ **RSC 경계**: Zustand·TanStack Query는 `"use client"` 경계 안에서만 동작. 서버 컴포넌트에서
  전역 store를 import하지 않도록 사용처를 클라이언트 컴포넌트로 한정(주석 명시).

### Stage 5 — prop drilling 탐지 → 09-3에 추가
- `src/features/` 아래 같은 prop이 컴포넌트 **3단계 이상** 연쇄 전달되는 케이스를 찾는다.
- 각 케이스: prop 이름 / 전달 경로(A→B→C→D) / 중간 컴포넌트가 그 prop을 실제로 쓰는지.
- 해결책 후보: ①합성(children/슬롯)으로 중간 단계 건너뛰기 ②서버 상태면 자식에서 직접 useQuery(전달 불필요)
  ③진짜 전역이면 Zustand 셀렉터. **무조건 전역화는 마지막 수단으로만 제안**.
- 표 정리 + 효과 큰 3건 리팩터링 초안 → 09-3.

### Stage 6 — 마무리 + 검증 체크리스트
`_검증체크리스트.md` 생성(`<주제>`/`<날짜>` 치환). 마지막으로 산출물 폴더 경로와
"global 승격·경계 사례는 초안 — 사람이 재검증, 서버 상태 store 복사 금지" 고지를 보고한다.

## 도구 정확성 (probe·degrade)
- **Context7 MCP**(probe) = TanStack Query v5·Zustand 최신 API 조회. v4→v5에서 `useQuery`가 객체
  단일 인자로 바뀌고 `cacheTime`→`gcTime` 개명 등 변경점이 있어 store·query 패턴을 짤 때 확인.
  없으면 **내장 지식 + "버전 확인 필요 ⚠️"** 표기(v5 시그니처를 v4 기억으로 짜지 말 것).
- **pnpm / npx**(bash probe) = 패키지 설치(`pnpm add @tanstack/react-query zustand`,
  `pnpm add -D @tanstack/react-query-devtools`). 없으면 설치 명령은 생성하되 **"로컬 실행 필요"** 안내.
  Devtools는 개발 환경에서만 마운트.
- **vercel-react-best-practices 스킬**(선택) = 리렌더 유발 패턴(전역 미셀렉터 구독) 검토 시 호출.
- **중단**은 필수 입력(08 화면 구현) 부재 시에만. 그 외는 degrade.

## _검증체크리스트 본문 (Stage 6 생성)
```markdown
# 검증 체크리스트 — <주제> 상태 관리 (작성일: <날짜>)

> AI는 상태 회수·분류 초안·store 골격까지. 전역 경계 판단은 사람의 일이다.

- [ ] 인벤토리의 "확인 필요" 항목을 화면 코드와 대조 (AI가 지어낸 상태 차단)
- [ ] 서버 상태로 분류된 항목이 Zustand store에 복사돼 있지 않은가 (동기화 안티패턴 차단)
```

## 주의
- **서버 상태를 Zustand에 넣지 않는다** — 가장 흔하고 비싼 실수. 복사하면 캐싱·무효화·재요청을
  손으로 짜야 하고 TanStack Query를 쓰는 의미가 사라진다. 서버 데이터는 useQuery가 단일 출처.
- **전역 과적을 경계한다** — AI는 의심스러우면 전역으로 올린다. global 승격 항목은 사람이 직접 재검증.
- **검색 필터·정렬·페이지네이션은 URL 우선** — Zustand에 넣으면 새로고침·뒤로가기·링크 공유에서 날아간다.
- **Zustand는 셀렉터 없이 구독하면 전부 리렌더** — `useStore(s => s.toasts)`로 구독 범위를 좁힌다(13 성능의 단골 원인).
- **Context를 전역 상태 대용으로 남용 금지** — Context는 DI(테마·로케일)용, 자주 바뀌는 값은 구독 트리 전체 리렌더 → Zustand(셀렉터).
- **흔한 실수 — 한 방 프롬프트**: 추출부터 store까지 한 번에 시키면 분류 오류·전역 과적이 그대로 코드에 박힌다. Stage 1~5를 끊고 검수한 뒤 넘긴다.
- **흔한 실수 — v4 기억으로 v5 작성**: Context7로 최신 시그니처 확인. 이 단계는 분류·골격까지 — 훅 구현은 10이 한다(경계 침범 금지).
