# 기술 스택 선정 (Tech Stack Selection)

01단계 요구사항·제약을 입력으로, "이 서비스를 무엇으로 만들 것인가"의 후보를 **같은 기준으로 비교**하고
그 결정의 **근거를 ADR(Architecture Decision Record)로 박아두는** 단계를 자동화한다. 산출물 =
제약·평가 기준표 → 후보 비교 매트릭스 → 영역별 ADR. **AI는 후보를 같은 잣대로 조사·정리하고
트레이드오프를 펼칠 뿐, "우리 팀·우리 트래픽·우리 일정"에서 무엇을 고를지는 사람이 결정한다.**

## 핵심 원칙
- **상위 산출물 계승·재발명 금지**: 01-2 비기능요구의 성능·트랜잭션·동시성·운영 제약을 평가 기준으로 계승한다.
  01이 미확정([확인 필요])인 항목은 ⚠️ 보존하고 추정으로 메우지 않는다.
- **기준 먼저, 후보 나중**: 평가 기준을 고정한 뒤 후보를 같은 축 위에 늘어놓는다. 기준 없이 비교시키면
  AI가 후보마다 다른 잣대로 그럴듯하게 정리한다.
- **결정은 사람, 조사·정리는 AI**: "뭐가 제일 좋아?"에 답하지 않는다. AI는 트레이드오프를 펼치고,
  고르는 행위는 맥락(팀·예산·일정)을 아는 사람이 한다.
- **최신 버전은 반드시 Context7로 재확인**: 버전·호환성은 학습 시점 이후 가장 잘 바뀐다. 1차 답을
  Context7로 검증한 뒤 ADR에 박는다. ADR의 버전은 "현재 합의"이지 "검증 완료"가 아니다(빌드는 06에서).
- **출처·트레이드오프·재검토 트리거가 ADR의 본체**: 결론부터 쓴 ADR(탈락 후보가 왜 졌는지 없는 ADR)·
  재검토 트리거 없는 ADR은 박제된다. 02-2에 없는 근거는 지어내지 말고 `[근거 보강 필요]` 표시.

## 입력
- **필수**: `backend-output/<주제-슬러그>/01_요구사항분석/01-2_비기능요구.md`(성능·트랜잭션·동시성·보안·운영 NFR).
  없으면 위치를 묻고 중단하거나, 사용자가 제약을 직접 제시하면 그 제약으로 진행(출처 = "사용자 직접 입력" 표기).
- **권장**: `01_요구사항분석/01-1_도메인분석.md`(애그리거트·트랜잭션 단위 — 일관성 요구 판단에 사용).
- **사람이 제시(맥락)**: 예상 트래픽 규모, 팀의 언어/프레임워크 역량, 운영 여건(전담 인프라 인력·클라우드 예산), 일정.
  이 중 (요구사항·제약)은 사람이 알고, (생태계 현황·버전)을 AI가 빠르고 정확하게 조사한다.

## 파이프라인

### Stage 0 — 입력 확인·도구 probe·degrade
- `01_요구사항분석/01-2_비기능요구.md` 로드. 없으면 위치 질의 또는 사용자 제약 직접 입력으로 진행(출처 표기).
- 01의 잔존 ⚠️/[확인 필요]를 식별해 평가 기준에 그대로 보존(추정 금지).
- **도구 probe**: deep-research(스킬 가용)·Context7(ToolSearch 존재)·Figma generate_diagram(선택)·
  superpowers:brainstorming(선택). 부재 시 degrade(아래 "도구 정확성").

### Stage 1 — 제약·평가 기준 고정 → 02-1
- 01-2 비기능요구 + 사람이 준 제약을 한 표로 정리(각 제약의 출처: `01-2 #섹션` 또는 "사용자 직접 입력").
- 그 제약을 바탕으로 후보를 평가할 **기준 6~8개**를 만든다. 각 기준에 "왜 우리(이 서비스)에 중요한가" 한 줄.
  예: 팀 학습비용 / 트랜잭션 일관성 지원 / 매니지드 운영 난이도 / 생태계 성숙도 / 채용 가능성 / 비용 / 일정 적합성.
- **가중치 칸은 비워둔다**(사람이 게이트에서 매김). → `02-1_제약요구표.md`

### Stage 2 — 후보 조사 (deep-research) → 02-2 채움
- 영역별 후보 2~3개를 02-1의 **같은 기준**으로 비교. 각 항목에 출처(공식 문서·운영 사례) 부착.
- 영역: 언어/프레임워크 · DB(RDB vs 그 외) · 캐시 · ORM/쿼리 · 인프라(클라우드/오케스트레이션).
- 01-2의 핵심 제약(예: 강한 일관성, 전담 인프라 없음)에 **각 후보가 어떻게 답하는지** 반드시 다룬다.
- 후보별 **"이걸 고르면 무엇을 포기하나"(트레이드오프)** 명시.
- (선택) superpowers:brainstorming으로 "익숙해서 고른" 후보의 약점을 적대적으로 캐묻는 반론을 1회 발산.
- **사례·벤치마크 출처 검증**: "X가 Y보다 빠르다"류 주장은 조건(버전·하드웨어·워크로드)이 우리와 다를 수 있다 —
  조건이 안 맞으면 비교에서 빼거나 단서를 단다. degrade: deep-research 부재 시 내장 지식으로 비교하되 "출처 미검증 ⚠️" 표기.

### Stage 3 — 최신 버전·호환성 확인 (Context7) → 02-2 버전 칸
- Context7 2-step(resolve-library-id → query-docs)으로 후보 라이브러리·프레임워크의 **최신 버전·요구 런타임·호환성** 조회.
  예: Spring Boot 3.3.x 요구 최소 JDK·LTS 권장 조합 / 호환 Spring Data JPA·QueryDSL·Flyway 버전 / PostgreSQL 16 알려진 이슈.
- 확인 결과를 02-2의 버전 칸에 채우고 출처 링크를 남긴다.
- degrade: Context7 부재 **또는 호출 실패(quota 초과·auth 오류 등 런타임 에러)** 시 내장 지식으로 채우되 각 버전에 **"버전 확인 필요 ⚠️"** 표기(06 빌드에서 최종 확정). 실패해도 중단하지 말고 격하한다.

### 🚦 게이트 — 🔴 스택 결정 (AskUserQuestion, 필수 · 되돌리기 비용 큼)
- AskUserQuestion으로 (1) **평가 기준 가중치** 확정 (2) 영역별 **최종 선택**을 사람에게 받는다.
- AI는 02-2 비교표와 트레이드오프를 근거로 **추천 1안**을 제시하되, 최종 결정은 사람.
- **이 게이트 전에는 ADR(Stage 4)로 넘어가지 않는다.** 결정이 없으면 ADR은 "결론부터 쓴 ADR"이 된다.
- 유행("요즘 다들 MSA/리액티브")은 제약이 아니다 — 01의 비기능 요구로 정당화되지 않는 선택은 근거 칸에서 막는다.

### Stage 4 — ADR 기록 → 02-ADR-NNN
- 사람이 확정한 결정을 영역별로 ADR 한 장씩(또는 핵심 결정 묶음)으로 기록. 형식:
  - **제목**: `ADR-00N. <결정 한 줄>` / **상태**: Accepted
  - **맥락(Context)**: 어떤 요구·제약 때문에 필요했나(01 분석·02-1 기준 참조)
  - **결정(Decision)**: 무엇을 선택했나(Context7 검증 버전 포함)
  - **근거(Rationale)**: 02-2 비교에서 이걸 고른 이유 + **같은 기준에서 탈락 후보가 진 이유**
  - **결과/트레이드오프(Consequences)**: 이 선택으로 감수하는 것
  - **재검토 트리거(Revisit when)**: "언제 이 결정을 다시 볼 것인가"(예: DAU가 N 초과로 단일 DB 쓰기 병목 시 읽기 복제/샤딩 재검토)
- **규칙**: 02-2에 없는 근거는 지어내지 말 것. 비교에서 안 다룬 결정은 `[근거 보강 필요]` 표시.

### Stage 5 — 마무리(_검증체크리스트 + 산출물 경로 보고)
- `_검증체크리스트.md`(아래 본문) 생성. 산출물 폴더 경로와 "ADR 버전 = 현재 합의, 빌드 확정은 06" 고지를 보고한다.
- (선택) Figma generate_diagram으로 후보 아키텍처 비교 다이어그램을 공유용으로 생성(본격 다이어그램은 03에서).
- 잔존 🔴/[근거 보강 필요]가 있으면 ⚠️로 표시하고 완료 보고를 하지 않는다.

## 도구 정확성 (probe·degrade)
- **deep-research 스킬**(probe) = 후보 장단점·운영 사례·성숙도를 출처 교차검증해 조사. 부재 시 내장 지식 비교 + "출처 미검증 ⚠️".
- **Context7 MCP**(probe, 2-step) = 최신 버전·요구 런타임·호환성. 부재 **또는 호출 실패(quota·auth 등)** 시 내장 지식 + "버전 확인 필요 ⚠️"(빌드는 06에서 최종 확인).
- **Figma MCP generate_diagram**(probe, 선택) = 후보 아키텍처 비교 다이어그램. 부재 시 Mermaid 폴백.
- **superpowers:brainstorming**(선택) = 후보 반론 발산. 부재 시 생략(필수 아님).
- **중단**: 필수 입력(01-2 비기능요구 또는 사용자 직접 제약) 부재 시에만. 그 외는 degrade.

## _검증체크리스트 본문 (Stage 5 생성)
```markdown
# 검증 체크리스트 — <주제> 기술 스택 선정 (작성일: <날짜>)

> AI는 같은 기준으로 조사·정리까지. 무엇을 고를지의 결정은 사람의 일이다.

- [ ] 평가 기준이 01-2 비기능요구에서 도출됐는가(유행을 NFR로 착각하지 않았는가)
- [ ] 후보가 모두 같은 기준으로 비교됐는가(후보마다 다른 잣대 아님)
- [ ] deep-research 인용 벤치마크의 조건(버전·하드웨어·워크로드)을 출처에서 확인했는가
- [ ] 버전·호환성을 Context7로 재확인했는가(옛 기억 그대로 쓰지 않았는가) — 단, 빌드 확정은 06
- [ ] ADR에 탈락 후보가 왜 졌는지가 들어있는가(결론부터 쓴 ADR 아님)
- [ ] ADR마다 재검토 트리거가 명시됐는가(박제된 ADR 아님)
- [ ] 02-2에 없는 근거를 지어내지 않았는가([근거 보강 필요] 표시 확인)
- [ ] 가중치·최종 선택은 사람이 게이트에서 확정했는가
```

## 주의
- **결정을 AI에게 맡기지 말 것.** "뭐가 제일 좋아?"에는 무난한 다수파 답(대개 가장 유명한 것)이 나온다 —
  우리 제약에 맞는지는 별개다. AI는 트레이드오프를 펼치는 데 쓴다.
- **사례·벤치마크 출처를 검증한다.** 조건이 우리와 다르면 비교에서 빼거나 단서를 단다.
- **버전 호환성은 빌드로 최종 확인**(06단계). ADR 버전은 "현재 합의"이지 "검증 완료"가 아니다.
- **흔한 실수 — 결론부터 쓴 ADR**: 탈락 후보가 왜 졌는지가 ADR에 들어가야 결정이 추적 가능하다.
- **흔한 실수 — 재검토 트리거 누락**: "언제 다시 볼 것인가"를 반드시 적는다.
