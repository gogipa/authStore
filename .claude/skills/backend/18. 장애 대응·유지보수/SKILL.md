# 장애 대응·유지보수 (Incident Response)

장애가 났을 때 빠르고 차분하게 복구하고, 같은 장애가 재발하지 않게 만드는 작업을 자동화한다.
산출물 = **장애 대응 패키지**: 대응 플레이북 · blameless 포스트모템 템플릿 · 5 Whys 근본원인 분석.
**AI는 흩어진 신호(로그·트레이스·메트릭)를 한 타임라인에 모아 가설을 좁히고 초안을 쓰는 분석가**이며,
**복구 명령 실행·롤백 여부·사용자 공지 결정은 온콜 담당자(사람)가 한다.**

## 핵심 원칙

- **상위 산출물 계승·재발명 금지**: 복구 절차는 17 런북에서, 알림·신호 정의는 14 관측성에서
  계승한다. 런북·알림룰을 새로 발명하지 않는다. 미확정 항목은 `⚠️` 보존.
- **장애 한복판에서 AI의 가치는 "실행"이 아니라 "좁히기"다.** 곧바로 코드를 고치거나 서버를
  재시작하지 말고, **systematic-debugging으로 증상→가설→증거→검증 절차를 강제**한다. 추측 기반
  수정 금지.
- **원인 미확정 상태의 단정 금지.** 증거로 검증되지 않은 가설은 `미확인`으로 남긴다. 미확정 원인에
  기대 롤백하면 효과가 없거나 새 장애를 부른다. 채택은 사람이 한다.
- **타임라인·인용은 환각 위험 1순위.** 시각·수치·로그 라인을 매끄럽게 지어내지 말 것. 근거 없는
  구간은 `[확인 필요]`로 둔다.
- **blameless**: "누가 잘못했나"가 아니라 "어떤 시스템적 조건이 이 장애를 가능하게 했나"를 묻는다.
  개인 이름·"~했어야"식 비난 표현 금지, "시스템이 ~를 허용했다"로 서술.
- **장애 컨텍스트의 시크릿·고객정보 마스킹.** 로그 발췌를 AI에 넣을 때 토큰·결제 정보·개인정보가
  섞이지 않게 마스킹한다(14 로그 마스킹을 해뒀어도 발췌 시 재확인).

## 파이프라인

### Stage 0 — 입력 확인·도구 probe·degrade
- `14_관측성/`의 알림룰·로깅설정·SLO를 읽어 **신호 정의**(어떤 알림이 무엇을 의미, traceId로 어떻게
  꿰는지)를 파악. `17_인프라/17-4_런북.md`(복구 절차)를 읽는다.
- **도구 probe**: Context7(ToolSearch 존재 시 가용 — LogQL/PromQL/Loki/Tempo 최신 문법 참조).
  로그 조회 CLI는 팀 환경에 따름.
- **degrade**: 14 부재 → 신호 출처 질의 + `⚠️ 14 미작성`. 17 부재 → 의사결정 표 실행 명령 칸
  `[런북 참조 필요]`. Context7 부재 → 내장 지식 + `버전 확인 필요 ⚠️`.
- **민감정보 점검**: 사용자가 붙여넣은 로그에 토큰·결제 정보·개인정보가 보이면 경고하고 마스킹 권고.
- **systematic-debugging 가용 안내**: 실제 장애 분석은 `/superpowers:systematic-debugging`을 먼저
  호출해 증상→가설→증거 절차를 강제할 것을 안내. 이 스킬의 18-3는 그 절차의 출력을 구조화한다.

### Stage 1 — 대응 플레이북 → 18-1
- **알림 수신 → 트리아지 → 신호 교차분석 → 복구 → 사후** 흐름을 문서화.
- 신호 교차분석 가이드: 14에서 정의한 로그(Loki/LogQL)·트레이스(Tempo span 분해)·메트릭
  (Prometheus/PromQL)·에러(Sentry)를 **traceId로 꿰어** 보는 출발점 명시. 쿼리 예시는 Context7로
  최신 문법 확인(없으면 `⚠️`).
- **17 런북 연결**: 복구 명령은 새로 쓰지 않고 `17-4_런북.md`의 해당 절차를 가리킨다.
- **14-3 `runbook_url` placeholder 실연결(계승 TODO)**: 14-3 알림룰의 각 알림이 단 `runbook_url: "{{runbook:*}}"`
  는 "18에서 실제 URL을 채운다"는 14의 핸드오프다(이 연결이 MTTR을 결정). 18-1에 **알림→플레이북 절차→17 런북**
  매핑 표를 만들어 각 `{{runbook:*}}`이 가리킬 18-1 앵커를 명시하고, `_검증체크리스트`에 "14-3 placeholder를 사람이
  치환" 항목을 둔다(placeholder 치환 자체는 사람·운영 작업).
- **롤백/핫픽스 의사결정 표 양식** 포함(컬럼: 옵션 / 조치 내용 / 복구 예상 시간 / 리스크 / 되돌리기
  쉬움 / 실행 명령(런북 참조) / 권장 여부). 표 하단에 **"실제 실행·최종 선택은 온콜 담당자가 한다"** 명시.
- 온콜 역할·에스컬레이션 경로(누가 무엇을 보는가). 별도 유료 인시던트 툴 불필요.

### Stage 2 — blameless 포스트모템 템플릿 → 18-2
- 재사용 가능한 **빈 정본 양식** 생성. 섹션: ① 요약(3~4문장, 비난 표현 없이) ② 영향(시간·건수·
  사용자·매출) ③ 타임라인(시각|사건|신호 출처|영향) ④ 근본 원인(5 Whys) ⑤ 잘된 것/아쉬운 것
  ⑥ 액션 아이템 표(항목 / 담당 `{{자리표시자}}` / 기한 / 종류[탐지·복구·예방]).
- **규칙 고지를 양식에 박아둔다**: 개인 이름·"~했어야"식 비난 금지, "시스템이 ~를 허용했다"로 서술.
  "예방" 성격 액션 아이템은 **19단계 개선 백로그로 넘긴다**는 표기란.

### 🚦 게이트 — 복구 실행·롤백 판단 확정 (사람 개입, 필수, 🔴)
AskUserQuestion으로 **사람 확정**을 받는다(전자동 금지). Stage 3 진행 전 반드시 통과.
- **확인 항목 제시**: ① 원인 가설 중 **증거로 검증되어 채택할 것**(나머지는 `미확인` 유지) ②
  의사결정 표의 옵션 중 **실제로 실행한/할 조치**(롤백/핫픽스/우회 — AI는 표까지만, 결정은 사람) ③
  **사용자 공지 발송 여부** ④ 18-3에 들어갈 시각·수치·로그가 **원본과 대조 완료**되었는지.
- **🔴 사람 확정 게이트(필수)**: 복구 명령의 실제 실행, "롤백한다/고친다"의 최종 결정, 사용자 공지
  결정은 **AI가 하지 않는다.** 사용자가 채택 가설·실행 조치를 확정해야 18-3 근본원인분석을 확정본으로
  쓴다. 미확정이면 18-3을 `⚠️ 원인 미확정` 상태로만 작성하고 단정하지 않는다.

게이트 전에는 Stage 3로 넘어가지 않는다.

### Stage 3 — 근본원인 분석 (사례 적용본) → 18-3
- **신호 교차분석 판정표**: 가설별(예: "외부 PG 지연" vs "우리 코드 회귀" vs "스레드풀 고갈")로
  `가설 | 근거 신호 | 판정(채택/기각/미확인)` 표. **증거 없는 가설은 `미확인`.** 채택은 게이트에서
  사람이 확정한 것만.
- **타임라인 재구성**: `시각 | 사건 | 신호 출처 | 영향` 표. 알림·배포·로그·대응 조치·복구 확인 시각.
  **추정 시각 금지**, 근거 없는 구간 `[확인 필요]`. 영향 정량화(영향 시간·실패 건수[로그 카운트]·
  사용자 수 추정).
- **5 Whys**: "왜?"를 5번 물어 시스템적 조건까지 도달(표면 증상 → 직접 원인 → … → 시스템 정책).
  systematic-debugging 절차의 결과를 옮긴다.
- **포스트모템 초안**: 18-2 양식에 타임라인·영향·5 Whys·액션 아이템을 채운 초안. 비난 표현 제거,
  액션 아이템에 담당 `{{자리표시자}}`·기한·종류. **"예방" 항목은 19단계 개선 백로그 회부 표기.**
- 파일명은 날짜를 붙여도 됨(예: `18-3_2026-06-20_결제장애_근본원인분석.md`). 평시 준비면 관통
  시나리오로 데모.

### Stage 4 — 마무리
- `_검증체크리스트.md` 생성(아래 본문) + 산출물 폴더 경로 보고.
- **19단계 회부**: 포스트모템 액션 아이템 중 "예방" 성격을 `19_고도화` 개선 백로그로 넘길 목록을
  명시 보고. **🔴/미확정 원인이 남아 있으면 ⚠️ 표기하고 "복구·롤백 판단은 사람" 고지를 다시 한다.**

## 도구 정확성 (probe·degrade)
- **Context7 MCP**(probe로 가용 확인) = LogQL/PromQL/Loki/Tempo 쿼리 최신 문법 참조. 없으면 내장
  지식으로 쿼리 예시 작성 + `버전 확인 필요 ⚠️`.
- **로그 조회 도구**(Grafana/Loki/Tempo/Sentry) = 팀 스택에 따름. 스킬은 쿼리 가이드·교차분석
  구조만 제공하고, 실제 조회·발췌는 사람이 한다.
- **python3 / bash** = 로그 카운트 등 단순 집계에 가용 시 사용. 없으면 사람이 직접 카운트 안내.
- **중단**: 14·17 둘 다 부재로 신호·복구 출처가 전혀 없을 때만. 그 외는 degrade.

## _검증체크리스트 본문 (Stage 4 생성)
```markdown
# 검증 체크리스트 — <주제> 장애 대응 (작성일: <날짜>)

> AI는 신호를 모아 가설을 좁히고 초안을 쓴다. 복구 실행·롤백 결정·공지는 사람이 한다.
```

## 주의
- **복구 명령·롤백 결정은 사람이.** AI에게 프로덕션 명령 실행이나 "롤백해"의 결정을 맡기지 말 것.
  AI는 의사결정 표까지, 실행은 온콜 담당자가 17 런북대로 한다.
- **원인 미확정 상태의 단정 금지.** 그럴듯하게 말해도 증거로 검증 안 된 가설은 `미확인`. 미확정
  원인에 기대 롤백하면 효과가 없거나 새 장애를 부른다.
- **타임라인·인용의 환각.** 시각·수치·로그를 매끄럽게 지어내는 경우가 있다 — 원본과 대조, 근거 없는
  구간은 `[확인 필요]`.
- **시크릿·고객정보 노출 주의.** 로그를 붙여넣을 때 토큰·결제·개인정보 마스킹.
- **포스트모템이 비난으로 흐르지 않게.** "~했어야 했다"는 액션 아이템(시스템 개선)으로 바꿔 쓴다.
- **흔한 실수** — ① 알림이 너무 많아 진짜 장애 알림이 묻힘: 분기마다 SLO 기준으로 룰 정리. ② 액션
  아이템에 담당·기한을 안 붙여 휘발: "예방" 항목은 19단계 개선 백로그로 명시적으로 넘긴다.
