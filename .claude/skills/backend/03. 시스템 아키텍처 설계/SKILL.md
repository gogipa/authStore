# 시스템 아키텍처 설계 (Architecture Design)

요구사항(01)과 확정한 기술 스택(02)을 입력으로, "시스템을 어떤 큰 덩어리로 쪼개고, 어떻게 통신하며,
어디에 배포할 것인가"를 **발산·시각화·기록**한다. 산출물 = 아키텍처 옵션 비교 매트릭스 + C4 다이어그램
+ ADR. **AI는 옵션을 빠짐없이 펼치고 다이어그램·ADR 양식으로 옮기고, 한 옵션을 고르는 선택은 사람이
한다** — AI에게 맡기면 거의 항상 "유행하는" 답(MSA·헥사고날)을 권하기 때문이다.

## 핵심 원칙

- **상위 산출물 계승, 재발명 금지 — 단 확정 상태일 때만**: 02 스택 ADR이 `Accepted`면 그대로 전제로
  쓰고, `Proposed`/⚠️면 "스택 미확정" 표기를 보존한 채 진행한다. 01의 도메인 경계·트랜잭션 단위를
  아키텍처 모듈 경계의 출발점으로 삼되 재발명하지 않는다.
- **발산은 AI, 선택은 사람.** 옵션을 빠짐없이 펼치는 일(회수율)은 AI, 팀 맥락으로 한 옵션을 고르는
  결정(정밀도)은 사람. AI 추천안은 "팀 규모·운영 역량을 모르고 나온 일반론"이다.
- **C4로 줌 레벨을 분리한다.** 한 장에 외부 시스템부터 클래스까지 욱여넣지 않는다. Context/Container/
  Component로 청중(경영진·신규 입사자·구현 담당)을 분리한다. 포밋은 3단계만(Code 생략).
- **ADR로 "왜"를 박제하고, 상태는 반드시 `Proposed`로 시작한다.** 그림은 "무엇", ADR은 "왜". 둘은 한
  쌍이다. AI가 만든 ADR을 팀 합의 전에 `Accepted`로 단정하지 않는다.
- **트랜잭션 경계를 그림에서 빠뜨리지 않는다.** 결제(Payment)-예약(Booking)처럼 정합성이 중요한 흐름은
  "한 트랜잭션인가, 결과적 일관성인가"를 다이어그램·ADR에 명시한다.

## 파이프라인

### Stage 0 — 입력 확인·도구 probe·degrade
- 01·02 폴더를 읽는다. 둘 다 없으면 **중단**. 02 스택 ADR 상태(`Accepted`/`Proposed`/⚠️) 감지·보존.
- **도구 probe**: Figma MCP(`generate_diagram`, ToolSearch 존재 시 가용)·Context7·deep-research 스킬·
  python3. 부재 시 degrade(아래 "도구 정확성").
- 도메인 엔티티 목록을 01에서 확정(없으면 **포밋 예시** 폴백: Member/SitterProfile/Pet/CareService/Booking/
  Payment/Settlement/Review/Chat/Notification — 다른 주제면 01이 없을 때 도메인 경계를 추정하지 말고 01 먼저 권장).

### Stage 1 — 아키텍처 옵션 비교 매트릭스 발산 → 03-1
- **배포 단위 축**: 모놀리식 / 모듈러 모놀리식 / MSA. **내부 구조 축**: 레이어드 / 헥사고날(포트&어댑터).
- 각 옵션마다: 장점 / 단점 / 적합 조건 / 도메인 적용 시 구체적 영향 / 운영·배포 복잡도 / 초기 개발 속도 /
  팀 규모 적합성 / **정합성이 중요한 핵심 트랜잭션 경계가 어떻게 그어지는지**(01의 TX 후보 —
  예: 포밋=결제-예약(Booking), 펫사료구독=해지-정산(Refund)).
- 마지막에 "현재 팀/트래픽 규모 권장안 1개 + 근거"를 제시하되, **근거가 약하거나 사업 판단이 필요한
  지점은 "사람 결정 필요"로 표시**. (예시 권장: 모듈러 모놀리식 + 레이어드, 핵심 도메인만 헥사고날 지향 —
  단일 배포로 운영 부담↓, 모듈 경계 명확화로 추후 MSA 진화 경로 확보. 이는 예시일 뿐 확정은 Stage 3.)
- **(옵트인) 생태계 사례**: deep-research 가용 시 "초기 스타트업이 결제·예약·정산 도메인을 모듈러
  모놀리식으로 시작했다 겪은 실제 사례(모듈 경계·Spring Modulith vs 멀티모듈 Gradle·MSA 전환 트리거·
  후회/만족 회고)"를 **출처 URL과 함께** 조사해 인용. 부재 시 이 절은 ⚠️ "사례 미조사"로 생략 가능.
- → `03-1_옵션비교.md`

### 🚦 게이트 — 아키텍처 스타일 결정 (사람 개입, 필수)
AskUserQuestion으로 **배포 단위 + 내부 구조 + 모듈 경계 기준**을 묻는다(AI 추천 1안 제시).
- 질문 예: ① 배포 단위(모놀리식 / 모듈러 모놀리식 / MSA) ② 내부 구조(레이어드 / 헥사고날 / 혼합) ③ 모듈
  경계(도메인 단위 / 기능 단위) ④ 핵심 트랜잭션(01의 TX 후보 — 예: 결제-예약 / 해지-정산)을 한
  트랜잭션으로 둘지(결과적 일관성 여부).
- **"우리 팀 2~3명이 이걸 운영할 수 있는가"로 AI 추천을 깎아낸다.** 이 결정 전에는 Stage 2(다이어그램)·
  Stage 3(ADR)로 넘어가지 않는다 — 다이어그램·ADR은 확정된 스타일을 그려야 하므로.

### Stage 2 — C4 다이어그램 생성 → 03-2
- 게이트에서 확정된 스타일로 C4 3단계를 그린다. **액터·외부시스템·모듈명은 01에서 확정한 주제 도메인에
  맞게 채운다 — 아래는 포밋(펫시터) 예시일 뿐, 다른 주제면 그대로 베끼지 말고 치환할 것.**
  1) **System Context**: 액터(예: 포밋=보호자·펫시터 / 펫사료구독=보호자·운영자·수의사), 백엔드 시스템,
     외부 시스템(예: PG·소셜로그인·Firebase FCM·SMS — 미정 사업자는 ⚠️ 표기) 관계.
  2) **Container**: 모바일/웹 앱 → ALB → Spring Boot 앱(확정 배포 단위) → PostgreSQL 16 / Redis 7 + 외부
     PG/FCM 호출.
  3) **Component**: Spring Boot 앱 내부를 확정 모듈 경계로 분해(**01의 바운디드 컨텍스트·엔티티에서 도출**.
     예시 포밋: member/sitter/booking/payment/settlement/review/chat/notification + 공통 모듈), **모듈 간
     의존 방향** 표시.
- 각 박스에 한 줄 설명, 화살표에 "무엇을 호출/저장하는지" 라벨. **정합성이 중요한 핵심 흐름의 트랜잭션
  경계를 주석으로 명시**(01에서 도출한 TX 후보 — 예: 포밋=결제-예약, 펫사료구독=해지-정산. "이 흐름은
  한 트랜잭션 / 결과적 일관성").
- **기본은 Mermaid `flowchart`** 코드블록으로 `03-2_C4다이어그램.md`에 넣는다. Figma `generate_diagram`이
  가용하고 사용자가 옵트인하면 FigJam 공유본도 만들고 파일에 링크를 남긴다(코드 리포 경량본=Mermaid,
  공유본=Figma 병행). → `03-2_C4다이어그램.md`

### Stage 3 — ADR로 결정 기록 → 03-ADR-003
- Stage 1 비교 + (있으면) 사례 조사 + 게이트 결정을 ADR 1건으로 기록. 양식:
  - `# ADR-003: 시스템 아키텍처 (배포 단위·내부 구조)` — ⚠️ 02단계도 `02-ADR-003`이 있을 수 있으니
    인용 시 **단계 접두(02-ADR-003 vs 03-ADR-003)** 로 구분(파일명 정본 = `03-ADR-003_아키텍처.md`).
  - **상태**: `Proposed` (← 리뷰 전이므로 `Accepted`로 단정 금지)
  - **맥락(Context)**: 팀 규모, 트래픽 가정, 도메인 특성, 02에서 정한 스택
  - **결정(Decision)**: 게이트에서 사람이 고른 배포 단위·내부 구조·모듈 경계·단일/분산 배포
  - **대안(Considered Options)**: 기각한 옵션 각각의 기각 사유
  - **영향(Consequences)**: 좋은 점 + 감수하는 비용 + **나중에 재검토할 트리거**(예: 특정 모듈 배포 충돌
    빈발 시 분리 검토)
- **상태는 반드시 `Proposed`로 두고, 팀 합의 전까지 확정 표현을 쓰지 않는다.** → `03-ADR-003_아키텍처.md`

### Stage 4 — 마무리(_검증체크리스트 + 산출물 경로 보고)
- `_검증체크리스트.md`(아래 본문) 생성. 산출물 폴더 경로와 "ADR 상태는 `Proposed` — 팀 리뷰 후
  `Accepted`로" 고지를 보고. 🔴/사람 결정 잔존 시 ⚠️ 표기하고 "완료" 단정 금지.
- 다음 단계 연결 안내: 확정 모듈 경계가 04(DB 스키마 분할)·06(패키지 구조)·17(배포 토폴로지)로 이어진다.

## 도구 정확성 (probe·degrade)

- **Figma MCP `generate_diagram`**(probe) = C4·배포 구성도 FigJam 공유본. **없으면 Mermaid 폴백**(기본도
  Mermaid). write 다이어그램은 사용자 옵트인일 때만.
- **deep-research 스킬**(probe) = 생태계 사례 조사(출처 기반). 없으면 "사례 미조사 ⚠️"로 생략하고 비교
  매트릭스는 내장 지식으로 진행.
- **Context7 MCP**(probe) = Spring Boot 3.3에서 모듈 분리(Spring Modulith)·멀티모듈 Gradle 최신 권장 방식
  확인 보조. 없으면 내장 지식 + "버전 확인 필요 ⚠️" 표기.
- **python3** = Mermaid 코드블록 구문 정합 정적 점검 보조. 없으면 정적 체크리스트 degrade.
- **중단**은 필수 입력(01·02) 부재 시에만. 그 외는 degrade.

## _검증체크리스트 본문 (Stage 4 생성, `<주제>`/`<날짜>` 치환)

```markdown
# 검증 체크리스트 — <주제> 시스템 아키텍처 설계 (작성일: <날짜>)

> 발산은 AI, 선택은 사람. 다이어그램은 합의안이지 진실이 아니다.

- [ ] AI 추천안을 "우리 팀 2~3명이 운영 가능한가"로 깎아냈는가 (MSA·CQRS 등 과설계 경계)
- [ ] 게이트에서 배포 단위·내부 구조·모듈 경계를 사람이 직접 확정했는가
- [ ] 결제(Payment)-예약(Booking) 트랜잭션 경계가 다이어그램·ADR에 명시됐는가 (한 트랜잭션 vs 결과적 일관성)
- [ ] ADR 상태가 `Proposed`인가 — 팀 리뷰 전 `Accepted` 금지
- [ ] 다이어그램과 ADR이 한 쌍으로 존재하는가 (그림만/ADR만 금지)
- [ ] (deep-research 사용 시) 인용 사례의 출처를 직접 열어 회사 규모·시점 맥락을 확인했는가
- [ ] 02 스택 ADR이 미확정(Proposed)이면 그 표기를 보존했는가
- [ ] 확정 모듈 경계를 04·06·17이 이어받을 수 있게 명확히 적었는가
- [ ] 큰 구조 변경 때 다이어그램을 갱신할 책임자를 정했는가
```

## 주의
- **AI는 거의 항상 "더 멋진" 걸 권한다.** MSA·이벤트소싱·CQRS를 초기 스타트업에 권하는 경우가 흔하다.
  모듈러 모놀리식을 기본값으로 두고, MSA는 명확한 트리거(트래픽·팀 분리)가 생길 때 간다.
- **다이어그램과 실제 코드는 갈라진다.** 그림은 합의안일 뿐 진실이 아니다 — 큰 구조 변경마다 갱신 책임자
  를 정한다.
- **ADR을 확정으로 단정하지 말 것.** AI가 만든 ADR은 "제안". 상태 필드를 반드시 `Proposed`로 거친다.
- **트랜잭션 경계를 그림에서 빠뜨리기 쉽다.** 결제-예약처럼 정합성이 중요한 흐름은 모듈을 쪼갤수록
  분산돼 복잡해진다. 다이어그램 단계에서 명시하지 않으면 08·11단계에서 비용이 폭발한다.
- **흔한 실수 — 다이어그램만 만들고 ADR을 안 남김.** 그림은 "무엇", ADR은 "왜". 한 쌍으로 만든다.
- **흔한 실수 — 조사 출처 미검증.** deep-research 사례도 출처를 직접 열어 규모·시점을 확인한다.
