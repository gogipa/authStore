# be-requirements-analysis — 요구사항·기능명세 분석 자동화 스킬

기획 핸드오프(12 기능명세·14 핸드오프 패키지)를 넣으면 백엔드 관점으로 다시 읽어 **도메인/엔티티 후보·유스케이스·비기능요구(NFR)·기획 질문 리스트**를 출처와 함께 추출·구조화하는 Claude Code 스킬입니다. AI는 빠짐없이 건져 1차 구조화(회수율)까지, 사람은 **도메인 경계·트랜잭션 단위 확정 1번**만 개입합니다.

> BE 프로세스 01단계 "요구사항·기능명세 분석"을 자동화합니다.
> 역할 분담: AI는 추출·구조화, **설계 판단(도메인 경계·트랜잭션 단위)은 사람**.

## 무엇을 만들어 주나

`backend-output/<주제>/01_요구사항분석/`에 생성:

| 파일 | 내용 |
|---|---|
| `01-1_도메인분석.md` | 엔티티/애그리거트 후보 표(속성·관계·상태·출처) + 바운디드 컨텍스트 후보 + 유스케이스 표(actor·흐름·트랜잭션 후보) |
| `01-2_비기능요구.md` | 성능·트랜잭션/일관성·보안·운영 4관점 NFR 표(명시/추정 구분, 임계값은 `[기획 확인 필요]`) |
| `01-3_기획질문리스트.md` | 모호점·충돌·누락 질문 표(질문·개발영향·대상·막힘정도, 블로커 우선) |
| `_검증체크리스트.md` | 사람이 확인할 항목 |

## 준비물 (입력)

1. **(필수) 기획 12 기능명세서** — 기능 목록·입력값/유효성/예외 표·상태 정의. 같은 볼트면 위키링크·경로 모두 동작.
2. **(권장) 기획 14 핸드오프 패키지** — 14-1 엣지케이스 Q&A·14-2 티켓·14-3 API 명세 초안·14-4 용어집. 없으면 12 기반으로 진행(엣지케이스 보강 제한 ⚠️).
3. **(연결·권장) 기획 06 정책·10 화면설계서** — NFR 보안/운영 근거, 상태/예외 화면. 없으면 ⚠️ 표기 후 진행.

> 기획 12가 없으면 위치를 묻고 중단합니다(원천 부재). 14만 없으면 12 기반으로 진행하되 엣지케이스 보강이 제한됩니다.

## 사전 요구사항

| 항목 | 필수? | 없으면 |

| Context7 MCP | 선택 | 내장 지식으로 진행 + "버전 확인 필요 ⚠️" |

## 사용법

기획 12·14 산출물 위치를 확인한 뒤:

```
기획 12 기능명세랑 14 핸드오프 읽고 "포밋" 백엔드 요구사항 분석해줘
```

1. 도메인/엔티티 후보 추출 → 유스케이스 재구성 (출처 자동 표기)
2. 4관점 NFR 발굴 (임계값은 비워두고 [기획 확인 필요])
3. **도메인 경계·트랜잭션 단위 확정** → 당신이 확정/수정 (유일한 개입)
4. 기획 질문 리스트 자동 (블로커 우선 정렬)

발동 키워드: `요구사항 분석`, `기능명세 분석`, `도메인 분석`, `엔티티 후보 추출`, `유스케이스 추출`, `비기능 요구`, `NFR`, `requirements analysis`, `domain analysis`, `use case`

## 주의

- **AI는 엔티티를 지어내기도 합니다** — 출처가 비거나 어색한 항목은 원문 대조.
- **도메인 경계는 후보일 뿐** — "Booking↔Payment 한 애그리거트?"는 04~08에서 사람이 확정.
- **NFR 임계값(p95/SLO)은 추정 금지** — 비워두고 12·14에서 합의해 채웁니다.
- **블로커 질문은 착수 전 닫기** — 미답 블로커 위에 짠 코드는 나중에 통째로 갈아엎습니다.
- **민감정보**(실 사용자 데이터·계약 정보)는 외부 MCP 전송 전 원천에서 제외.
- **한 방 프롬프트 금지** — 01-1→01-3 단계별로 사람이 확인하고 넘어갑니다.
