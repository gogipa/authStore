# 요구사항·기능명세 분석 (Requirements Analysis)

기획 시리즈가 넘긴 산출물(12 기능명세·14 핸드오프)을 "어떤 도메인 객체가, 어떤 트랜잭션 경계 안에서, 어떤 상태로 변하는가"라는 백엔드 개발자의 언어로 다시 읽는다. 산출물 = **도메인 분석(엔티티/애그리거트 후보·유스케이스)·비기능요구·기획 질문 리스트**. AI는 명세에 적힌 명사·행위·요구를 빠짐없이 건져 1차 구조화(회수율)까지만, **도메인 경계·트랜잭션 단위·우선순위 판단은 사람**.

## 핵심 원칙
- 상위 산출물(기획 12·14) 계승·재발명 금지. **확정 상태일 때만 계승**, 미확정(⚠️/[확인 필요])은 그 플래그째 보존해 질문 리스트로 회부.
- **추출과 설계 판단을 분리한다** — AI는 명세의 명사·행위·요구를 빠짐없이 건져 구조화까지만. 도메인 경계를 어디에 긋고 무엇을 한 트랜잭션으로 묶을지는 사람이 정한다.
- **모든 항목에 출처를 강제한다** — 어느 기능명세 항목/용어집 줄에서 나왔는지 표기. 출처가 비거나 어색하면 원문 대조(AI가 지어낸 엔티티 차단).
- **빈칸을 지어내지 말고 표시한다** — 명세에 답이 없으면 `[명세 누락]`·`[확인 필요]`, NFR 임계값(p95 등)은 채우지 말고 `[기획 확인 필요]`.
- **단계별 산출물을 파일로 끊는다** — 01-1→01-2→01-3을 따로 남겨 사람이 검토 후 넘긴다(한 방 프롬프트 금지).

## 파이프라인

### Stage 0 — 입력 확인·도구 probe·degrade
- 기획 **12 기능명세** 로드(없으면 위치를 묻고 **중단**). **14 핸드오프**(14-1·14-2·14-3·14-4) 로드. 06·10 있으면 보조 로드.
- **계승 상태 분기**: 12·14 항목에 잔존 `⚠️`/`[확인 필요]`/🔴가 있으면 미확정으로 표시해 Stage 4 질문 리스트로 계승(재발견 금지, 출처 표기).
- **도구 probe**: Context7(ToolSearch 존재 시 가용). 없으면 내장 지식 + "버전 확인 필요 ⚠️".
- **민감정보 점검**: 핸드오프에 실제 사용자 데이터·계약 정보가 섞여 있을 수 있다 — 외부 MCP로 보내기 전 원천에서 걸러내라고 사용자에게 경고.

### Stage 1 — 도메인/엔티티 후보 추출 → 01-1 (전반)
- 명세에 등장하는 **명사를 후보 엔티티**로 올리고, 각 후보에 속성 후보·관계(1:N, N:M 등)를 표시.
- **출처 강제**: 어느 기능명세 항목/용어집 줄에서 나왔는지. 출처 없는 후보는 만들지 않는다.
- 엔티티인지 값 객체(VO)인지·엔티티인지 단순 상태값인지 애매하면 `[확인 필요]`.
- 상태를 가지는 엔티티는 가능한 상태값·전이를 함께 적되, 명세에 없으면 지어내지 말고 `[명세 누락]`.
- **바운디드 컨텍스트 후보**도 가늠해 묶음(확정 아님 — 후보).
- 표: `엔티티 후보 | 속성 후보 | 관계 | 상태(있으면) | 출처 | 확인필요/누락`
- > 포밋이라면 Member(OWNER/SITTER), SitterProfile, Pet, CareService, Booking, Payment, Settlement, Review, Chat, Notification이 후보. 단 이름·경계는 **04(DB 설계)에서 ERD로 확정**하므로 여기서는 후보.

### Stage 2 — 유스케이스 재구성 → 01-1 (후반)
- 단위: `actor + 행위`("보호자가 예약을 요청한다", "시터가 예약을 수락한다").
- 각 유스케이스에 actor / 사전조건 / 기본 흐름(번호) / 예외 흐름 / 관련 엔티티.
- **트랜잭션 후보**: 결제-예약 확정처럼 여러 엔티티가 한 흐름에서 함께 바뀌는 것은 별도 표시(애그리거트/트랜잭션 경계 판단 입력 — 확정은 사람).
- 기획의 상태 정의(Booking: REQUESTED→ACCEPTED→…)와 어긋나는 흐름은 `[정합성 의심]`.

### Stage 3 — 비기능 요구(NFR) 발굴 → 01-2
- 4개 관점 체크리스트로 명세를 훑어 NFR 후보를 강제 발굴(관점마다 빠진 게 없는지 발산 점검):
  1. **성능**: 응답시간 목표가 명시/암시된 곳(검색·목록), 예상 동시 사용자, 피크 시점.
  2. **트랜잭션·일관성**: 함께 바뀌어야 하는 데이터(결제 승인↔예약 확정↔정산), 동시 예약 충돌, 멱등성 필요 지점(결제 콜백).
  3. **보안**: 개인정보(연락처·주소)·결제 데이터·신원확인 정보의 저장/전송, 권한 분리(OWNER vs SITTER).
  4. **운영**: 외부 연동 장애 시 거동(PG/FCM 다운), 로깅·감사, 데이터 보존/삭제.
- **명시된 것 vs 개발자가 추정한 것을 구분 표시**. 추정 항목은 전부 `[기획 확인 필요]` + 무엇을 물어야 하는지 한 줄.
- **임계값(p95/SLO 등)은 채우지 않는다** — 근거 없는 수치 금지. 비워두고 12(캐싱·성능)·14(SLO/SLI)에서 합의해 채운다고 표기.
- (선택) Context7 probe 시 "이 요구를 Spring Boot 3.3/JPA에서 어떤 메커니즘으로 받칠 수 있나"를 가벼운 가늠용으로만 조회(본격 사용은 04 이후).

### 🚦 게이트 — 도메인 경계·트랜잭션 단위 확정 (사람 개입, 필수)
AskUserQuestion으로 Stage 1·2에서 도출한 **트랜잭션 후보/애그리거트 묶음 후보**를 제시 → 사람이 경계를 확정/수정.
- 예: "Booking과 Payment를 한 애그리거트(한 트랜잭션)로 묶을지" — DDD·트랜잭션·비즈니스 맥락 판단이라 AI가 정하지 않는다.
- 사람이 확정하기 전에는 01-1의 트랜잭션 경계를 "확정"으로 표기하지 않고 **후보**로 남기며, Stage 4로 넘어가지 않는다.
- **확정 결과 반영 위치**: 게이트에서 사람이 정한 경계는 **01-1의 트랜잭션 후보 표를 편집**해 해당 행을 "확정"으로 갱신(확정 못 한 후보는 후보 유지). 별도 파일을 새로 만들지 않는다.
- **무인 실행(자동진행)**: AskUserQuestion을 띄울 수 없으면 합리적 기본값을 채택하되 01-1·_검증체크리스트에 "게이트 자동진행: <선택>(실사용 시 사람 확정 필요)"로 남긴다.

### Stage 4 — 기획 질문 리스트 → 01-3
- Stage 1~3에서 `[확인 필요]`/`[명세 누락]`/`[정합성 의심]`/`[기획 확인 필요]`로 표시된 항목 + 12·14에서 계승한 미확정(⚠️/🔴) 항목을 **모두 모은다**.
- 표: `질문 | 왜 필요한지(개발 영향) | 대상(기획/디자인/PG/법무) | 막힘 정도(블로커/논의/참고)`.
- **블로커(이 답이 없으면 착수 불가)를 맨 위로 정렬**. 비슷한 질문은 묶되 근거 항목 모두 나열.

### Stage 5 — 마무리(_검증체크리스트 + 경로 보고)
- `_검증체크리스트.md` 생성(아래 본문). 산출물 폴더 경로와 "블로커 질문은 착수 전 반드시 닫기 / 도메인 경계는 04~08에서 사람 확정" 고지를 보고.
- (운영 가이드) 질문 리스트의 **블로커만 모아 기획·핸드오프 담당과 짧은 확인 미팅**을 잡고, 답이 채워진 산출물을 다음 단계(02 기술 스택 선정·04 DB 설계)의 입력으로 넘긴다.

## 도구 정확성 (probe·degrade)
- **Context7 MCP**(probe) = Spring Boot 3.3/JPA 최신 메커니즘 가벼운 확인용(이 단계는 코드를 짜지 않음, 본격 사용은 04 이후). 없으면 내장 지식 + "버전 확인 필요 ⚠️".
- **중단**은 기획 12(원천) 부재 시에만. 그 외(14·06·10 일부 부재, Context7 부재)는 ⚠️ 표기 후 degrade.

## _검증체크리스트 본문 (Stage 5 생성)
```
- [ ] 출처가 비거나 인용이 어색한 엔티티·NFR 항목 원문 대조 (AI가 지어낸 엔티티/필드 차단)
- [ ] 도메인 경계·애그리거트 묶음은 후보 — 04~08에서 사람이 확정 (AI 제안 그대로 확정 금지)
- [ ] 트랜잭션 단위(결제↔예약 확정 등)는 게이트에서 사람 확정한 값인지
- [ ] NFR 임계값(p95/SLO)이 [기획 확인 필요]로 비워져 있는지 (근거 없는 수치 차단)
- [ ] 질문 리스트의 블로커 항목이 착수 전 모두 닫혔는지 (미답 블로커 위 코드 금지)
- [ ] 12·14에서 계승한 ⚠️/[확인 필요]/🔴가 질문 리스트에 빠짐없이 반영됐는지
- [ ] 민감정보(실 사용자 데이터·계약 정보)가 외부 전송 전 원천에서 제외됐는지
```

## 주의
- **AI는 엔티티를 만들어내기도 한다** — 명세에 없는 그럴듯한 엔티티·필드를 끼워 넣는다. 출처 인용을 강제하고 출처가 비거나 어색한 항목은 원문 대조.
- **도메인 경계는 AI가 정하지 않는다** — "Booking과 Payment를 한 애그리거트로 묶을지"는 DDD·트랜잭션 판단. AI 제안은 후보, 04~08에서 사람 확정.
- **비기능 요구의 숫자는 추정이다** — "검색 p95 300ms" 같은 임계값을 AI가 채우면 근거 없는 수치. `[기획 확인 필요]`로 비우고 12·14에서 합의.
- **흔한 실수 — 한 방 프롬프트**: 추출부터 분석 종합까지 한 번에 시키면 중간 오류(특히 지어낸 엔티티)를 못 잡는다. 01-1→01-3 단계마다 사람이 확인.
- **흔한 실수 — 질문 리스트 없이 착수**: 블로커에 답이 없는 채로 코드를 시작하면 그 추정 위에 쌓은 04~09를 통째로 다시 손봐야 한다.
