# 핵심 비즈니스 로직 개발 (Core Business Logic Development)

API 껍데기가 아니라 그 안에서 도는 **서비스의 본질적 규칙**(예약 상태 전이·결제 선행조건·취소 가능 조건)을 코드로 굳히는 단계다. 포밋의 `Booking`·`Payment` 도메인을 예로, 04 엔티티와 05 엔드포인트 사이를 채우는 도메인 서비스·애그리거트를 생성한다. **규칙의 정의는 사람의 실패 테스트가 진실의 원천이고, AI는 그 테스트를 만족시키는 구현과 리팩토링을 맡는다** — AI에게 규칙을 발명하게 하면 컴파일 오류처럼 드러나지 않는 그럴듯한 거짓이 코드에 박힌다.

## 핵심 원칙
- **상위 산출물 계승, 재발명 금지 — 확정 상태일 때만**: 규칙의 출처는 기획 정책(06)·기능명세(12)와 04 ERD다. 명세에 없거나 애매하면 **추측하지 말고 `[확인 필요]`로 보존**(미확정 ⚠️ 유지).
- **AI에게 비즈니스 규칙을 발명하게 하지 않는다(제1원칙).** "취소 정책 적당히 만들어줘"가 아니라 "이 규칙(사람이 정의)을 테스트와 코드로 옮겨줘"여야 한다.
- **규칙 정의와 구현의 분리 = TDD가 경계.** 사람이 규칙을 **실패 테스트(Red)**로 명세화 → AI가 통과 구현(Green) → 테스트 보존 리팩토링(Refactor). 테스트가 규칙의 단일 진실 원천.
- **테스트를 통과시키려고 테스트(또는 규칙)를 바꾸지 않는다.** "테스트 수정 금지, 구현만 고칠 것"을 강제하고 테스트 diff를 사람이 본다.
- **상태 불변식은 애그리거트 안에 둔다(DDD).** 전이 규칙을 서비스에 흩지 말고 `Booking`이 자기 상태를 스스로 책임지게.
- **트랜잭션 경계와 외부 호출을 의식적으로 가른다.** 결제 PG 호출(11단계 소관)은 DB 트랜잭션 밖. 여기선 외부를 인터페이스로 모킹하고 도메인 규칙·보상만 검증.

## 파이프라인

### Stage 0 — 입력 확인·도구 probe·degrade
- `01-1_도메인분석.md`·`04-1_ERD.md`·`04-3_JPA엔티티초안.md`를 읽는다. 없으면 중단(위치 질의). 기획 12·06·07-3는 있으면 로드.
- **도구 probe**: Context7(ToolSearch 존재 시 가용)·Figma generate_diagram(read/diagram). 없으면 아래 degrade.
- **test-driven-development 스킬 호출**로 Red→Green→Refactor 절차를 강제한다. 규칙 위반 디버깅 시 systematic-debugging.

### Stage 1 — 규칙을 먼저 문장으로 (유스케이스 → 규칙 목록)
- 기획 12 기능명세·04 ERD를 참고해 도메인 규칙을 **사람이 읽을 목록**으로 정리. 아직 코드/테스트 금지.
- **상태 집합은 입력에서 가져온다**(04 ERD enum·12-2 상태정의 SSOT) — 도메인마다 다르다. 예: 포밋 `Booking`은 `REQUESTED/ACCEPTED/IN_PROGRESS/COMPLETED/CANCELED`, 펫사료구독 `Subscription`은 `active/alt_offered/cancelling/cancelled/paused`. **이 상태 목록을 발명하지 말고 입력 enum을 그대로 계승**.
- 그 상태별 **허용 전이·금지 전이**를 표로, 각 전이의 **행위 주체·선행 조건** 함께. 행위 주체는 07-3 RBAC 계승(포밋은 OWNER/SITTER 2역할, 단일 actor 도메인은 OWNER + 소유권 가드만). 결제 시점·취소/환불 영향 명시.
- 명세에 없거나 애매하면 **`[확인 필요]`**(추측 금지). → `08-1_도메인규칙명세.md`. (게이트 전까지 코드/테스트 금지.)

### 🚦 게이트 — 도메인 규칙 확정 (사람 개입, 필수)
Stage 1에서 만든 `08-1_도메인규칙명세.md`의 상태 전이표·`[확인 필요]` 항목을 AskUserQuestion으로 제시 → 사람이 확정/수정.
- 확인 항목 예시: ① 허용/금지 전이가 맞는가 ② 결제는 어느 전이 시점인가(포밋: 수락 후 결제→확정 / 펫사료구독: 정기결제·해지정산 시점) ③ 취소·해지 가능 조건·환불 영향(할인분 차감·위약금 계산식) ④ 같은 자원 동시 변경 시 무엇이 이기는가(포밋: 중복 예약 / 펫사료구독: 두 기기 동시 해지).
- **여기서 규칙이 틀리면 이후 전부 틀린다.** 규칙 확정 전에는 Stage 2(테스트 작성)로 넘어가지 않는다. AI는 규칙을 발명하지 않는다 — `[확인 필요]`는 사람이 06 정책·12 명세와 대조해 채운다.

### Stage 2 — 규칙을 실패하는 테스트로 (Red)
- 확정된 08-1 규칙을 `Booking` 애그리거트의 **실패 테스트**로만 작성(프로덕션 코드 금지).
- **금지/예외 케이스 우선**: `COMPLETED는 cancel 불가(예외)`, `정의되지 않은 전이(REQUESTED→COMPLETED 등)는 모두 예외`, `IN_PROGRESS 전이는 결제 완료 선행`, `OWNER가 자기 예약 아닌 것 취소 시 거부`. 해피패스(`accept→ACCEPTED`)도 포함.
- 메서드명은 규칙이 읽히게. "전부 실패(또는 컴파일 실패)" 확인 후 결과 보고. → `08-2_테스트목록.md`.

### Stage 3 — 테스트를 통과시키는 최소 구현 (Green)
- 상태 전이를 `Booking` 애그리거트 내부 메서드(`accept()/start()/complete()/cancel(by)`)로 캡슐화. 허용 안 되는 전이는 도메인 예외(`IllegalStateException` 또는 전용 예외)로 차단.
- **상태 불변식은 애그리거트가**, 결제 선행 등 조율은 `BookingService`(도메인/애플리케이션 서비스)가. 전부 Green 확인 후 보고.
- **테스트는 절대 수정 금지**(통과시키려 규칙을 바꾸지 않는다). → `08-3_도메인서비스초안.md`.

### Stage 4 — 트랜잭션 경계와 동시성 (규칙을 깨는 경계 케이스)
- **트랜잭션 경계표**: "예약 수락 + 결제 요청 + 알림 발행" 중 어디까지가 한 트랜잭션인지 표로(결제 PG 호출은 트랜잭션 밖). 외부 실패 시 도메인 상태 롤백/보상을 테스트로 명세.
- **동시성**: 같은 자원 동시 변경(예: 포밋 = 같은 CareService 같은 시간대 두 OWNER 동시 예약 / 펫사료구독 = 같은 Subscription 두 기기 동시 해지·대안적용) 시 낙관적 잠금(`@Version`) vs 비관적 잠금 **트레이드오프를 정리하고 추천만**(결정은 사람). 결정된 방식의 동시성 테스트(중복 처리가 막히는지) 작성.
- 외부 연동 실제 구현은 11단계 소관 — 여기선 인터페이스로 모킹. Context7 가용 시 `@Transactional` 전파·`@Lock` 최신 용법 확인(없으면 ⚠️). → `08-3`에 보강.

### Stage 5 — 리팩토링 + 상태 다이어그램 역생성 (Refactor)
- 테스트 Green 유지하며 리팩토링: 중복 상태 검사 정리·매직스트링→enum·서비스 책임 과부하 점검(도메인 vs 애플리케이션 서비스 경계 제안, 헥사고날: 도메인은 프레임워크·외부 의존 모르게).
- 구현된 전이 코드에서 **Mermaid stateDiagram 역생성** → `08-4_상태전이.md`. **08-1 규칙표와 대조**, 불일치는 **보고만 하고 임의 수정 금지**(Figma 가용 시 공유본 FigJam 옵트인, 없으면 Mermaid).

### Stage N+1 — 마무리
- `_검증체크리스트.md` 생성(아래 본문) + 산출물 폴더 경로 보고. `[확인 필요]`·🔴 잔존 시 ⚠️ 표기하고 "완료" 단정 금지.

## 도구 정확성 (probe·degrade)
- **Context7 MCP**(probe) = JPA 트랜잭션 전파(`@Transactional` propagation)·잠금(`@Version`/`@Lock`)·도메인 이벤트(`ApplicationEventPublisher`) 최신 용법. 없으면 내장 지식 + "버전 확인 필요 ⚠️".
- **Figma MCP generate_diagram**(probe) = 확정 상태 전이 공유용 FigJam. 없으면 **Mermaid stateDiagram 폴백**(코드 안에는 어차피 Mermaid).
- **JUnit5/AssertJ/Mockito** = 06에서 `spring-boot-starter-test`로 추가됨(단위 테스트 위주, 실제 DB·외부 통합은 13단계 Testcontainers). 로컬에서 `./gradlew test` 직접 실행 필요 시 안내.
- **중단**은 필수 입력(01·04) 부재 시에만. 그 외는 degrade.

## 주의
- **AI에게 비즈니스 규칙을 발명하게 하지 마라(제1원칙).** 규칙 출처는 06 정책·12 명세. 없으면 `[확인 필요]`.
- **통과한 테스트 ≠ 올바른 규칙.** 테스트가 잘못된 규칙을 검증하면 잘못된 구현을 통과시킨다 — 테스트가 08-1 규칙표와 맞는지 대조가 핵심 검수.
- **외부 연동을 도메인 트랜잭션에 끌어들이지 마라.** 결제 PG·FCM은 11단계. 여기선 모킹하고 트랜잭션 밖에서 호출.
- **동시성 버그는 단위 테스트로 잘 안 잡힌다.** 100% 보장 어려움 — 11·13단계 통합/부하 테스트·systematic-debugging으로 재현 보강.
- **흔한 실수 — 상태 전이를 서비스에 흩뿌리기**: 검사 복붙은 한 곳에서 빠진다. 전이 규칙은 애그리거트 한곳으로.
- **흔한 실수 — 해피패스만 테스트**: 금지 규칙이 무방비가 된다. 금지/예외를 더 꼼꼼히.
