# be-business-logic — 핵심 비즈니스 로직 개발 자동화 스킬

서비스의 본질적 규칙(예약 상태 전이·결제 선행조건·취소/환불 영향)을 **사람이 실패 테스트로 명세화하면 AI가 통과 구현·리팩토링**을 맡는 TDD 기반 도메인 로직 개발 스킬입니다. 포밋의 `Booking`·`Payment` 도메인을 예로, 04 엔티티와 05 엔드포인트 사이를 채우는 도메인 서비스·애그리거트를 만들고 상태 전이 다이어그램을 코드에서 역생성합니다.

> BE 프로세스 08단계 "핵심 비즈니스 로직 개발"을 자동화합니다.
> 역할 분담: **규칙의 정의는 사람**(테스트가 진실의 원천), AI는 통과 구현·리팩토링·다이어그램 역생성. AI에게 규칙을 발명하게 하면 그럴듯한 거짓이 코드에 박힙니다.

## 무엇을 만들어 주나

`backend-output/<주제>/08_비즈니스로직/`에 생성:

| `08-2_테스트목록.md` | TDD Red 케이스(JUnit5/AssertJ, 규칙이 메서드명에 읽힘)·기대값·금지/예외 우선 |
| `08-3_도메인서비스초안.md` | Green 최소 구현(Booking 애그리거트·도메인 예외)·BookingService 조율·트랜잭션 경계표·동시성 트레이드오프 |

## 준비물 (입력)

1. **(필수) 01 도메인분석 + 04 데이터베이스** — `<루트>/01_요구사항분석/01-1_도메인분석.md` + `04_데이터베이스/04-1_ERD.md`·`04-3_JPA엔티티초안.md`. 엔티티 구조·애그리거트·유스케이스의 원본.
2. **(권장) 기획 12 기능명세·06 정책** — 도메인 규칙의 원천. 없으면 `[확인 필요]`가 늘고 게이트에서 사람이 채웁니다.
3. **(연결) 07-3 RBAC 권한 매트릭스** — OWNER/SITTER 행위 주체 검사 근거.

## 사용법

01·04 산출물을 준비한 뒤:

```
예약(Booking) 도메인의 비즈니스 로직을 TDD로 개발해줘
```

1. **Stage 1** — 규칙을 사람이 읽는 목록으로 정리(`08-1`, 아직 코드 금지)
2. **🚦 도메인 규칙 확정** → 당신이 상태 전이표·`[확인 필요]`를 확정 (유일한 필수 개입)
3. **Red** — 규칙을 실패 테스트로(`08-2`, 금지/예외 케이스 우선)
4. **Green** — 테스트 통과 최소 구현(`08-3`, 테스트 수정 금지)
5. **트랜잭션·동시성** — 경계표 + 잠금 트레이드오프(결정은 사람)
6. **Refactor** — 리팩토링 + stateDiagram 역생성(`08-4`, 규칙표 대조)

발동 키워드: `비즈니스 로직`, `도메인 로직`, `도메인 서비스`, `상태 전이`, `애그리거트`, `TDD`, `트랜잭션 경계`, `동시성`, `business logic`, `domain service`

## 주의

- **AI에게 규칙을 발명하게 하지 마세요.** 규칙 출처는 06 정책·12 명세, 없으면 `[확인 필요]`.
- **통과한 테스트 ≠ 올바른 규칙.** 테스트가 규칙표(08-1)와 맞는지 대조가 핵심 검수.
- **테스트는 수정 금지** — AI가 Green 만들려고 기대값을 무르게 바꾸지 않았는지 diff 확인.
- **외부 연동(결제 PG·FCM)은 도메인 트랜잭션 밖** — 여기선 모킹, 실제 연동은 11단계.
- **동시성 잠금 선택은 사람** — AI는 트레이드오프 정리만, 단위 테스트로 100% 보장 불가.
