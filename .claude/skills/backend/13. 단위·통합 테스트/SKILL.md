# 단위·통합 테스트 (Unit & Integration Testing)

08(비즈니스 로직)·09(API)·10(쿼리)·11(외부 연동)에서 만든 코드가 "정말 명세대로 동작하는가"를 자동으로 증명하는 단계다. 산출물은 테스트 피라미드(단위 多 > 통합 中 > E2E 少)를 따른 테스트 계획·단위 테스트·통합 테스트·커버리지 빈틈 보강안. 이 테스트는 그 자체가 산출물이면서 16(배포) CI 게이트·19(고도화) 리팩터링 안전망이 된다. **AI는 케이스 회수(happy/경계값/예외)와 골격, 기대값(assertion) 정의·정답 판단은 사람.**

## 핵심 원칙
- 상위 산출물 계승·재발명 금지: 08 도메인 규칙·09 API 명세가 **확정 상태일 때만** 테스트 기대값의 근거로 삼고, 미확정·모호점은 `[확인 필요]`로 보존한다(AI가 정답을 발명하지 않는다).
- **기대값은 사람, 케이스는 AI.** AI는 입력 조합(경계값·null·예외)을 회수하는 데 압도적이지만 "그래서 정답이 무엇인가"는 명세를 아는 사람의 몫이다. 둘을 섞으면 구현을 그대로 베끼는 동어반복 테스트가 된다.
- **레벨을 먼저 고정하고 생성한다.** "테스트 짜줘"만 시키면 단위로 충분한 걸 무거운 `@SpringBootTest`로 짜거나 DB 정합성을 Mock으로 때운다. 피라미드 분배(Stage 1)를 사람이 먼저 정의해야 빠르고 의미 있는 스위트가 나온다.
- **인메모리 DB 대신 Testcontainers.** 포밋 정본은 PostgreSQL 16. H2로 통과한 쿼리가 운영에서 깨지는 사고(방언·`jsonb`·인덱스 차이)를 막으려면 통합 테스트는 실제 같은 엔진으로 돈다.
- **커버리지는 신호이지 목표가 아니다.** JaCoCo는 "어디를 안 봤나"를 알려주는 지도로만 쓰고, 그중 위험한 빈틈만 메운다. 숫자를 KPI로 걸면 assertion 없는 가짜 테스트가 생긴다.
- **외부 연동은 실제로 때리지 않는다.** 토스페이먼츠·FCM(11단계)은 WireMock 등으로 목 처리(실결제·실발송 호출 금지).

## 파이프라인

### Stage 0 — 입력 확인·도구 probe·degrade
- 08·09 산출물을 읽는다. 둘 다 없으면 **중단**(코드/명세 위치 질의). 한쪽만 있으면 있는 범위로 진행 + ⚠️ 표기.
- 기획 12 예약 정책 로드(있으면 기대값 근거, 없으면 Stage 1에서 `[확인 필요]` 처리).
- **도구 probe**: Context7(ToolSearch 존재) = Testcontainers `@ServiceConnection`·REST Assured·JUnit5 최신 API 확인. docker/gradle CLI = bash 시도로 판별. 없으면 아래 degrade.

### Stage 1 — 테스트 계획(피라미드 분배) → 13-1
- 08 도메인규칙명세·12 핵심 정책을 읽고 검증 항목을 **[단위/통합/E2E]** 레벨로 분류한 표로 정리.
  - (아래 예시는 관통 예시=포밋 시터 예약 기준. **본인 주제의 08·09 애그리거트·상태·actor로 치환**할 것 — 예: 구독서비스는 Subscription 해지·정산·일시정지.)
  - **단위**: 상태 전이 규칙(포밋 예: `REQUESTED→ACCEPTED` 허용, `COMPLETED`에서 취소 불가 / 구독 예: `active→cancelling`, `cancelled`에서 전이 불가), 정산금·수수료/위약금 계산.
  - **통합**: 애그리거트 저장+조회 영속성, 결제(환불) 승인→상태 확정→정산행 생성 트랜잭션(보상 롤백 포함), Redis 캐시 적중.
  - **E2E**: 핵심 플로우 HTTP 관통 1~2개만(포밋 예: 예약요청→시터수락→결제 / 구독 예: 해지요청→정산→cancelled).
- 각 항목에 "기대 동작" 1줄, 모호하면 `[확인 필요]` 태그. 외부 연동(토스페이먼츠·FCM)은 "WireMock 목" 표시.
- → `13-1_테스트계획.md`(게이트 검수 대상). **기대 동작은 게이트에서 사람이 확정한다.**

### 🚦 게이트 — 테스트 레벨 분배 + 기대값(assertion) 확정 (AskUserQuestion, 필수)
Stage 1에서 만든 `13-1_테스트계획.md` 초안(검증항목 × [단위/통합/E2E] + 각 "기대 동작")을 AskUserQuestion으로 제시 → 사람이 확정/수정한다. (게이트 시점에 13-1이 이미 존재해야 한다.)
- 확인 대상: ① 각 항목의 레벨 배정이 맞는가(단위로 충분한 걸 통합으로 올리지 않았는가) ② 각 "기대 동작"이 **명세 기준 옳은 정답인가**(현재 구현을 그대로 베낀 게 아닌가) ③ `[확인 필요]` 모호점(예: "취소는 언제까지 가능한가")은 기획 12로 되돌릴 것인가.
- **이 게이트 통과(레벨·기대값 확정) 전에는 Stage 2(테스트 코드 생성)로 넘어가지 않는다.** 기대값을 사람이 정의해야 동어반복 테스트를 막는다.

### Stage 2 — 단위 테스트 생성 → 13-2 (게이트 통과 후)
- 08 도메인 클래스(`Booking`)·서비스(`BookingService`)를 읽고 게이트 확정 [단위] 항목에 대해 JUnit5 테스트 작성.
- 의존성(`PaymentClient`·`BookingRepository`)은 Mockito Mock, **Spring 컨텍스트는 띄우지 않는다**(순수 객체, 빠르게).
- AssertJ 단언, `@Nested`+한글 `@DisplayName`으로 시나리오 그룹화. 상태 전이는 `@ParameterizedTest`로 (현재상태, 요청전이, 허용여부) 조합 검증.
- 예외 케이스: `COMPLETED` 예약 취소 → `IllegalStateException`, 과거 날짜 예약 → 검증 실패. 각 테스트에 `// 기대: ...` 주석.
- **동작(결과) 검증 우선, 구현 절차(Mock 호출 횟수)는 최소만** — 과밀착 테스트는 리팩터링만으로 깨진다.
- → `13-2_단위테스트초안.md`. 생성 직후 **모든 assertion을 명세 기준으로 사람이 대조**(구현이 던지는 값을 그대로 박았을 수 있음).

### Stage 3 — 통합·API 테스트 생성 → 13-3 (게이트 통과 후)
> 아래 예시는 관통 예시=포밋 시터 예약. **본인 주제의 애그리거트·상태·actor·에러코드로 치환**(예: 구독서비스=Subscription/cancelled/OWNER 단일 actor). 골격(Testcontainers·WireMock 목·계약 검증)은 도메인 불변.
- **통합(Testcontainers)**: Context7로 `@ServiceConnection` 최신 사용법 확인 후 적용. `@SpringBootTest`+`@Testcontainers`, PostgreSQL 16·Redis 7 컨테이너.
  - 테스트 1: 결제(환불) 승인 → 애그리거트 확정 전이 + 정산행 1건 생성(실제 DB 조회 검증, **트랜잭션 보상 롤백 케이스 포함** — 실패 시 부분 row 없음). 포밋: `Booking ACCEPTED`+`Settlement` / 구독: `Subscription cancelled`+`Refund COMPLETED`.
  - 테스트 2: 동일 조회조건 2회 호출 시 2번째가 Redis 캐시에서 응답(쿼리 카운트로 검증).
  - 테스트 데이터는 `@Sql`/빌더 픽스처로 시드, 테스트 간 격리. **컨테이너는 클래스 단위 재사용**(기동 시간 단축).
- **API(REST Assured)**: `@SpringBootTest(webEnvironment=RANDOM_PORT)`+Testcontainers.
  - happy path: 핵심 플로우 HTTP 관통. 계약: 응답 JSON 스키마, 에러코드(미존재 자원 → 404 + 해당 `code`).
  - 인증: 주제 actor 모델대로 JWT 케이스 분리 — **다중 역할이면 역할 권한(403), 단일 actor면 소유권 가드(403)**(역할 없는 도메인에 SITTER 등 발명 금지).
- **외부 PG·FCM(11단계)은 WireMock 등으로 목** — 실결제·실발송 호출 금지.
- → `13-3_통합테스트.md`.

### Stage 4 — 커버리지 빈틈 보강 → 13-4
- `./gradlew test jacocoTestReport` 리포트(`build/reports/jacoco/...`)가 있으면 읽어 핵심 도메인·돈 관련 패키지(포밋 예: `Booking`·`Payment` / 구독 예: `Subscription`·`Refund`) 미커버 분기 목록화. 없으면 코드 정적 분석으로 분기 후보 도출 + "리포트 첨부 시 정밀화 ⚠️".
- 단순 getter/DTO 같은 무의미한 미커버는 제외. "이 미분기가 운영에서 버그로 이어질 위험"을 상/중/하 평가.
- **상·중 항목에 대해서만 추가 테스트 제안(코드는 사람 승인 후 생성)**. 숫자(커버리지 %)를 올리는 게 목적이 아님을 전제로.
- → `13-4_커버리지보강.md`.

### Stage 5 — 마무리(_검증체크리스트 + 산출물 경로 보고)
- `_검증체크리스트.md`(아래 본문) 생성. 산출물 폴더 경로 보고.
- `verification-before-completion` 관점 안내: 전체 스위트를 실제 실행(`./gradlew test`)해 초록불을 확인한 뒤에야 16(배포) CI 게이트로 넘긴다. CLI/Docker 부재 시 "로컬에서 직접 실행 필요" 고지.
- 환류: 테스트 중 드러난 명세 모호점(예: "취소 가능 기한")은 기획 12로 질문 환류(사용자 확인 후, 폴더 한정 append).

## 도구 정확성 (probe·degrade)
- **Context7 MCP**(probe) = Testcontainers `@ServiceConnection`·REST Assured·JUnit5 최신 설정 확인(2-step: resolve-library-id → query-docs). 부재 → 내장 지식으로 진행 + "버전 확인 필요 ⚠️"(학습 시점 이후 API 변동 가능).
- **test-driven-development 스킬** = 신규 케이스 보강·버그 재현 시 "실패 테스트 먼저 → 통과" 사이클. **systematic-debugging 스킬** = 생성 테스트가 깨졌을 때 "구현이 틀렸나 vs 기대값이 틀렸나"를 가설→검증으로 좁힐 때.
- **docker/gradle CLI** = bash 가용 시 스위트 실행. 부재 → 테스트 코드·설정은 생성하되 "로컬에서 직접 실행 필요" 안내(Testcontainers는 Docker 필요·CI 러너에 Docker 떠 있는지 확인).
- 필수 입력(08·09) 부재 시에만 중단. 그 외는 degrade.

## _검증체크리스트 본문 (Stage 5 생성)
```markdown
# 검증 체크리스트 — <주제> 단위·통합 테스트 (작성일: <날짜>)

> AI는 케이스 회수·골격까지. 기대값(정답) 정의는 사람의 일이다.

- [ ] 생성된 모든 assertion을 명세 기준으로 대조 (구현이 던지는 값을 그대로 박지 않았는가)
- [ ] 일부러 구현을 깨뜨려 테스트가 빨갛게 되는지 확인 (가짜 초록불 차단)
- [ ] 테스트 레벨 분배 적정 — 단위로 충분한 걸 무거운 @SpringBootTest로 짜지 않았는가
- [ ] Mock 호출 횟수까지 과검증해 리팩터링만으로 깨지는 테스트가 없는가 (동작 검증 우선)
- [ ] Testcontainers는 클래스 단위 컨테이너 재사용 — 통합 테스트 남발로 스위트가 분 단위로 길어지지 않는가
- [ ] 외부 연동(토스페이먼츠·FCM)은 WireMock 목 처리 — 실결제·실발송 호출 없음
- [ ] 커버리지는 빈틈 지도로만 — assertion 없는 "커버리지용 테스트" 없음(코드 리뷰에서 걸러냄)
- [ ] 플레이키 테스트(시간·랜덤·동시성 의존) 없음 — 발견 즉시 고정 시계·시드 주입으로 격리
- [ ] 전체 스위트 실제 실행해 초록불 확인 후 16(배포) CI 게이트로 전달
- [ ] 테스트 중 드러난 명세 모호점은 기획 12로 질문 환류
```

## 주의
- **AI가 짠 테스트는 "통과시키는" 방향으로 기운다.** 구현이 던지는 값을 그대로 기대값에 박으면 버그가 있어도 초록불이다. 가능하면 구현을 일부러 깨뜨려 빨갛게 되는지 확인한다.
- **테스트가 구현 내부에 너무 밀착하면 깨지기 쉽다.** "동작(결과)"을 검증하고 "구현 절차"는 최소만 검증하도록 한다.
- **Testcontainers는 느리고 Docker가 필요하다.** 컨테이너 재사용·통합 최소화로 관리하고, CI 러너에 Docker가 떠 있는지 확인한다.
- **커버리지 100%는 함정이다.** 닿지 않은 코드를 아는 데만 쓰고 숫자를 목표로 삼지 않는다.
- **외부 연동은 실제로 때리지 않는다.** 실결제·실발송을 테스트가 호출하면 사고다.
- **흔한 실수 — 한 방 생성**: "전 패키지 테스트 다 짜줘"는 레벨이 섞이고 기대값 검토가 불가능한 더미를 만든다. 도메인 단위로 Stage를 끊고 매 단계 사람이 검토한다.
- **흔한 실수 — 플레이키 테스트 방치**: 시간·랜덤·동시성에 의존해 가끔 깨지는 테스트는 CI 신뢰를 무너뜨린다. 발견 즉시 원인(고정 시계·시드 주입)을 잡거나 격리한다.
