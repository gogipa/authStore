# 성능 모니터링·고도화 (Performance Tuning)

운영이 안정된 백엔드의 질문을 "동작하는가"에서 "충분히 빠르고 효율적인가"로 옮긴다. 14단계 APM 지표(p95/p99·처리량·에러율)를 **해석**해 병목과 성능 회귀를 찾고, 트래픽 추세로 용량을 계획하고, 근거 지표가 붙은 개선 가설 백로그를 만든 뒤 — **다시 be-requirements-analysis(01)로 회귀시켜 다음 개발 사이클을 시작**한다. AI는 지표 해석 초안·회귀 구간 지목·개선 가설 정리를 담당하고, **무엇을 먼저 개선할지·용량을 얼마나 늘릴지의 우선순위와 투자 결정은 사람**이 한다. 기획 시리즈 18(improvement-planning)의 백엔드 짝꿍이다.

## 핵심 원칙
- **상위 산출물 계승·재발명 금지** — 14 SLO/SLI·12 부하테스트 결과·17 자원 현황·16 배포 이력을 그대로 인용. 확정된 값만 계승, 미확정은 ⚠️로 보존.
- **지표는 "본다"가 아니라 "해석한다"** — 대시보드를 띄우는 것과 "검색 p99가 결제 시간대에만 튄다"를 읽어내는 것은 다른 일. AI는 해석 초안, "이 정도면 고칠 문제인가"의 SLO 기준은 사람.
- **평균이 아니라 꼬리(p99)를 본다** — 평균은 거짓말을 한다. 일부가 매우 느리면 평균은 괜찮아 보인다. 분위수(p95/p99) 꼬리 레이턴시가 진짜 불만의 원천. 리포트에 "평균 말고 분위수로" 명시.
- **상관은 인과가 아니다** — "배포 직후 느려짐"이 곧 "그 배포가 원인"은 아니다(트래픽 증가가 겹쳤을 수 있다). 회귀 가설은 systematic-debugging으로 증거 확인, 미확정은 가설로 남긴다.
- **측정 없는 최적화 금지** — 지표로 확인되지 않은 곳을 "느릴 것 같다"고 미리 손대면 복잡도만 는다. 측정으로 확인된 병목만 처방.
- **루프 마감** — 이 단계의 끝은 다음 사이클의 시작. 백로그의 `[1단계 회귀]` 항목을 be-requirements-analysis(01) 입력으로 인계한다.

## 입력
- **필수**: `<루트>/14_관측성/`(14-2 메트릭대시보드·14-3 알림룰·14-4 SLO_SLI — 지표·기준의 원천). 없으면 **중단**(또는 사용자에게 APM 지표/대시보드 export 위치 질의).
- **권장**:
  - `<루트>/12_캐싱성능/`(12-1 부하테스트.k6.js·12-2 병목분석·12-3 캐시전략 — 한계 RPS·캐시 적중률 인용)
  - `<루트>/18_장애대응/`(18-2 포스트모템·18-3 근본원인분석 — "예방" 액션이 개선 백로그로 합류)
  - `<루트>/17_인프라/`(17-1 terraform·17-2 오토스케일 — ECS/RDS/Redis 자원 현황·비용 점검)
  - `<루트>/16_배포/`(16-1 github-actions — 릴리즈 태그·배포 시각, 회귀 구간 상관 분석용)
  - 실측 APM 지표(Grafana CSV/PromQL 결과 export, 분기 시계열)
- 14가 없으면 중단. 그 외 권장 입력 부재는 degrade(해당 분석에 "데이터 없음 — 추가 필요" 표기).

## 파이프라인

### Stage 0 — 입력 확인·도구 probe·degrade
- `14_관측성/` 필수 확인(없으면 중단). 12·18·17·16·실측 APM export 로드(있으면). 부재 입력은 degrade로 기록.
- **단위·분위수 점검 준비**: 원본 대시보드의 단위(ms/s)·RPS/분당요청·p95/p99 구분을 Stage 1에서 대조한다는 전제 고정.
- **도구 probe**: Context7(ToolSearch 존재) / k6·python3(bash 시도) / Notion(ToolSearch 존재) / systematic-debugging 스킬.
- 분석 대상 엔드포인트(트래픽 상위)·분석 구간(분기) 확인 준비.

### Stage 1 — APM 지표 해석 → 19-1
- 트래픽 상위 엔드포인트(**대상 도메인의 09 컨트롤러·12-1 부하 분포에서 확정** — 도메인별로 다름. 예시일 뿐: 시터 검색/예약, 또는 구독목록 조회/정기결제/해지정산 등)별로 p50/p95/**p99**·처리량(RPS)·에러율을 **주 단위 시계열**로 정리.
- 14-4 SLO 대비 위반 구간 표시(예: 읽기 진입점 p99 < 목표 위반 주차).
- 꼬리 레이턴시(p99) 큰 엔드포인트 강조 + 원인 후보(콜드 캐시? 12-3 캐시 적중률 저하? 10 N+1 잔존? 11 외부 PG 지연?) 제시. **데이터로 확인 안 되는 원인은 "추가 분석 필요"로 둔다(근거 없는 단정 금지).**
- PromQL 쿼리는 Context7로 문법 확인 후 병기(부재 시 내장 지식 + ⚠️ 문법 확인 필요).
- **수치·단위는 원본 대시보드와 대조**(p95/p99·ms/s·RPS 혼동 차단).

### Stage 2 — 병목 추세·성능 회귀 → 19-2
- 병목 후보를 메트릭에서 추출(느린 쿼리·N+1 잔존·캐시 적중률 저하). 추세(악화/유지)를 시계열로 판정.
- 배포 이력(릴리즈 태그·배포 시각)과 엔드포인트별 p95 시계열을 겹쳐 **"어느 배포 직후부터 p95가 유의하게 올랐는가"** 회귀 구간 지목. 회귀 의심 배포는 그 릴리즈 변경 범위와 묶어 가설 제시. ⚠️ **배포 이력은 16-1 파일(파이프라인 정의)이 아니라 GitHub Releases/ECR 이미지 태그·배포 타임스탬프(런타임 조회)에서 얻는다** — 본 정보가 없으면 회귀 구간을 `[확인 필요]`로 두고 자연 증가/구조 병목 분석만 진행(단정 금지).
- **자연 증가(트래픽 증가)와 회귀(코드 변경)를 구분**. 회귀 원인 추적은 `/superpowers:systematic-debugging` 절차로 진행, 증거로 확정 안 된 건 가설로만. **롤백/수정 결정은 사람**이라고 명시.

### 🚦 게이트 — 개선 우선순위 결정 (사람 개입, 필수)
AskUserQuestion으로 19-1·19-2 해석 결과와 개선 후보를 제시 → 사람이 **우선순위·SLO 기준·투자 의향**을 확정.
- 제시 항목: ① 어떤 병목/회귀를 먼저 다룰지(영향 기준) ② "이 정도면 고칠 문제인가"의 SLO 임계 판단 ③ 증설 의향(예산·시점) ④ `[1단계 회귀]` 후보 중 다음 사이클로 올릴 항목.
- **AI 우선순위 초안은 일반론** — 비용·리스크·전략을 아는 사람이 확정한다. 확정 전에는 Stage 3 백로그를 "확정 순위"로 표기하지 않는다.

### Stage 3 — 개선 가설 백로그 → 19-3
- 가설 형식: **"[근거 지표] 때문에 [개선]을 하면 [성능 지표]가 [예상 방향]으로 변할 것이다"**.
- 근거 지표(p99·캐시 적중률·N+1 횟수 등) 출처를 **모든 가설에 명시**(19-1/19-2 인용). **근거 없는 가설 금지.**
- 우선순위 초안: 영향(레이턴시/비용/안정성) × 노력(개발 추정, `[개발 확인 필요]` 라벨). 게이트에서 확정한 우선순위 반영.
- 유형 태그: `[쿼리최적화](→10단계)` / `[캐싱](→12단계)` / `[아키텍처](→03단계)` / `[신규요구](→01단계)`.
- **"신규 요구사항" 성격(예: 별도 검색엔진 도입)은 `[1단계 회귀]` 라벨** — 검증 없이 바로 구현 금지, 반드시 01 분석부터 다시.
- 18 포스트모템 "예방" 액션이 있으면 백로그로 흡수(출처=`18-2 #n`).
- 우선순위 내림차순 표로 저장.

### Stage 4 — 용량 계획 → 19-4
- 트래픽 추세(주간 RPS·DAU) + 17 자원 현황으로 ECS 태스크·RDS 연결·Redis 메모리가 임계에 도달하는 예상 시점 추정.
- 12 k6 부하 테스트 결과가 있으면 인용해 "현재 구성의 한계 RPS" 추정. **외삽은 외삽일 뿐 — k6 실측으로 교차 검증**(이벤트성 급증은 외삽이 못 잡음 명시).
- 증설 옵션(스케일 아웃 vs 인스턴스 등급 상향) × 비용 영향(17 비용 점검 참조). "지금 당장 / 다음 분기 / 모니터링만" 3단계 권고를 **의사결정용 표**로.
- **증설 예산·시점 결정은 사람**이라는 전제 표기.

### Stage 5 — 사이클 회귀 + 검증 체크리스트 → 19-5
- 이번 사이클 누적 산출물 요약: 갱신된 ADR(02·03), ERD 변경(04), 새 OpenAPI 엔드포인트(05), 런북 추가분(17), 포스트모템 액션(18) 목록.
- 19-3에서 `[1단계 회귀]` 라벨 항목을 추려 **be-requirements-analysis(01)의 입력**이 되도록 정리(BE 19 → BE 01 인계 문서).
- **기획 18(improvement-planning) 개선 백로그와 합류 지점 표시**(같은 서비스의 기획/개발 백로그를 한 로드맵에서).
- `_검증체크리스트.md` 생성(아래 본문).

### Stage 6 — (옵트인) Notion 동기화
- Notion MCP 인증 확인. 미인증/미설치면 스킵하고 마크다운 SSOT 유지(`/mcp` 인증 안내).
- 인증되면 개선 백로그를 기획 18 백로그와 같은 곳에 동기화. **외부 전송 전 민감정보(실 엔드포인트·내부 식별자·비용 실수치) 점검.**

## 도구 정확성 (probe·degrade)
- **Context7 MCP**(probe) = PromQL·Grafana 패널 문법 최신 확인. 부재 시 내장 지식 + "⚠️ 문법 확인 필요" 표기.
- **systematic-debugging 스킬** = 성능 회귀·꼬리 레이턴시 원인 추적(18단계와 동일 적용). `/superpowers:systematic-debugging`.
- **k6**(bash probe) = 용량 계획 한계 RPS 실측. 부재 시 12-1 기존 결과 인용 또는 "로컬 실측 필요" 안내(추정에 ⚠️).
- **python3** = 시계열 CSV 집계·분위수 계산. 부재 시 정적 해석 degrade(수동 대조 안내).
- **Notion MCP**(probe) = 백로그 공유본 옵트인. 부재 시 마크다운 SSOT.
- **중단**은 14 관측성 입력 부재 시에만. 그 외 권장 입력·도구 부재는 degrade.

## _검증체크리스트 본문 (Stage 5 생성)

## 주의
- **우선순위·투자 결정은 사람** — AI는 개선 가설과 우선순위 초안까지. "무엇을 먼저, 얼마를 들여" 고도화할지는 비용·리스크·전략을 아는 사람이. AI 우선순위를 확정 순위처럼 공유하지 말 것.
- **상관은 인과가 아니다** — "배포 직후 느려짐"이 원인 확정은 아니다(트래픽 겹침 가능). 미확정은 가설로 남기고 증거 확인 후 사람이 롤백/수정 결정.
- **지표 환각·단위 혼동** — p95/p99, ms/s, RPS/분당요청을 섞어 쓰는 일이 있다. 수치·단위는 원본 대시보드와 대조.
- **용량 추정은 외삽일 뿐** — 트래픽 외삽은 이벤트성 급증(프로모션)을 못 잡는다. k6로 한계 RPS를 실측해 교차 검증.
- **조기 최적화 경계** — 측정으로 확인된 병목만 손댄다. "느릴 것 같다"는 미리 최적화 금지.
- **흔한 실수**: ① p99를 보지 않고 평균만 보다 꼬리 사용자 불만을 놓침. ② `[1단계 회귀]` 라벨을 안 붙여 신규 요구 성격의 큰 변경을 검증 없이 바로 구현 — 신규 요구는 반드시 01단계 분석부터 다시.
