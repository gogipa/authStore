# be-performance-tuning — 성능 모니터링·고도화 자동화 스킬

운영이 안정된 백엔드의 APM 지표(p95/p99·처리량·에러율)를 **해석**해 병목과 성능 회귀를 찾고, 용량을 계획하고, 근거 지표가 붙은 개선 가설 백로그를 만든 뒤 — **다시 be-requirements-analysis(01)로 회귀시켜 개발 루프를 마감**하는 Claude Code 스킬입니다.

> BE 프로세스 19단계 "성능 모니터링·고도화"를 자동화합니다.
> 역할 분담: AI는 지표 해석 초안·회귀 지목·개선 가설 정리, **우선순위·투자·롤백 결정은 사람**.
> 기획 시리즈 18(improvement-planning)의 백엔드 짝꿍입니다.

## 무엇을 만들어 주나

`backend-output/<주제>/19_고도화/`에 생성:

| 파일 | 내용 |
|---|---|
| `19-1_APM지표해석.md` | 엔드포인트별 p50/p95/p99·RPS·에러율 분기 추세, SLO 위반 구간, 꼬리 레이턴시 원인 후보, PromQL 병기 |
| `19-2_병목추세회귀분석.md` | 병목 추세 + 배포 이력×p95 회귀 구간 지목, 자연 증가 vs 코드 회귀 구분, systematic-debugging 가설 |
| `19-3_개선백로그.md` | 근거 지표 붙은 개선 가설(영향×노력 우선순위), 유형 태그(쿼리/캐싱/아키텍처/신규요구) |
| `19-4_용량계획.md` | 자원 임계 도달 시점 추정, k6 한계 RPS 교차검증, 증설 옵션×비용, 3단계 권고 |
| `19-5_차기사이클_입력.md` | 누적 산출물 요약 + [1단계 회귀] 항목 → 01 입력, 기획 18 백로그 합류 지점 |
| `_검증체크리스트.md` | 사람이 확인할 항목 |

## 준비물 (입력)

1. **필수 — 14 관측성** `<루트>/14_관측성/`(14-2 메트릭대시보드·14-3 알림룰·14-4 SLO_SLI). 지표·기준의 원천. 실측 APM 지표(Grafana CSV/PromQL export)도 함께.
2. **(연결) 이전 단계** — 12 캐싱성능(부하테스트·캐시 적중률), 18 장애대응(포스트모템 예방 액션), 17 인프라(ECS/RDS/Redis 자원·비용), 16 배포(릴리즈 태그·시각). 없으면 해당 분석에 "데이터 없음" 표기.

## 사용법

분기 운영을 마치고 성능을 점검해 다음 사이클로 넘길 때:

```
14단계 Grafana 대시보드의 이번 분기 지표를 해석해서 성능 고도화 패키지를 만들어줘
```

1. APM 지표 해석(19-1) → 병목·회귀 분석(19-2) 자동
2. **개선 우선순위 결정** → 당신이 우선순위·SLO 기준·투자 의향 확정 (사람 개입 게이트)
3. 개선 백로그(19-3) → 용량 계획(19-4) → 차기 사이클 입력(19-5) 자동
4. (선택) Notion 동기화 → 기획 18 백로그와 합류

발동 키워드: `성능 모니터링`, `고도화`, `APM 지표 해석`, `병목 분석`, `성능 회귀`, `p99`, `용량 계획`, `개선 백로그`, `performance tuning`, `capacity planning`

## 주의

- **우선순위·투자 결정은 사람.** AI 우선순위 초안을 "확정 순위"처럼 공유하지 마세요.
- **상관은 인과가 아닙니다.** "배포 직후 느려짐"이 원인 확정은 아님 — 증거 확인 후 사람이 롤백/수정 결정.
- **지표 환각·단위 혼동.** p95/p99, ms/s, RPS 혼용 — 수치·단위는 원본 대시보드와 대조.
- **용량 추정은 외삽일 뿐.** 이벤트성 급증은 못 잡습니다 — k6 한계 RPS 실측으로 교차 검증.
- **조기 최적화 경계.** 측정으로 확인된 병목만 손댑니다.
- **[1단계 회귀] 누락 주의.** 신규 요구 성격의 큰 변경은 검증 없이 바로 구현하지 말고 01단계부터 다시.
