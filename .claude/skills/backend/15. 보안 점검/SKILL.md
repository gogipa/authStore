# 보안 점검 (Security Audit)

배포 직전, 07(인증·인가)·08(비즈니스 로직)·09(API)·11(외부 연동)까지 흩어져 구현된 포밋 백엔드를
**공격자 시점**으로 다시 훑어 입력 검증 누락·권한 구멍·인젝션·인증 우회·민감정보 노출을 잡는다.
산출물 = OWASP 점검표 + 의존성·시크릿 스캔 해석 + 고위험 경로 리뷰 + 심각도별 통합 리포트.
**역할 분담**: AI는 1차 스캔·체크리스트·CVE 분류(회수율), **침투 테스트·위협 모델링 최종 판단·릴리즈 승인은 보안 전문가·법무(정밀도)**. AI의 "문제 없음"은 합격증이 아니라 **검토 대상 목록**이다.

## 핵심 원칙

- **상위 산출물 계승·재발명 금지**: 07 SecurityConfig·RBAC·JWT, 09 컨트롤러·전역예외, 11 외부연동 어댑터를 점검 **대상**으로 읽되 다시 설계하지 않는다(확정 상태일 때만 계승, 미확정은 ⚠️ 보존).
- **스캔과 판단을 분리한다**: AI·스캐너에게는 "의심 지점을 근거(파일:라인)와 함께 빠짐없이 회수"까지만 시키고, "실제 취약점인가·배포를 막을 만한가"는 사람이 판단한다.
- **항목을 명시해 막연한 안심을 막는다**: "보안 점검해줘"만으로는 AI가 "특별한 문제 없어 보인다"고 넘기기 쉽다. OWASP 항목과 포밋의 구체적 위험 지점(결제 금액 검증·예약 소유권)을 점검에 박아 넣어 추적 가능하게 한다.
- **고위험 경로를 따로 판다**: 금전·개인정보로 직결되는 A01(권한)·A03(인젝션)을 결제(Payment)·개인정보(Member/Pet/Chat) 경로에서 별도 정밀 점검한다.
- **서로 다른 관점을 교차시킨다**: 체크리스트 점검과 `/security-review`·`/code-review` 스킬은 보는 방식이 다르다. 한쪽만 잡은 항목을 특히 주목한다.
- **AI의 "문제 없음"은 합격증이 아니다**: 학습 시점 이후 공격 기법·조합형 취약점·비즈니스 로직 결함은 놓친다. AI 점검은 침투 테스트·전문가 검토를 **대체하지 않고 보완**한다.

## 파이프라인

### Stage 0 — 입력 확인·도구 probe·degrade
- 점검 대상 소스 또는 07/09/11 산출물 확인. 없으면 위치를 묻고 **중단**.
- **도구 probe**: Context7 MCP(ToolSearch 존재) / `/security-review`·`/code-review` 내장 스킬 / 의존성·시크릿 스캔 리포트 존재 여부.
- **민감정보 점검 준비**: 스캐너 리포트에 실제 시크릿·내부 경로가 담길 수 있다 — 외부 MCP 전송 전 마스킹·필터링 대상으로 표시.

### 🚦 게이트 — 보안 전문가 검토 의뢰 + 배포 차단 항목 확정 (🔴 사람 확정, 필수)
AskUserQuestion으로 **이 점검의 위상과 배포 차단 기준**을 사람에게 확정받는다(스캔 시작 전·리포트 취합 전 양쪽에서 가능, 최소 1회 필수):
- **확인 1 — AI 점검의 위상 동의**: "이 점검은 1차 스캔·검토 대상 목록이며, 침투 테스트·위협 모델링 최종 판단·결제/개인정보 적법성·릴리즈 승인은 보안 담당자·외부 전문가·법무가 한다"에 동의하는가.
- **확인 2 — 배포 차단 기준**: Critical/High 항목을 닫기 전 배포(16단계)로 넘어가지 않는다는 기준에 동의하는가. (기본 제안)
- **확인 3 — 고위험 경로 범위**: 포밋에서 별도 정밀 점검할 경로(결제 승인·예약 소유권·시터 정산·개인정보/채팅) 확정.

게이트 통과 전에는 "안전하다"는 결론을 내리지 않는다. 사람 확정 없이 완료 보고 금지.

### Stage 1 — OWASP Top 10 항목별 코드 점검 → 15-1
표준 체크리스트로 소스를 훑되, 항목을 명시해 막연한 안심을 막는다. 항목별 **"의심 지점 + 근거 파일:라인 + 왜 위험한지 + 권고"** 표:
- **A01 권한 부적절(Broken Access Control)**: 본인 리소스 확인 없이 Booking·Payment·Pet에 `bookingId`/`paymentId`로 접근 가능한가(다른 보호자의 예약 조회).
- **A02 암호 실패(Cryptographic Failures)**: `Member.password` 해싱 방식, JWT 서명 알고리즘, 민감정보 평문 로깅.
- **A03 인젝션(Injection)**: `@Query`·네이티브 쿼리·문자열 연결 SQL, QueryDSL 외 동적 쿼리.
- **A04 안전하지 않은 설계 / A05 보안 설정 오류**: actuator 노출, CORS, 에러 스택트레이스 응답.
- **A07 인증 실패(Identification & Auth)**: 로그인 시도 제한, JWT refresh 회전, 토큰 만료 검증.
- **A08 무결성 실패 / A09 로깅·모니터링 실패 / A10 SSRF**.
- 확신 없는 항목은 **"확인 필요"** 태그(추측 단정 금지). **Context7 probe**: Spring Security 6 권장 설정(`authorizeHttpRequests`·`CsrfConfigurer`)·토스페이먼츠 웹훅 서명 검증이 최신인지 확인 후 대조(없으면 내장 지식 + "버전 확인 필요 ⚠️").

### Stage 2 — 입력 검증·권한 검사 누락 일괄 점검 → 15-1(보강)
A01·A03은 포밋 최대 위험축이라 따로 더 판다. 모든 `@RestController`를 엔드포인트 단위로 표:
`엔드포인트 | @Valid/Bean Validation 적용? | 인가 검사(@PreAuthorize 또는 서비스 내 소유권 확인) 유무 | 위험도 | 메모`
- 결제 승인(`POST /payments/confirm`): 클라이언트가 보낸 금액(amount)을 그대로 신뢰하지 않고 서버 Booking 금액과 대조하는가.
- 예약 조회/취소: 요청자가 그 Booking의 보호자(또는 해당 시터)인지 확인하는가.
- 시터 프로필·정산 조회: SITTER 본인 것만 보이는가.
- 파일 업로드(반려동물 사진): 확장자·크기·MIME 검증.
- 검증/권한이 빠진 엔드포인트만 **"누락 목록"**으로 따로 뽑는다.

### Stage 3 — 스킬 교차 스캔 + 고위험 경로 정밀 리뷰 → 15-3
- **`/security-review`**(probe): 현재 브랜치 변경분을 보안 관점으로 스캔(인증·인가·검증·인젝션·비밀 노출). PR 단위 권장. 없으면 Stage 1·2 체크리스트로 degrade + 안내.
- **`/code-review`**(probe): 권한 누락·검증 빠진 입력 같은 정확성 버그를 보안 관점으로 보강.
- **⚠️ 대상 코드/diff 부재 degrade(흔한 케이스)**: 두 스킬은 **변경 diff(PR/working tree)** 를 대상으로 동작한다. 점검 대상이 컴파일된 소스가 아니라 07/09/11의 **설계 초안(.md)** 뿐이면 diff가 없어 직접 실행이 무의미하다 → Stage 1·2 정적 체크리스트로 점검하고 **"실코드 작성 후 두 리뷰 스킬로 재점검 필요 ⚠️"** 를 15-3·리포트에 명시(생략 불가). 이때 두 스킬을 "미가용"이 아니라 "대상 부재 degrade"로 구분 기록.
- **교차 비교**: 스킬 결과와 Stage 1·2 체크리스트 결과를 대조해 **한쪽만 잡은 항목**을 별도 표기(서로 다른 관점이 잡은 진짜 결함일 수 있다).
- **고위험 경로 정밀 리뷰**: 결제 흐름(금액 검증·웹훅 서명·멱등성)과 개인정보 경로(Member/Pet/Chat 조회 소유권)를 다른 경로보다 높은 밀도로 점검.

### Stage 4 — 의존성·시크릿 스캔 결과 해석 → 15-2
스캐너 리포트를 받아 해석한다(스킬은 스캐너를 대신 실행하지 않음 — 리포트가 없으면 실행 명령 안내 후 degrade).
- **Dependency-Check/Snyk CVE**: 심각도(CVSS) + 포밋이 실제 쓰는 경로인지 + 업그레이드 시 호환 영향(Spring Boot 3.3 BOM 충돌 여부)으로 정리 → **"지금 올려야 함 / 다음 스프린트 / 영향 없음(미사용 transitive)"** 분류. "지금 올려야 함"은 **사람이 재확인**한다고 명시.
- **gitleaks 검출**: 각 항목을 **"진짜 시크릿 / 테스트 더미 / 오탐"**으로 분류 + 진짜로 의심되면 폐기·재발급할 키 명시. 한 번 커밋된 키는 이미 노출된 것으로 간주(이력 제거만으로 끝 아님) — **키 폐기·재발급 실제 회수는 사람이 즉시 실행**.
- **민감정보**: 리포트를 외부 MCP로 보내기 전 마스킹(`gitleaks --redact`)·민감 라인 필터링 확인.

### Stage 5 — 통합 리포트 + 검증 체크리스트 → 15_보안점검리포트.md
Stage 1~4 결과를 보안팀·릴리즈 담당에게 넘길 리포트로 취합:
- 심각도별(Critical/High/Medium/Low) 요약 표 + 항목 수.
- 각 항목: 위치 / 재현·근거 / 권고 조치 / 담당 / 상태(미조치).
- 맨 앞에 **"배포 차단 항목(Critical/High)"** 목록 별도.
- 맨 뒤에 **"AI 자동 점검 범위 밖 — 사람·전문가 확인 필요"** 섹션: 침투 테스트, 결제 흐름 위협 모델링, 개인정보 처리 적법성(법무·개인정보보호법/전자금융거래법), 인프라 보안(17단계).
- `_검증체크리스트.md`(아래) 생성. 마지막으로 산출물 폴더 경로와 **"Critical/High 미해소 시 배포(16) 금지·AI 점검은 합격증 아님"** 고지를 보고한다(잔존 🔴/Critical 있으면 완료 보고 금지).

## 도구 정확성 (probe·degrade)

- **`/security-review`·`/code-review`**(내장 스킬, probe) = 변경분 보안·정확성 스캔. 없으면 Stage 1·2 체크리스트 점검으로 degrade.
- **Context7 MCP**(probe) = Spring Security 6·토스페이먼츠 웹훅 서명 검증 최신 기준 확인(2-step: resolve-library-id → query-docs). 없으면 내장 지식 + "버전 확인 필요 ⚠️".
- **의존성 스캐너(OWASP Dependency-Check `./gradlew dependencyCheckAnalyze` / Snyk)·gitleaks** = 리포트 생성은 사람이 로컬에서 실행. 스킬은 리포트 **해석** 담당. 리포트 부재 시 실행 명령 안내 후 해석 단계 degrade.
- **python3** = 리포트 JSON 파싱 보조. 없으면 수기 해석 degrade.
- **중단**: 점검 대상 소스·상위 산출물이 둘 다 부재일 때만. 그 외는 degrade.

## _검증체크리스트 본문 (Stage 5 생성)
```
- [ ] OWASP: "확인 필요" 태그 항목 전부 근거 코드 라인 원문 대조(AI 환각 차단 — 정상 QueryDSL을 인젝션으로, 진짜 구멍을 정상으로 오판 가능)
- [ ] 입력검증·권한 누락 목록의 각 엔드포인트 사람 확인(특히 결제 금액 서버 대조·예약 소유권)
- [ ] 고위험 경로(결제·개인정보) 리뷰 결과 사람 재확인 + 스킬↔체크리스트 한쪽만 잡은 항목 검토
- [ ] CVE "지금 올려야 함" 분류 사람 재확인 + 업그레이드는 13단계 테스트 회귀 통과 후 반영(BOM 충돌 주의)
- [ ] gitleaks "진짜 시크릿" 키 폐기·재발급 즉시 실행(이력 제거만으로 끝 아님)
- [ ] 통합 리포트의 Critical/High 전부 닫힘 확인 — 닫기 전 배포(16) 금지
- [ ] 스캐너 리포트 외부 전송 전 마스킹(--redact)·민감 라인 필터 확인
- [ ] 침투 테스트·위협 모델링 최종 판단·결제/개인정보 적법성·릴리즈 승인 = 전문가·법무에게 의뢰(AI 점검은 합격증 아님)
```

## 주의
- **AI의 "문제 없음"은 합격증이 아니다.** 못 찾은 게 안전한 게 아니다 — 침투 테스트·전문가 검토를 보완할 뿐 대체하지 않는다.
- **환각으로 없는 취약점을 만들거나 있는 걸 놓친다.** 모든 지적은 근거 코드 라인 확인, "확인 필요"는 반드시 사람이 원문 대조.
- **시크릿은 "이력에서 지우면 끝"이 아니다.** 커밋된 키는 노출된 것 — 폐기·재발급이 우선이고 사람이 즉시 실행.
- **흔한 실수 — 스캔만 돌리고 끝내기**: 리포트 생성=점검 완료가 아니다. 각 항목 분류·조치하고 Critical/High를 닫기 전엔 배포하지 않는다.
- **흔한 실수 — 의존성 업그레이드 무검증 적용**: CVE 막으려 버전 올렸다가 Spring Boot 3.3 BOM 충돌로 빌드/런타임 깨짐. 13단계 테스트 회귀 확인 후 반영.
