# 캐싱·성능 최적화 (Caching & Performance Optimization)

백엔드의 가장 무거운 읽기 경로(09에서 계승한 부하 대상 API — 예: 검색·목록·피드)를 대상으로, **먼저 측정하고(k6) → 병목을 확인하고(p95/p99) → 캐시·인덱스로 줄이고 → 같은 조건으로 재측정해 효과를 입증하는** 단계를 자동화한다. 산출물 = k6 부하 스크립트·병목 분석·Redis 캐시 전략(무효화 매핑 포함)·검증 체크리스트. **AI는 k6 스크립트·캐시 코드 초안·측정 결과 해석을 하고, "어디가 진짜 병목인가"와 "무엇을 캐싱할 것인가"의 판단은 측정값을 보고 사람이 한다.**

## 핵심 원칙
- 상위 산출물 계승·재발명 금지(09 API·10 쿼리 최적화가 확정 상태일 때만 계승, 미확정은 ⚠️ 보존).
- **측정 없는 최적화 금지.** 워크플로우의 첫 작업은 코드가 아니라 측정이다. "느린 것 같다"를 "p99 800ms로 임계 200ms 위반"이라는 숫자로 바꾼 다음에만 손댄다.
- **systematic-debugging 사고틀**: 가설(여기가 병목일 것) → 측정(k6로 p95/p99) → 수정(병목에만 적용) → 재측정(정말 빨라졌는지). 추측 기반으로 캐시부터 뿌리지 않는다.
- **p95/p99로 본다.** 평균은 거짓말을 한다. 꼬리 지연(tail latency)이 사용자 체감과 장애의 진짜 원인이므로 임계값을 p95/p99로 건다.
- **캐시의 어려움은 넣기가 아니라 무효화다.** 캐시를 설계할 때는 항상 "어떤 변경이 어떤 캐시를 낡게 만드는가" 매핑표를 함께 만든다.
- **캐싱해도 되는 것만 캐싱한다.** 검색 결과·시터 프로필처럼 약간 낡아도 되는 데이터만. 결제·예약 상태·정산 금액처럼 정확성이 생명인 데이터는 캐싱 금지.
- **캐시는 반창고가 아니다.** 병목이 쿼리 자체면 10단계(인덱스·fetch join)로 원인을 먼저 고친다. 캐시는 호출량을 줄이는 용도로만.

## 파이프라인

### Stage 0 — 입력 확인·도구 probe·degrade
- 10·09 산출물 로드(검색 쿼리·엔드포인트). 부재 시 측정 대상 API를 사용자에게 질의(상위 산출물 완전 부재 시에만 중단).
- **도구 probe**: Context7 MCP(ToolSearch 존재 여부)·k6 CLI(`k6 version`)·python3.
- **degrade**: k6 CLI 부재 → 스크립트는 생성하되 "로컬에서 `k6 run`으로 직접 실행 필요" 안내 / Context7 부재 → 내장 지식으로 Spring Cache 설정 + "Spring Boot 3.3 기준 확인 필요 ⚠️" / 측정 결과가 아직 없으면 Stage 2/4는 "결과 붙여넣기 대기" 상태로 보류.
- **실측 불가(k6 부재+결과 미제공) 시**: 12-2는 *상위 적재 기준(10단계 데이터량)으로 추정한 가상 baseline*으로 해석·전략 초안만 작성하고, 문서 최상단에 **"⚠️ 가상 수치 — 실측 summary.json으로 교체 전 운영 결정 금지"**를 굵게 명시한다. 가상 수치로 게이트를 "사람 확정"으로 통과시키지 말 것(설계 초안 진행은 가능, 운영 적용은 실측 필수).
- **측정 환경 경고**: 데이터 양·인덱스·커넥션 풀이 운영과 다르면 결론이 통째로 틀린다. 로컬 소량 데이터 측정이면 "운영 비슷한 조건(Testcontainers/스테이징) 권장" 고지.

### Stage 1 — k6 부하 테스트 스크립트 → 12-1
- 대상: **09에서 계승한 그 도메인의 가장 무거운 읽기 경로**(예: 포밋=시터 검색 `GET /api/v1/care-services?region=&date=`. 검색이 없으면 회원별 목록·피드·상세 중 트래픽·N+1 위험이 큰 경로). 10-1 N+1 진단의 1급 대상과 일치시킨다.
- 시나리오: ramp-up(0→50 VU 30초)·유지(50 VU 1분)·ramp-down(30초). 파라미터는 현실적 분포(인기 키 쏠림 ~50%, 나머지 분산 — 캐시 적중률·N+1 폭발이 드러나게).
- thresholds: `http_req_duration` p95<300ms·p99<500ms, `http_req_failed`<1%. 응답 200 `check`. 콘솔 요약 + `summary.json`(handleSummary) 출력.
- BASE_URL·VU 수·임계값은 **변경포인트 주석**으로 상단 고정(AI 제안 숫자는 출발점일 뿐 — 사람이 조정).
- → `12-1_부하테스트.k6.js`

### Stage 2 — baseline 측정 해석 → 12-2 (사용자가 k6 결과 제공)
- 사용자가 `k6 run` 결과(콘솔 요약/summary.json)를 붙여넣으면: 임계 위반 항목·p50/p95/p99·에러율 정리, ramp-up 어느 지점에서 응답시간이 꺾이는지, 병목 후보 가설을 **우선순위로**(쿼리? 호출량? 직렬화?) 제시.
- 각 가설에 **확인 방법**을 함께 적는다(EXPLAIN ANALYZE / 캐시 적중률 로그 / 슬로우 쿼리 로그). 추측으로 캐시부터 넣지 말고 측정으로 좁히는 순서.
- 결과 미제공 시 "baseline 실행 후 결과를 붙여넣어 주세요"로 보류(스크립트만 전달).
- → `12-2_병목분석.md`(baseline 섹션)

### 🚦 게이트 — 캐시 적용 여부·대상 결정 (AskUserQuestion, 필수)
측정 결과(12-2 병목 가설)를 근거로 **무엇을 캐싱할지/캐시가 답인지**를 사람이 확정한다. AI 추천 1안 제시:
- **캐시 적용**(병목이 "반복 조회"·호출량이면) → Stage 3로. 캐싱 대상은 검색 결과로 한정, 결제·예약·정산은 제외 확인.
- **쿼리부터 고침**(병목이 쿼리 자체·인덱스 미사용이면) → 10단계로 회귀 안내(캐시는 반창고). Stage 3 건너뜀.
- **최적화 불필요**(임계 만족) → 마무리로.

측정 없이는 이 게이트를 통과하지 않는다(가설만으로 캐시 적용 금지). 게이트 전에는 Stage 3로 넘어가지 않는다.

### Stage 3 — 캐시 전략 설계 → 12-3 (게이트에서 "캐시 적용" 시에만)
- **look-aside(cache-aside)** 설계: Spring Cache `@Cacheable`, `cacheManager`=`RedisCacheManager`. 캐시 미스 시에만 DB 조회(10 QueryDSL 검색 쿼리 재사용).
- **캐시 키**: 결과를 유일하게 결정하는 모든 파라미터를 포함(필터·정렬·페이지 + 회원별 데이터면 memberId 필수 — 빠지면 권한 사고). 예 포밋 `search:care-services:{region}:{date}:{page}`. 값: 목록/검색 결과 DTO 리스트(엔티티 직접 캐싱 금지 — LAZY 프록시·순환참조). **TTL 10분 + 키별 랜덤 지터(±60초)**로 동시 만료 방지.
- **무효화 매핑표(필수)**: 그 도메인의 쓰기 이벤트 → 낡아지는 캐시를 표로(@CacheEvict 또는 키 패턴 삭제). 예 포밋 `CareService` 등록/수정/비활성·`SitterProfile.verificationStatus` 변경 → 지역 검색 캐시. **⚠️ `@CacheEvict`는 와일드카드(`{key}:*`) 삭제 불가** — 패턴 삭제가 필요하면 키를 단일화(회원/대상당 1키)하거나 `RedisTemplate` SCAN+del(KEYS 금지). 무효화 없는 캐시는 낡은 데이터 버그.
- **캐싱 금지 명시**: 결제·예약/구독 상태·정산 금액·환불/위약금 등 정확성이 생명인 데이터는 캐싱 대상에서 제외.
- **스탬피드 방지(택1, 과한 추상화 금지)**: ① TTL 지터(이미 적용) ② Redis SETNX 분산 락(재생성은 한 요청, 나머지 대기/직전값) ③ 캐시 워밍. **MVP 규모엔 보통 TTL 지터 + 단순 락이면 충분** — 측정으로 필요성이 확인되기 전엔 워밍까지 넣지 않는다. AI가 셋 다 넣으려 하면 막는다.
- Context7 가용 시 Spring Cache/Redis 직렬화·TTL 최신 설정 확인(부재 시 내장 지식 + ⚠️).
- → `12-3_캐시전략.md`

### Stage 4 — 재측정·before/after 비교 → 12-2 (사용자가 after 결과 제공)
- 캐시 적용 후 **동일한 12-1 스크립트**를 재실행한 결과를 받아 비교: p50/p95/p99·에러율·throughput(RPS) 비교표, 임계값(p95<300·p99<500) 충족 여부, 캐시 적중률 해석.
- **개선이 캐시 덕인지 측정 변동인지** 판단 근거 제시. 효과가 미미하면 솔직히 "이 캐시는 효과 없음, 병목은 다른 곳(→10단계 회귀)"이라고 적는다.
- → `12-2_병목분석.md`(before/after 섹션 추가)

### Stage 5 — 마무리(_검증체크리스트 + 산출물 경로 보고)
`_검증체크리스트.md` 생성 후, 산출물 폴더 경로와 "AI 제안 TTL·임계값은 출발점 — 운영 SLO는 사람이 측정으로 확정" 고지를 보고한다. 캐시로 안 풀린 잔여 병목이 있으면 ⚠️와 함께 10단계 회귀를 안내한다.

## 도구 정확성 (probe·degrade)
- **Context7 MCP**(probe) = Spring Cache(@Cacheable/@CacheEvict)·Redis 직렬화·TTL 최신 설정 확인. 없으면 내장 지식 + "Spring Boot 3.3 기준 확인 필요 ⚠️".
- **k6 CLI**(`k6 version` probe) = 부하 측정. 없으면 스크립트만 생성 + "로컬에서 `k6 run 12-1_부하테스트.k6.js` 직접 실행" 안내.
- **python3** = summary.json 파싱·비교표 보조. 없으면 수기 해석 degrade.
- **EXPLAIN ANALYZE** = 병목이 쿼리면 캐시 전에 진단(10단계 위임). 캐시가 느린 쿼리를 가리는 반창고가 되지 않게 원인부터 구분.

```
- [ ] 무효화 매핑표 존재 — "어떤 변경→어떤 캐시 무효화"가 코드 리뷰에서 확인됨(낡은 데이터 버그 차단)
- [ ] 스탬피드 방지가 과하지 않은가 — 측정으로 필요성 확인 전 워밍 등 미사용 옵션 미추가
- [ ] before/after 재측정으로 효과 입증 — 개선이 캐시 덕인지 측정 변동인지 판단 근거 있음
- [ ] AI 제안 TTL·임계값은 출발점 — 운영 SLO로 그대로 박지 않고 사람이 조정
- [ ] 캐시로 안 풀린 병목은 10단계(인덱스·fetch join)로 회귀 — 캐시를 반창고로 쓰지 않음
```

## 주의
- **측정 환경이 곧 신뢰도다.** 데이터 1천 건짜리 로컬에서 잰 수치는 운영을 대변하지 못한다.
- **캐시 무효화 누락 = 사용자에게 낡은 데이터.** 시터가 중단했는데 검색에 계속 뜨면 신뢰 문제 — 무효화 지점은 코드 리뷰에서 반드시 확인한다.
- **AI 제안 TTL·임계값은 출발점일 뿐.** TTL 10분·p95 300ms를 운영 SLO로 그대로 박지 말 것.
- **캐싱하면 안 되는 데이터를 캐싱하는 사고** — 정확성 데이터는 명시적으로 캐싱 대상에서 뺀다.
- **흔한 실수 — 캐시부터 넣기.** 측정 없이 깔면 효과도 모른 채 무효화 버그·복잡도만 떠안는다. 측정→병목 확인→적용→재측정 순서.
- **흔한 실수 — 평균만 보기.** p95/p99와 에러율을 함께 본다.
