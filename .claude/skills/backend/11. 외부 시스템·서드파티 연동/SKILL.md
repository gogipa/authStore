# 외부 시스템·서드파티 연동 (External & Third-party Integration)

내가 통제할 수 없는 시스템(토스페이먼츠 결제, Firebase FCM 푸시)에 우리 서비스를 붙이는 단계다.
이 스킬은 외부 장애가 우리 서비스로 전파되지 않게 가두는 **격리 설계**(멱등성 키·재시도·서킷브레이커·
타임아웃·웹훅 서명 검증)와 그 격리를 검증하는 **WireMock 실패 시나리오 테스트** 초안을 자동 생성한다.
**AI는 보일러플레이트·격리 설정·스텁 초안 생성, 판단(재시도 가능/불가 구분·시크릿·금액 검증·임계값
확정)은 사람.** 결제는 돈이 오가므로 생성 코드의 검토 시간은 줄이지 않는다.

## 핵심 원칙
- **상위 산출물 계승·재발명 금지**(확정 상태일 때만 계승, 미확정은 ⚠️ 보존). 08 도메인 상태 전이·09 컨트롤러/DTO·09 전역예외핸들러를 그대로 잇고, **엔티티명·결제 모델은 08·09에서 계승한 그대로 1:1 유지**(돌봄매칭=Booking/일회성결제, 정기구독=Subscription/빌링키, 본문 예시는 전자 — 본인 도메인으로 치환). 08이 결제를 포트(`PaymentGateway`/`RefundGateway`)로 모킹해 뒀다면 본 단계는 그 포트의 **실제 벤더 어댑터 구현**이 핵심.
- **생성 전 문서 확인 강제** — 결제·푸시 SDK는 버전마다 API가 바뀐다. Context7로 토스페이먼츠·FCM·Resilience4j 최신 시그니처를 **못박은 뒤** 코드를 생성한다. "AI가 기억하는 결제 API"는 그럴듯하지만 동작하지 않는다.
- **멱등성을 재시도보다 먼저** — "실패하면 재시도"는 결제에서 이중 결제로 직결된다. 멱등성 키(우리 `Payment.id` 기반 결정적 생성)가 전제되어야만 재시도가 안전하다.
- **외부 장애를 우리 경계 안에 가둔다** — 외부 호출은 항상 격리 어노테이션(@CircuitBreaker/@Retry/@TimeLimiter)과 fallback을 한 쌍으로. 4xx는 재시도 금지, 5xx·타임아웃·네트워크 오류만 재시도.
- **외부 호출을 긴 @Transactional 안에 두지 않는다** — 외부 응답을 기다리며 DB 커넥션을 점유하면 10단계 커넥션 풀 고갈로 이어진다. 외부 호출은 트랜잭션 밖, 결과 반영만 짧은 트랜잭션으로 커밋.
- **웹훅은 신뢰하지 않는다** — 서명 검증을 본문 파싱보다 먼저, 실패는 401로 끊고, 검증된 웹훅도 중복 도착 전제로 멱등 수신.
- **시크릿은 코드·프롬프트·로그에 절대 넣지 않는다** — 환경변수로만 주입(`${TOSS_SECRET_KEY}`·`${FCM_CREDENTIALS_PATH}` 플레이스홀더). 결제 요청/응답 로그는 카드번호·키 마스킹.

- → `11-1_연동설계.md`

### Stage 2 — 어댑터·격리·트랜잭션 초안 → 11-2
- **TossPaymentClient**: confirm/cancel 메서드, RestClient 사용, 결제 승인 요청에 멱등성 키를 `Idempotency-Key` 헤더로 전송(키 = `Payment.id` 기반 결정적 생성). `@CircuitBreaker(name="toss", fallbackMethod=...)` + `@Retry` + `@TimeLimiter`. **4xx 재시도 금지·5xx/타임아웃만 재시도**(4xx는 `PaymentDeclinedException`을 retry/circuit `ignore-exceptions`에 등록). fallback은 `PaymentGatewayUnavailableException`을 던지고 우리 Payment 상태는 그대로 둔다(이중 결제 방지). **09가 결제 거절 에러코드(예: `PAYMENT_DECLINED` 402)를 "11단계 위임"으로 미커버해 뒀다면, 09 전역예외핸들러에 `PaymentDeclinedException`→해당 코드 매핑 추가를 핸드오프로 함께 명시**(09 미커버 항목 회수). `application.yml`의 resilience4j 설정 포함.
- **PaymentService.confirmPayment(bookingId, paymentKey, amount)**: ① Booking 상태 검증(08-4 상태전이 준수, 아니면 09-2 예외) ② Payment를 PENDING으로 선기록(멱등 기준점) ③ TossPaymentClient.confirm 호출 ④ 성공 시 Payment DONE·Booking 결제확정 ⑤ **결제 금액≠Booking.totalPrice면 즉시 예외 + 결제 취소 시도**. **외부 호출은 긴 @Transactional 밖에서**, 결과 반영만 짧은 트랜잭션으로. 성공/실패 모두 Payment 상태로 기록해 재진입 시 멱등.
- **FcmNotificationSender**: 결제 확정 시 시터에게 푸시. `@TransactionalEventListener(phase = AFTER_COMMIT)`로 결제 트랜잭션과 분리(알림 실패가 결제를 롤백시키지 않게). 발송 실패는 로그 + 재시도 큐 자리만(지금은 단순 로깅). FCM 자격증명은 `${FCM_CREDENTIALS_PATH}` 환경변수 경로 주입.
- 시크릿은 전부 플레이스홀더. → `11-2_어댑터초안.md`

### Stage 3 — WireMock 실패 시나리오 통합 테스트 → 11-3
- WireMock으로 토스 결제 승인 API를 흉내 내는 통합 테스트(시나리오별 별도 테스트):
  1. 정상 200 → Payment DONE·Booking 결제확정
  2. 5xx → @Retry 3회 후 fallback, Payment PENDING 유지(이중 결제 없음)
  3. 응답 지연(타임아웃 초과) → @TimeLimiter 발동·fallback
  4. 같은 멱등성 키 두 번 호출 → 두 번째도 안전(중복 승인 없음)
  5. 4xx(잘못된 paymentKey) → 재시도 없이 즉시 실패
- WireMock 스텁은 응답 본문·상태코드·지연을 시나리오별로 명시. **Testcontainers PostgreSQL**을 함께 띄워(13단계 통합 테스트 규약) 실제 DB 상태까지 검증. docker 부재 시 코드는 생성하되 "로컬에서 직접 실행 필요" 안내.
- → `11-3_WireMock테스트.md`

## 도구 정확성 (probe·degrade)
- **Context7 MCP**(probe = ToolSearch 존재) = 토스페이먼츠·FCM·Resilience4j 최신 문서. 이 단계 핵심. 2-step(resolve-library-id → query-docs). 부재 시 **내장 지식 + "버전 확인 필요 ⚠️"** 표기(중단하지 않음).
- **python3**(bash 가용 시) = 산출물 내 yaml/설정 정적 검증 보조. 부재 시 정적 체크리스트 degrade.
- **docker**(bash 가용 시) = WireMock standalone·Testcontainers 로컬 실행. 부재 시 테스트 코드·스텁은 생성하되 "로컬에서 직접 실행 필요" 안내.
- **systematic-debugging 스킬**(선택) = 연동이 간헐적으로 실패할 때(타임아웃·서명 불일치) 가설→로그 확인→재현으로 좁힌다.
- **중단**은 필수 입력(08·09 산출물) 부재 시에만. 그 외는 degrade.

## _검증체크리스트 본문 (Stage 5 생성)
```
# 검증 체크리스트 — <주제> 외부 시스템·서드파티 연동 (작성일: <날짜>)

> AI는 보일러플레이트·격리 설정·스텁 초안까지. 결제는 돈이 오가므로 검토 시간을 줄이지 않는다.

- [ ] 🔴 결제 코드 사람 전수 검토 — 금액·환불·이중 결제 로직 한 줄씩 확인
- [ ] 🔴 시크릿(토스 키·FCM 자격증명) 코드/프롬프트/로그에 없음 — 환경변수 플레이스홀더만, 산출물 키·금액 전부 더미
- [ ] 재시도 가능/불가 구분 확인 — 4xx 재시도 금지, 5xx·타임아웃·네트워크만 재시도
- [ ] 멱등성 키 생성 규칙 확인 — Payment.id 기반 결정적, 같은 결제 재시도 시 동일 키
- [ ] 외부 호출이 긴 @Transactional 밖에 있음 — 결과 반영만 짧은 트랜잭션(커넥션 풀 고갈 방지)
- [ ] fallback이 우리 Payment 상태를 바꾸지 않음(이중 결제 방지) + PaymentGatewayUnavailableException
- [ ] 결제 금액 ≠ Booking.totalPrice 검증·즉시 예외·취소 시도 존재
- [ ] WireMock 실패 시나리오(5xx 재시도·타임아웃·멱등 중복·4xx 즉시실패) 테스트 존재 + Testcontainers DB 상태 검증
- [ ] 웹훅: 서명 검증이 본문 파싱보다 먼저·실패 401, 검증된 웹훅도 멱등 수신
- [ ] 알림(FCM)이 AFTER_COMMIT으로 분리 — 알림 실패가 결제를 롤백시키지 않음
- [ ] 서킷/타임아웃/재시도 수치는 추정값 — 운영 응답 분포 보고 사람이 조정(기본값 그대로 올리지 말 것)
- [ ] 결제 요청/응답 로그에 카드번호·키 마스킹(15단계 보안 점검 재검수 대상)
```

## 주의
- **결제 코드는 AI가 만들었어도 사람이 끝까지 검토한다.** 금액·환불·이중 결제는 곧바로 금전 사고. "재시도해도 되는 실패"와 "안 되는 실패"의 구분, 멱등성 키 규칙은 한 줄씩 직접 확인.
- **시크릿을 프롬프트·코드·로그에 절대 넣지 않는다.** 환경변수로만 주입, 결제 로그는 카드번호·키 마스킹(15단계 재검수).
- **웹훅은 외부 입력이므로 신뢰하지 않는다.** 서명 검증을 본문 파싱보다 먼저, 검증 실패는 401, 검증된 웹훅도 멱등 처리.
- **AI가 만든 서킷/타임아웃 수치는 추정값이다.** 운영 응답 시간 분포를 보고 사람이 조정. 기본값을 운영에 그대로 올리지 말 것.
- **흔한 실수 — 외부 호출을 @Transactional 안에 그대로 둠**: 외부가 3초 멈추면 DB 커넥션도 3초 점유, 동시 요청 몰리면 풀 고갈. 외부 호출은 트랜잭션 경계 밖으로.
- **흔한 실수 — 모든 실패를 똑같이 재시도**: 4xx(우리 요청 오류)는 재시도해도 계속 실패. 재시도는 5xx·타임아웃·네트워크 오류로만 한정.
